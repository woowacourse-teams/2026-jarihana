케이스별 JSON에 실제 DB 건수, HTTP 오류와 SSE 연결 종료, 송신기 일정 지연, 서버별 자원 시계열을 담았다. 원본 GC 로그의 시간은 각 JVM의 기동 이후 경과 시간이다. 결과는 공유 로컬 Docker 환경에서 케이스당 한 번 관측했다.

## 관측한 병목

- 무채팅 512개 방의 서버 2대 측정에서 NOTIFY는 revision 조회를 28,672회에서 0회로 줄였다. DB CPU는 22.43%에서 0.55%, 앱 CPU 합계는 78.69%에서 15.75%로 줄었다. Poll의 JDBC 대기는 서버별 최대 291·480개였고 NOTIFY에서는 두 서버 모두 0개였다.
- 분산 480건/초에서는 네 조합이 모두 12,000건을 저장했다. NOTIFY가 줄인 revision 조회는 비교적 적었고 DB CPU는 단일·이중 서버에서 모두 증가했다. 저장 p95는 단일 서버에서 Poll이, 이중 서버에서 NOTIFY가 더 낮았다.
- 집중 800건/초의 서버 2대 측정에서 Poll은 4,163건, NOTIFY는 2,614건의 HTTP 타임아웃을 기록했다. DB에는 두 방식 모두 20,000건이 있었다. 양쪽 모두 서버마다 Tomcat 작업 스레드가 200개까지 찼고 JDBC 풀 10개가 모두 사용됐다. 큐가 밀린 구간의 JVM 요청 표본은 서버당 4개씩 수집하지 못했다. GC 횟수와 정지 시간은 성공한 시작·종료 스크레이프의 누적값 차이다.
- 집중 부하의 저장 TPS와 p95는 HTTP 성공 응답으로 계산했다. 타임아웃 건은 지연 백분위에 들어가지 않으므로 성공 비율과 함께 봐야 한다. 방별 쓰기 잠금과 384MiB 힙, JDBC 풀 10개가 적용된 격리 환경의 단기 관측이다.
