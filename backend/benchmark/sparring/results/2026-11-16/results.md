## 해석

아래 화살표는 Poll에서 NOTIFY로 바꿨을 때의 측정값이다.

- **글이 드문 방이 많을 때** revision 조회 감소가 가장 컸다. 활성 방 48개, SSE 192개, 글 0건에서 조회는 1대 816 → 0회, 2대 1,632 → 0회였다. 2대 DB CPU는 3.8 → 0.28%였다. Poll은 같은 방에 구독자가 양쪽에 걸쳐 있으면 두 서버가 각각 DB를 확인한다.
- **모든 방이 자주 바뀔 때** 두 방식의 조회 수가 가까워졌다. 방 24개에 초당 24건을 분산한 단일 서버에서 revision 조회는 408 → 357회, DB CPU는 3.55 → 4.13%, 저장 p95는 16.36 → 19.74ms였다. 2대에서도 DB CPU는 5.63 → 6.12%, 저장 p95는 15.4 → 22.4ms였다. 이 조건에서는 Poll이 DB CPU와 저장 p95에서 앞섰다. 매 틱 대부분의 방이 바뀌면 건너뛸 조회가 적어지고 NOTIFY는 글마다 발행한다.
- **한 방에 글이 몰릴 때** 변경이 적은 나머지 방의 조회를 계속 생략할 수 있다. 2대에서 초당 60건의 약 90%를 한 방에 보낸 경우 revision 조회는 816 → 204회, DB CPU는 5.84 → 4.99%, SSE p95는 966.9 → 966.5ms였다. 두 방식 모두 시나리오에서 예정된 글 900건을 저장했다. NOTIFY에서는 900회 발행했고 두 서버가 각각 900회 수신했다.
- 총 5,052건을 저장했고 각 글의 SSE 연결별 기대 전달 34,608건 중 누락 0건, 중복 0건을 집계했다. 모든 케이스에서 HTTP 성공 건수와 DB에 실제 저장된 글 수가 일치했다.

각 조합을 공유 개발 호스트에서 한 번 실행했다. 저빈도 케이스의 저장 지연 표본은 3건이다. 표의 CPU 100%는 논리 CPU 하나에 해당한다. DB 전체 호출 수에는 트랜잭션 제어 SQL과 계측 호출이 들어가며 트리거 내부 발행 호출은 마지막 열에 별도 표시했다. 앱 CPU와 최대 RSS는 서버별로 기록했다. CPU, RSS, 지연의 변동성이나 포화 처리량을 확인하려면 더 긴 반복 실행이 필요하다.

2대 측정에서는 두 서버가 같은 DB와 방을 공유하고 쓰기 요청을 교대로 받았다. 실제 배포 프록시 전환과 SSE 재접속 구간은 측정 범위 밖이다. SSE에 재접속하면 기존 동작대로 최신 30개 스냅샷을 받는다. 연결이 끊긴 동안 30개를 넘는 글이 생겼을 때 SSE 재접속만으로 이전 구간의 글까지 받는지는 이 결과로 판단할 수 없다.
