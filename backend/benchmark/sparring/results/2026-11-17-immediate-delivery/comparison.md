# 알림 수신 직후 SSE 전송 실측

즉시 전송의 SSE p99는 A 회차에서 1,109.23ms 대비 1,711.99ms로 늘었고,
B 회차에서는 1,988.32ms 대비 1,293.51ms로 줄었다. 두 회차에서 일관된
p99 개선은 확인되지 않았다. A 회차에서 저장 커넥션 획득 p99가 173.81ms와
685.86ms였고, B 회차에서는 278.28ms와 276.25ms였다. 추가 스케줄 대기를
제거해도 커넥션 대기와 조회 처리 시간이 남는다. 이전 버전에서도 두 스케줄의
상대적인 실행 시점에 따라 알림 수신 직후 조회할 수 있어 매번 1초가 추가되는
것은 아니다. 각 회차의 차이를 호스트 부하 또는 스케줄 위상으로 완전히
설명할 수 있는 시각별 계측은 수집하지 않았다.

변경 확인 조회는 즉시 전송에서 두 회차 모두 늘었으며, DB 평균 CPU도
A 회차에서 39.75%와 47.50%, B 회차에서 41.74%와 46.91%로 높아졌다.
보완 조회와 후속 알림을 다음 틱까지 병합하던 동작이 즉시 실행으로 바뀌는 점도
조회 수 차이에 영향을 줄 수 있다. 그 기여분은 별도로 분리하지 않았다.

모든 실행에서 저장 12,000건과 SSE 48,000건을 대조했고 실패·누락·중복·
연결 끊김·JDBC 타임아웃은 0건이었다. 모든 실행의 SSE p99는 1초를 초과했다.

단일 백엔드, 활성 방 256개, SSE 연결 1,024개, 분산 480 TPS를 25초간 적용했다. 모든 실행에서 같은 JAR, Docker 이미지, JVM 힙 한도 384 MiB, JDBC 풀 10개를 사용했다. 매번 새 DB와 백엔드 컨테이너를 순차 실행했다.

노티파이 5초는 저장마다 발행하고 5초마다 보완 조회한다. 노티파이 1초 두 버전은 방별 1초 배치 발행과 5초 보완 조회를 공유한다. 즉시 전송은 수신 알림, 보완 조회, LISTEN 재연결의 변경 신호를 받으면 바로 조회·SSE 작업을 시작한다. 같은 방에서 조회 중인 경우 후속 신호를 모아 끝나는 즉시 재조회한다.

CPU 100%는 논리 코어 하나다. DB 메모리는 컨테이너 전체 cgroup 사용량으로 캐시를 포함한다. 백엔드는 표본 최대 RSS다. GC 횟수와 누적 정지는 JVM 메트릭 값이며 전체 safepoint STW와 다르다. 부하 종료 후 SSE 관측 2.2초와 연결 정리 구간도 자원 측정에 포함된다.

## 구현과 검증

실험 옵션 `sparring.benchmark.immediate-delivery=true`에서 활성 방 신호를
받으면 즉시 조회를 시작한다. 조회 중 신호는 dirty 상태로 보존하고 완료 직후
재조회한다. 초기 스냅샷과 keepalive는 기존 주기로 처리한다.

변경 파일은 `SparringStreams.java`, `SparringStreamsTest.java`,
`benchmark/sparring/run.py`, `benchmark/sparring/README.md`다.

`./gradlew bootJar`와 토론 스트림·리스너·인수 테스트 31개가 통과했다.
추가 회귀 테스트는 즉시 전송, 비활성 방 제외, 조회 중 신호 병합, 재연결과
보완 조회 복구를 확인했다. `git diff --check`도 통과했다.

각 모드의 측정은 25초이며 변경 전후는 실행 순서를 바꿔 2회 측정했다.
운영 부하에서의 지연, 무중단 배포, 프로세스 강제 종료 중 알림 복구는 이번에
실측하지 않았다. 원본 로그와 JSON은 각 회차 디렉터리에 보관했다.
