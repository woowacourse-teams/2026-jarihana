# ADR 0003. GitHub OAuth 인가 시작의 소유와 state 검증

- 상태: 채택
- 날짜: 2026-08-20
- 관련 문서: [ADR 0001](0001-github-oauth-authentication.md), [ADR 0002](0002-access-token-cookie.md),
  [보안과 개인정보](../conventions/security.md), [API 엔드포인트 설계](../context/api/endpoints.md)
- 이 문서는 ADR 0001 결정 2의 `state` 보관 방식을 대체한다.
- 개정: 2026-08-20. 최초 채택본은 인가 시작을 **백엔드**가 소유한다고 정했으나, 그 결정은
  회의에서 이미 백엔드 인가 시작 엔드포인트를 두지 않기로 했다는 사실을 모른 채 내려졌다.
  결론을 뒤집고 `state` 검증 방식을 새로 정한다.

## 배경

팀 회의에서 `GET /api/oauth/github/authorization`을 두지 않기로 했다. 프론트엔드가 GitHub의
authorize URL로 직접 보내면 되므로 백엔드에 엔드포인트를 둘 이유가 없다는 결론이었다.

저장소는 이 결정을 반영하지 못한 상태다.

- 명세 스냅샷(`docs/context/api/`, 마지막 동기화 2026-08-15)에 그 엔드포인트가 전체 목록과 상세
  명세, `OAUTH_CONFIGURATION_ERROR`까지 그대로 남아 있다.
- ADR 0001 결정 2는 "`state`는 인가 시작 시 세션에 저장하고, 콜백에서 읽는 즉시 제거해 1회만
  사용한다"고 규정한다.
- 콜백 명세는 `state`를 필수 쿼리 파라미터로 요구한다.

콜백 구현도 그 전제를 따라 세션에서 `state`를 읽는다. 그런데 세션에 `state`를 쓰는 코드는 한 곳도
없다. 콜백은 읽고 지우기만 한다.

```text
GithubOAuthCommandController   session.getAttribute(OAUTH_STATE)      읽기
GithubOAuthCommandController   session.removeAttribute(OAUTH_STATE)   삭제
쓰는 곳                         없음
```

그래서 실제 브라우저 흐름에서는 `consumeIssuedState()`가 항상 `null`을 돌려주고 콜백이 무조건
`OAUTH_STATE_INVALID` 400으로 끝난다. **지금 이 서비스는 GitHub 로그인이 한 번도 성공할 수 없다.**
기존 인수 테스트는 세션에 `state`를 직접 심고 콜백을 호출하므로 이 공백이 드러나지 않았다.

인가 시작을 프론트엔드가 소유하기로 한 이상, `state`를 어디에 두고 누가 검증할지 다시 정해야 한다.

## 결정

1. 인가 시작은 프론트엔드가 소유한다. 백엔드는 인가 시작 엔드포인트를 두지 않는다.
   ADR 0001 결정 2와 명세의 `GET /api/oauth/github/authorization` 항목은 무효다.
2. `state`는 프론트엔드가 요청마다 새로 생성한다.
3. 프론트엔드는 같은 값을 **쿠키와 authorize URL의 `state` 쿼리 양쪽**에 싣는다.
4. 백엔드 콜백은 쿼리 `state`와 쿠키 값을 `MessageDigest.isEqual`로 대조한다. 대조 후 쿠키를
   만료시켜 1회만 쓰이게 한다. 값이 없거나 다르면 `OAUTH_STATE_INVALID`(400)로 응답한다.
5. 쿠키 이름은 서버 설정으로 관리하고 프론트엔드와 합의한 값을 쓴다. 프론트엔드 JavaScript가
   심어야 하므로 `HttpOnly`를 적용하지 않는다.

## 왜 double submit인가

- **검증이 인가 코드 교환보다 앞선다.** 위조된 콜백은 GitHub에 코드를 보내기 전에 걸러진다.
- **백엔드 엔드포인트가 필요 없다.** 회의 결론을 그대로 만족한다.
- Spring Security의 `CookieCsrfTokenRepository`가 CSRF 토큰에 쓰는 것과 같은 패턴이다.

## 콜백이 `state`를 스스로 만들 수 없는 이유

`state`가 만들어지는 지점과 검증되는 지점은 다르다.

```text
1. 브라우저를 GitHub authorize URL로 보낸다        state를 만들어 보관하는 지점
   https://github.com/login/oauth/authorize?client_id=...&state=XYZ

2. 사용자가 GitHub에서 승인한다

3. GitHub이 콜백으로 되돌려보낸다                  state를 받는 지점
   /api/oauth/github/callback?code=...&state=XYZ

4. 콜백이 3의 값과 1에서 보관한 값을 대조한다
```

콜백은 3번이다. 콜백이 `state`를 만들면 자기가 방금 만든 값을 자기가 검증하게 되어 위조 방지
효과가 사라진다. 그래서 생성 주체는 반드시 콜백 바깥에 있어야 하고, 백엔드 엔드포인트를 두지
않기로 한 이상 그 자리는 프론트엔드다.

같은 이유로 `POST /api/members`가 이 역할을 대신할 수 없다. 그것은 콜백 **이후**에 가입 세션의
`githubId`로 `Member`를 만드는 엔드포인트이고, `state`는 콜백 **이전**에 만들어져야 한다.
"GitHub 인증 후 우리 회원인지 판단"하는 로직은 이미 콜백의 `findByGithubId`에 있다. `state`는
그 신원 판단과 다른 층위로, "이 콜백 요청이 우리가 시작한 로그인에서 왔는가"를 확인한다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| A. 프론트엔드가 만들고 프론트엔드가 검증 | 백엔드 변경이 가장 작다 | 검증 시점이 코드 교환보다 뒤라 예방이 아니라 사후 탐지가 된다 |
| C. `state` 검증을 제거 | 구현이 가장 단순하다 | 로그인 CSRF에 그대로 노출된다 |
| D. 백엔드 인가 시작 엔드포인트 | 검증 주체가 서버 한 곳이고 설정도 서버에 모인다 | 회의에서 프론트엔드가 직접 링크하면 된다는 이유로 기각됐다 |

### 대안 A. 프론트엔드가 만들고 프론트엔드가 검증

프론트엔드가 `state`를 `sessionStorage`에 보관하고 authorize URL에 싣는다. 백엔드는 검증하지
않고 콜백이 받은 `state`를 리다이렉트 쿼리로 되돌려주며, 프론트엔드가 `sessionStorage` 값과
대조한다.

- 장점: 백엔드는 `state`를 통과시키기만 하면 되어 변경이 가장 작다. 쿠키 도메인 제약이 없어
  프론트엔드와 백엔드가 완전히 다른 도메인이어도 동작한다.
- 단점: 프론트엔드가 대조하는 시점에 백엔드는 **이미 인가 코드를 교환하고 가입 세션과 토큰을
  발급한 뒤**다. 불일치를 발견해도 되돌릴 수 있는 것은 로그아웃뿐이고, 그 사이 공격자 계정에
  묶인 세션이 잠시라도 존재한다. 예방이 아니라 사후 탐지다.
- 배포 도메인이 갈려 쿠키를 공유할 수 없을 때의 차선책으로만 고려한다.

### 대안 C. `state` 검증을 제거

콜백에서 `state`를 요구하지 않고 인가 코드만으로 처리한다.

- 장점: 프론트엔드와 백엔드 양쪽에서 할 일이 없다.
- 단점: 로그인 CSRF에 노출된다. 공격자가 자신의 GitHub 계정으로 얻은 인가 코드를 담은 콜백 URL을
  피해자에게 클릭하게 만들면, 피해자의 브라우저는 공격자 계정으로 로그인된다. 피해자는 자기
  계정이라 믿고 그룹을 만들거나 가입을 신청하고, 그 기록은 공격자가 소유한 계정에 쌓인다.
  공격자는 이후 자기 계정으로 그 내용을 열람할 수 있다.
- 계정 탈취만큼 치명적이지는 않지만 실재하는 취약점이고, [보안과 개인정보](../conventions/security.md)가
  요구하는 수준에 미치지 못한다. 감수하기로 한다면 이 ADR을 고쳐 명시적으로 남겨야 한다.

## 제약과 전제

- **쿠키 도메인.** 쿠키는 포트를 구분하지 않으므로 로컬 개발(`localhost:5173`과 `localhost:8080`)
  에서는 그대로 동작한다. 운영에서는 프론트엔드와 백엔드가 상위 도메인을 공유해야 한다
  (`app.example.com`과 `api.example.com`에 `Domain=example.com`). 배포 도메인이 완전히 갈리면
  이 결정을 재검토하고 대안 A로 물러난다.
- **XSS.** 쿠키가 `HttpOnly`가 아니므로 XSS가 있으면 읽히거나 덮어써진다. 다만 `state`의 위협
  모델은 CSRF이고, XSS가 성립하는 상황이면 이미 더 큰 문제가 있다. CSRF 토큰에 double submit을
  쓰는 것과 같은 판단이다.

## 결과

- GitHub 로그인이 실제 브라우저에서 처음으로 끝까지 동작한다.
- 백엔드에 인가 시작 엔드포인트를 만들지 않는다. `OAUTH_CONFIGURATION_ERROR`도 쓰지 않는다.
- 프론트엔드가 GitHub `client_id`와 `redirect_uri`를 알아야 한다. 설정이 프론트엔드와 백엔드
  양쪽에 존재하게 되므로 값이 어긋나지 않도록 배포 구성에서 함께 관리한다.
- 콜백은 더 이상 `state` 때문에 세션을 필요로 하지 않는다. 가입 세션(`signup.githubId`)은
  ADR 0001 결정 3대로 유지한다.
- 인수 테스트가 세션을 직접 심지 않고 쿠키와 쿼리를 함께 보내는 형태로 바뀐다.

## 후속 작업

- 명세 스냅샷의 `GET /api/oauth/github/authorization` 항목과 콜백의 `state` 설명을 이 결정에 맞게
  갱신하거나, Notion 원본을 고친 뒤 다시 동기화한다.
- `state` 쿠키의 이름, 길이, 생성 방법을 프론트엔드와 합의한다.
- 운영 배포에서 프론트엔드와 백엔드가 상위 도메인을 공유하는지 확인한다. 공유하지 못하면 대안 A로
  전환하고 이 ADR을 개정한다.
