# ADR 0006. 4인 병렬 개발을 위한 CQRS-lite 협업 경계

- 상태: 채택
- 날짜: 2026-08-19
- 관련 문서: [아키텍처 컨벤션](../conventions/architecture.md),
  [협업방식 결정: CQRS-Lite](https://app.notion.com/p/3c10978a6e6c80f681bfed3fc116dfe2),
  [백엔드 API 개발 역할 분담](https://app.notion.com/p/3bc0978a6e6c81879ddcf60f803d9f95)

## 배경

백엔드 개발자 4명이 MVP 범위의 활성 API 27개를 병렬로 구현해야 했다. 따라서 가장 먼저
결정해야 할 문제는 API와 코드를 어떤 기준으로 나눠야 각 팀원이 의미 있는 핵심 책임을
맡으면서도 동시에 작업할 때 발생하는 파일 충돌과 조정 비용을 줄일 수 있는가였다.

처음에는 `Member`, `Group`, `Recruitment`, `Registration`, `GroupMember`와 같이 도메인별로
담당자를 나누는 방식을 고려했다. 도메인별 분담은 담당 범위가 직관적이지만, 자리하나의 핵심
유스케이스는 하나의 도메인 안에서 독립적으로 끝나지 않는다. 특히 그룹, 모집, 신청, 멤버십은
하나의 상태 변경 과정에서 함께 사용된다.

또한 MVP의 전체 도메인 수와 비즈니스 복잡도는 각 도메인을 독립적인 팀이나 서비스로 나눌
만큼 크지 않았다. 반면 중요한 상태 전이와 동시성 문제는 그룹·모집·신청 영역에 집중되어
있었다. 순수하게 도메인만 기준으로 업무를 나누면 다음 문제가 발생한다.

- 그룹과 모집 담당자에게 핵심 비즈니스 로직이 집중된다.
- 하나의 유스케이스가 여러 도메인을 변경해 담당 경계가 모호해진다.
- 작업량을 조정하기 위해 하나의 도메인을 여러 사람이 맡으면 같은 Controller, Service,
  Repository를 동시에 수정할 가능성이 커진다.
- 목록과 상세 조회는 여러 도메인을 조합하므로 특정 도메인 담당자 한 명에게 귀속시키기 어렵다.
- API 수가 비슷하더라도 인증, 동시성, 조회 성능과 같은 기술적 난이도는 균등하게 분배되지 않는다.

따라서 도메인 응집도는 유지하면서도 실제 변경 이유와 작업 특성에 따라 파일 소유권을 나눌
수 있는 구조가 필요했다.

## 도메인별 분담의 문제 사례

| 유스케이스 | 관련 영역 | 도메인별 분담 시 문제 |
| --- | --- | --- |
| 그룹 생성 | Member, Group, GroupMember | 그룹 저장 후 최초 모임장을 구성원으로 생성해야 하므로 Group과 GroupMember 작업을 조정해야 한다. |
| 새 모집 생성 | Group, GroupMember, Recruitment, Registration | 모임장 권한 확인, 기존 모집 마감, 기존 `PENDING` 신청 처리가 하나의 작업에 포함된다. |
| 신청 승인 | Group, Recruitment, Registration, GroupMember, Member | 정원 확인, 신청 승인, 구성원 생성, 모집 자동 마감을 하나의 트랜잭션으로 처리해야 한다. |
| 그룹 목록 조회 | Group, GroupMember, Recruitment, Registration | 그룹 정보, 구성원 수, 활성 모집과 승인 인원을 함께 조회하고 집계해야 한다. |

예를 들어 신청 승인 과정은 다음과 같이 여러 도메인의 상태 변경이 연결된다.

```text
모임장 권한 확인
-> 신청 상태 확인
-> 모집 정원 확인
-> 신청 승인
-> GroupMember 생성
-> 정원 도달 시 모집 마감
-> 남은 PENDING 신청 처리
```

이를 Recruitment, Registration, GroupMember 담당자에게 각각 나누면 하나의 기능을 구현하기
위해 여러 담당자의 작업 순서를 계속 맞춰야 한다. 반대로 한 명이 전체 기능을 구현하기 위해
다른 담당자의 Service와 Repository를 직접 수정하면 도메인별 소유권이 불분명해지고 병합과
리뷰 충돌 가능성이 커진다.

조회도 마찬가지다. 그룹 목록 하나를 반환하기 위해 그룹, 구성원, 모집, 신청 데이터를 함께
읽어야 하므로 조회 구현을 각 도메인 담당자에게 분산하면 하나의 응답을 완성하기 위한 조정
비용이 발생한다.

따라서 이 프로젝트에서는 "도메인을 나누면 작업도 독립된다"는 전제가 핵심 유스케이스에
적용되지 않는다고 판단했다.

## 결정

기능 기반 패키지 구조를 유지하면서, 각 기능 내부에서 상태 변경을 담당하는 `command`와 조회를
담당하는 `query`를 분리하는 CQRS-lite 구조를 사용한다.

```text
group
├── domain
├── command
│   ├── controller
│   ├── service
│   └── repository
└── query
    ├── controller
    ├── service
    └── repository
```

CQRS-lite는 확장성을 위한 분산 아키텍처가 아니라 다음을 위한 코드 및 협업 경계다.

- 상태 변경과 조회의 변경 이유 분리
- 파일별 주 담당자 명확화
- 병렬 작업 시 동일 파일 수정 최소화
- 핵심 기술 책임의 분산
- 도메인 응집도 유지

하나의 Spring 애플리케이션, 하나의 데이터베이스, 하나의 엔티티와 테이블 모델을 유지한다.
별도의 조회 데이터베이스, 이벤트 버스 또는 비동기 Projection은 도입하지 않는다.

## 결정 당시 역할 분담

API 수와 담당자는 변경될 수 있으므로 다음 표는 결정 당시 역할 분담을 나타낸다. ADR의
지속적인 결정은 특정 담당자가 아니라 command/query 코드 경계다.

| 역할 | API 수 | 핵심 책임 |
| --- | ---: | --- |
| A · 인증·회원·공통 기반 | 6 | GitHub OAuth, JWT·Refresh Token, 가입 세션, 회원가입, 회원 조회, 인증 주체, 공통 응답·예외 기반 |
| B · 그룹 명령·일정·이미지 | 8 | 그룹 생성·수정·삭제·종료, 반복·세션 일정, 대표 이미지 업로드 |
| C · 모집·신청·멤버십 명령 | 6 | 모집 생성·마감, 신청 상태 전이, 정원 동시성, 구성원 생성, 모임장 위임 |
| D · 조회·검색·집계 | 7 | 그룹·구성원·모집·신청 목록 및 상세 조회, 커서·필터, Projection, 집계와 N+1 최적화 |

이 배치는 API 개수만 기계적으로 같게 나누는 방식이 아니다. 각 역할이 프로젝트에서 서로 다른
핵심 기술 문제를 소유하도록 구성한다.

- A는 인증과 보안, 공통 기반의 안정성을 책임진다.
- B는 그룹의 생명주기와 일정·이미지 기능을 책임진다.
- C는 강한 원자성과 동시성 보장이 필요한 상태 변경을 책임진다.
- D는 여러 도메인을 조합하는 조회 모델과 성능을 책임진다.

이를 통해 그룹과 모집 도메인에만 중요 로직이 몰리는 문제를 완화하면서, 네 명 모두 프로젝트에서
독립적으로 중요한 기술 책임을 맡는다.

## 소유권 규칙

- 각 API와 명령 유스케이스에는 정확히 한 명의 주 담당자를 둔다.
- A는 인증·회원 및 공통 기반과 관련된 command/query를 담당한다.
- B와 C는 담당 명령의 Controller, Service, Repository와 상태 전이 및 불변식을 주로 변경한다.
- D는 그룹·구성원·모집·신청의 Query Controller, QueryService, QueryRepository와 Projection을
  주로 변경한다.
- D는 조회 응답을 만들기 위해 도메인 엔티티에 API 전용 필드나 역방향 연관관계를 추가하지 않는다.
- 다른 역할이 소유한 상태 변경이 필요하면 해당 역할이 제공하는 공개된 명령 서비스 경계를 사용한다.
- 공통 엔티티와 데이터베이스 스키마 변경은 도메인 담당자가 주도하고 조회 담당자가 조회 조건과
  인덱스를 함께 검토한다.
- 조회 결과의 비즈니스 의미와 권한 해석은 D가 단독 결정하지 않고 해당 도메인 담당자가 함께
  리뷰한다.
- 담당자나 API 배정이 변경되어도 command/query 패키지 경계는 유지한다.

## 선택 이유

### 병렬 작업의 파일 충돌을 줄인다

일반적인 CRUD 구조에서는 상태 변경과 조회가 하나의 Controller와 Service에 함께 배치되기 쉽다.

```text
GroupController
├── POST /groups
├── PUT /groups/{groupId}
├── DELETE /groups/{groupId}
├── GET /groups
└── GET /groups/{groupId}
```

이 경우 B가 그룹 생성·수정을 구현하는 동안 D가 그룹 목록·상세 조회를 구현하면 같은 파일을
동시에 수정하게 된다. CQRS-lite에서는 이를 다음과 같이 분리한다.

```text
GroupCommandController  # POST, PUT, PATCH, DELETE
GroupQueryController    # GET
```

B와 D가 동일한 `group` 기능을 작업하더라도 주요 변경 파일이 달라진다. 따라서 도메인 코드를
멀리 흩어놓지 않으면서 병렬 작업 시 동일 파일 충돌을 줄일 수 있다.

### 강하게 연결된 명령의 응집도를 유지한다

모집, 신청, 멤버십은 서로 다른 엔티티지만 하나의 트랜잭션 안에서 함께 변경된다. 이를 각각
다른 담당자에게 나누지 않고 C가 전체 명령 흐름을 소유함으로써 정원 확인, 신청 상태 전이,
구성원 생성과 모집 마감의 원자성을 일관되게 관리한다.

### 핵심 기술 책임을 분산한다

순수 도메인 분담에서는 상태 전이, 권한과 동시성 처리가 그룹·모집 담당자에게 집중될 수 있다.
선택한 구조에서는 보안, 그룹 생명주기, 동시성 명령, 조회 성능이라는 서로 다른 핵심 과제를 각
역할이 담당한다. 따라서 API 수뿐 아니라 구현 난이도와 프로젝트 위험까지 고려한 업무 분담이 된다.

### 조회 관심사를 독립적으로 관리한다

조회는 상태 전이보다 검색 조건, Projection, 커서 페이지네이션, 집계와 N+1 최적화의 영향을
크게 받는다. D가 그룹·구성원·모집·신청 조회를 통합 소유하면 도메인마다 조회 방식이 달라지는
것을 줄이고, 조회 성능 개선 때문에 명령 Service나 도메인 엔티티가 불필요하게 변경되는 것을
방지할 수 있다.

### MVP 규모에 적합하다

현재 프로젝트는 별도의 읽기 모델이나 최종적 일관성이 필요한 규모가 아니다. 완전한 CQRS를
도입하면 이벤트 발행, 조회 모델 동기화, 장애 복구와 운영 복잡도가 추가된다. CQRS-lite는
이러한 비용 없이 현재 필요한 코드 소유권과 관심사 분리만 적용한다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 도메인별 일반 CRUD 구조 | 구조와 담당 범위가 직관적이다. | 핵심 유스케이스가 여러 도메인에 걸치며 그룹·모집 영역에 난이도가 집중된다. 작업량을 재분배하면 동일 파일 충돌 가능성도 커진다. |
| 최상위 command/query 패키지 | 명령과 조회 역할이 명확하다. | 동일한 도메인의 코드가 멀리 떨어져 도메인 규칙과 변경 범위를 파악하기 어렵다. |
| 완전한 CQRS | 명령과 조회를 독립적으로 확장할 수 있다. | 현재 해결하려는 문제보다 이벤트 동기화와 운영 복잡도가 더 커진다. |

## 결과

### 긍정적 결과

- 명령과 조회 담당자가 같은 파일을 수정할 가능성이 줄어든다.
- 하나의 API와 유스케이스에 대한 주 책임이 명확해진다.
- 네 명이 서로 다른 핵심 기술 책임을 맡을 수 있다.
- 모집·신청·멤버십의 트랜잭션과 동시성 책임이 한 역할에 모인다.
- 조회 모델과 성능 최적화를 명령 코드와 독립적으로 관리할 수 있다.
- 담당자가 변경되어도 코드의 책임 경계를 유지할 수 있다.

### 감수하는 비용

- command/query Controller, Service, DTO가 분리되어 파일 수가 증가한다.
- 공통 엔티티와 스키마 변경에서는 여전히 역할 간 협의가 필요하다.
- D의 조회 범위가 여러 도메인에 걸쳐 있어 작업량이 커질 수 있다.
- 조회 담당자가 도메인 규칙을 잘못 해석하지 않도록 교차 리뷰가 필요하다.
- 이 구조가 Git 충돌을 완전히 제거하지는 않는다.

## 후속 작업

- 역할별 작업량은 API 수뿐 아니라 동시성, 상태 전이와 조회 복잡도를 함께 기준으로 점검한다.
- 간단한 조회 API의 담당자를 조정하더라도 기존 command/query 패키지 경계는 유지한다.
- 별도 조회 저장소, 이벤트 기반 Projection 또는 최종적 일관성이 필요해지면 새로운 ADR로
  결정한다.

## 적용하지 않는 범위

이번 결정에는 다음을 포함하지 않는다.

- 별도의 조회 데이터베이스
- 명령 모델과 조회 모델의 물리적 분리
- Kafka 또는 이벤트 버스
- 비동기 Projection
- 최종적 일관성
- 도메인별 마이크로서비스 분리
- 담당자 외에는 코드를 수정할 수 없도록 하는 지식 사일로

CQRS-lite는 다른 팀원의 변경을 제한하기 위한 구조가 아니라, 변경의 주 책임과 리뷰 경계를
명확하게 하기 위한 구조다.
