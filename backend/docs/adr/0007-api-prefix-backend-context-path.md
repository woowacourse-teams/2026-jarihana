# ADR 0007. `/api` 접두사를 백엔드 `context-path`로 받는다

- 상태: 채택
- 날짜: 2026-08-24
- 관련 문서: [ADR 0006](0006-remove-local-development-auth-bypass.md),
  [`/api` 접두사는 누가 떼는가](../retrospectives/api-prefix-troubleshooting.md)
- 이 문서는 `/api` 접두사를 처리하는 책임을 엣지 계층에서 백엔드 애플리케이션으로 옮긴다.

## 배경

프론트엔드는 경로만으로 요청의 목적지를 구분할 수 있도록 API를 `/api/...`로 호출한다. `/groups`는
SPA 경로이고 `/api/groups`는 데이터 요청 경로다. 그러나 컨트롤러에는 `/api` 없이 경로가 매핑되어
있었다.

```java
@RequestMapping("/groups")          // GroupQueryController
@RequestMapping("/oauth/github")    // GithubOAuthCommandController
```

브라우저가 전송하는 요청 경로와 백엔드가 인식하는 경로가 다르므로, 중간 계층에서 `/api`를 제거해야
했다. 그러나 어느 계층이 이 작업을 담당하는지는 명확하게 정해져 있지 않았다.

로컬 환경에서는 webpack에 설정한 개발 서버 프록시가 이 작업을 담당했다.

```js
{ context: ["/api"], pathRewrite: { "^/api": "" }, target: "http://localhost:8080" }
```

운영 환경에는 이 프록시가 없다. 배포된 프론트엔드는 정적 파일이며, 요청 경로에 따라 목적지를
선택하는 역할은 CloudFront가 담당한다. 그러나 CloudFront의 동작은 요청을 어느 오리진(origin)으로
전달할지만 결정할 뿐, 요청 경로는 변경하지 않는다. 따라서 `/api/groups`가 그대로 백엔드에
도착했고, `SecurityConfig`의 매처와 일치하지 않아 마지막 `anyRequest().authenticated()` 조건이
적용되었다.

```text
https://jarihana.com/api/groups            401
https://jarihana.com/api/zzz-nonexistent   401
```

`GET /groups`는 `PUBLIC_GET_PATHS`에 포함되어 있으므로 인증 없이 200 응답을 반환해야 한다. 그러나
존재하지 않는 경로와 동일하게 401 응답을 반환했다. 이는 인증이 아니라 경로 매핑에 문제가 있음을
의미한다. Spring Security는 컨트롤러를 찾기 전에 인가 여부를 먼저 판단하므로, 매핑이 없는 경로도
404가 아닌 401을 반환했다. 이 때문에 원인을 파악하는 데 시간이 오래 걸렸다.

정리하면 `/api` 접두사를 제거하는 규칙이 로컬 환경에만 있고 운영 환경에는 없었다. 두 환경의 구성이
일치하지 않았기 때문에 로컬에서만 요청이 정상적으로 처리되었다.

## 결정

1. 백엔드가 `/api`를 직접 처리한다. `application.yaml`에 `server.servlet.context-path: /api`를
   설정한다.
2. 개발 서버 프록시의 `pathRewrite`를 제거한다. 프록시는 경로를 있는 그대로 전달한다.
3. `SecurityConfig`의 매처는 변경하지 않는다. 매처는 `context-path` 기준 상대 경로를 사용하므로
   `/groups`를 그대로 유지한다.
4. 테스트에도 같은 `context-path`를 설정하고, `RestAssured.basePath`가 해당 설정값을 사용하도록 한다.

```text
application.yaml                 context-path: /api 추가
webpack.config.mjs               프록시의 pathRewrite 제거
SecurityConfig                   변경 없음
IntegrationTestSupport           RestAssured.basePath = ${server.servlet.context-path}
```

## 왜 이 방법인가

**접두사 규칙을 한 곳에서 관리한다.** 엣지 계층에서 접두사를 제거하려면 같은 규칙을 개발 서버
설정과 CloudFront Function에 각각 정의해야 한다. 서로 다른 기술에 정의한 규칙이 일치하지 않을 때
발생하는 문제는 이미 경험했다. 환경별 구성 차이로 문제를 해결하는 데 하루를 소모한 상황에서,
구성이 달라질 수 있는 지점을 추가할 이유가 없었다.

**프론트엔드가 실행 환경을 구분할 필요가 없다.** 로컬과 운영 환경에서 모두 `/api`를 사용하므로
개발 모드인지 확인하는 분기가 필요하지 않다. API 기본 경로는 하나의 고정된 값으로 정의한다.

```js
baseUrl = "/api/"        // frontend/src/shared/api/client.js
```

로컬 실행을 위해 프론트엔드에 환경별 분기를 추가하면서 발생하는 문제는 이미 경험했다.
[ADR 0006](0006-remove-local-development-auth-bypass.md)에서 폐지한 개발 계정 우회가 그 사례이며,
이 우회로 인해 정상적인 로그인 동작을 검증하지 못했다. 따라서 API 주소에서도 같은 종류의 분기를
제거한다.

**제약을 인지하고 선택한다.** 이 결정을 적용하면 백엔드는 `/api` 외부의 경로를 처리할 수 없다.
비용이 없는 방법이어서 선택한 것이 아니라, 당장 감수하지 않아도 되는 비용과 이미 발생한 비용을
비교한 결과다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| A. 엣지 계층에서 제거한다 (개발 서버 프록시 + CloudFront Function) | 애플리케이션이 배포 구조를 알 필요가 없다. 접두사는 인프라 계층의 정보로 남는다 | 같은 규칙을 서로 다른 두 기술에 각각 정의해야 한다. 이번 장애도 두 규칙의 불일치 때문에 발생했다. CloudFront Function을 새로 구현하고 운영해야 한다 |
| B. `context-path`로 처리한다 | 접두사를 별도로 제거할 필요가 없다. 설정 한 줄이면 충분하며, `SecurityConfig`와 프론트엔드 코드를 변경하지 않아도 된다 | **채택** |
| C. 컨트롤러 매핑에 `/api`를 직접 추가한다 | 인프라 설정을 변경하지 않고 애플리케이션 코드만 수정하면 된다 | 모든 컨트롤러와 `SecurityConfig` 매처를 함께 수정해야 한다. 이후 추가하는 컨트롤러에서도 접두사를 빠뜨리지 않아야 하며, 누락하면 같은 401 오류가 재발한다 |
| D. 로컬 프록시만 수정한다 (현행 유지) | 로컬 로그인을 즉시 복구할 수 있다 | 운영 환경의 문제는 해결되지 않는다. 로컬 환경에서 정상적으로 동작하기 때문에 오히려 운영 환경의 문제를 발견하기 어려워진다 |

CloudFront의 Origin Path도 검토했지만 사용할 수 없다. Origin Path는 오리진에 요청을 전달할 때
지정한 경로를 **앞에 추가하는** 기능이므로 이 문제에 필요한 동작과 반대다.

## 제약과 전제

- **백엔드는 `/api` 외부의 경로를 처리할 수 없다.** 외부에서 경로를 지정하는 웹훅이나 헬스 체크
  (`/actuator/health`)를 도입하면 문제가 될 수 있다. 현재 프로젝트에는 Actuator와 Swagger가 없어
  해당하지 않으며, 이를 도입할 때 다시 검토한다.
- 정적 리소스에도 `context-path`가 적용된다. `8080/images/...`는 404가 되고
  `8080/api/images/...`가 200이 된다. 아래 후속 작업을 참조한다.
- `SecurityConfig`의 매처가 `context-path` 기준 상대 경로라는 전제에 의존한다. 매처를 절대 경로로
  변경하거나 서블릿 경로 기준으로 옮기면 이 전제가 성립하지 않는다.
- 테스트 설정이 `main` 설정 전체를 덮어쓰지 않아야 한다. 이전에는 테스트 설정이 `main` 설정을
  덮어써서 경로 구조가 전혀 검증되지 않았다. 이 문제가 모든 테스트를 통과하고도 발견되지 않은 이유
  중 하나다.

## 결과

- 접두사를 제거하는 규칙 자체가 사라진다. 로컬과 운영 환경이 같은 경로를 같은 방식으로 처리한다.
- 로컬 환경에서 로그인이 성공하면 운영 환경에서도 같은 경로로 요청이 처리된다고 기대할 수 있다.
  ADR 0006에서 인증 경로에 적용한 환경 일관성을 경로 계층에도 확보한다.
- CloudFront는 `/api/*`를 백엔드로, 나머지를 S3로 전달하는 분기만 유지한다. 새 함수가 필요 없다.
- 프론트엔드는 `/api/`를 고정된 값으로 사용하며, 환경별 분기를 두지 않는다.
- **경로를 명시하지 않은 쿠키의 범위가 `/api`로 제한된다.** `context-path`는 서블릿 경로만 변경하는
  것이 아니라, 경로를 지정하지 않은 쿠키의 기본 `Path`로도 사용된다. 이 결정을 적용한 다음 날
  CSRF 쿠키가 `Path=/api`로 설정되었고, 루트 경로에서 제공되는 SPA가 토큰을 읽지 못해 모든 변경
  요청이 403 응답으로 차단되었다. [ADR 0005](0005-csrf-token-delivery.md)의 결정 6에서 쿠키 경로를
  `/`로 명시하여 문제를 해결했다.
  Access Token 쿠키는 [ADR 0002](0002-access-token-cookie.md)가 처음부터 경로를 `/`로 정해
  두어 영향을 받지 않았다. **추후 추가하는 쿠키는 경로를 반드시 명시한다.**

## 후속 작업

- **기본 그룹 이미지의 위치를 정한다.** `context-path`로 인해 백엔드 정적 이미지에도 `/api`가
  적용되었고, 현재는 `frontend/public/images/default-group.png`와
  `backend/src/main/resources/static/images/default-group.png`가 둘 다 있다. 프론트엔드의
  `groupImageUrl`은 여전히 `/api`를 포함해 백엔드의 정적 리소스를 가리킨다. 파일을 프론트엔드로
  옮기고 `/api` 접두사를 제거하는 방향으로 정리한다.
  **갱신(2026-08-27).** "백엔드에는 업로드 기능이 없고 플레이스홀더 한 장뿐"이라는 전제는 더
  이상 유효하지 않다. 2026-08-26에 S3 기반 이미지 업로드 기능을 도입하면서 사용자 이미지는
  CloudFront 공개 URL로 제공된다. 다만 기본 이미지 `images/default-group.png`는 여전히 백엔드 정적
  리소스이며 두 위치에 모두 남아 있으므로, 기존 정리 방향은 여전히 유효하다. 이미지 업로드에 관한
  결정은 별도 ADR에서 다룬다.
- Actuator나 웹훅을 도입할 때 이 결정을 다시 검토한다. 그때는 대안 A의 비용을 다시 평가한다.
