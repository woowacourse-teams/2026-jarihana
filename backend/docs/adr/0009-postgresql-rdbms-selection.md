## 배경

자리하나의 회원, 모임, 모집 공고, 가입 신청과 구성원 데이터는 구조와 관계가 명확하다.
비즈니스 정책 역시 이러한 관계와 데이터 정합성을 중심으로 표현되므로, 운영 데이터
저장소로 RDBMS를 사용하는 것은 자연스러운 전제였다.

팀원 4명 중 2명은 MySQL을, 나머지 2명은 PostgreSQL을 사용해 본 경험이 있었다. 이에 따라
팀원이 실제 경험을 바탕으로 비교하고 이후 개발 과정에서도 서로 보완할 수 있는 MySQL과
PostgreSQL을 후보로 선정했다.

현재 MVP에서는 기본적인 관계 매핑, CRUD와 트랜잭션을 중심으로 사용하며 JPA를 통해 데이터에
접근한다. 따라서 현재 요구사항만 보면 두 DBMS 모두 충분했고, 애플리케이션 코드가 DBMS별 SQL
문법에 직접 의존하는 정도도 낮을 것으로 예상했다.

그러나 향후 채팅, 추천, 유사도 검색 같은 기능이 추가될 가능성이 있었다. 현재 기능의 구현
편의만 비교하기보다 새로운 데이터 형태와 조회 방식이 필요해졌을 때 대응할 수 있는 확장성을
함께 비교할 필요가 있었다.

## 결정 기준

두 후보를 다음 기준으로 비교한다.

1. **현재 MVP 요구사항 충족 여부**
   회원, 모임, 모집과 가입 신청의 관계를 표현하고 기본적인 CRUD, 트랜잭션과 동시성 제어를
   수행할 수 있어야 한다. 이 기준은 MySQL과 PostgreSQL 모두 충족한다.
2. **초기 개발 비용**
   팀원 절반씩 각 DBMS 사용 경험이 있고, MVP에서는 JPA를 통한 표준적인 관계 매핑과 데이터
   접근이 중심이다. 따라서 익숙함이나 초기 학습 비용은 두 후보를 구분하는 주요 기준으로
   삼지 않는다.
3. **반정형 데이터 확장성**
   향후 채팅처럼 메시지 종류에 따라 부가 데이터 구조가 달라지는 기능이 추가될 수 있다.
   PostgreSQL의 `jsonb`는 JSON 문서에 GIN 인덱스를 적용하고 포함·경로 조건으로 조회할 수
   있어 관계형 모델과 유연한 데이터를 함께 다루는 선택지가 비교적 명확하다.
4. **검색과 추천 기능의 확장 가능성**
   추천이나 유사도 검색이 필요해질 경우 `pgvector` 확장을 통해 관계형 데이터와 벡터를 함께
   저장하고 최근접 이웃 검색을 수행할 수 있다. 이는 현재 기능에 바로 도입한다는 의미가
   아니라 미래 요구에 대응할 선택지를 확보한다는 의미다.

## 결정

운영 RDBMS로 PostgreSQL을 사용한다.

현재 도메인 데이터는 일반적인 관계형 스키마로 관리한다. 채팅 데이터를 반드시 `jsonb`로
저장하거나 `pgvector`를 바로 도입한다는 의미는 아니다. 향후 반정형 데이터나 유사도 검색이
실제 요구사항으로 확정되면 별도의 설계와 검증을 거쳐 해당 기능의 도입 여부를 결정한다.

PostgreSQL 고유 타입, 인덱스와 쿼리를 사용하기 시작하면 PostgreSQL에 대한 의존성이
높아진다. 이러한 기능은 가능성만으로 미리 사용하지 않고 실제 필요성이 확인된 경우에만
도입한다.

## 검토한 대안

### MySQL

MySQL은 팀원 2명이 사용해 본 경험이 있고 현재 MVP에서 필요한 관계 매핑, CRUD, 트랜잭션과
동시성 제어를 충분히 지원한다. JPA를 사용하므로 초기 애플리케이션 개발에서도 PostgreSQL과
큰 차이가 없었다.

MySQL도 JSON 타입과 조회 기능을 제공하며, 생성 컬럼·함수 기반 인덱스와 JSON 배열용 다중 값
인덱스를 사용할 수 있다. 다만 JSON 컬럼의 값을 인덱싱하려면 특정 값을 추출하거나 형 변환하는
구성이 필요하다. `jsonb` 문서에 GIN 인덱스를 적용하고 여러 연산자를 활용할 수 있는
PostgreSQL의 접근 방식이 향후 요구사항을 탐색하기에 더 유연하다고 판단했다.

### PostgreSQL

PostgreSQL 역시 팀원 2명이 사용해 본 경험이 있고 현재 MVP 요구사항을 충족한다. 여기에
`jsonb`와 GIN 인덱스를 이용해 관계형 데이터와 반정형 데이터를 함께 조회할 수 있으며,
`pgvector` 확장을 통해 추천과 유사도 검색으로 확장할 수 있는 선택지가 있었다.

현재 필요한 기능만 보면 MySQL과 차이가 크지 않았지만, 미래 요구사항이 추가됐을 때 활용할 수
있는 데이터 타입과 확장 생태계의 범위가 더 넓다고 판단했다.

## 결과

### 긍정적인 결과

- 현재 MVP에서 필요한 관계형 모델과 트랜잭션을 팀의 기존 경험 안에서 구현할 수 있다.
- 관계형 데이터와 함께 반정형 데이터나 벡터를 다뤄야 할 때 추가 저장소를 곧바로 도입하지
  않고 PostgreSQL 안에서 해결 가능성을 먼저 검토할 수 있다.
- 로컬과 운영 환경에서 같은 PostgreSQL 계열을 사용해 기본적인 데이터베이스 동작을 맞출 수
  있다.

### 감수하는 비용

- `jsonb`, GIN 인덱스, `pgvector`와 PostgreSQL 전용 SQL을 사용하면 다른 DBMS로 이전할 때
  해당 스키마와 조회를 다시 설계해야 한다.
- JPA가 반복적인 SQL과 매핑 코드를 줄여 주더라도 DBMS별 타입, 인덱스, 잠금과 쿼리 동작의
  차이까지 없애지는 않는다.
- 테스트 환경은 H2를 사용하므로 PostgreSQL 고유 기능과 쿼리의 동작을 H2 테스트만으로
  검증할 수 없다.
- 미래 확장 가능성을 근거로 선택했기 때문에 예상한 채팅, 추천이나 유사도 검색 요구가 실제로
  추가되지 않을 수도 있다.

## 문서 작성 시점의 적용 상태

- 백엔드는 PostgreSQL JDBC 드라이버를 런타임 의존성으로 사용한다.
- 로컬과 운영 Docker Compose는 PostgreSQL 17 이미지를 사용한다.
- 현재 엔티티는 일반적인 관계형 스키마로 매핑하며 `jsonb`와 `pgvector`는 사용하지 않는다.

## 후속 작업

- PostgreSQL 고유 타입, 인덱스나 쿼리를 도입할 때는 실제 PostgreSQL에서 동작을 검증하는
  테스트를 추가한다.
- 채팅의 데이터 구조가 확정되면 일반 컬럼, 별도 테이블과 `jsonb`를 비교한 뒤 저장 방식을
  결정한다.
- 추천이나 유사도 검색 요구가 확정되면 검색 품질, 데이터 규모와 조회 성능을 측정하고
  `pgvector` 또는 별도 검색 저장소 도입을 새로운 ADR로 결정한다.
- DBMS 이전을 검토할 때는 PostgreSQL 전용 타입, 인덱스, 쿼리와 확장 사용 여부를 먼저
  확인한다.

## 적용하지 않는 범위

이번 결정은 다음을 의미하지 않는다.

- PostgreSQL이 모든 워크로드에서 MySQL보다 우수하다.
- 현재 MVP에 `jsonb`, `pgvector` 또는 별도 NoSQL 저장소를 도입한다.
- 채팅, 추천과 유사도 검색의 구체적인 데이터 모델이나 구현 방식을 확정한다.
- JPA를 사용하면 DBMS별 차이를 고려하지 않아도 된다.
