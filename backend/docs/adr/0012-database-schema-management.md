# ADR 0012. 데이터베이스 스키마를 저장소에서 관리한다

- 상태: 제안. 결정 6(테스트 DBMS를 PostgreSQL로 통일)은 2026-08-27에, 결정 7(Testcontainers
  사용)은 팀에서 확정했으며 H2 유지는 검토 대상이 아니다. 나머지 결정은 채택을 기다리고 있으며,
  마이그레이션 도구(결정 4)가 우선 미결정 항목이다.
- 날짜: 2026-08-27
- 관련 문서: [ADR 0011](0011-postgresql-rdbms-selection.md), [ADR 0009](0009-aws-deployment-topology.md),
  [영속성 컨벤션](../conventions/persistence.md), [프로젝트 운영 컨벤션](../conventions/project-operations.md)
- **이 문서는 아직 채택되지 않았다.** 현재 스키마 관리 방식과 그에 따른 비용을 기록하고, 도구 선택을
  팀의 결정 안건으로 제시한다. 결정이 내려지면 상태를 갱신한다.
- 개정: 2026-08-27. 팀에서 자동화 테스트를 PostgreSQL로 전환하기로 했다. 최초 작성본에서는 이 항목을
  결정에서 제외하고 후속 작업으로 미뤘으나, 결정 6에 포함한다.
- 개정: 2026-09-02. CI 러너에 관한 잘못된 설명을 바로잡고 테스트 데이터베이스 격리 문제를 제약으로
  기록한다.
- 개정: 2026-09-14. PR 본문에서 마이그레이션을 안내하고 SQL 코드는 저장소 파일로 관리하는 현재
  관행을 기록하고, 전체 스키마 베이스라인과 자동 적용 도구의 부재를 명확히 한다.
- 개정: 2026-09-14. 팀에서 결정한 Testcontainers 사용을 반영하고, Docker Compose 재사용을 전제로 쓴
  테스트 제약을 정리한다.

## 배경

[프로젝트 운영 컨벤션](../conventions/project-operations.md)의 ADR 우선 대상 첫 항목은
"데이터베이스와 마이그레이션 도구"다. [ADR 0011](0011-postgresql-rdbms-selection.md)에서는
DBMS를 선택했다. 그러나 **스키마를 누가 만들고 어떻게 변경할 것인가**는 아직 정하지 않았다.

이 기준 없이도 개발을 이어갈 수 있었던 이유는 환경마다 스키마가 자동으로 생성되었기 때문이다.

| 환경 | DBMS | 스키마 생성 방식 |
| --- | --- | --- |
| 테스트 | H2 인메모리 | `ddl-auto: create-drop`. 엔티티를 기준으로 매번 새로 생성한다 |
| 로컬 | PostgreSQL 17 | `ddl-auto: update`. 엔티티 변경 사항을 Hibernate가 스키마에 반영한다 |
| 운영 | PostgreSQL 17 | `ddl-auto: validate`. **스키마를 생성하거나 변경하지 않는다** |

세 환경은 스키마를 생성하는 방식이 모두 다르며, 테스트 환경은 DBMS도 다르다.

운영 환경에서만 `validate`를 사용한다. 애플리케이션을 실행하려면 스키마가 이미 있어야 한다.
저장소에는 운영 데이터베이스 전체를 처음부터 구성할 베이스라인이 없고, `backend/src/main` 아래에도
SQL 파일이 없다. Flyway나 Liquibase 의존성도 없어 마이그레이션을 애플리케이션이 자동 적용하지 않는다.

현재는 PR 본문에서 마이그레이션과 적용 절차를 안내하고, 실제 DB 마이그레이션 SQL 코드는 저장소의
`backend/db/migrations/`에 둔다. 두 방식은 서로 대체하는 선택지가 아니라 함께 사용한다. 이 디렉터리의
회원 유형·이름 정책 마이그레이션은 기존 `member` 테이블을 변경하며, 전체 운영 스키마를 재구성하는
베이스라인은 아니다.

과거 이미지 업로드 기능을 배포할 때 새 테이블이 필요했고, 당시 해당 DDL을 **Pull Request 본문**에
기록한 사례가 있다. 아래는 그 본문에서 발췌한 SQL이다. 이 과거 사례는 현재의 역할 구분, 즉 PR 본문은
변경과 적용 절차를 알리고 SQL 코드는 저장소 파일에서 관리하는 방식을 설명하는 예로 일반화하지 않는다.

```sql
-- PR #133 본문에서 발췌
CREATE TABLE IF NOT EXISTS image_upload (
    id uuid NOT NULL,
    ...
);
```

따라서 현재는 PR 본문으로 마이그레이션 변경과 적용 절차를 알리고, 저장소 SQL 파일을 운영자가 별도로
적용한다. 다만 저장소에 전체 운영 스키마 베이스라인이 없으므로 현재 SQL 파일만으로 운영 스키마의
전체 변경 이력을 재구성할 수 없다. 운영 환경에서는 처음부터 `validate`를 사용했으므로 애플리케이션이
테이블을 생성하지 않았다. Spring Session JDBC의 세션 테이블도 마찬가지다. `initialize-schema: always`는
로컬과 테스트 프로필에만 있고 운영 프로필에는 없으므로, 운영 환경의 세션 테이블 역시 별도로 생성되었다.

## 문제

현재 방식에는 다음과 같은 문제가 있다.

- **운영 DB를 처음부터 재구성할 수 없다.** EC2 인스턴스를 새로 생성하거나 볼륨이 손실되면 전체 스키마를
  복원할 베이스라인이 저장소에 없다. 저장소의 회원 정책 마이그레이션은 기존 테이블만 변경하므로 전체
  변경을 재생할 수 없다.
- **마이그레이션 적용 상태가 자동으로 기록되지 않는다.** PR 본문에서 적용할 변경을 안내하고 SQL을
  저장소 파일로 관리하더라도, 현재는 운영자가 수동으로 적용하므로 적용 여부와 순서를 자동으로 확인할 수 없다.
  변경을 빠뜨리면 `validate`로 인해 애플리케이션 기동이 실패한 뒤에야 알 수 있으며, 이마저도 배포 후에
  확인하게 된다.
- **되돌릴 절차가 없다.** 애플리케이션을 롤백해도 스키마는 변경된 상태로 남는다.
- **로컬 환경에서 운영 환경을 검증할 수 없다.** 로컬에서는 `update`를 사용하므로 엔티티만 수정해도
  스키마가 자동으로 변경된다. 따라서 운영에 필요한 DDL을 작성하지 않아도 로컬에서는 문제가 발생하지
  않으며, 누락 사실은 배포 시점에야 드러난다. [ADR 0007](0007-api-prefix-backend-context-path.md)이
  경로 계층에서 제거한 "로컬에서만 성립하는 구성"이 스키마 계층에는 그대로 남아 있다.

여기에 테스트 환경에서 다른 DBMS를 사용한다는 문제까지 더해진다.
[ADR 0011](0011-postgresql-rdbms-selection.md)에서도 이를 감수해야 할 비용으로 기록했다. 테스트에서는
H2와 `create-drop`으로 스키마를 생성하므로 운영 스키마와의 일치 여부를 검증하지 않는다. 실제로 이러한 차이 때문에 `nullable` 파라미터 CAST와 관련된 운영 오류가
발생했다(PR #93). H2에서 정상적으로 동작하던 조회가 PostgreSQL에서는 실패했고, 모든 테스트를
통과한 코드가 운영 환경에서 오류를 일으켰다.

팀은 2026-08-27에 자동화 테스트를 PostgreSQL로 전환하기로 했다. 마이그레이션 파일을 테스트에서도
실행하게 되므로 스키마 관리 방식과 테스트 DBMS 선택은 하나의 결정으로 연결된다. 테스트 DBMS로
H2를 유지하는 방안은 이 ADR의 검토 대상이 아니다.

## 제안하는 결정

1. **스키마 변경 SQL을 저장소에서 관리한다.** 모든 스키마 변경은 버전이 매겨진 마이그레이션 파일로
   `backend/db/migrations/`에 기록하고, 코드와 같은 PR에서 함께 리뷰한다. PR 본문에서는 변경할
   마이그레이션과 수동 실행 절차를 안내한다. SQL 변경 코드는 PR 본문이 아니라 저장소 파일에서 관리한다.
2. **운영은 `ddl-auto: validate`를 유지한다.** 애플리케이션이 스키마를 직접 변경하지 않는 현재 원칙은
   타당하다. 마이그레이션 도구가 스키마를 생성하고, Hibernate는 엔티티와 스키마의 일치 여부만 검증한다.
3. **로컬에서도 마이그레이션을 적용한다.** `ddl-auto: update`를 제거하고, 로컬과 운영 환경이 같은
   마이그레이션 파일로 동일한 스키마를 구성하도록 한다. 마이그레이션 파일을 누락하면 로컬에서 즉시
   확인할 수 있다.
4. **도구는 Flyway를 사용한다.** 아래의 대안 비교를 참고한다. 이 항목은 팀의 확정이 필요하다.
5. **첫 마이그레이션은 현재 운영 스키마를 그대로 반영한 베이스라인(baseline)이다.** 현재 운영 환경에
   존재하는 테이블을 `V1__baseline.sql`로 덤프하고, 이후의 변경 사항만 새 버전으로 추가한다.
6. **자동화 테스트의 DBMS는 PostgreSQL로 통일한다**(2026-08-27 팀 결정). H2는 선택지에서 제외한다.
   H2 의존성과 `ddl-auto: create-drop`을 제거하고 테스트에서도 같은 마이그레이션 파일로 스키마를
   구성한다. 그러면 세 환경의 DBMS와 스키마 생성 방식이 통일되고, 마이그레이션 파일 자체도
   테스트할 때마다 검증된다.
7. **PostgreSQL 테스트 컨테이너는 Testcontainers로 실행한다**(팀 결정). 테스트 실행 시 격리된
   PostgreSQL 컨테이너의 생명주기를 관리한다. 테스트 실행을 위해 개발자가 로컬 Docker Compose
   컨테이너를 미리 실행할 필요는 없다.

결정 6은 결정 1의 실효성을 확보하는 장치다. 테스트에서 마이그레이션을 실행하지 않으면 파일에
오류가 있어도 배포 전까지 발견할 수 없다. 반대로 테스트에서 해당 파일로 스키마를 구성하면,
엔티티와 마이그레이션이 일치하지 않을 때 CI 단계에서 오류를 발견할 수 있다.

자동화 테스트는 결정 7에 따라 Testcontainers로 PostgreSQL을 실행한다.
[`docker-compose-local.yaml`](../../docker-compose-local.yaml)은 로컬 개발 DB 구성에 사용하며 자동화
테스트의 컨테이너 실행을 담당하지 않는다. 로컬과 CI는 같은 Testcontainers 테스트 설정을 사용한다.

## 검토한 대안

테스트 DBMS로 H2를 유지하는 방안은 이미 제외되었다. 아래에서는 스키마 관리 방식과 마이그레이션
도구만 비교한다.

| 대안 | 장점 | 평가 |
| --- | --- | --- |
| A. 현행 방식 유지 (PR 본문 안내 + 저장소 SQL 마이그레이션 + 수동 실행) | 추가 학습 비용이 없다 | 전체 베이스라인이 없고, 수동 적용으로 인해 적용 이력·누락·순서를 도구로 관리하지 못한다 |
| B. Flyway | SQL 파일과 버전 번호만 알면 된다. Spring Boot가 기동 시 자동 적용한다. 적용 이력을 `flyway_schema_history` 테이블에 남긴다 | **추천.** 학습 비용이 가장 낮으며, 스키마를 저장소에서 관리하고 적용 이력을 남긴다는 요구 사항을 정확히 충족한다 |
| C. Liquibase | XML/YAML/SQL 중에서 형식을 선택할 수 있고 롤백 스크립트를 정식으로 지원한다 | 기능이 더 많지만 changelog 개념도 함께 익혀야 한다. MVP 범위에서는 이러한 추가 표현력을 활용할 가능성이 낮다 |
| D. 운영도 `ddl-auto: update`로 바꾼다 | 수동 DDL 실행이 사라진다. 변경 사항을 즉시 적용할 수 있다 | 애플리케이션이 운영 스키마를 직접 변경하게 된다. Hibernate가 컬럼 삭제와 타입 변경을 어떻게 처리할지 예측하기 어렵고, 변경 이력과 복구 방법도 없다. 문제의 형태만 바꿀 뿐 근본적인 해결책이 아니다 |

## 제약과 전제

- 운영 DB에는 이미 데이터가 저장되어 있다. 베이스라인은 기존 스키마와 정확히 일치해야 하며, 처음
  적용할 때는 `baseline-on-migrate`로 기존 상태를 인정한 뒤 시작해야 한다.
- 운영 DB는 PostgreSQL 컨테이너 안에 있고 호스트 포트를 열지 않는다
  ([ADR 0009](0009-aws-deployment-topology.md)). 현재 스키마를 덤프하려면 EC2 안에서 컨테이너에
  직접 접속해야 한다.
- 마이그레이션은 백엔드 컨테이너 기동 시점에 실행된다. 배포와 스키마 변경이 같은 순간에 일어나므로,
  기존 컬럼을 삭제하는 변경은 여러 단계로 나누어 배포해야 한다.
- [`truncate.sql`](../../src/test/resources/sql/truncate.sql)이 H2 전용 구문
  (`SET REFERENTIAL_INTEGRITY FALSE`)을 사용한다. 결정 6을 적용하려면 이 파일을 PostgreSQL 구문으로
  다시 작성해야 한다. `TRUNCATE ... RESTART IDENTITY CASCADE`로 변경하거나 외래 키 검사를 잠시
  지연하는 방식 중 하나를 선택한다.
- 테스트는 이미 GitHub 호스팅 러너(`ubuntu-latest`)에서 실행된다
  ([`ci.yml`](../../../.github/workflows/ci.yml)). 자체 호스팅 러너는 배포
  ([`backend-build.yml`](../../../.github/workflows/backend-build.yml))에만 사용한다. 호스팅 러너에는
  Docker가 있으므로 컨테이너 실행 가능 여부는 문제가 되지 않는다.
- Testcontainers가 실행하는 PostgreSQL 테스트 컨테이너와 로컬 Compose의 영구 `jarihana` 데이터베이스는
  분리된다. 테스트 전에 로컬 DB를 비우거나 별도 Compose 테스트 DB를 구성할 필요가 없다.
- Testcontainers를 사용하는 로컬·CI 실행 환경에는 Docker가 필요하다. CI는 GitHub 호스팅 러너를 사용하며
  해당 러너에서 컨테이너를 실행하도록 구성한다.

## 결과

### 적용했을 때 얻는 것

- 저장소만으로 운영 DB를 처음부터 만들 수 있다.
- DDL이 코드 리뷰를 거친다.
- 어떤 변경 사항이 언제 적용되었는지 DB에 이력이 남는다.
- 테스트, 로컬, 운영 환경의 스키마 생성 방식이 하나로 통일된다.
- 테스트가 운영과 같은 DBMS에서 실행되어 PostgreSQL 고유 동작을 배포 전에 검증할 수 있다.
  PR #93과 같은 실패를 CI에서 발견할 수 있다. [ADR 0011](0011-postgresql-rdbms-selection.md)이
  감수 비용으로 적어 둔 "H2 테스트만으로는 PostgreSQL 동작을 검증할 수 없다"는 문제도 함께 해소된다.
- 테스트할 때마다 마이그레이션 파일이 실행되므로 파일 자체도 검증 대상이 된다.

### 감수하는 비용

- 엔티티를 수정할 때마다 마이그레이션 파일도 함께 작성해야 한다. 현재는 로컬에서 엔티티의 변경 사항이
  스키마에 자동으로 반영된다.
- 베이스라인을 잘못 만들면 운영 환경에서 첫 적용이 실패하므로 신중하게 작성해야 한다.
- 테스트 실행 시간이 늘어난다. 인메모리 H2 대신 PostgreSQL과 마이그레이션을 사용하고 Testcontainers가
  테스트 컨테이너를 시작하기 때문이다.
- 테스트 실행에 Docker 의존성이 생긴다. Docker가 없는 환경에서는 백엔드 테스트를 실행할 수 없다.

## 후속 작업

- 도구를 확정한다(대안 B와 C). 이 ADR의 상태를 그 결정에 맞춰 갱신한다.
- Testcontainers 의존성과 PostgreSQL 테스트 구성을 추가하고, 같은 구성을 로컬 및 CI에서 사용해
  실제 컨테이너 실행을 검증한다.
- 운영 스키마를 덤프해 베이스라인 마이그레이션을 만든다. Spring Session JDBC의 세션 테이블도 함께
  포함한다.
- 로컬 프로필에서 `ddl-auto: update`를 제거한다.
- 테스트 프로필에서 H2 의존성과 `ddl-auto: create-drop`을 제거하고
  [`truncate.sql`](../../src/test/resources/sql/truncate.sql)을 PostgreSQL 구문으로 다시 작성한다.
- [ADR 0011](0011-postgresql-rdbms-selection.md)을 개정한다. 감수 비용의 "테스트 환경은 H2를
  사용하므로 PostgreSQL 고유 기능과 쿼리의 동작을 H2 테스트만으로 검증할 수 없다"와 그에 딸린
  후속 작업은 결정 6으로 해소된다.
- 운영 DB 백업 절차를 정한다. 마이그레이션이 실패했을 때 되돌릴 지점이 필요하다.
