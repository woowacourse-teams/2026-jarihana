# ADR 0014. 초기 관찰 플랫폼으로 Amazon CloudWatch를 사용한다

- 상태: 채택
- 날짜: 2026-09-23
- 관련 문서: [백엔드 ADR 목록](README.md),
  [배포 토폴로지 ADR](0009-aws-deployment-topology.md),
  [관측성 설계 회의 기록](https://app.notion.com/p/1-3e40978a6e6c80f58498d22ac57465de)

## 배경

자리하나는 로그, 메트릭, 대시보드와 알림을 처음 도입한다. 팀이 현재 마주한 목표는 관찰 도구를
직접 운영하는 경험을 쌓는 것보다 서비스 장애를 감지하고, 요청과 서버 상태를 바탕으로 원인을
찾을 수 있게 하는 것이다. 애플리케이션과 데이터베이스는 AWS 환경에서 운영하고 있으며,
팀의 인프라 운영 인력과 비용도 제한되어 있다.

회의에서는 Amazon CloudWatch, 관리형 Grafana Cloud, 별도 EC2에 Prometheus·Loki·Grafana를
직접 구축하는 방식을 비교했다. 직접 구축하면 수집·조회·시각화를 자유롭게 구성하고 AWS 외 환경으로 옮기기 쉽지만,
관찰 서버 자체의 자원, 장애, 업데이트, 데이터 보관과 복구도 팀이 책임져야 한다. 특히
애플리케이션과 같은 EC2에 관찰 스택을 두면 호스트 장애 시 서비스와 관찰 도구가 함께
중단될 수 있고, 별도 EC2에 두면 상시 운영 자원이 늘어난다.

## 결정

초기 로그·메트릭·대시보드·알림의 관찰 플랫폼으로 **Amazon CloudWatch를 사용한다**.
Prometheus·Loki·Grafana를 별도 EC2에 직접 구축하지 않는다. 먼저 CloudWatch에서 실제 장애를
감지하고 조사하는 흐름을 운영한 뒤, 조회·시각화·비용·이식성에 부족함이 확인되면 수집 계층
또는 관찰 플랫폼 변경을 재검토한다.

이 결정은 관찰 데이터를 어디에서 확인하고 알림을 운영할지에 관한 것이다. 애플리케이션의
ECS JSON 로그, 요청 ID, 비즈니스 로그 대상과 환경별 출력 형식은 별도 로깅 설계에서 다룬다.
CloudWatch로 데이터를 보내는 수집기, 메트릭별 수집 방법, 보관 기간과 세부 요금은 이 ADR에서
확정하지 않는다. 회의에서 Alloy를 중간에 두는 방안은 장래의 전환 가능성으로 언급됐지만,
초기 구성 요소로 채택한 것은 아니다.

## 선택 이유

- **우선순위:** 지금은 관찰 스택 자체의 운영보다 애플리케이션 장애 감지와 원인 추적을 먼저
  완성해야 한다.
- **운영 부담:** 직접 구축 시 필요한 별도 서버 운영, 구성 요소 업데이트, 저장 공간 관리와
  백업·복구 설계를 초기 범위에서 줄일 수 있다.
- **AWS 환경과의 연결:** 기존 EC2 및 향후 RDS 자원 지표를 같은 플랫폼의 대시보드·알림과
  연결할 수 있다. 애플리케이션 지표는 필요한 수집 설정을 별도로 마련해야 한다.
- **단계적 검증:** 실제 로그량, 메트릭 수, 조회 경험과 비용을 확인한 뒤 다른 도구로 옮길지
  판단할 수 있다.

## 검토한 대안

| 대안 | 장점 | 검토 내용과 미채택 배경 |
| --- | --- | --- |
| Grafana Cloud | 관찰 스택을 직접 운영하는 부담을 줄이면서 Grafana를 활용할 수 있다 | 유료 요금·무료 제공량·보관 기간과 도입 목적을 비교했으나, 팀의 다수결로 CloudWatch가 선택되어 채택하지 않았다. Grafana Cloud의 구체적인 미채택 사유는 별도로 정리하지 않았다 |
| 별도 EC2의 Prometheus·Loki·Grafana 직접 운영 | 수집·조회·시각화 구성을 직접 제어할 수 있고 AWS 종속을 줄일 수 있다 | 별도 호스트와 세 구성 요소의 운영, 저장 공간, 보관·복구, 장애 대응까지 초기부터 맡아야 한다 |
| 애플리케이션 EC2에 관찰 스택 함께 운영 | 추가 호스트 비용을 줄일 수 있다 | 호스트 자원을 서비스와 경쟁하고, 호스트 장애 시 관찰 도구도 함께 중단될 수 있다 |

Grafana Cloud는 단순히 언급된 후보가 아니라 다음 항목을 실제로 비교한 관리형 대안이다.

- **운영 편의성:** 관찰 스택을 관리해 주는 방식이라는 점을 직접 구축과 구분했다
  (녹취 18:40~19:32).
- **도입 목적:** 오픈소스 Grafana의 인지도가 Grafana Cloud를 선택할 근거로도 충분한지,
  관리형 사용이 Prometheus·Loki를 직접 운영하는 경험과 같은지 논의했다
  (녹취 21:38~23:18, 29:59~30:13).
- **비용과 보관:** 유료 요금, 무료 제공량과 14일 보관 기간을 CloudWatch와 비교했다
  (녹취 22:31~22:51, 26:16~29:59). 이는 회의 당시의 검토 내용이며, 현재 요금이나
  제공 조건을 검증·확정한 기록은 아니다.

CloudWatch를 지지한 발언은 직접 운영 공수 감소와 예상 비용을 근거로 했다
(녹취 31:29~32:03). 최종적으로 팀의 다수결로 CloudWatch를 선택했으며, Grafana Cloud는
채택하지 않았다. 각 대안을 배제하는 이유를 하나씩 확정하기보다 최종 플랫폼을 선택한
결정이므로, Grafana Cloud의 구체적인 미채택 사유가 별도로 정리되지는 않았다.

## 결과와 감수하는 비용

- 초기에는 관찰 전용 EC2와 자체 스택의 운영·복구 절차를 추가하지 않아도 된다.
- 로그·메트릭·알림을 AWS 서비스에 의존한다. 다른 플랫폼으로 옮길 때 수집 설정,
  대시보드와 알림 규칙을 다시 구성해야 할 수 있다.
- CloudWatch도 로그 수집·보관, 커스텀 메트릭 등에 비용이 발생할 수 있다. 회의에서 언급된
  무료 사용량이나 예상 금액을 확정 비용으로 간주하지 않는다.
- 관리형 플랫폼 선택만으로 애플리케이션 로그와 DB 지표가 자동으로 모두 수집되는 것은
  아니다. 필요한 신호와 수집 경로를 구현하고 장애 시나리오로 검증해야 한다.

## 후속 작업

- EC2·RDS·애플리케이션별 필수 로그와 메트릭, 수집 방법 및 권한을 정한다.
- 실제 API 헬스체크와 5xx 등 회의에서 정한 초기 알림을 구성하고 발생·해결을 시험한다.
- 로그 보관 기간, 예상 수집량과 CloudWatch 비용을 확인한다.
- 운영 후 조회·시각화 또는 비용 문제가 확인되면 Alloy 같은 수집 계층과 다른 관찰
  플랫폼으로의 전환을 새 결정으로 검토한다.
