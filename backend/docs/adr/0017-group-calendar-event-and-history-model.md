# ADR 0017. 모임 달력 일정과 정기 규칙 이력을 분리한다

- 상태: 채택
- 날짜: 2026-10-12
- 관련 문서: [백엔드 ADR 목록](README.md), [일정 모델](../context/domain/model/schedule.md),
  [비즈니스 정책](../context/domain/business-policies.md), [그룹 달력 API](../context/api/endpoints/group-calendar.md),
  [운영 데이터 이관·배포 가이드](../operations/group-calendar-rollout.md)

## 배경

기존 `Group`은 현재 반복 일정 또는 `SESSION` 일정을 embedded 값으로 보관한다. 이 구조만으로는 과거에 적용된 정기 규칙, 날짜별 정기 모임, 여러 날의 개별 일정과 장소 변경 당시 값을 달력에 제공할 수 없다. 달력 외부에서 같은 일정 ID를 참조할 수 있어야 하며, 장래 정기 회차별 참석 RSVP와 모임 소속 단기 모집으로 확장할 가능성도 고려해야 한다.

운영 DB에는 이미 그룹 정보가 있으므로 새 스키마는 기존 값을 바꾸지 않고 확장해야 한다. 운영은 애플리케이션 기동 시 schema validation만 수행하고, SQL 적용과 백필은 별도 운영 절차다.

## 결정

### 1. 개별 일정과 날짜별 정기 모임을 모임 소속 일정 자원으로 저장한다

- `GroupEvent`는 `INDIVIDUAL`과 `REGULAR_MEETING`을 구분한다. 일정은 `Group`에 속하며 달력, 장래 홈·목록 등 여러 화면이 같은 ID를 참조한다.
- 날짜별 정기 모임은 하루짜리 `REGULAR_MEETING` 일정으로 저장한다. 반복 규칙을 바꾸지 않고 회차 하나만 수정한 경우에도 같은 모델을 사용한다.
- 일반 반복 발생은 DB 행으로 미리 만들지 않고 조회 범위 안에서 계산한다. 안정적인 발생 키는 `seriesId + 발생 날짜`다. 수정된 회차는 `GroupEvent.id`를 가지며 원래 발생일 키를 유지한다.
- 반복 회차 삭제는 연결된 행을 soft delete tombstone으로 남겨 규칙 재계산이나 새로고침 뒤에 되살아나지 않게 한다.

### 2. 정기 규칙의 전체 기간과 규칙 변경 이력을 분리한다

- `GroupRecurringSeries`는 정기 규칙 묶음의 안정적인 ID와 전체 달력 표시 기간을 가진다.
- `GroupRecurringPeriod`는 묶음 안에서 요일·시각이 적용된 구간을 보관한다. 날짜 구간은 겹치지 않으며 시작·종료일은 포함한다.
- 요일·시각 수정 범위는 `모든 일정`, `이 이후의 일정도`, `이 일정만`이다. 선택한 회차 날짜가 기준이며, 규칙 구간 경계는 UI의 편집 범위로 사용하지 않는다. 전체 표시 시작·종료일은 별도 명령으로 수정한다.
- 날짜별 정기 모임과 변경 후 반복 규칙이 같은 날짜를 차지하면 규칙 변경을 거절한다. 사용자는 수동 회차를 옮기거나 삭제한 뒤 다시 시도한다.

### 3. 현재 모임 장소와 당시 장소 이력을 함께 보관한다

현재 `Group.location`은 기존 그룹 상세 계약을 위해 유지한다. 새 `GroupLocationHistory`에는 장소의 유효 구간을 기록해 달력 일정 상세에 당시 장소를 제공한다. 시각이 있는 정기·세션 일정은 발생 시각의 장소, 시각이 없는 정기 일정은 그날 마지막 장소를 사용한다. 이력이 없는 과거 시점은 현재 장소로 채우지 않는다.

### 4. 그룹 정보 저장과 일정 저장을 서로 다른 명령으로 처리한다

- 기존 그룹의 이름·소개·현재 장소 등 정보 수정은 일정 수정 요청을 자동으로 실행하지 않는다. 일정 모달 저장도 그룹 정보 수정 API를 호출하지 않는다.
- 정기 규칙과 이력 구간, 현재 장소와 장소 이력은 각 일정 명령 안에서 하나의 트랜잭션으로 저장한다.
- 새 그룹 생성은 기존 동작대로 생성 요청에서 최초 일정을 함께 저장한다.
- 변경 범위가 없는 구버전 정기 규칙 수정 경로는 새 달력 기능을 공개한 뒤 차단한다. 새 범위 선택 명령은 기존 API와 분리된 경로로 제공한다.

### 5. 미래 참석·모집 기능은 그룹 가입과 분리한다

- 장래 반복 회차 RSVP와 정원 제한은 `seriesId + 발생 날짜`를 참조한다. 이번 일정 단계에서는 RSVP 테이블이나 참석 정책을 추가하지 않는다.
- 장래 모임 주최 단기 모집은 `GroupEvent`를 기준 자원으로 연결한다. 기존 일정을 모집 대상으로 바꾸는 흐름과 일정·모집을 처음부터 함께 만드는 흐름을 모두 지원하는 방향으로 둔다. 두 흐름은 같은 `GroupEvent.id`를 달력·홈·목록에서 사용한다.
- 일정 신청은 그룹 가입이 아니므로 기존 `GroupRecruitment`·`Registration`을 재사용하지 않는다. 별도 참석 도메인으로 정의하고 일정과 모집을 함께 만들 때는 함께 성공하거나 롤백한다.
- 기존 `GroupType.SESSION`은 독립된 같이해요 그룹이므로 그룹 부속 단기 세션으로 재사용하지 않는다.
- 장래 마이페이지 개인 달력은 일정 데이터를 사용자별로 복제하지 않고, 모임 일정과 참석 근거를 모은 조회 모델로 만든다. 개인 달력에 자동 포함할 모임 기준은 기능 설계 시 결정한다.

## 선택 이유

- 날짜별 일정은 그룹의 다른 화면과 향후 RSVP가 재사용할 수 있는 안정 ID를 갖는다.
- 규칙 변경 이력은 날짜 경계를 보존하고, 발생 건별 영속화 없이 해당 달력 범위를 계산할 수 있다.
- 현재 그룹 정보 API와 장소 공개 계약을 유지하면서 달력 상세에서만 당시 장소를 제공한다.
- 정보 수정과 일정 수정을 별도 요청으로 두되, 각각의 데이터와 이력은 트랜잭션으로 원자성을 지킨다.
- RSVP, 외부 모집, 개인 달력의 공통 참조점을 정하되 현재 범위에 속하지 않는 저장 모델과 정책은 미리 만들지 않는다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| `Group` embedded 현재 일정 값만 사용 | 기존 모델 변경이 작다 | 과거 규칙·기간·날짜별 회차를 보존하거나 동일 일정 ID를 재사용할 수 없다 |
| 반복 발생 건을 전부 일정 행으로 생성 | 행별 상태와 참석자를 붙이기 쉽다 | 무기한 정기 일정과 규칙 변경에 불필요한 행이 쌓이고, 이번에는 참석 기능이 필요하지 않다 |
| 현재 장소만 달력 상세에 재사용 | 이력 테이블이 필요 없다 | 과거 장소를 잘못 표시한다. 운영 전 장소 변경은 복원할 수 없으므로 이력 시작 이전에는 빈 값으로 둔다 |
| 일정 참석에 그룹 가입 신청을 재사용 | 기존 신청 상태와 정원 모델을 활용할 수 있다 | 그룹 소속 생성과 단기 일정 참석은 다른 관계다. 외부 일정 참석만으로 `GroupMember`가 되면 안 된다 |
| 그룹 정보와 정기 일정을 한 번의 수정 요청으로 저장 | 화면상 한 번에 저장할 수 있다 | 한 영역만 실패해도 사용자가 저장 상태를 알기 어렵고, 그룹 정보 저장이 일정 이력 작업에 결합된다 |

## 결과와 후속 작업

- 확장 SQL과 백필은 코드 배포와 별도 단계다. 운영 DB의 실제 데이터·스키마·백업 복원은 이 ADR이나 테스트만으로 검증되지 않는다. 절차는 [운영 가이드](../operations/group-calendar-rollout.md)를 따른다.
- 기존 정기 규칙 변경 이력과 장소 변경 이력은 배포 전까지 복구할 수 없다. 초기 이력의 기준과 공백을 모임장이 확인할 수 있게 한다.
- 정기 요일 변경으로 예약된 발생일이 사라질 때 이미 참석 신청한 구성원을 어떻게 처리할지는 RSVP 기능 설계에서 결정한다.
- 외부 모집의 공개 상세 정보, 정원·대기·취소 규칙과 개인 달력 포함 기준은 이 기능을 구현할 때 별도로 확정한다.
