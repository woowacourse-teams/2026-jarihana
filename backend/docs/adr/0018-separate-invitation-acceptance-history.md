# ADR 0018. 초대 합류 이력을 모집 신청과 분리한다

- 상태: 채택. 저장 기반·모집 정원 집계 구분·초대 발급·수신 구현, 초대 수락·소속·PENDING 승인 연결 구현.
- 날짜: 2026-10-11
- 결정 근거: 초대 설계 논의에서 사용자가 기존 신청 모델 확장과 별도 초대·수락 모델을 비교한 뒤 분리하는 방향을 채택했다.
- 관련 문서: [백엔드 ADR 목록](README.md), [신청 모델](../context/domain/model/registration.md),
  [초대 모델](../context/domain/model/invitation.md), [초대 정책](../context/domain/business-policies.md#초대-발급과-합류),
  [초대 운영](../operations/invitations.md), [수동 DDL](../../db/migrations/2026-10-11-invitation.sql).

## 배경

기존 Registration은 특정 회원과 모집 공고를 필수로 연결하는 신청 이력이다.
초대는 모집 공고가 없거나 마감·정원 도달한 모임에서도 합류를 허용해야 한다.
초대 합류자를 모두 Registration에 기록하려면 모집 연결을 선택 사항으로 바꾸고,
모임 연결·참여 유형을 추가한 뒤 기존 신청·승인·정원 집계·조회·알림의 전제를 함께 바꿔야 한다.

공유 링크는 모임 기준으로 발급하며 사람별 합류 기록과 별도로 존재한다.
하나의 링크를 여러 사람이 사용할 수 있다는 사실 자체가 Registration 통합을 불가능하게 하지는 않는다.
이번 선택의 핵심은 기존 모집 신청 모델의 의미와 필수 관계를 유지하면서 초대 합류를 표현하는 것이다.

## 결정

1. Invitation은 모임·발급자·유형·지정 대상·만료·취소를 관리한다. 모집 공고나 신청을 요구하지 않는다.
2. 초대로 실제 신규 합류한 사람의 사건은 InvitationAcceptance에 기록한다.
   공유 초대 하나에 여러 회원의 수락 이력을 연결하고, 같은 초대·회원의 수락은 한 건으로 제한한다.
3. 실제 모임 소속은 기존 GroupMember를 기준으로 한다. 초대 이력에 현재 소속을 중복 저장하지 않는다.
4. 기존 PENDING 신청이 있으면 해당 Registration도 초대 출처로 승인한다.
   기존 신청이 없으면 가짜 모집 공고나 Registration을 만들지 않는다.
5. Registration에 approvalOrigin(RECRUITMENT/INVITATION)을 둔다.
   기존 데이터와 일반 신청 경로는 RECRUITMENT로 보존한다.
   초대 경로는 APPROVED·SYSTEM으로 기록하며 leaderViewedAt을 유지한다.
6. 모집 정원에는 모집으로 가입한 인원만 집계하고 실제 구성원 수는 GroupMember로 계산한다.
   집계 변경은 3단계에서 구현했으며 소속·수락·신청 승인의 원자적 연결은 6단계에서 구현했다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 또는 선택 이유 |
| --- | --- | --- |
| Registration을 모든 참여 이력으로 확장 | 참여 이력을 한 모델에서 조회할 수 있다 | 모집 연결을 선택 사항으로 바꾸고 모임·유형별 처리를 기존 신청·승인·조회·알림에 추가해야 한다. 현재 모집 신청의 필수 관계와 의미를 유지하기 어렵다 |
| 초대 합류에도 모집 공고·신청을 생성 | 기존 모델을 그대로 사용한다 | 모집 없는 합류를 표현하려고 실제로 존재하지 않는 모집·신청을 만들며 신청 통계·정원·업무 의미가 달라진다 |
| Invitation·InvitationAcceptance를 분리하고 기존 신청의 승인 출처를 보존 (**채택**) | 모집 없이 합류할 수 있고 기존 신청 모델과 실제 소속을 유지한다 | 초대·수락 테이블과 승인 출처 보정이 추가되지만 현재 기능의 의미를 바꾸는 범위를 줄인다 |

## 선택 이유

- 신청은 회원의 모집 참여 요청이고 초대 합류는 초대를 수락해 새 소속을 만든 사건이다. 서로 다른 의미를 별도 모델로 표현한다.
- 초대 합류 이력을 남기기 위해 Registration.recruitment의 필수 조건을 완화하지 않는다.
- 기존 신청이 있는 사람은 신청 결정 이력도 보존하되, 출처를 구분해 모집 정원에 잘못 포함하지 않는다.
- 모든 초대 합류는 수락 이력에서, 현재 구성원은 GroupMember에서 조회할 수 있다.

## 감수하는 비용

- 전체 참여 이력을 한 화면에 제공하려면 신청과 초대 수락 기록을 조합해야 한다.
- 초대·수락 테이블과 유일 제약·삭제 순서를 관리해야 한다.
- 승인 출처 필드 추가와 기존 데이터 보정이 필요하며 정원 관련 모든 집계를 점검해야 한다.
- 소속 생성·수락 이력·기존 신청 승인은 한 트랜잭션에서 처리해야 한다.

## 검증과 후속 작업

- 저장 기반 검증: PostgreSQL 17에서 DDL 적용·재적용·기존 승인 보존·Hibernate validate를 확인했다. 저장 기반을 추가한 2단계 당시 전체 백엔드 테스트 642개와 빌드가 통과했다. 공유·운영 DB에는 아직 적용하지 않았다.
- 3단계에서 선착순 가입·수동 승인·정원 수정, 모임/모집 목록·상세와 모집 중 필터를 RECRUITMENT 출처 기준으로 변경했다. 신청 상태별 이력 집계와 실제 구성원 집계는 각각 유지한다.
- 6단계에서 소속·수락·PENDING 승인을 연결했다. 모집 없는 합류·프록시 대상·기존 이력·동시 승인/수락/취소/종료를 실제 PostgreSQL·HTTP에서 검증했다.
- 그룹 삭제 시 수락 이력 → 초대 → 기존 연관 데이터 → 그룹 순서로 같은 트랜잭션에서 정리한다. 10단계에서 기존 삭제 명령에 연결했으며 알림은 보존하고 미완료 초대 전송만 취소한다. 삭제 FK에 DB cascade를 추가하지 않고 기존 서비스의 명시적 삭제 흐름을 사용한다.
- 공유 링크 재복사를 위한 해시·암호문 저장과 키 관리는 [백엔드 ADR 0019](0019-encrypted-invitation-token-storage.md)에서 채택했다.
  수락의 동시성 선택은 [백엔드 ADR 0020](0020-optimistic-invitation-acceptance.md)를 따른다.
  이 ADR의 결정 범위는 초대·수락 이력과 모집 신청의 분리다.
