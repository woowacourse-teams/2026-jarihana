# ADR 0019. 초대 합류는 unique 제약과 낙관적 잠금으로 충돌을 처리한다

- 상태: 채택. 6단계 구현과 로컬 PostgreSQL·HTTP·전체 백엔드 검증 완료.

- 결정 근거: 사용자는 모임 전체의 비관적 잠금과 낙관적 잠금을 비교한 뒤, 서로 다른 회원의 합류를 동시에 처리하고 실제 충돌에만 롤백·재시도를 적용하는 방향을 채택했다.

## 배경

모임장이 공유 링크를 전달하면 서로 다른 회원이 같은 모임에 함께 합류할 수 있다.
초대 합류는 모집 정원을 소진하지 않으므로, 이 요청들을 모임 한 행의 배타적 잠금으로 모두 순서대로 처리할 필요가 없다.
다만 같은 회원의 중복 수락, 기존 신청 승인과 초대 수락, 초대 취소·모임 종료와 수락이 겹칠 때는 결과의 정합성을 보장해야 한다.

여기서 소속은 GroupMember다. 한 회원이 특정 모임의 구성원이라는 기록이며 초대 수락 이력과 모집 신청 이력은 별도로 저장한다.

## 결정

1. 정상 초대 수락은 모임의 PESSIMISTIC_WRITE 잠금을 획득하지 않는다. 서로 다른 회원은 같은 공유 링크로 동시에 합류할 수 있다.
2. 같은 모임·회원의 중복 소속은 기존 GroupMember unique 제약으로 막는다. 충돌한 요청은 트랜잭션 전체를 롤백한 뒤 새 트랜잭션에서 자격과 소속을 다시 조회한다. 이미 합류했으면 ALREADY_JOINED와 기존 소속을 반환한다.
3. Registration에 버전을 두고 기존 신청 승인과 초대 승인 사이의 덮어쓰기를 감지한다. 신청 상태 전이로 만든 새 인스턴스에도 읽은 버전을 보존한다.
4. Group과 Invitation에 버전을 두고 수락 트랜잭션에서 OPTIMISTIC 검증을 요청한다. 공유 링크 수락만으로 두 버전을 증가시키지 않는다. 지정 초대 수락은 OPTIMISTIC_FORCE_INCREMENT로 초대 버전을 증가시켜 수락 이력 저장과 대상 회원의 거절 갱신 사이의 경쟁도 감지한다. 취소·종료·거절 등 상태 변경이 감지되면 롤백 후 현재 상태를 다시 판단한다.
5. 소속 생성·초대 수락 이력·같은 모임과 회원의 모든 기존 PENDING 승인을 한 트랜잭션에 저장한다. 하나라도 실패하면 함께 롤백한다. 모집 정원 집계와 일반 승인 알림은 추가하지 않는다.
6. 버전 충돌과 소속·수락 이력의 지정된 unique 제약 충돌만 재시도한다. 최초 요청을 포함해 최대 3번 시도하고, 계속 충돌하면 CONCURRENT_MODIFICATION(409)을 반환한다. 임의의 저장 실패나 비즈니스 오류는 재시도하지 않는다.
7. 일반 모집의 정원 보호를 위한 모집 행 잠금은 유지한다. 초대 수락과 함께 사용하는 신청 명령은 모임의 배타적 잠금 대신 상태 버전을 검증한다. 신청 변경을 먼저 flush하여 동일 신청의 충돌을 소속 저장 전에 확인한다.
8. 같은 회원이 서로 다른 모집에 PENDING을 중복 생성하지 않도록 신청 생성의 기존 모임 잠금은 유지한다. 소속 저장 이후 PENDING을 다시 조회해 수락 도중 새로 생성된 신청도 같은 트랜잭션에서 승인한다. 신청 생성과 신청 승인의 잠금 범위는 구분한다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 또는 선택 이유 |
| --- | --- | --- |
| 수락·일반 승인·취소·종료에 공통 모임 비관적 잠금 | 같은 모임 요청을 순서대로 처리해 충돌 판단이 단순하다 | 서로 다른 회원의 정상 합류까지 대기시키므로 채택하지 않았다 |
| 모든 수락에서 모임 버전을 증가시키는 낙관적 잠금 | 모임 단위 변경 경쟁을 감지하기 쉽다 | 서로 다른 회원의 합류도 동일 버전 갱신 충돌을 일으키므로 채택하지 않았다 |
| 소속 unique 제약과 필요한 상태의 낙관적 검증 (**채택**) | 정상 합류를 함께 처리하고 중복·상태 변경·신청 갱신 충돌을 구분한다 | 버전 보존과 롤백 이후 재조회·제한된 재시도의 비용을 감수한다 |
| 상태를 처음 한 번 조회하고 unique 제약만 적용 | 구현이 간단하고 중복 소속을 막는다 | 확인 이후 발생한 초대 취소·모임 종료와 신청 결정 변경을 검증할 수 없다 |

## 선택 이유

초대는 모집 자리 배분과 무관하며 서로 다른 회원의 합류는 서로의 소속을 변경하지 않는다.
이 요청들이 모임의 배타적 잠금을 공유할 필요는 없다는 사용자의 판단을 반영한다.
중복 소속은 DB unique 제약, 신청의 변경은 신청 버전, 취소·종료는 초대와 모임의 버전 검증이 각각 담당한다.
실제 충돌 빈도와 처리량은 아직 측정하지 않았으며 성능 향상을 확정된 결과로 주장하지 않는다.

## 감수하는 비용

- Group·Invitation·Registration의 버전 컬럼을 운영 반영 전에 증분 DDL로 추가해야 한다.
- 불변 엔티티의 모든 상태 전이에서 버전을 보존해야 하며 직접 SQL로 상태를 바꿀 때도 버전을 증가시켜야 한다.
- 충돌 시 실패한 트랜잭션 안에서 계속 저장하지 않고, 롤백이 끝난 후 새 트랜잭션에서 다시 판단해야 한다.
- 낙관적 검증도 DB의 실제 읽기·쓰기 잠금을 없애지는 않는다. 모임 배타적 잠금과 모임 버전 증가를 제거하며, 지정 초대의 수락·거절 경쟁을 감지하기 위한 초대 버전 증가는 유지한다.
- 겹친 요청의 성공 여부는 DB에서 상태 검증과 변경이 수행된 순서로 결정한다. HTTP 도착 순서만으로 수락·취소·종료의 우선순위를 보장하지 않는다.
- 가입 승인 외에도 확인 처리·철회·종료가 신청 버전과 충돌할 수 있으므로 관련 기존 명령을 회귀 검증한다.

## 검증과 후속 작업

- 2026-10-12: 지정 대상의 영구 거절을 추가했다. 거절만 version을 변경하면 수락이 먼저 커밋된 경쟁을 거절 트랜잭션이 감지하지 못하므로 지정 초대 수락에도 초대 version 증가를 적용한다. 공유 링크의 서로 다른 회원은 기존 동시 합류 경로를 유지한다.

- 서로 다른 회원이 동일 공유 링크의 저장 단계에 동시에 도달하고 모두 합류하는지 확인한다.
- 같은 회원의 중복 수락·일반 승인과 초대 수락·취소와 수락·종료와 수락의 결과와 전체 롤백을 PostgreSQL 및 HTTP 테스트로 확인한다.
- 증분 DDL 적용·재적용과 기존 데이터 보존, Hibernate validate를 확인한다.
- 2026-10-11: 동일 링크의 서로 다른 회원이 소속 저장에 동시에 도달해 모두 합류하고, 이 수락만으로 모임·초대 버전이 증가하지 않음을 확인했다. 동일 신청을 읽은 일반 승인과 초대 수락의 양방향 충돌, 상태 확인 이후 취소·종료의 전체 롤백, 수락 도중 새로 생성된 신청의 초대 승인을 확인했다.
- 증분 DDL 적용·재적용·기존 이력과 증가한 버전 보존 및 Hibernate validate를 격리 스키마에서 확인했다.
- `./gradlew test build --rerun-tasks` 통과: 89개 suite, 732개 테스트, 실패·오류·생략 0. 공유·운영 DB 적용과 부하 측정은 수행하지 않았다.
