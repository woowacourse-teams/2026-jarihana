## 쉽게 보는 요약

이 문서는 **배포가 실패했을 때 제대로 되돌리는 방법**과 **개발 환경에서 점검한 이미지를 운영에 배포하는 방법**을 제안한다.
아직 구현하지 않았다. 보존 개수, 수동 배포 예외처럼 팀 합의가 필요했던 항목은 2026-10-16에 정했다
([합의 결과](#합의-결과)).

| 해결할 문제 | 현재 동작 | 제안하는 동작 |
| --- | --- | --- |
| 설정을 잘못 바꾸면 이미지 롤백만으로 복구되지 않는다 | 앱 이미지만 이전 버전으로 바꾸고, 잘못된 새 설정은 계속 쓴다 | 직전 성공 배포의 이미지와 설정 파일을 함께 되돌린다 |
| 개발 환경 점검에 실패한 이미지도 운영에 배포될 수 있다 | 이미지가 만들어졌다는 표시만 보고 운영에서 가져온다 | 개발 환경 점검을 통과한 이미지에 별도 표시를 붙이고, 운영 자동 배포는 그 이미지만 가져온다 |

첫 번째 제안은 다음 상황을 복구하기 위한 것이다.

```text
직전 배포 성공: 이미지 A + 설정 v1
이번 배포 실패: 이미지 A + 설정 v2(포트 오류)

현재: 이미지가 같아 롤백을 건너뛰거나, 잘못된 설정 v2로 다시 실행한다.
제안: 이미지 A + 설정 v1을 함께 실행해 직전 성공 상태로 돌아간다.
```

두 번째 제안은 이미지에 붙은 표시의 의미를 구분한다.

```text
이미지 빌드 → "만들어짐" 표시 → 개발 환경 배포와 점검 → "점검 통과" 표시
운영 자동 배포는 "점검 통과" 표시가 있는 이미지를 선택한다.
```

설정 파일의 사본은 서버에 보관한다. DB 비밀번호 같은 GitHub Environment 값과 데이터베이스 스키마는
이 사본에 포함하지 않으며, 이 제안으로 이전 값이나 상태를 복원할 수 없다.

## 용어

| 용어 | 이 문서에서의 의미 |
| --- | --- |
| dev / prod | 각각 개발 환경과 운영 환경 |
| runner / job | runner는 GitHub Actions 작업을 실행하는 컴퓨터, job은 워크플로 안의 작업 단위 |
| 이미지 태그(tag) | 이미지에 붙이는 이름. 같은 이름이 나중에 다른 이미지를 가리킬 수 있다 |
| 이미지 digest | 이미지 내용으로 정해지는 고유 식별자. 점검한 이미지 자체를 지정할 때 사용한다 |
| backend 트리 해시 | `backend/` 디렉터리의 파일 내용을 식별하는 값. 병합 후 커밋 SHA가 달라도 파일 내용이 같으면 같다 |
| 릴리스 | 배포에 사용하는 이미지와 설정 파일의 조합 |
| 릴리스 디렉터리 | 해당 배포에 사용한 설정 파일과 점검 스크립트의 사본을 보관하는 서버 폴더 |
| 검증 태그 / 승격 | 검증 태그는 dev 점검을 통과한 이미지에 붙이는 이름. 승격은 그 태그를 붙여 prod가 선택할 수 있게 하는 단계 |

## 배경

[백엔드 ADR 0016](0016-github-hosted-build-and-ghcr.md)에 따른 현재 배포 순서는 다음과 같다.

1. GitHub 호스팅 ARM runner가 백엔드 이미지를 만들고 GHCR(이미지 저장소)에 올린다.
2. dev와 prod EC2의 runner가 이미지를 받아 Compose로 컨테이너를 교체한다.
3. `infra/scripts/verify-backend.sh`로 배포 후 점검을 실행한다.
4. 점검에 실패하면 서버에 기록된 직전 성공 태그로 이미지를 되돌린다(백엔드 ADR 0016 결정 4).

2026-10-12 dev 수동 배포([실행 38209431773](https://github.com/woowacourse-teams/2026-jarihana/actions/runs/38209431773))에서는
점검 실패 후 직전 성공 이미지로 돌아가 같은 점검을 통과했다. 이미지 롤백의 동작은 확인했다.

2026-10-15 외부 리뷰는 이 흐름의 빈틈 두 가지를 지적했고, 워크플로 코드에서 둘 다 사실로 확인했다.

### 문제 1. 롤백이 설정 변경 장애를 복구하지 못한다

**현재 롤백은 이미지만 되돌린다. 설정 파일은 실패한 배포의 것을 계속 사용한다.**

배포 job은 실행한 커밋을 runner 작업 디렉터리에 체크아웃한다. 배포와 롤백은 모두 이 디렉터리의
다음 파일을 사용한다.

- `infra/docker-compose.yml`(prod), `infra/docker-compose.dev.yml`(dev)
- `infra/monitoring/alloy/config.alloy`(로그와 지표 수집기인 Alloy가 읽는 설정 파일)
- `infra/scripts/verify-backend.sh`

"직전 성공 태그로 롤백" 단계에서 바꾸는 값은 `BACKEND_TAG`뿐이다. Compose의 포트나 Alloy 설정을
잘못 바꿨다면 이전 이미지도 그 잘못된 설정으로 실행된다. 이전 컨테이너는 `--force-recreate`로
이미 교체했기 때문에, 롤백 점검도 실패하면 서비스가 중단된 채로 남는다.

이미지 태그가 같으면 롤백을 시도하지 않는 문제도 있다.

- prod는 `tree-<트리 해시>` 이미지의 revision 라벨을 `BACKEND_TAG`로 사용한다.
- prod Compose 파일인 `infra/docker-compose.yml`은 dev 워크플로의 `paths`에 없다. 이 파일만 바꾸면
  이미지가 새로 만들어지지 않아 `BACKEND_TAG`도 그대로다.
- 롤백 조건인 `steps.previous.outputs.tag != env.BACKEND_TAG`가 거짓이 되어 롤백을 건너뛴다.
  dev에서 실행 중인 태그를 수동으로 다시 배포할 때도 같은 조건이 적용된다.
- `config.alloy`처럼 dev 재빌드를 일으키는 파일이 바뀌면 태그가 달라져 롤백은 시도한다.
  하지만 잘못된 새 설정을 계속 사용하므로 복구에 실패할 수 있다.

### 문제 2. prod가 dev 점검 결과를 확인하지 않는다

**현재 `tree-<해시>` 태그는 이미지가 만들어졌다는 뜻이다. dev 점검 통과를 뜻하지 않는다.**

dev의 build job은 배포와 점검 전에 이 태그를 붙인다. 이후 dev 점검에 실패해 롤백하더라도 태그는
남는다. prod의 "배포할 이미지 정하기" 단계는 `tree-<main의 backend 트리 해시>` 태그의 존재만
확인하므로, 해당 코드가 main에 병합되면 dev에서 실패한 이미지도 배포할 수 있다.

[백엔드 ADR 0016](0016-github-hosted-build-and-ghcr.md) 결정 5에서도 이 한계를 명시했다.
현재는 사람이 develop을 main으로 릴리스 병합하는 절차가 운영 배포의 관문이다.

같은 `tree-` 태그가 가리키는 이미지도 바뀔 수 있다. 예를 들어 `config.alloy`만 바뀌어도 dev 빌드가
다시 실행된다. backend 트리는 같지만 이미지의 revision 라벨은 새 커밋 SHA로 바뀌므로 digest가
달라진다. 따라서 태그 이름만 같다고 dev에서 점검한 이미지 자체라고 볼 수 없다.

### 워크플로로 되돌릴 수 없는 것

DB 비밀번호 같은 실행 값은 GitHub Environment(dev, prod)의 Variables와 Secrets에서 job `env`로
주입한다. 현재 워크플로는 이전 값을 보관하지 않고, Secrets의 값은 다시 조회할 수도 없어
직전 성공 시점의 값으로 복원할 수 없다. 롤백할 때도 현재 워크플로의 job `env`를 사용한다.

이 문서는 설정 파일을 되돌리는 방법을 제안한다. 실행 값까지 되돌릴 수는 없으므로, 값의 이름을
바꾸는 배포에서도 롤백이 가능하도록 별도 규칙을 둔다(결정 4).

## 결정

아래 1~6은 구현할 동작에 대한 제안이다. 현재 워크플로에 적용된 동작과 구분해서 읽는다.

### 흐름 요약

| 단계 | 실행 위치 | 하는 일 |
| --- | --- | --- |
| dev build | GitHub 호스팅 runner | jar 빌드 후 이미지를 올리고, digest와 backend 트리 해시를 출력한다 |
| dev deploy | dev EC2 runner | 그 digest로 배포하고 점검한다. 성공하면 이미지와 설정을 기록하고, 실패하면 직전 성공 조합으로 돌아간다 |
| dev promote(승격) | GitHub 호스팅 runner | 빌드한 이미지와 dev에서 점검한 이미지가 같은지 확인하고 검증 태그를 붙인다 |
| prod deploy | prod EC2 runner | main의 backend 트리에 해당하는 검증 태그로 digest를 정하고, dev deploy와 같은 순서로 배포한다 |

dev와 prod의 배포 job 안에서는 다음 순서를 따른다.

```text
직전 성공 기록 읽기 → digest로 이미지 받기 → 설정 사본 준비
→ Compose 설정 해석 → Alloy 설정 검증 → 컨테이너 교체 → 배포 후 점검

성공: 이미지와 설정 조합을 기록
실패: 교체를 시도했고 직전 성공 릴리스와 다르면 롤백(결정 2)
```

### 1. 성공한 이미지와 설정의 버전을 함께 기록한다

롤백할 때 무엇을 실행해야 하는지 알 수 있도록, 성공 기록에 이미지 digest와 설정 파일 위치를 함께 남긴다.

- 기록 파일 경로는 지금처럼 runner 계정 홈의 `.jarihana/backend-<env>-last-success`로 두고, 형식만
  태그 한 줄에서 `이름=값` 줄로 바꾼다.

  ```text
  backend_tag=<APP_VERSION으로 쓰는 커밋 SHA>
  image_digest=sha256:<점검을 통과한 이미지의 digest>
  config_sha=<배포한 워크플로 실행의 GITHUB_SHA>
  release_dir=<결정 2의 릴리스 디렉터리 절대 경로>
  run_url=<기록을 남긴 워크플로 실행 URL>
  ```

- prod 기록에는 `verified=<true|false>`를 더한다. 검증 태그로 고른 digest면 `true`, 검증 태그 없는
  이미지를 수동 실행으로 배포했으면 `false`다(결정 6).
- 기록은 점검을 모두 통과한 뒤에만 갱신한다. 임시 파일을 완성한 다음 `mv`로 바꿔 끼워,
  작업이 중간에 끊겨도 일부만 저장된 기록이 남지 않게 한다.
- 읽을 때는 필요한 키만 골라 읽는다. 파일을 `source`로 실행하지 않는다.
- 이미지 식별에는 digest를 사용한다. 같은 커밋의 build job을 다시 실행하면 `<커밋 SHA>` 태그도
  다른 이미지로 옮겨질 수 있지만, 기록한 digest는 점검한 이미지를 계속 가리킨다.
- 옛 형식(태그 한 줄)은 `backend_tag`만 있는 기록으로 읽는다. 이때는 설정을 되돌릴 수 없으므로 지금처럼
  이미지만 되돌리고 경고를 남긴다. 새 형식으로 한 번 성공하면 기록이 바뀐다.

### 2. 설정 사본으로 배포하고, 롤백도 이전 사본으로 실행한다

체크아웃한 작업 디렉터리는 다음 배포 때 내용이 바뀐다. 배포에 쓴 설정이 나중에 바뀌지 않도록,
서버의 별도 폴더에 사본을 만들어 그 파일로 실행한다.

#### 설정 사본을 만드는 규칙

- 위치는 runner 홈의 `~/.jarihana/backend-<env>-releases/<config_sha>/`다.
- 워크플로 `paths`에 있는 infra 파일(Compose, `infra/monitoring/alloy/config.alloy`,
  `infra/scripts/verify-backend.sh`)을 같은 상대 경로로 복사한다.
- 같은 이름의 폴더가 이미 있으면 덮어쓰지 않는다. 한 번 만든 릴리스 디렉터리는 수정하지 않는다.
- Compose 설정 해석, Alloy 검증, 컨테이너 교체와 배포 후 점검은 모두 이 사본을 사용한다.

Compose 파일의 `name:`이 각각 `jarihana-dev`, `jarihana-prod`로 고정되어 있다. 실행 폴더가 달라져도
같은 프로젝트의 컨테이너와 `alloy-data` 볼륨을 관리한다.

#### 롤백을 실행하는 조건

배포가 실패하면 아래 세 조건을 모두 만족할 때 롤백한다.

1. 직전 성공 기록이 있다.
2. 컨테이너 교체 단계를 시도했다.
3. 직전 성공 기록과 비교해 `image_digest` 또는 `config_sha`가 다르다.

이미지가 같아도 설정 커밋이 다르면 롤백 대상이다. 둘 다 같으면 같은 릴리스를 다시 실행하는 경우이므로
롤백을 건너뛴다.

#### 롤백 순서

1. 직전 성공 기록의 digest로 이미지를 확보한다. 서버에 없으면 `<이미지>@<digest>`로 받는다.
2. 직전 성공 기록의 `backend_tag`를 해당 이미지의 로컬 태그로 다시 붙인다. 같은 이름의 로컬 태그가 다른 이미지를
   가리키더라도, 점검한 이미지로 되돌아가도록 한다.
3. 직전 `release_dir`의 Compose 파일로 `up -d --no-build --force-recreate backend alloy`를 실행한다.
4. 그 디렉터리의 점검 스크립트와 Alloy 준비 상태(readiness) 확인으로 복구를 점검한다.
   복구에 성공해도 이번 배포 결과는 실패로 남긴다.

#### 예외와 사본 정리

- 옛 형식 기록이나 수동 정리 때문에 직전 릴리스 디렉터리가 없으면, 현재 체크아웃의 설정으로 이미지만
  되돌리고 경고를 남긴다.
- "오래된 Backend 이미지 정리" 단계에서 릴리스 디렉터리도 함께 정리한다. 최근 5개와 직전 성공 기록이
  가리키는 디렉터리를 남긴다(2026-10-16 합의).

#### 배포와 롤백 스크립트

배포와 롤백 절차는 워크플로 단계 안의 셸 코드로 두지 않고 `infra/scripts`의 스크립트로 옮긴다. 워크플로는
이 스크립트를 호출한다. 같은 스크립트를 로컬 Docker에서도 실행해, 설정 오류를 낸 뒤 이전 상태로
복구되는지 확인한다(2026-10-16 합의).

- 롤백은 현재 체크아웃의 스크립트가 실행하고, 직전 릴리스 디렉터리의 Compose 파일과 점검 스크립트를 사용한다.
- 스크립트 자체의 결함은 워크플로 파일의 결함처럼 롤백으로 복구할 수 없다.

### 3. 컨테이너를 교체하기 전에 Compose 설정을 검사한다

- 교체 단계 전에 `docker compose -f <릴리스 디렉터리의 Compose 파일> config --quiet`를 실행한다. 문법
  오류와 `${이름:?}`로 요구한 값의 누락이 교체 전에 드러나므로, 기존 컨테이너를 지우지 않고 멈춘다.
- `config`의 출력에는 실행 값이 펼쳐지므로 `--quiet` 없이 로그에 남기지 않는다.
- 이 검증은 설정 파일을 해석할 수 있는지 확인한다. 컨테이너 기동 후에 드러나는 오류(잘못된 포트,
  메모리 제한, 값의 내용)는 배포 후 점검과 결정 2의 롤백으로 처리한다.

### 4. 실행 값의 이름은 이전 설정도 읽을 수 있게 두 번에 나눠 바꾼다

Compose 파일을 되돌려도 job `env`와 GitHub Environment 값은 현재 값을 사용한다. 이전 Compose가
`${이름:?}`로 요구하는 이름까지 한 번에 지우면, 이전 설정을 읽을 수 없어 롤백에 실패한다.

그래서 이름을 바꾸거나 지울 때는 다음 순서를 따른다. 예를 들어 `OLD`를 `NEW`로 바꾸는 경우다.

| 배포 | Compose | job `env`와 GitHub Environment | 이유 |
| --- | --- | --- | --- |
| 첫 번째 배포(이름을 바꾸는 PR) | `NEW`를 사용한다 | `OLD`와 `NEW`를 모두 유지한다 | 실패해 롤백해도 직전 성공 Compose가 읽는 `OLD`가 남아 있다 |
| 첫 번째 배포가 성공한 뒤의 다음 배포(이후 PR) | 계속 `NEW`를 사용한다 | `OLD`를 제거한다 | 롤백 대상인 직전 성공 Compose가 이제 `NEW`만 요구한다 |

두 번째 배포는 같은 릴리스를 다시 실행하는 것이 아니다. `NEW`를 쓰는 릴리스가 성공한 뒤에 이어지는 후속
배포이고, 따로 실행하지 않고 다음 PR에 `OLD` 제거를 넣으면 된다. 첫 번째 배포가 실패해 롤백됐다면 `OLD`를
지우지 않고, `NEW`를 쓰는 배포가 성공할 때까지 남겨 둔다. 이 규칙은
백엔드 팀 컨벤션인 [프로젝트 운영 컨벤션](../conventions/project-operations.md)의 실행 환경 절에 넣는다
(2026-10-16 합의).

Environment 값은 다음처럼 관리한다(2026-10-16 합의).

- 저장소에는 `infra/docs/environment-changes.md`에 키의 추가, 변경, 삭제 이력만 남긴다. 날짜, 환경, 키와
  변경 종류를 적고 값은 적지 않는다. 잘못된 값은 롤백으로 복원할 수 없으므로, 장애를 확인할 때 최근 변경을
  찾기 위한 기록이다.
- 노션에는 사용하는 도구와 비밀값의 보관 위치를 정리한다.
- 실제 값은 접근 권한이 제한된 별도 도구에서 관리한다. GitHub는 이전 값을 보관하지 않으므로, 잘못 바꾼
  값을 사람이 되돌릴 때는 이 도구의 값을 기준으로 삼는다.

### 5. dev 점검에 통과한 이미지에 별도 job이 검증 태그를 붙인다

dev 배포 job이 성공하면 GitHub 호스팅 runner에서 승격 job을 실행한다. 승격은 이미지를 다시 빌드하거나
배포하는 작업이 아니다. **점검한 이미지에 운영 배포가 찾을 표시를 붙이는 작업**이다.

1. dev 배포 job은 build job이 출력한 digest로 이미지를 받아 실행한다.
2. 점검에 통과하면 실제 실행한 digest를 job 출력으로 남긴다.
3. 승격 job은 그 digest가 build job이 GHCR에 올린 digest와 같은지 대조한다.
   빌드 없이 수동 재배포했다면 GHCR에서 조회한 `image_tag`의 digest와 비교한다.
4. 같을 때만 해당 digest에 `dev-verified-tree-<backend 트리 해시>` 태그를 붙인다.
   태그는 레지스트리에서 붙이고 이미지를 다시 push하지 않는다.

트리 해시는 build job 출력에서 받는다. 수동 재배포에서도 확인할 수 있도록 이미지에도 트리 해시 라벨을
남긴다. 그 라벨이 없는 옛 이미지는 승격하지 않는다.

권한은 다음처럼 나눈다.

| job | 실행 위치 | GHCR 권한 | Environment |
| --- | --- | --- | --- |
| dev 배포 | dev EC2 runner | `packages: read` 유지 | dev 실행 값 사용 |
| 승격 | GitHub 호스팅 runner | `packages: write`만 부여 | 연결하지 않음, 실행 값 시크릿 없음 |

검증 태그가 보장하는 범위는 dev에서 `verify-backend.sh`의 준비 상태 확인과 스모크 테스트를 통과했다는
것까지다. 기능 검증이나 QA 통과를 뜻하지 않는다.

### 6. prod 자동 배포는 검증 태그로 이미지를 고른다

push로 실행된 prod 배포는 `dev-verified-tree-<main의 backend 트리 해시>`를 조회한다. 해당 태그가 가리키는
digest를 한 번 확정한 뒤, 이미지 받기와 성공 기록에는 그 digest만 사용한다.

검증 태그가 없으면 기존 컨테이너를 교체하기 전에 실패로 끝낸다. 원인을 구분하기 위해 일반 `tree-` 태그도
함께 확인한다.

| GHCR의 태그 상태 | 의미와 후속 조치 |
| --- | --- |
| `tree-` 태그도 없음 | develop을 거치지 않은 backend 코드이므로 배포하지 않는다 |
| `tree-` 태그만 있음 | dev 점검 실패, 배포 진행 중 또는 승격 미완료 상태다. dev 배포와 승격이 성공한 뒤 prod를 다시 실행한다 |

`BACKEND_TAG`(`APP_VERSION`)는 지금처럼 이미지의 revision 라벨에서 정한다. prod 배포 job의 권한도
`contents: read`, `packages: read`를 유지한다.

`image_tag`를 지정한 수동 실행은 긴급 복구 경로다. **검증 태그가 없어도 허용한다**(2026-10-16 합의).
대신 선택한 digest에 검증 태그가 없거나 검증 태그의 digest와 다르면 실행 요약에 경고를 남기고, 성공
기록에 `verified=false`를 남긴다(결정 1).

발견한 오류는 이전 사본으로 복구한다.

## 문제 2의 선택지

**제안은 2C(호스팅 runner의 별도 승격 job)**다. 서버의 GHCR 권한은 읽기로 유지하면서,
실제로 점검한 이미지의 digest를 대조한다.

<details>
<summary>검토한 방법 6개 비교</summary>

| 선택지 | 방법과 이점 | 필요한 권한과 한계 |
| --- | --- | --- |
| 2A. 현행 유지 | prod가 `tree-` 태그의 존재만 확인한다. 구현 변경이 없다 | 권한 변경 없음. dev에서 실패한 이미지도 배포할 수 있고, 확인을 사람의 릴리스 병합에 맡긴다 |
| 2B. dev 서버에서 태그 부여 | 점검을 통과한 dev 배포 job이 직접 검증 태그를 붙인다. job 하나로 끝난다 | dev EC2에 `packages: write` 필요. 서버가 침해되면 임의 이미지를 prod용으로 표시할 수 있다. 태그 부여 실패도 배포 실패로 표시된다 |
| 2C. 호스팅 runner의 승격 job(제안) | dev 배포 성공 뒤 별도 job이 digest를 대조하고 태그를 붙인다. 승격 실패만 다시 실행할 수 있다 | 새 job에 `packages: write` 부여. dev와 prod 배포 job은 읽기 권한 유지. job 하나와 호스팅 runner 대기 시간(수십 초)이 추가된다 |
| 2D. GitHub API로 점검 결과 조회 | prod가 이미지 revision 라벨의 커밋 SHA로 dev 배포 기록이나 워크플로 결과를 조회한다. GHCR 쓰기 권한을 추가하지 않는다 | prod에 `deployments: read` 또는 `actions: read` 필요. 기록 기준이 digest가 아닌 커밋 SHA라 재빌드나 수동 배포에서 이미지와 어긋날 수 있다. API 페이지 처리와 진행 중 상태 해석도 필요하다 |
| 2E. 서명된 증명(attestation) | dev 점검 통과를 서명으로 남기고 prod가 확인한다. 위조 방지에 가장 강한 선택지다 | dev에 `id-token: write`, `attestations: write`와 prod 검증 도구 필요. 공개 저장소의 서명은 공개 투명성 로그에 남고, 팀 규모에 비해 도구와 개념이 복잡하다 |
| 2F. 사람의 운영 배포 승인 | prod Environment 승인 규칙으로 사람이 dev 결과를 확인한다. 워크플로 변경이 작다 | 관리자의 Environment 설정 변경 필요. digest 대조 없이 사람의 확인에 의존하고, 배포마다 승인을 기다린다 |

</details>

## 문제 2의 실패 시나리오

## 선택 이유

문제 1에는 1C와 1E를 제안한다.

- **점검을 통과한 조합을 그대로 되살린다:** 롤백이 직전에 점검을 통과한 이미지 digest와 설정 파일을
  함께 다시 실행한다. 이미지만 맞추고 설정은 새것을 쓰는 지금의 어긋남이 사라진다.
- **장애 중에 설정을 다시 받지 않는다:** 1B는 GitHub에서 설정 커밋을 받아야 한다. 1C는 서버에 있는
  사본을 사용한다. 이전 이미지가 서버에 없으면 이미지를 받는 과정은 여전히 필요하다.
- **실행 중인 설정이 고정된다:** 컨테이너의 bind mount가 다음 체크아웃에 덮어쓰이는 작업 디렉터리 대신
  바뀌지 않는 릴리스 디렉터리를 가리킨다. 1B로는 이 문제가 남는다.
- **새 권한과 설정이 필요 없다:** runner 홈의 기존 기록 위치를 그대로 쓰고, GitHub 권한이나 Environment
  설정을 바꾸지 않는다.

문제 2에는 2C를 제안한다.

- **쓰기 권한의 위치가 바뀌지 않는다:** [백엔드 ADR 0016](0016-github-hosted-build-and-ghcr.md)처럼
  GHCR에 쓰는 것은 GitHub 호스팅 runner뿐이고 서버의 runner는 읽기만 한다.
  dev 서버가 침해되더라도 임의 이미지를 GHCR에 올려 prod에 배포하는 권한은 주지 않는다.
  다만 [백엔드 ADR 0009](0009-aws-deployment-topology.md)의 runner 침해 위험 자체는 남는다.
  dev 서버가 점검 결과를 속여 build job이 만든 미검증 이미지를 승격시키는 위험도 있다(문제 2의 실패 시나리오).
- **prod가 받는 것이 dev가 실행한 digest 그 자체다:** 태그의 존재나 커밋 SHA가 아니라 digest로 dev와
  prod가 이어진다. 재빌드로 `tree-` 태그가 옮겨져도 영향이 없다.
- **승격 실패가 배포 실패와 분리된다:** 레지스트리 장애로 태그를 못 붙여도 dev 배포 결과는 그대로이고,
  승격 job만 다시 실행하면 된다.
- **이미지 선택에 필요한 권한이 늘지 않는다:** prod 배포 job의 권한과 Environment 설정을 유지하면서
  검증 태그로 이미지를 선택한다. 설정 롤백에 필요한 변경은 결정 1~4에서 별도로 다룬다.

## 제약과 전제

- **실제 배포 검증:** 워크플로는 develop과 main에서만 실행되므로 병합 전에는 실제 배포로 확인할 수 없다
  (백엔드 ADR 0016과 같다). 설정 장애 롤백은 dev에서 시연하지 않는다. 결정 2의 스크립트로 로컬 Docker나
  별도 테스트 환경에서 확인하고, 로컬에서 확인할 수 없는 runner 홈 경로, GHCR digest 조회와 승격 job은
  병합 뒤 실제 배포 로그로 확인한다.
- 레지스트리에서 태그만 붙이는 명령(예: `docker buildx imagetools create`, `crane tag`)이 digest를 그대로
  유지하는지 구현할 때 확인한다. 유지되지 않는 명령은 쓰지 않는다.
- **설정 검증 범위:** dev와 prod의 Compose 파일은 별개다. `config.alloy`는 두 환경이 같은 파일을 쓰므로 dev에서 먼저
  실행되지만, `infra/docker-compose.yml`의 변경은 dev에서 실행되지 않는다. 검증 태그는 이미지를
  보증할 뿐 prod 설정을 보증하지 않는다.
- **데이터베이스:** 롤백은 이미 적용한 Flyway 마이그레이션을 되돌리지 않는다. 스키마 호환은
  [Flyway baseline 운영 문서](../operations/flyway-baseline.md)의 규칙을 따른다.
- **서버 재생성:** 기록과 릴리스 디렉터리는 서버에만 있어, 서버를 새로 만들면 첫 배포는 되돌릴 곳이 없다(백엔드 ADR
  0016과 같다).
- 새 GitHub Variables, Secrets, Environment 설정은 필요 없다.

## 결과

### 채택하고 구현하면 달라지는 점

- 설정 변경 때문에 실패한 배포도 직전 성공 릴리스로 자동 복구된다.
- prod에서 Compose 파일만 바뀐 릴리스도 롤백 대상이 된다.
- prod에는 dev 점검을 통과한 digest만 자동 배포된다. 백엔드 ADR 0016 결정 5가 감수한 비용이 사라진다.
- 성공 기록과 롤백이 digest 기준이라, 태그가 옮겨져도 점검한 이미지로 되돌아간다.
- 실행 중인 Alloy가 읽는 설정 파일이 성공한 릴리스에 고정된다.

### 감수하는 비용

- 워크플로 단계가 늘고 dev 워크플로에 job이 하나 늘어난다. prod 릴리스는 dev 배포와 승격이 끝나야
  진행된다.
- runner 홈에 릴리스 디렉터리가 쌓여 정리 규칙이 필요하다.
- 실행 값(Variables, Secrets)의 결함은 여전히 자동 복구되지 않는다. Compose가 요구하는 값의 이름을
  바꾸면 옛 이름은 다음 배포에서 지워야 하고, 키를 바꿀 때마다 변경 기록 파일을 고쳐야 한다.
- 배포와 롤백 절차를 워크플로에서 스크립트로 옮기는 작업이 늘어난다.
- 검증 태그는 스모크 테스트 통과만 뜻하고, 한 번 붙인 태그를 취소할 마땅한 수단이 없다.
- 이 변경 전에 만든 이미지에는 검증 태그와 트리 해시 라벨이 없다. 바뀐 prod 워크플로가 처음 실행되기
  전에 같은 backend 트리로 dev 배포와 승격이 한 번 성공해야 한다.

## 후속 작업

### 채택 후 구현할 것

이 ADR이 채택되면 같은 작업 브랜치에서 다음을 구현한다.

| 대상 | 작업 |
| --- | --- |
| dev 워크플로 | build job의 digest와 트리 해시 출력, 트리 해시 라벨, digest로 배포, 릴리스 디렉터리, `compose config` 검증, 성공 기록과 롤백 조건 변경, 승격 job 추가 |
| prod 워크플로 | 검증 태그로 이미지 선택, 릴리스 디렉터리, `compose config` 검증, 성공 기록과 롤백 조건 변경 |
| ADR | [백엔드 ADR 0016](0016-github-hosted-build-and-ghcr.md)의 결정 4, 결정 5와 적용 범위에 이 문서를 연결하고, 백엔드 ADR 목록의 대체 관계 수정 |
| 운영 문서 | runner 안내, 성공 기록 형식, 릴리스 디렉터리 위치와 수동 복구 절차 기록 |
| 배포 스크립트 | 배포와 롤백 절차를 `infra/scripts`로 옮기고 워크플로가 호출하게 한다. 로컬 Docker에서 설정 오류를 내고 복구를 확인하는 방법을 남긴다 |
| 백엔드 컨벤션 | [프로젝트 운영 컨벤션](../conventions/project-operations.md)의 실행 환경 절에 실행 값 이름 변경 규칙을 넣는다 |
| 변경 기록 | `infra/docs/environment-changes.md`를 만들고 키 변경 이력의 형식을 정한다 |

### 구현 후 확인할 것

- develop 병합 뒤 dev 배포와 승격 job이 성공하는지 확인한다.
- GHCR 검증 태그의 digest와 dev에서 실제 실행한 digest가 같은지 확인한다.
- 첫 prod 릴리스의 이미지 선택 로그를 확인한다.
- 병합 전에 결정 2의 스크립트로 로컬에서 설정 오류를 내고 이전 상태로 복구되는지 확인한다.

### 관련 운영 작업

- GHCR 정리 시 검증 태그와 각 서버의 직전 성공 digest를 보존한다(백엔드 ADR 0016 후속 작업).
- 배포 결과 알림에 롤백 여부와 복구한 릴리스의 digest, 설정 커밋을 포함한다(백엔드 ADR 0016 후속 작업).
- 사용하는 도구와 비밀값 보관 위치를 노션에 정리하고, 실제 값을 접근 권한이 제한된 별도 도구로 옮긴다(결정 4).
- dev에서 실행하지 않는 `infra/docker-compose.yml`의 검증 공백은 별도로 다룬다.
  두 환경의 Compose 파일 차이를 CI에서 비교하는 방안을 검토한다.

## 적용하지 않는 범위

이 제안으로도 아래 항목은 해결되지 않는다.

- GitHub Environment의 Variables와 Secrets를 이전 값으로 복원하는 것
- 이미 적용한 데이터베이스 스키마 변경을 되돌리는 것
- 워크플로 파일과 배포 스크립트 자체의 결함을 롤백으로 복구하는 것
- 이미지의 기능 검증이나 QA 통과를 보장하는 것
- 컨테이너 교체와 롤백 동안의 짧은 중단을 없애는 것
