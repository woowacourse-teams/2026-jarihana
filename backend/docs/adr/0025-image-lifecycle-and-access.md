# ADR 0025: 이미지의 참조 수명주기와 조회 접근을 함께 관리한다

- 상태: 채택 · Flyway V4 구현, 최신 `develop` 반영
- 날짜: 2026-10-14
- 관련 영역: 이미지 업로드, 그룹, 활동기록, S3, CloudFront, 데이터베이스

## 배경

이미지는 먼저 임시 경로에 업로드되고 그룹 대표 이미지, 그룹 소개 Markdown, 활동기록 사진에서 사용된다.
기존 구현은 업로드 성공 여부만 기록했기 때문에 이미지가 현재 어디에서 사용되는지, 숨김 또는 연결 해제 후
언제 삭제해야 하는지 판단할 수 없었다. CloudFront 원본 주소가 응답에 그대로 노출되고 주소를 아는 사용자가
계속 접근할 수 있는 문제도 있었다.

한편 그룹의 `ENDED` 상태는 삭제가 아니다. 사용자가 종료된 그룹을 계속 조회하므로 대표·소개·활동기록
이미지도 보존해야 한다. 반대로 삭제된 그룹과 숨김 처리된 활동기록의 이미지는 더 이상 조회할 수 없어야 하며,
실수나 일시적인 장애를 복구할 시간을 둔 뒤 물리적으로 삭제해야 한다.

저장소는 Flyway V1 baseline으로 스키마를 초기화하며, 새 변경은 버전 migration으로 적용한다.
활동기록 댓글·반응 PR #369가 V2와 V3를 추가했다. 따라서 이미지 수명주기 변경은 V4를 사용하고,
V3의 하트 반응 제약 migration 뒤에 적용한다.

## 결정

1. 새 업로드는 `groups/tmp/{uuid}`에서 시작한다. 그룹에 처음 연결할 때
   `groups/{groupId}/{uuid}` 경로로 복사하고 연결이 확정되면 임시 객체를 정리한다.
2. 새 업로드 하나는 한 그룹에만 연결한다. 다른 그룹에서 재사용하려면 다시 업로드한다. 이미 여러 곳에서
   참조 중인 레거시 이미지는 마지막 참조가 사라질 때까지 보호한다.
3. 기존 이미지는 일괄 이동하지 않는다. 기존 경로를 유지하고 참조만 백필한다.
4. `image_reference`가 그룹 대표, 그룹 소개, 활동기록의 논리적 참조를 기록한다. 종료된 그룹의 참조는
   유지한다. 삭제된 그룹과 숨김 처리된 활동기록의 참조는 제거한다.
5. 참조가 없는 이미지와 만료된 임시 이미지는 즉시 지우지 않고 7일 뒤 삭제 대상으로 만든다.
   S3 작업 실패는 재시도하며, 삭제 작업은 별도 레코드로 보존한다.
6. DB 트랜잭션과 S3 복사를 원자적으로 묶을 수 없으므로, 복사 전에 `image_promotion_task`를 별도
   트랜잭션으로 기록한다. 중단된 작업은 정리 작업이 원본과 대상의 상태를 확인해 수습한다.
7. 업로드 직후 프리뷰는 업로더에게만 30분 동안 허용한다. 연결된 이미지는 서비스 도메인의 안정적인
   `/api/images/...` 주소를 사용하고, 백엔드는 접근 가능 여부를 확인한 뒤 같은 도메인의
   `/images/groups/...`에 대한 최대 5분짜리 CloudFront 서명 URL로 리다이렉트한다. 숨김·미연결 이미지는
   새 조회 URL을 발급하지 않는다.
8. 정리 작업은 인프라 권한과 백필 결과를 확인하기 전까지 기본 비활성화한다. S3 접근은 EC2 IAM Role을
   사용하고 장기 Access Key를 새로 추가하지 않는다.
9. 이미지 스키마와 백필은 `src/main/resources/db/migration/V4__image_lifecycle.sql`에서 관리한다.
   현재 `develop`의 V2 댓글·반응 스키마와 V3 하트 반응 제약을 먼저 적용한 뒤 V4를 적용한다.

## 백필 정책

- 남아 있는 모든 그룹의 대표·소개 이미지 참조를 복원한다. `ENDED` 그룹도 포함한다.
- 삭제되지 않은 활동기록의 사진 참조만 복원한다.
- 이미 숨김 처리된 활동기록은 참조를 만들지 않는다. 정리 작업을 켠 시점부터 7일 유예 후 삭제된다.
- 백필은 이미지 키가 `image_upload`에 존재할 때만 참조를 만든다. 누락된 레거시 객체는 별도 점검 대상으로
  보고 자동으로 추정하거나 이동하지 않는다.
- 여러 그룹에서 이미 사용 중인 레거시 업로드는 특정 그룹 소유로 단정하지 않는다.

## 결과

- 연결된 이미지를 실수로 삭제하지 않고, 숨김·미연결 이미지를 예측 가능한 시점에 정리할 수 있다.
- 종료된 그룹 이미지가 보존되고 숨김 처리된 콘텐츠는 새 서명 URL을 얻을 수 없다.
- 사용자에게 CloudFront 배포 도메인 대신 서비스 도메인을 노출할 수 있다.
- S3와 DB 사이의 작업 상태 및 실패를 추적할 수 있지만, 정리 작업과 CloudFront 서명 키 운영에 대한
  모니터링이 추가로 필요하다.
- 이미지 수명주기 변경은 Flyway V4로 추적하며 `develop`의 V2와 V3가 선행 적용되어야 한다.

## 배포와 롤백

1. 활동기록 댓글·반응 PR #369의 Flyway V2와 V3가 `develop`에 병합되었는지 확인한다.
2. 이 브랜치를 최신 `develop`에 리베이스하고 V2, V3 다음에 V4가 실행되는지 검증한다.
3. 마이그레이션과 백필 결과를 검증한 뒤 애플리케이션을 배포한다.
4. CloudFront 별칭·인증서·서명 키와 IAM 권한을 확인한 뒤 정리 작업을 활성화한다.

애플리케이션을 롤백할 때는 정리 작업부터 비활성화하고 이전 버전을 배포한다. 추가된 테이블과 컬럼은
데이터 보존을 위해 즉시 제거하지 않는다. 물리 삭제가 이미 수행된 S3 객체는 DB 롤백만으로 복구할 수
없으므로, 정리 작업 활성화 전 점검과 7일 유예를 롤백 안전장치로 사용한다.

## 검토한 대안

- **기존 이미지를 모두 그룹 경로로 이동**: 배포 범위와 장애 위험이 커서 선택하지 않았다.
- **연결 해제 즉시 삭제**: 오조작과 트랜잭션 불일치를 복구하기 어려워 선택하지 않았다.
- **S3 객체 존재 여부만으로 정리**: Markdown과 활동기록 등 참조 위치를 안전하게 판단할 수 없어 선택하지
  않았다.
- **CloudFront URL을 그대로 저장·노출**: 도메인 변경과 접근 제어가 어려워 선택하지 않았다.
