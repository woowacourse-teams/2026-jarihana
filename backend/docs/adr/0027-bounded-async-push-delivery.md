# ADR 0027. 푸시 전송을 제한된 동시성으로 비동기 처리한다

- 상태: 제안 · 구현·로컬 검증 완료, PR 검토 및 배포 후 성능 측정 예정
- 날짜: 2026-10-21
- 관련 이슈: [#441](https://github.com/woowacourse-teams/2026-jarihana/issues/441)
- 관련 결정: [백엔드 ADR 0015 · 알림함과 Web Push 분리](0015-web-push-and-notification-inbox.md), [백엔드 ADR 0025 · 인덱스 기반 선점](0025-push-claim-indexed-candidates.md)

## 배경

기존 워커는 한 건을 선점하고 전송을 준비한 뒤 HTTP 응답과 결과 저장을 기다려 다음 건으로 넘어간다.
HTTP 클라이언트와 연결 관리자도 요청마다 생성·종료해 연결을 재사용하지 않는다.
외부 응답을 기다리는 시간이 겹치지 않으며 선점·준비·시도 횟수 조회의 DB 왕복도 건별로 발생한다.
이는 코드와 로컬 서버에서 확인한 구조다. 실제 제공자의 응답시간이나 운영 처리량 저하를 측정한 결과는 아니다.

## 결정

기존 Apache HttpClient 5 의존성의 비동기 클라이언트와 연결 풀을 애플리케이션 수명 동안 재사용한다.
요청 수만큼 대기 스레드를 만들지 않고 기본 I/O 스레드 1개로 전송 대기를 겹친다.
DNS 조회와 암호화 준비는 별도 스레드 2개, 최대 대기열 4개로 제한한다.
HTTP 완료 콜백은 결과 저장을 최대 2개의 별도 스레드에 넘겨 I/O 스레드에서 JDBC를 실행하지 않는다.
타이머·클라이언트 관리 스레드도 있으므로 이를 전체 스레드가 3개라는 뜻으로 해석하지 않는다.

1. 동시 처리 슬롯을 먼저 확보한다. 기본 최대 4건이며 선점부터 결과 저장까지 슬롯을 유지한다.
2. 빈 슬롯 수와 기존 `batch-size` 실행 예산 중 작은 수만큼 한 SQL에서 선점한다.
3. 선점한 `(id, leaseToken)` 쌍으로 한 번에 전송 준비를 검증한다. 유효한 4건의 선점·준비는 SQL 2회다.
4. 준비된 요청을 비동기로 전송하고 호출자는 HTTP 응답을 기다리지 않는다.
5. 먼저 끝난 요청부터 개별 결과를 저장하고 슬롯을 반환한 뒤 다음 작업을 채운다. 느린 한 건 때문에 나머지 결과 저장과 재충전을 기다리지 않는다.

선점 SQL은 백엔드 ADR 0025의 분기별 `SKIP LOCKED` 후 `LIMIT`을 유지한다.
due·만료 lease 분기에서 각각 최대 N개, 최종 N개를 갱신하므로 짧은 선점 TX에서 최대 2N개 행을 잠글 수 있다.
선택한 후보에만 JOIN하며, 두 분기의 선행 행이 잠겨 있어도 뒤의 작업을 찾는 계약을 우선한다.
공통 배치 토큰을 사용하더라도 id와 토큰을 한 쌍으로 검증한다. 결과 저장에는 반환된 시도 횟수를 사용해 재조회를 없앤다.
결과 저장의 구독 잠금과 조건부 UPDATE는 개별 작업별로 유지한다.

## 연결과 보안

route별 연결 상한은 4개, 전체 상한은 12개다. route는 프로토콜·호스트·포트·검증한 IP를 포함한다.
같은 호스트의 다른 IP는 다른 route이며 전체 요청은 동시 처리 슬롯 4개로 제한한다.
필요한 연결만 만들며 12건 동시 전송을 뜻하지 않는다.
풀 대기는 1초, 유휴 연결 정리는 60초, 연결 수명은 5분으로 시작한다.
기존 연결 제한 5초와 요청 전체 제한 10초를 유지한다.

DNS의 모든 반환 주소가 공개 주소인지 검사하고 선택한 IP를 요청별 `HttpHost` 대상에 고정한다.
원래 호스트명은 Host·TLS 인증서 검증·SNI에 유지하며 다른 요청의 DNS 결과로 덮어쓰는 전역 상태를 두지 않는다.
고정 주소가 없는 DNS 재조회 경로는 거부한다. redirect와 HTTP 라이브러리 자체 재시도도 끈다.
응답 본문은 저장하지 않고 소비해 연결을 반환하며, 전체 제한시간은 응답이 조금씩 도착해도 연장하지 않는다.

## 실패와 종료

기존 최대 5회 시도, 유효기간, Retry-After 해석과 429·5xx·네트워크 재시도 정책을 유지한다.
새로운 제공자별 속도 제한이나 429 대응 정책은 이번 변경에 포함하지 않는다.

종료 시 새 선점을 멈추고 진행 중인 결과 저장을 기본 최대 15초 기다린다.
준비·결과 저장 실패나 강제 종료로 DB 반영을 끝내지 못하면 IN_FLIGHT lease가 만료된 뒤 재선점한다.
예전 콜백은 id·토큰·lease 유효기간·구독 generation 조건으로 새 상태를 덮어쓰지 못한다.
제공자 수락 직후 DB 반영 전에 죽으면 중복 전송될 수 있는 기존 at-least-once 경계는 유지한다.

Blue-Green 인계에서는 배치 선점 전부터 각 작업의 처리 허가를 확보하고, 비동기 응답과
결과 저장 트랜잭션의 커밋이 끝날 때까지 유지한다. 중단 후에는 이미 승인한 작업만 마치고
빈 슬롯을 다시 채우지 않는다. 선점·준비·결과 저장 실패로 처리 결과가 불명확하면
`BLOCKED` 상태로 신규 선점과 인계를 차단한다. lease 만료만으로 다른 서버에 권한을 넘기지 않는다.
외부 전송 실패를 기존 정책대로 `RETRY`·`FAILED`로 저장한 경우는 정상적으로 처리를 마친 것이다.
상세 상태와 복구 경계는 [worker 제어 API](../../../infra/blue-green-deploy/controller/architecture.md#worker-제어-api)와
[인프라 ADR 0005](../../../infra/docs/adr/0005-nginx-ec2-blue-green-deployment.md)를 따른다.

동시 요청은 같은 구독으로도 시작할 수 있다. 삭제·로그아웃·410 응답 이전에 이미 시작한 HTTP를 회수한다고 보장하지 않는다.
취소된 작업의 늦은 결과는 반영하지 않으며 아직 선점하지 않은 작업은 취소해 외부 요청을 막는다.
Service Worker의 연결 재확인과 내용 API의 소유권 검증도 그대로 적용한다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 동기 워커 스레드만 늘림 | I/O 대기마다 스레드를 점유하고 요청별 연결·건별 조회 비용이 남는다 |
| 제한 없는 비동기 전송 | 대기열·연결·DB 결과 저장을 제한할 수 없어 제외한다 |
| 배치 전체 완료 후 결과 저장 | 느린 요청 하나가 다른 결과 저장과 다음 전송을 지연시켜 제외한다 |
| WebFlux 또는 새 HTTP 의존성 추가 | 기존 HttpClient 5로 구현 가능해 추가하지 않는다 |
| 선점 후보를 먼저 LIMIT 후 잠금 | 잠긴 선행 행 때문에 처리할 뒤쪽 행을 놓칠 수 있어 제외한다 |

## 검증과 후속 작업

제어 가능한 future로 동시성 상한·빈 슬롯 재충전·개별 결과 저장·종료를 검증한다.
실제 PostgreSQL로 배치 SQL 수, 중복 선점 방지, 잠긴 행 건너뛰기, 만료 복구와 오래된 결과 무시를 검증한다.
로컬 HTTP 서버로 연결 재사용·요청별 IP 분리·redirect 차단·전체 제한시간을 확인한다.
이 테스트의 지연이나 처리 건수를 운영 성능 향상 수치로 사용하지 않는다.

2026-10-21 Java 21에서 `./gradlew build --no-daemon --console=plain`을 실행해 전체 890개 테스트가 통과했다.
이 중 푸시·구독·초대 알림 전송 관련 137개 테스트가 포함되며, 실제 스케줄러의 선점부터 비동기 응답 후 DB 반영까지 확인했다.
실제 제공자의 HTTPS 수락·기기 수신과 운영 성능은 아직 검증하지 않았다.

배포 후 같은 대상 수·제공자 분포에서 처리량, 생성부터 수락까지의 지연, 요청시간, 재시도율,
진행 중 작업 수와 DB 쿼리 수·시간을 비교한다. 기준 데이터와 실제 제공자 수신 결과는 별도로 기록한다.
동시성 4와 연결·스레드 설정은 이 관측을 바탕으로 조정한다.
