# 백엔드 ADR 0029. 오목 명령은 HTTP, 판 상태 알림은 SSE를 사용한다

- 상태: 채택
- 날짜: 2026-11-02
- 범위: 1:1 오목의 첫 버전

## 결정과 근거

오목은 한 수씩 진행해 메시지 빈도가 낮고, 사용자 행동은 기존 HTTP API로 처리할 수 있다.
착수의 인증, CSRF, 실패 응답과 재시도를 기존 경계에서 처리하고 서버에서 확정한 전체 판은
SSE로 전달한다. 기존 채팅용 WebSocket과 생명주기를 공유하지 않으며, 방에 있을 때만 게임
연결을 유지한다. 이 선택은 사용자가 대안 비교 후 명시적으로 선택했다.

## 대안

| 대안 | 장점 | 감수할 점 |
| --- | --- | --- |
| 채팅 WebSocket 공유 | 연결 재사용 | 채팅 전용 권한과 연결 관리 확장, 회귀 범위 증가 |
| 게임 WebSocket 분리 | 게임 연결 독립, 양방향 확장 | 별도 연결 관리와 메시지 계약 필요 |
| HTTP + SSE | 기존 명령 처리 활용, 게임 알림 독립 | 별도 수신 연결, 브라우저 발신은 API 필요 |
| 주기적 브라우저 조회 | 가장 단순 | 변경 없이도 요청하고 조회 간격만큼 지연 |

## 다중 서버와 비용

방과 판을 PostgreSQL에 저장하고 방 잠금으로 명령을 직렬화한다. 각 서버는 현재 구독 중인
방들의 id/revision을 500ms마다 한 번의 묶음 쿼리로 확인하고, 변경된 방만 전체 snapshot을
조회한다. 같은 방의 연결은 snapshot과 조회를 공유한다. 상세 조회는 서버당 최대 4개이며
같은 방의 중복 실행과 대기열 적재 없이 다음 tick에서 다시 확인한다. 변경 없는 방은 캐시한
snapshot으로 heartbeat와 토큰 만료를 확인한다. SSE 자체가 폴링인 것은 아니며 이 DB 확인은 서버 사이에서 변경을 발견하는 별도 전략이다.

별도 Redis, 브로커나 이벤트 버스를 추가하지 않는 대신 감지에 0~500ms와 조회/네트워크 시간이
더해지고, 조회량은 활성 방과 서버 수에 비례한다. SSE 연결은 서버당 500개로 제한한다.
낮은 지연, 많은 방 또는 빈번한 양방향 입력을 요구하게 되면 계측 결과를 기준으로
PostgreSQL 알림, 공통 메시징 또는 WebSocket을 재검토한다.

서버는 최초/재연결에 전체 snapshot을 보내며 클라이언트는 revision으로 역행을 차단한다.
정상 수신 후 첫 재연결은 즉시 시도하고 조작을 유지하되 복구 실패부터 잠근다. 실패 재시도에는
최대 30초의 지수 백오프와 지터를 적용한다. 명령 성공과 후속 조회 성공은 분리한다.
실시간 연결이 끊겨도 서버 기한은 유지한다. 저장 모델과 판정은 전송 방식에 의존하지 않는다.

## 배포와 복구

V17은 신규 테이블만 추가한다. 기존 앱의 테이블과 컬럼은 변경하지 않으며 앱 롤백 때도
신규 테이블과 이력을 유지한다. 백엔드 배포 후 프론트를 배포한다. 이전 앱으로 롤백하면
게임 API가 없어 진행 중인 방을 이용할 수 없다는 기능적 공백은 감수한다. DB 다운 마이그레이션은 하지 않는다.
