## 배경

모임 채팅에 푸시를 추가하면서, 서비스를 사용하고 있는 사람의 다른 기기까지 알림이 울리는
상황을 줄이기로 했다. 처음에는 같은 채팅방을 보고 있을 때만 푸시를 막는 방식과 기기별 보기
상태를 검토했다. 이후 결정자는 홈이나 모임 상세를 사용 중인 경우까지 포함해, 어느 기기에서든
서비스를 활성 상태로 사용하면 모든 방의 채팅 푸시를 보류하는 정책을 선택했다.

보기 상태를 10초마다 DB에 기록하는 비용, 메모리·TTL 저장소와 PostgreSQL 임시 테이블의
차이, 소켓 연결과 실제 사용자 활동의 차이, 브라우저 강제 종료 시 상태 만료를 함께 검토했다.
다른 메신저의 활성·유휴 상태 처리 논의는 비교의 계기였으며, 특정 서비스와 동일한 내부
저장소나 구현을 사용한다는 근거로 삼지는 않는다.

활성 상태는 짧은 시간 뒤 다시 보고되는 푸시 보류 판단용 정보다. 메시지·읽음 위치·알림함·전송
대기처럼 장애 뒤에도 보존해야 하는 데이터와 같은 내구성이 필요한지 검토하고, LOGGED와
UNLOGGED의 부하 및 강제 종료 후 복구를 비교했다.

## 활성 상태와 보고

활성 조건은 다음과 같다. 특정 방을 보고 있는지는 검사하지 않는다.

```text
로그인
AND document.visibilityState === "visible"
AND document.hasFocus()
AND 마지막 사용자 활동 이후 5분 미만
```

마우스 이동·클릭·키보드·휠·터치를 로컬 활동으로 기록한다. 사용자 스크롤은 휠·터치·키보드·
마우스 입력으로 감지하며 새 메시지나 레이아웃 변경에 의한 자동 스크롤은 활동이 아니다.
마우스 이동의 로컬 시각 갱신은 1초에 한 번으로 제한한다. 활동 이벤트마다 서버에 요청하지 않는다.

최초 진입과 활성 화면 복귀는 활동으로 처리한다. 다른 탭·앱의 활동과 소켓 재연결 자체는
활동 시각을 갱신하지 않는다. 활동 재개·복귀·재연결 때 현재 활성 조건을 확인해 즉시 보고하고,
이후 활성일 때만 10초마다 보고한다. 매 전송 직전에 조건을 다시 검사하며, 끊긴 동안의 보고를
쌓아 재전송하지 않는다. 로그아웃·계정 전환 때 이전 계정의 타이머와 연결을 정리한다.

기존 `ChatSessionProvider`·`useChat` 연결을 재사용하고, 별도 소켓이나 활성 보고용 HTTP
폴링은 만들지 않는다. 인증된 소켓의 `SEND /app/presence/active`만 제한적으로 허용한다.
회원은 인증된 소켓에서 식별하고 시각은 서버가 정한다. 클라이언트의 회원 ID·시각을 신뢰하지
않으며 기존 인증·Origin·CSRF 검증을 유지한다. 백그라운드에서는 활성 보고만 멈추고 배지
수신 연결을 의도적으로 끊지 않는다.

## 계정당 한 행과 15초 유효기간

상태는 `member_activity(member_id PK/FK, last_active_at)`에 저장한다. 방 ID나 `view_id`는
두지 않는다. 여러 기기·탭·서버가 같은 계정의 행을 갱신하고 푸시 워커도 같은 DB를 조회한다.
새 시각이 기존 시각보다 클 때만 UPSERT해 동시 요청이나 처리 순서 때문에 과거로 돌아가지
않게 한다. 이는 같은 시각·과거 보고의 중복 갱신을 피하는 것이며 정상적인 새 보고의 쓰기까지
없애는 것은 아니다. 계정당 한 행이므로 새로고침마다 행이 늘지는 않는다.

한 화면이 이탈·종료해도 계정 행을 삭제하거나 비활성으로 덮어쓰지 않는다. 해당 화면의 보고만
멈추며 다른 화면이 계속 보고하면 활성 상태가 유지된다. 모든 보고가 멈추면 마지막 보고에서
15초가 지난 시점부터 비활성으로 판단한다. 종료 이벤트가 전달되지 않는 강제 종료도 같은
만료 규칙으로 처리한다. 이 TTL은 행 자동 삭제가 아니라 조회 시각에 따른 유효성 판단이다.

**15초는 결정자가 기존 30초 대신 선택한 값이다.** 10초 보고와의 여유가 5초이므로 지연·유실에
의한 일시적인 비활성 오판을 수용했다. 소켓이 연결돼 있다는 이유로 만료를 연장하지 않는다.
화면 이탈 순간이나 만료 순간에 푸시가 즉시 도착하는 것은 아니며, 실제 재판정은 다음 워커
처리에서 일어난다.

## 푸시 보류·읽음·묶음

계정이 활성 상태면 채팅 전송을 보류하고 다음 판단 시각을 예약한다. 보류 자체는 외부 전송
실패가 아니므로 재시도 횟수를 소진하지 않는다. 원본 메시지는 사건 키로 연결하고 기존 채팅
읽음 순번과 비교한다. 보류 중 읽었다면 취소하고, 비활성이 된 뒤에도 미읽음이면 발송을 다시
판단한다. 활성 보고나 배지 수신은 메시지를 읽었다는 뜻이 아니다.

같은 계정·구독·구독 generation·방에 쌓인 전송은 최신 메시지를 대표로 묶는다. 메시지별
알림함 기록은 유지하고, 기존 발송 유효기간을 늘리지 않는다. 여러 워커의 동시 선점은 구독
잠금과 lease로 조정한다. 준비 이후 시작된 외부 전송의 회수나 제공자 수락 직후 장애 경계의
정확히 한 번 전달까지 보장하는 결정은 아니다.

**활성 중 받은 미읽음 메시지도 비활성 전환 후 푸시가 올 수 있다.** 이 정책은 채팅 푸시에만
적용한다. 서비스 안의 배지·미읽음 갱신과 다른 종류의 알림은 기존 동작을 유지한다.

## UNLOGGED와 작성자가 수용한 장애 영향

`member_activity`에는 오래 보존할 원본 데이터가 아니라 최근 활성 보고만 있다. 이를
UNLOGGED로 저장해 해당 테이블의 WAL 기록 비용을 줄이기로 한다. UNLOGGED는 메모리
전용 테이블이나 세션 전용 임시 테이블이 아니며, 같은 DB의 여러 연결에서 공유한다.
DB 쓰기·행 잠금·vacuum 비용은 남는다.

PostgreSQL 비정상 종료 후에는 테이블이 비워질 수 있다. 다음 유효한 활성 보고가 기록되기
전까지 서비스를 사용 중인 계정도 비활성으로 판단돼 푸시를 받을 수 있다. **결정자는 이
일시적인 추가 푸시 가능성을 인지했으며, 치명적인 문제로 보지 않고 수용했다.** 이는 미결
위험이나 재승인 대기 항목이 아니라 이번 선택에서 받아들인 동작이다.

브라우저나 백엔드 프로세스의 종료가 곧 UNLOGGED 테이블을 비운다는 뜻은 아니다. 브라우저
이탈에는 위의 15초 만료가 적용되고, 테이블 유실은 PostgreSQL의 비정상 종료·복구와 관련된다.
정상 DB 재시작에서는 행이 유지되는 것을 확인했다. standby로 내용이 복제되지 않으므로
복제본에서 활성 상태를 읽는 구조는 사용하지 않고, 장애 전환 뒤에도 재보고로 복구하는 전제를
유지한다. 복제·failover 환경 자체를 이번 실험에서 검증한 것은 아니다.

메시지·읽음·알림함·전송 대기는 기존 LOGGED 테이블에 유지한다. 이번 수용은 활성 상태 유실에
따른 추가 푸시에 한정하며, 이 영구 기록의 유실을 허용하는 결정으로 확대하지 않는다.
UNLOGGED의 복구·복제 특성은 [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/sql-createtable.html#SQL-CREATETABLE-UNLOGGED)를 따른다.

## 검토한 대안

| 대안 | 검토 결과 |
| --- | --- |
| 방별 보기 상태 | 같은 방을 보는지에 따라 구분하는 기존 방향. 서비스 어디서든 활성인 계정의 모든 방을 보류한다는 최종 정책에 맞춰 교체한다. |
| 기기별 상태 행·종료 시 삭제 | 한 기기 종료가 다른 기기의 활성 판단을 덮어쓰지 않도록 집계·정리가 필요하다. 계정 단위 마지막 보고로 충분해 채택하지 않는다. |
| 서버 프로세스의 메모리 Map | 로컬 조회·갱신은 가볍지만 다른 백엔드와 워커에 공유되지 않는다. 별도 공유·동기화 없이 사용하지 않는다. |
| Redis 등 TTL 저장소 | 공유 상태·만료에 적합한 대안이다. 현재는 기존 PostgreSQL을 재사용하고 추가 저장소 운영을 피한다. |
| PostgreSQL TEMP 테이블 | DB 세션별 상태이므로 여러 서버·연결 풀·워커가 공유할 계정 상태 저장소로 사용하지 않는다. |
| PostgreSQL LOGGED 테이블 | 내구성이 필요하면 적합하며 V30에서 이 방식으로 테이블을 만든다. 짧게 유효한 상태의 내구성보다 WAL 절감을 선택한다. |
| 연결 heartbeat만으로 활성 판단 | 포커스·화면 표시·최근 사용자 활동을 구분하지 못한다. 연결 유지와 활성 보고를 분리한다. |
| 활성 중 푸시 영구 취소 | 마지막 보고 직후 종료한 사용자의 미읽음 푸시가 영구 누락될 수 있어 보류 후 재판정한다. |
| 유효기간 30초 | 지연 여유가 늘지만 이탈 뒤 보류도 길어진다. 결정자가 지연·유실 가능성을 알고 15초를 선택했다. |

## 검증 근거와 한계

2026-11-06에 PostgreSQL 17.11, 2 CPU·1 GiB의 격리된 컨테이너에서 실제 UPSERT 조건을
사용해 총 36회 비교했다. 조건별 3회 중앙값과 한계를 [측정 기록](evidence/0030-member-activity-benchmark.md)에 남긴다.

| 비교 항목 | LOGGED | UNLOGGED |
| --- | ---: | ---: |
| 초당 1,000건의 WAL / 20초 | 5.43 MiB | 0.76 MiB |
| 제한 없는 부하의 처리량 | 16,847건/초 | 31,357건/초 |
| 초당 10,000건의 p99 지연 | 803ms | 874ms |
| 초당 20,000건의 p99 지연 | 4,798ms | 21ms |

WAL 감소와 고부하 처리량 개선은 확인했지만 모든 부하에서 지연이 개선된 것은 아니다.
20~30초씩의 DB 단독 비교이며 CPU에는 부하 생성기도 포함된다. WebSocket·연결 풀·채팅
저장·푸시 워커를 함께 실행한 서비스 전체 성능, 장시간 부하, 운영 수용량은 검증하지 않았다.
측정한 지연을 실제 15초 활성 만료 오판율로 바꾸어 해석하지 않는다.

정상 재시작에서는 LOGGED·UNLOGGED 모두 1행을 유지했고, 강제 종료 후 복구에서는
UNLOGGED만 0행이 됐다. 별도 영구 데이터 대조 테이블은 1행을 유지했다. 이는 저장소 실험이며
장애 중 실제 푸시 수신을 검증한 것은 아니다.

## 구현과 적용 경계

기준 커밋 `8712bcc0`에는 계정 활성 보고·보류·읽음 취소·묶음 처리와 관련 테스트가 있다.
V30은 LOGGED 테이블을 만들고, [V31 마이그레이션](../../src/main/resources/db/migration/V31__member_activity_unlogged.sql)이
`ALTER TABLE member_activity SET UNLOGGED`로 전환한다. 기존 V20과 develop의 V21~V28 SQL은 유지한다.
테이블과 PK 인덱스의 저장 방식만 바꾸며 회원 FK·활성 시각·계정당 한 행 계약은 유지한다.

전환은 테이블 재작성을 수반하고 `ACCESS EXCLUSIVE` 잠금을 요구하므로, 적용 중 활성 보고와
푸시 판단 조회가 잠시 대기할 수 있다. 운영 적용 전 행 수·장기 트랜잭션·잠금 대기와 여유 디스크를
확인하고, 다른 DDL과 겹치지 않는 배포 순서로 실행한다. 로컬 적용 시간은 운영 잠금 시간을
보장하지 않는다. [PostgreSQL 17 ALTER TABLE 문서](https://www.postgresql.org/docs/17/sql-altertable.html)를 따른다.

V31은 V30 스키마의 조회·쓰기 계약을 유지한다. 되돌릴 필요가 있다면 후속
마이그레이션에서 `SET LOGGED`를 사용하되 다시 잠금·재작성 비용이 들며 이미 유실된 상태는
복구되지 않는다. 새 알림 사건·계약 3과 V30의 `chat_views` 제거에 관한 구버전 호환 배포 문제는
기존 [배포 경계](../context/api/endpoints/notifications.md#채팅-알림-배포-경계)를 별도로 따른다.

2026-11-06 로컬 `jarihana_chat_push`에 애플리케이션 기동 시 Flyway로 당시 V23을 적용했다.
이후 develop의 V21~V28과 번호가 겹쳐 PR의 V21~V23을 V29~V31로 옮겼다. 아래 로컬 기록은 이전 번호를 따른다.
`member_activity`와 PK 인덱스의 `relpersistence=u`, 회원·메시지·읽음·알림·전송 테이블의
`p`, V20~V22 체크섬 유지와 `GET /api/groups?size=1` HTTP 200을 확인했다.
Flyway의 V23 실행 기록은 27ms였으며 로컬 상태 테이블은 비어 있었다. 데이터가 있는 전환은
별도 격리 스키마에 회원·활성 행을 넣은 테스트로 검증했다. 실제 운영 데이터 규모에서의
전환 시간이나 운영 DB 적용을 확인했다는 뜻은 아니다. 기동 검증 때 외부 푸시·워커는 껐다.

`FlywayBaselineTest`는 V30→V31의 회원·활성 행, 기존 이력, 다른 테이블·인덱스 저장 방식,
PK/FK/NOT NULL/cascade 보존과 재실행 0건을 검증한다. `MemberActivityPersistenceTest`는
UNLOGGED 상태에서 여러 연결의 보고·단조 시각·중복 갱신 생략을 검증한다.
`ChatActivityPushTest`는 15초 만료와 보류·읽음·묶음을, `ChatWebSocketTest`는 인증된 활성
보고 경로를 검증한다. 이 네 테스트 클래스의 총 44개 테스트가 통과했다. 이후 Java 21 `./gradlew check bootJar --no-daemon --console=plain`도
163개 클래스·1,289개 테스트 모두 통과했다(실패·오류·건너뜀 0). 장애 후 실제 기기 수신은
검증하지 않았으며 앞의 격리 DB 강제 종료 실험과 구분한다.

향후 재검토 사유는 활성 상태의 장애 보존이 제품 요구로 바뀌거나, 읽기 복제본에서 이 상태를
사용해야 하거나, 실제 서비스 부하에서 DB 쓰기·경합이 병목으로 확인되는 경우다.

## 결정 출처

계정 단위 보류와 5분·10초·15초 설정, 기존 소켓 재사용, 한 행 저장, 보류 후 재판정은
결정자가 메인 작업 대화에 전달한 사이드 대화 합의문을 기준으로 기록했다. 별도 사이드 대화
원문 전체를 다시 검증했다고 주장하지 않는다. UNLOGGED 비교는 같은 작업에서 실행한
측정 자료이며, 강제 종료 후 일시적 추가 푸시를 치명적이지 않다고 보고 수용한 판단은
2026-11-06 결정자의 명시적 요청을 반영했다. AI의 대안 설명이나 추천을 팀 전체의 합의로
기록하지 않는다.
