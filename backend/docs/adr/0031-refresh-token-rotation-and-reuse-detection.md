# 백엔드 ADR 0031. Refresh Token을 갱신할 때마다 회전하고, 재사용되면 그 로그인을 폐기한다

- 상태: 제안
- 날짜: 2026-11-03
- 관련 문서: [백엔드 ADR 0001](0001-github-oauth-authentication.md), [백엔드 ADR 0002](0002-access-token-cookie.md),
  [백엔드 ADR 0005](0005-csrf-token-delivery.md), [백엔드 ADR 0013](0013-testcontainers-test-database.md),
  [인증과 회원 API](../context/api/endpoints/auth-members.md), [보안과 개인정보](../conventions/security.md),
  [배포 중 DB 변경 규칙](../../../docs/database-changes.md)
- 이 문서는 [`AuthCommandService.refresh`](../../src/main/java/com/project/jarihana/auth/command/service/AuthCommandService.java)의
  주석이 별도 결정으로 남겨 둔 회전과 재사용 감지를 정한다. 채택되면 백엔드 ADR 0001의 후속 작업인
  만료 Refresh Token 정리가 필수 작업이 된다.

## 배경

현재 Refresh Token은 회전하지 않는다. `POST /api/auth/refresh`는 쿠키의 Refresh Token을 해시로 조회해
만료 전이면 Access Token만 새로 발급하고, Refresh Token은 로그인 때 받은 값을 14일
(`jarihana.auth.refresh-token-validity: P14D`) 동안 그대로 쓴다. Access Token은 유효 기간 1시간의 서명
JWT라 발급한 뒤에는 회수할 수 없다(백엔드 ADR 0002). 서버가 로그인 상태를 끊을 수 있는 곳은
`refresh_token` 행 하나뿐이고, 이 행도 사용자가 로그아웃할 때만 지워진다.

Refresh Token은 `HttpOnly` 쿠키에 있어 스크립트가 값을 읽을 수 없고, 저장소에는 SHA-256 해시만
남는다(백엔드 ADR 0001 결정 4, 5). 그러나 요청 헤더를 기록하는 로그나 오류 추적 도구, 공용 PC나 잠기지
않은 기기에 남은 쿠키, 디버깅 중 메신저에 붙여 넣은 값처럼 다른 유출 경로는 남아 있다.

정적 Refresh Token이 유출되면 서버는 사용자와 공격자의 갱신 요청을 구별할 수 없다. 두 요청 모두 같은
값을 가진 유효한 토큰이기 때문이다. 공격자는 남은 유효 기간 동안 Access Token을 반복해서 받을 수 있고,
사용자에게는 이상 징후가 나타나지 않으며, 서버에도 아무 기록이 남지 않는다. 피해 규모보다 유출을
탐지할 방법이 없다는 점이 더 큰 문제다.

브라우저 SPA는 클라이언트 비밀을 보관할 수 없는 public client다.
[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)(OAuth 2.0 Security Best Current Practice)은 public
client에 발급하는 Refresh Token에 발신자 제한(sender-constrained)과 재사용 감지를 동반한 회전 중 하나를
요구한다. 자리하나는 별도 인가 서버 없이 백엔드가 로그인과 API를 함께 제공하지만, 갱신 엔드포인트와
브라우저 사이의 관계는 같다.

## 결정

1. **갱신할 때마다 Refresh Token을 새로 발급한다.** 갱신에 성공하면 `accessToken`과 `refreshToken`
   쿠키를 함께 내린다. 요청에 쓰인 토큰은 삭제하지 않고 `rotated_at`에 회전 시각을 기록한다.
2. **한 번의 로그인을 패밀리로 묶는다.** 로그인할 때 `refresh_token_family` 행을 만들고, 회전으로
   발급하는 후속 토큰은 같은 패밀리에 넣는다. 폐기와 절대 만료는 패밀리 단위로 관리한다.
3. **회전된 토큰이 유예 시간 뒤에 다시 오면 패밀리 전체를 폐기한다.** 정상 브라우저는 쿠키가 새 값으로
   바뀌므로 회전된 토큰을 다시 보낼 일이 없다. 회전된 토큰이 다시 왔다면 같은 값의 사본이 있다는
   증거로 본다. 폐기 대상에는 지금 유효한 최신 토큰도 포함한다. 응답은 기존과 같은
   `REFRESH_TOKEN_INVALID`(401)이며, 재사용을 감지했다는 사실은 응답에 드러내지 않는다.
4. **유예 시간 안의 재제출에는 Access Token만 발급한다.** 설정값
   `jarihana.auth.refresh-token-reuse-grace`(기본 `PT10S`)를 추가한다. 회전 시각으로부터 이 시간 안에
   같은 토큰이 오면 패밀리를 폐기하지 않고, 다시 회전하지도 않으며, Refresh Token 쿠키도 내리지 않는다.
   브라우저의 Refresh Token 쿠키는 먼저 성공한 응답이 이미 새 값으로 바꾸어 두었다.
5. **회전은 절대 만료를 늘리지 않는다.** 패밀리의 절대 만료는 로그인 시각에 `refresh-token-validity`를
   더한 값이고, 후속 토큰의 `expires_at`은 이 값을 그대로 물려받는다. "로그인 후 14일이 지나면 다시
   로그인한다"는 사용자 경험은 지금과 같다.
6. **회전 상태 전이는 조건부 UPDATE 하나로 처리한다.** `rotated_at is null` 조건을 건 UPDATE의 변경 행
   수가 1인 요청만 새 토큰을 발급한다. 0이면 다른 요청이 방금 회전한 것이므로 결정 4의 유예 처리로
   넘긴다.
7. **로그아웃은 패밀리를 폐기한다.** 지금처럼 제시된 행 하나만 지우면 같은 로그인에서 회전된 이전
   토큰이 남는다. 패밀리를 폐기하면 재사용 감지와 로그아웃 모두 패밀리에 `revoked_at`과 사유를 기록하고,
   회전된 이전 토큰까지 그 패밀리의 토큰 행을 지운다. 지우는 사이 회전으로 새 토큰이 끼어들어도 패밀리가
   폐기되어 있어 쓰이지 않는다. 패밀리 없이 저장된 이전 행은 지금처럼 그 행만 지운다.
8. **재사용 감지는 WARN 로그로 남긴다.** 패밀리 ID, 회원 ID, 회전 후 경과 시간과 처리 결과를 기록하고,
   토큰 원문과 해시는 남기지 않는다. 유예 안의 재제출도 경과 시간과 함께 기록해 유예 값을 조정하는
   근거로 쓴다.

### 스키마

```text
refresh_token_family                         추가
  id                       bigint PK
  member_id                bigint FK, NOT NULL
  absolute_expires_at      timestamp NOT NULL   로그인 시각 + refresh-token-validity
  revoked_at               timestamp NULL
  revoke_reason            varchar NULL         REUSE_DETECTED, LOGOUT
  created_at, updated_at                        BaseEntity

refresh_token                                기존 테이블
  refresh_token_family_id  bigint FK, NULL      추가. 구버전이 만든 행은 비어 있다
  rotated_at               timestamp NULL       추가. 비어 있으면 활성 토큰이다
  token_hash, expires_at, member_id             기존과 같다
```

다음 Flyway 버전에서 새 테이블과 nullable 컬럼만 추가한다(Expand). `refresh_token_family_id`의
NOT NULL 전환은 별도 PR(Contract)로 미룬다.

### 갱신 판정 순서

```text
쿠키 없음                                 REFRESH_TOKEN_REQUIRED (401)
해시로 조회 실패                          REFRESH_TOKEN_INVALID  (401)
패밀리 폐기됨, 또는 절대 만료 경과        REFRESH_TOKEN_INVALID  (401)
rotated_at 있음, 유예 시간 이내           Access Token만 발급 (200)
rotated_at 있음, 유예 시간 경과           패밀리 폐기 후 REFRESH_TOKEN_INVALID (401)
expires_at 경과                           REFRESH_TOKEN_INVALID  (401)
조건부 UPDATE 0행                         유예 시간 이내와 같이 처리 (200)
조건부 UPDATE 1행                         같은 패밀리에 새 토큰 발급, 두 쿠키 발급 (200)
```

회전 여부는 `expires_at`보다 먼저 확인한다. 아래 배포 호환성 규칙에 따라 회전된 토큰의 `expires_at`을
당겨 두므로, 순서가 바뀌면 재사용이 단순 만료로 처리되어 패밀리가 폐기되지 않는다.

## 왜 패밀리 전체를 폐기하는가

재사용을 감지한 순간 서버가 아는 것은 같은 패밀리의 토큰이 두 곳에 있다는 사실뿐이다.

- 사용자가 먼저 갱신했다면 회전된 토큰을 다시 보낸 쪽은 공격자다. 공격자는 새 토큰을 얻지 못한다.
- 공격자가 먼저 갱신했다면 최신 토큰은 공격자에게 있고, 회전된 토큰을 보낸 쪽은 사용자다.

두 경우를 구별할 정보가 없으므로 최신 토큰까지 폐기해야 어느 순서든 공격이 멈춘다. 사용자는 한 번 다시
로그인해야 하지만, GitHub에 로그인된 상태라면 로그인 버튼을 한 번 누르는 정도의 비용이다.

폐기 범위는 회원이 아닌 패밀리로 정한다. 회원은 기기와 브라우저마다 별도 패밀리를 가지므로, 회원 전체를
폐기하면 유출과 무관한 기기까지 로그아웃된다.

## 유예 시간 안에서 Access Token만 주는 이유

공격이 없어도 같은 토큰이 짧은 간격으로 두 번 오는 경로가 현재 클라이언트에 있다.

- `accessToken` 쿠키는 모든 탭이 공유하므로 모든 탭에서 같은 시각에 만료된다. 여러 탭이 거의 동시에
  401을 받으면 각 탭이 같은 Refresh Token 쿠키로 갱신을 요청한다. 탭 안의 요청은
  [`refreshOnce`](../../../frontend/src/shared/api/client.js)가 하나로 묶지만 탭 사이에는 묶는 장치가 없다.
- 앱을 시작할 때 [`bootstrapAuth`](../../../frontend/src/features/auth/bootstrap.js)는 `client.refresh()`를
  바로 호출하므로 `refreshOnce`를 거치지 않는다. 뒤로 가기로 bfcache에서 복원된 페이지도 `pageshow`에서 같은
  경로를 다시 부른다. 탭 여러 개를 한꺼번에 다시 열면 이 경로들이 겹친다.

이런 재제출은 첫 회전 뒤 수십 밀리초에서 몇 초 안에 도착하고, 유출된 사본은 대개 그보다 훨씬 뒤에 쓰인다.
이 시간 차이를 이용해 짧은 유예 안의 재제출은 폐기하지 않는다. 유예 안의 요청에 무엇을 돌려줄지는 다음
네 가지를 비교하였다.

| 유예 안의 응답 | 유예 안에 들어온 공격자가 얻는 것 | 판단 |
| --- | --- | --- |
| Access Token만 발급 (**채택**) | 유효 기간 1시간의 Access Token 하나 | 응답이 성공 형태라 지금 프론트엔드가 그대로 동작한다 |
| 폐기 없이 409로 거절 | 없음 | 현재 프론트엔드는 갱신 실패를 응답 코드와 관계없이 세션 만료로 처리한다 |
| 새 Refresh Token을 하나 더 발급 | 살아 있는 Refresh Token | 체인이 둘로 갈라진다 |
| 직전에 발급한 토큰을 다시 반환 | 현재 최신 Refresh Token | 새 토큰 원문을 보관해야 한다 |

409 거절은 보안상 가장 깔끔하지만 지금 클라이언트와 맞지 않는다.
[`AuthProvider`의 세션 만료 처리](../../../frontend/src/features/auth/context.jsx)는 갱신이 실패하면 로그인
상태를 지우고 웹 푸시 연결도 해제한다. 프론트엔드와 백엔드는 배포 순서를 보장하지 않으므로, 백엔드가
먼저 배포되면 이미 열려 있던 탭이 공격 없이 로그아웃된다.

Access Token만 주면 유예 안에 들어온 공격자도 체인을 이어 갈 Refresh Token은 얻지 못한다. 공격자가 가진
사본은 이미 회전된 토큰이므로, 유예가 지난 뒤 다시 쓰는 순간 감지된다. 직전 토큰 재반환은 해시만
저장한다는 백엔드 ADR 0001 결정 5와 충돌하고, 탭이 쿠키 저장소를 공유하는 구조에서는 동시 요청을 위해
필요하지도 않다.

기본값 `PT10S`는 탭 사이 동시 요청(1초 이내)과 여러 탭을 한꺼번에 여는 경우(몇 초)를 덮는 값이다. 길수록
유예 안에서 Access Token을 받을 수 있는 시간이 늘어나므로, 결정 8의 경과 시간 기록을 보고 줄인다.

## 회전이 해결하지 못하는 것

- **탈취 자체를 막지 않는다.** 사본이 쓰이는 순간을 드러내고, 공격자가 들키지 않고 쓸 수 있는 기간을
  사용자의 다음 갱신까지로 줄인다. 사용자가 활동 중이라면 대략 Access Token 수명인 1시간 안이다.
- **사용자가 오프라인이면 감지가 늦어진다.** 공격자가 먼저 회전한 뒤 사용자가 브라우저를 열지 않으면,
  공격자는 절대 만료(로그인 후 14일)까지 혼자 체인을 이어 간다. 회전이 절대 만료를 늘리지 않게 한
  이유다.
- **폐기해도 이미 발급한 Access Token은 남은 수명 동안 유효하다.** 백엔드 ADR 0002가 서명 JWT를
  택하면서 받아들인 제약이다.
- **페이지 안에서 스크립트가 실행되는 XSS에는 효과가 작다.** 쿠키 값을 읽지 못해도 브라우저 안에서
  API를 직접 호출하는 요청은 정상 요청과 구별되지 않는다. XSS 방어는 별도 문제로 남는다.
- **응답 유실은 오탐으로 남는다.** 서버가 회전했는데 응답 헤더가 브라우저에 닿지 못하면 브라우저에는
  회전된 토큰만 남는다. 유예 안의 재시도는 Access Token을 받지만 쿠키는 그대로이므로, 다음 갱신에서
  재사용으로 판정되어 다시 로그인해야 한다.

## 배포 호환성

Blue-Green 배포 중에는 구버전과 신버전이 같은 DB를 쓰고, 앱을 롤백해도 스키마와 데이터는 되돌아가지
않는다. 구버전은 `token_hash`와 `expires_at`만 읽고 새 컬럼과 패밀리 테이블을 모른다. 다음 규칙으로 두
버전이 함께 동작하게 한다.

- 구버전이 만든 행은 `refresh_token_family_id`가 비어 있다. 신버전은 이런 행을 그 행의 `expires_at`을 절대
  만료로 하는 패밀리로 받아들인다. 패밀리는 조건부 UPDATE로 회전에 성공한 요청만 만들어 중복 생성을
  막는다.
- 회전할 때 이전 행의 `expires_at`을 회전 시각에 유예 시간을 더한 값으로 당긴다. 롤백한 구버전이 회전된
  토큰을 다시 받아 주지 않게 하기 위해서다. 이 변경은 결정 6의 조건부 UPDATE에 함께 넣는다.
- 패밀리를 폐기할 때 그 패밀리의 토큰 행을 지운다(결정 7). 구버전은 `revoked_at`을 읽지 않으므로, 행이
  남으면 롤백한 구버전이 폐기된 토큰을 받아 준다.
- 구버전의 로그아웃은 토큰 행을 지운다. 남은 패밀리 행은 인증에 쓰이지 않으며 정리 작업에서 지운다.
- 롤백한 구버전은 회전만 하지 않을 뿐 신버전이 발급한 최신 토큰을 정상으로 받는다. 롤백 기간에는
  재사용 감지와 폐기가 일어나지 않는다.
- `refresh_token_family_id`의 NOT NULL 전환은 구버전이 만든 행이 모두 만료된 뒤 별도 PR로 한다. 이 PR
  이후에는 회전 이전 버전으로 롤백할 수 없다. 구버전이 패밀리 없이 행을 넣으려다 실패하기 때문이다.

## 트랜잭션과 동시성

현재 `refresh`는 실패하면 `BusinessException`을 던지고, `@Transactional`은 런타임 예외에서 트랜잭션 전체를
되돌린다. 패밀리 폐기를 같은 트랜잭션에서 실행한 뒤 예외를 던지면 폐기도 함께 사라져, 재사용은
감지했지만 최신 토큰이 살아남는다. 패밀리 폐기는 별도 빈의 `REQUIRES_NEW` 트랜잭션에서 커밋한 뒤 기존처럼
`BusinessException`을 던진다. 같은 클래스 안에서 호출하면 프록시를 거치지 않아 `REQUIRES_NEW`가 적용되지
않으므로 빈을 나눈다. 예외 응답은 [아키텍처 컨벤션](../conventions/architecture.md)대로
`GlobalExceptionHandler`가 만든다.

결정 6의 조건부 UPDATE는 PostgreSQL 기본 격리 수준인 READ COMMITTED에서 다음처럼 동작한다. 같은 행을
바꾸려는 두 번째 트랜잭션은 첫 번째가 커밋할 때까지 기다린 뒤 갱신된 행으로 조건을 다시 평가하고,
조건이 맞지 않아 0행을 바꾼다. 따라서 같은 토큰으로 요청이 동시에 와도 새 토큰은 하나만 발급된다.
REPEATABLE READ 이상에서는 0행 대신 직렬화 실패 예외가 나므로 이 경로의 격리 수준을 올리지 않는다.
조회한 상태를 확인한 뒤 저장하는 방식은 두 요청이 모두 활성 상태를 읽고 각자 새 토큰을 받아 체인이
갈라지므로 쓰지 않는다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 회전 없이 현행 유지 | 추가 구현이 없고 동시 요청 문제도 없다 | 유출되어도 감지할 수 없고, 공격자는 남은 유효 기간 동안 사용자 모르게 Access Token을 받는다. RFC 9700의 public client 요건을 충족하지 못한다 |
| 회전만 하고 재사용은 감지하지 않음(기존 행을 새 값으로 교체) | 행 하나만 바꾸면 되어 구현이 가장 쉽다 | 공격자가 먼저 갱신하면 사용자만 로그아웃되고 공격자가 체인을 차지한다. 서버에는 기록도 남지 않아 현행보다 나쁘다 |
| 만료가 가까울 때만 새 토큰 발급 | 대부분의 갱신이 조회만 한다 | 같은 토큰을 여러 번 쓰는 것이 정상 동작이어서 재사용을 이상 신호로 볼 수 없다 |
| 유예 없는 엄격한 회전 | 규칙이 가장 단순하고 감지 공백이 없다 | 탭 사이 동시 갱신이나 앱 시작 시 갱신이 겹치면 공격이 없어도 패밀리가 폐기된다 |
| 유예 안의 재제출을 409로 거절 | 유예 안에 들어온 요청은 아무 토큰도 얻지 못한다 | 열려 있던 구버전 탭이 갱신 실패를 세션 만료로 처리해 로그아웃되고 웹 푸시가 해제된다. 프론트엔드를 먼저 배포하고 409 재시도를 넣어야 한다 |
| 유예 안의 재제출에 새 Refresh Token을 하나 더 발급 | 클라이언트 입장에서 가장 매끄럽다 | 체인이 갈라지고, 유예 안에 들어온 공격자도 살아 있는 Refresh Token을 얻는다 |
| 유예 안의 재제출에 직전 발급 토큰을 다시 반환 | 응답 유실까지 구제한다 | 새 토큰 원문을 보관해야 해 백엔드 ADR 0001 결정 5와 충돌한다. 쿠키 저장소를 탭이 공유하므로 동시 요청에는 필요하지 않다 |
| 재사용 감지 시 회원의 모든 패밀리 폐기 | 폐기 범위가 넓어 놓친 사본이 남지 않는다 | 유출과 무관한 다른 기기까지 로그아웃되어 오탐 비용이 커진다 |
| 회전할 때마다 만료 연장, 또는 비활성 만료와 더 긴 절대 상한 | 활발한 사용자가 14일마다 다시 로그인하지 않아도 된다 | 사용자가 오프라인일 때 공격자가 혼자 이어 갈 수 있는 기간이 길어진다. GitHub 재로그인 비용이 작아 얻는 편의도 작고, 로그인 유지 기간은 제품 결정이므로 분리한다 |
| DPoP([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449))로 토큰을 클라이언트 키에 결속 | 토큰 문자열만 훔쳐서는 쓸 수 없다 | 브라우저가 키를 만들어 보관하고 요청마다 증명을 서명해야 한다. 쿠키로 토큰을 전달하는 현재 구조와 맞지 않고, 페이지 안 스크립트가 키를 사용하는 것은 막지 못한다 |
| 브라우저에 토큰을 두지 않는 BFF | 브라우저에 장기 자격 증명이 남지 않는다 | 사실상 서버 세션 인증으로 돌아가는 구조라 백엔드 ADR 0001과 0002를 다시 정해야 한다 |

## 감수하는 비용

- 갱신이 조회에서 쓰기 트랜잭션으로 바뀐다. 빈도는 브라우저마다 대략 Access Token 수명(1시간)에 한
  번이다.
- 회전된 행을 지우지 않으므로 행이 쌓인다. 14일 동안 1시간마다 갱신하면 한 패밀리에 최대 약 336행이
  생긴다. 정리 작업이 필수가 된다.
- 유예 안에 재제출한 요청은 유효 기간 1시간의 Access Token을 하나 받는다.
- 응답 유실과 공격을 구별할 수 없어, 응답을 잃은 사용자는 다시 로그인한다.
- 스키마 변경을 Expand와 Contract 두 PR로 나누어 진행해야 한다.

## 결과

- `POST /api/auth/refresh`의 성공 응답이 `Set-Cookie`를 두 개(Access, Refresh) 내린다. 유예 안의 재제출에는
  Access Token 쿠키만 내린다. 응답 본문(`expiresIn`)과 오류 코드는 바뀌지 않는다.
- 실패하면 두 쿠키를 만료시키는 `AuthCommandController.refreshOrExpireCredentials`의 동작은 그대로 둔다.
  재사용 감지도 이 경로로 응답한다.
- 로그아웃의 의미가 "제시된 토큰 삭제"에서 "이 로그인의 패밀리 폐기"로 바뀐다.
- 프론트엔드는 바꾸지 않아도 동작한다. 쿠키 교체는 브라우저가 처리하고, 동시 갱신은 유예 처리로
  성공한다.
- `POST /api/auth/refresh`는 지금처럼 CSRF 토큰(`X-XSRF-TOKEN`)이 필요하다(백엔드 ADR 0005).

## 검증 계획

구현 PR에서 Testcontainers PostgreSQL(백엔드 ADR 0013)로 다음을 확인한다.

- 정상 회전: 새 토큰을 발급하고, 이전 토큰에 `rotated_at`을 기록하며, 두 쿠키를 내린다.
- 유예가 지난 재사용: 패밀리를 폐기하고, 같은 패밀리의 최신 토큰도 401을 받는다. 폐기가 롤백되지 않았는지를
  이 단계로 확인한다.
- 유예 안의 재제출: Access Token만 발급하고, 패밀리를 유지하며, Refresh Token 쿠키를 내리지 않는다.
- 같은 토큰의 동시 요청 여러 개: 새 토큰은 정확히 하나만 발급되고, 나머지는 Access Token만 받으며,
  폐기는 일어나지 않는다.
- 구버전이 만든 행: 패밀리를 만들고 원래 절대 만료를 유지한다.
- 로그아웃: 회전된 이전 토큰까지 같은 패밀리의 토큰 행이 남지 않고, 패밀리에 로그아웃 사유가 남는다.
- 호환성: 회전 뒤 이전 행의 `expires_at`이 유예 끝으로 당겨져 있고, 폐기 뒤 그 패밀리의 토큰 행이 남지 않는다.

## 후속 작업

- 구현 PR: 엔티티, 저장소, Flyway Expand, 서비스, 컨트롤러를 바꾸고, `AuthCommandService.refresh`의
  "회전은 도입하지 않는다" 주석과 [인증과 회원 API](../context/api/endpoints/auth-members.md)의 "Refresh
  Token은 회전하지 않으며" 문구를 함께 고친다.
- 정리 작업: 절대 만료가 지난 패밀리와 그 토큰을 지운다. 이 ADR이 채택되면 백엔드 ADR 0001의 후속
  작업을 필수로 표시한다.
- Contract PR: 구버전이 만든 행이 모두 만료된 뒤 `refresh_token_family_id`를 NOT NULL로 바꾼다.
- 관찰: CloudWatch(백엔드 ADR 0014)에서 재사용 감지 WARN에 알람을 걸고, 유예 안 재제출의 경과 시간
  분포로 `PT10S`를 조정한다. IP와 User-Agent를 함께 기록할지는 개인정보 기준과 함께 정한다.
- 프론트엔드(선택): `bootstrapAuth`의 갱신도 `refreshOnce`를 거치게 하고 탭 사이 갱신을 Web Locks로
  직렬화하면, 유예 처리에 기대는 요청과 불필요한 Access Token 발급이 줄어든다. 프론트엔드 영역의
  결정이므로 [프론트엔드 ADR 목록](../../../frontend/docs/adr/README.md)에서 따로 다룬다.
- 로그인 유지 기간 연장(비활성 만료와 절대 상한)과 Access Token 유효 기간(1시간) 조정은 제품 결정으로
  따로 논의한다.
