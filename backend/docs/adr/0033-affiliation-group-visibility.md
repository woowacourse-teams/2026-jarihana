# 백엔드 ADR 0033. 소속 공개 모임은 확인된 소속으로 판정하고 요청 앞단의 인터셉터와 목록 SQL 조건으로 숨긴다

- 상태: 제안

## 배경

서비스 대상이 우테코 크루에서 모임을 열거나 참여하고 싶은 누구나로 넓어졌다. 크루는 GitHub 로그인 때 크루
명단으로 인증되어 `MemberType.CREW`가 되지만, 지금까지 그 사실로 얻는 권한은 없었다. 같은 단체 사람끼리만 모이고
싶은 모임장은 모집 문구로만 대상을 알릴 수 있었고, 다른 회원은 신청할 수 없는 모임도 목록에서 보게 되었다.
신청도 못 하는 모임을 보여 줄 이유가 없으므로 같은 소속에게만 공개한 모임은 숨긴다.

처음에는 공개 범위를 크루 여부에 묶은 크루 전용 모임으로 설계했다. 그러나 다양한 소속의 사용자가 쓰는 서비스에서
크루 여부에만 묶으면 다른 단체의 회원은 이 기능을 쓸 수 없다. 크루 명단은 우아한테크코스라는 한 소속을 확인하는
방법 중 하나이므로, 공개 범위는 "모임이 정한 소속의 회원"으로 일반화한다.

문제는 소속을 무엇으로 판단하느냐다. 회원 정보에 남은 부트캠프와 회사 이름은 가입 때 직접 적은 자유 입력이라,
누구나 같은 소속이라고 적고 모임을 볼 수 있어 숨김의 경계가 되지 못한다. 지금 서비스가 확인할 수 있는 소속은
크루 명단으로 대조하는 우아한테크코스 하나다.

모임은 한 API에서만 드러나지 않는다. develop(efaf04aa)에서 모임 ID나 이름이 응답에 실리는 경로는 목록과 검색,
홈, 상세, 공유 미리보기, 구성원, 모집, 신청, 캘린더, 아지트와 실시간 입장 토큰, 그룹 음악과 변경 알림 SSE, 공지,
활동 기록 피드와 댓글, 반응, 초대, 알림함과 푸시 내용이다. 이 경로들은 서로 다른 모듈과 담당자가 소유한다
(백엔드 ADR 0008). 판정을 경로마다 따로 넣으면 새 경로가 생길 때 한 곳만 빠져도 숨긴 모임이 드러난다.

인증 토큰에는 회원 ID만 들어 있다. 소속은 명단 인증으로 로그인 중에도 생길 수 있으므로 DB의
`member_affiliation`이 기준이다.

## 결정

1. **소속을 테이블로 두고, 확인된 소속만 회원에게 붙인다.** V52로 `affiliation`(코드, 이름)과
   `member_affiliation`(회원, 소속, 둘의 유일 제약)을 만든다. 첫 소속은 크루 명단으로 확인하는 우아한테크코스
   (`WOOTECO`)다. 명단으로 `CREW`가 되는 가입, GitHub 로그인, 명단 적재 때 소속 행을 넣고, 이미 `CREW`이며 명단에
   있는 회원은 V52에서 옮긴다. 명단 인증 전부터 있던 자가 신고 크루는 명단에 없으면 `CREW`로 남되 소속은 얻지 않는다.
   자가 입력 소속은 옮기지 않는다. 한 회원은 여러 소속을 가질 수 있다. 코치(`COACH`)는 명단으로 확인하지 않으므로
   소속을 얻지 않는다.
2. **`groups.visibility`와 `groups.visible_affiliation_id`를 Expand 마이그레이션(V53)으로 더한다.** 값은 `PUBLIC`,
   `PRIVATE`, `AFFILIATION_ONLY`이고 기본값은 `PUBLIC`이다. `AFFILIATION_ONLY`일 때만 소속이 있도록 CHECK로 묶는다.
   기존 모임과 공개 범위를 보내지 않은 새 모임은 전체 공개다.
3. **보이는지는 한 가지 조건으로 판정한다.** `visibility = PUBLIC`이거나, 조회자가 현재 구성원이거나,
   `AFFILIATION_ONLY` 모임의 소속이 조회자의 `member_affiliation`에 있으면 보인다. 회원 유형(`memberType`)은 판정에
   쓰지 않는다. 숨김 조건 JPQL은 `GroupVisibilityRepository.HIDDEN_FROM_VIEWER` 한 곳에 둔다.
4. **숨김은 가능한 앞단, 컨트롤러에 닿기 전의 인터셉터에서 처리한다.** `GroupVisibilityInterceptor`가 경로
   접두사와 변수(`/groups/{groupId}`, `/recruitments/{recruitmentId}`, `/activity-posts/{postId}`,
   `/activity-post-comments/{commentId}`, `/invitations/{invitationId}`)로 모임을 찾고, 보이지 않으면 없는 자원과
   같은 404(`GROUP_NOT_FOUND`, `RECRUITMENT_NOT_FOUND`, `ACTIVITY_POST_NOT_FOUND`,
   `ACTIVITY_POST_COMMENT_NOT_FOUND`, `INVITATION_NOT_FOUND`)를 낸다. 조회와 명령 모두에 걸리므로 모임장 전용
   조회와 모임원 전용 명령도 보이지 않는 조회자에게는 403 대신 404가 된다. 서비스마다 판정을 두지 않는다.
5. **인터셉터가 막을 수 없는 경로는 각자 막고, 경로 표 테스트로 빠짐을 잡는다.** 페이지를 나누는 목록(모임 목록과
   홈, 활동 기록 피드, 내 신청, 받은 초대, 알림 목록과 안 읽은 수)은 숨김 조건을 SQL WHERE에 넣는다. 조회 뒤에
   거르면 cursor 페이지가 요청 크기보다 짧아진다(백엔드 ADR 0003). 공유 초대 링크 미리보기는 경로에 모임 ID가
   없어 서비스에서 판정한다. `GroupVisibilityRouteCoverageTest`는 모임을 드러낼 수 있는 기능 패키지의 모든 API가
   인터셉터 규칙에 걸리거나 막는 방법이 표에 적혀 있지 않으면 실패한다.
6. **공유 미리보기는 404를 내지 않는다.** CloudFront가 모든 `/groups/{id}` 첫 요청을 미리보기 HTML로 보내고 5분
   동안 공개 캐시에 두기 때문이다. 소속 공개와 비공개 모임은 이름과 소개를 뺀 일반 미리보기로 모임
   페이지에 넘기고, 넘어간 화면의 모임 API가 다시 판정한다.
7. **새로 들어오는 경로는 커밋 시점에 다시 판정한다.** 소속 공개 모임에는 그 소속 회원만 신청하고 초대를 수락할 수
   있다. 인터셉터 판정 뒤 트랜잭션이 시작되기 전에 공개 범위가 바뀔 수 있으므로, 신청은 모임 행 공유 잠금 안에서,
   초대 수락은 모임 버전을 검증하는 낙관적 잠금 안에서(백엔드 ADR 0020) 다시 판정한다. 공개 범위 전환은 같은 모임
   행에 쓰기 잠금을 잡고 버전을 올리므로 둘 중 먼저 끝난 쪽의 상태로 판정된다. 지정 초대 대상과 초대 후보도
   그 소속 회원으로 제한하고, 소속 공개로 만든 모임의 새 모임 알림은 그 소속 회원에게만 저장한다.
8. **이미 들어온 소속 밖 구성원은 그대로 둔다.** 소속 공개로 바꿔도 내보내지 않고 구성원인 동안 계속 본다.
   나가면 판정 조건에서 빠지므로 다시 볼 수 없다.
9. **전환 전에 남은 소속 밖 회원의 대기 신청은 모임장 재량에 맡긴다.** 모임장이 거절하고 싶으면 거절하고,
   승인하면 승인한다. 자동으로 거절하거나 전환을 막지 않는다. 승인되면 구성원이 되어 모임이 보인다. 결정 전까지
   신청자에게는 그 모임과 신청이 보이지 않고, 신청 철회도 404가 된다.
10. **소속 공개는 모임장이 확인된 소속 중 하나로만 켠다.** 모임장 위임은 소속과 관계없이 허용하되, 위임으로
    모임장이 된 회원이 그 소속이 아니면 지금 범위를 유지하거나 공개 또는 비공개로 바꿀 수만 있다. 수정 API의
    `visibility`를 생략하면 지금 값을 유지한다.
11. **숨김과 설정 화면을 두 PR로 나눠 따로 배포한다.** 먼저 숨김만 배포하고(공개 범위를 바꾸는 API와 화면은 없다),
    그 배포가 운영에 나간 뒤 비공개와 소속 공개를 저장하는 API를 배포하고 그 다음 화면을 배포한다. 롤백은 직전
    릴리스까지이므로(백엔드 ADR 0023), 소속 공개 모임이 생길 수 있는 릴리스에서 롤백해도 숨김을 아는 버전으로
    돌아간다. 프론트엔드는 백엔드 다음에 배포한다. 구 백엔드는 모르는 `visibility`를 무시하고 전체 공개로 만들기
    때문이다.
12. **비공개 모임에는 초대로 합류한다.** 현재 구성원만 모임을 본다. 지정 초대는 수신자가, 공유 초대는
    유효한 토큰을 가진 사람이 볼 수 있다. 비구성원에게는 모임 소개를 생략한다. 일반 가입 신청과 기존 대기
    신청의 승인은 비공개 상태에서 거절한다. 지정 초대 알림은 수신자에게 표시하고 새 모임 알림은 발송하지 않는다.

## 결정 이유

- 공개 범위를 크루 여부가 아니라 소속에 묶으면, 판정 조건과 숨김 경로는 그대로 두고 소속과 확인 방법만 늘려
  다른 단체도 같은 기능을 쓸 수 있다. 회원 유형에 소속별 값을 더하는 방식은 한 회원이 여러 소속을 가질 수 없고
  소속이 늘 때마다 코드를 고쳐야 한다.
- 숨김은 다른 사람이 모임 내용을 보지 못하게 하는 경계이므로, 서비스가 확인하지 않은 소속은 쓰지 않는다.
  자가 입력 소속을 쓰면 같은 이름을 적는 것만으로 모임을 볼 수 있다.
- 숨기는 대상은 모임의 내용(이름, 소개, 구성원, 기록, 채팅, 일정)이고, 소속 공개 모임이 있다는 사실 자체는 알려져도
  문제가 없다고 판단했다. 그래도 직접 접근에 404를 내는 것은, 모임 ID가 순번이라 403을 내면 번호를 차례로 넣어
  숨긴 모임의 수를 셀 수 있기 때문이다. 이름 유일 제약 때문에 같은 이름의 모임이 있다는 사실이 드러나는 것은
  감수한다.
- 숨김을 요청 앞단에서 처리하면, 새 API가 생겨도 경로 규칙에 걸리는 한 판정을 따로 넣지 않아도 된다. 서비스마다
  판정을 두면 새 조회 경로에서 빠뜨리기 쉽다. 같은 앞단 중 필터가 아니라 인터셉터를 고른 이유는 아래 대안 표에 있다.
- 소속 공개로 바꾸기 전에 들어온 대기 신청은 모임장이 상황에 맞게 판단할 일로 보았다. 소속 밖 신청을 거절할지
  승인할지는 모임장이 정한다.
- 모임장 위임은 막지 않는다. 다만 소속 공개는 그 소속 회원을 위한 설정이므로, 소속 밖 모임장은 끄거나 그대로 두는
  것만 할 수 있게 했다.
- 배포를 나누는 것은 소속 공개 모임이 생긴 뒤 롤백하더라도 숨김을 유지하기 위해서다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 크루 여부(`MemberType.CREW`)로만 판정 | 테이블을 더하지 않는다 | 우아한테크코스 밖의 단체는 같은 기능을 쓸 수 없다. 처음 설계는 이 방식이었다 |
| 자가 입력 소속(부트캠프, 회사 이름)으로 판정 | 지금 데이터로 바로 쓸 수 있다 | 누구나 같은 이름을 적으면 모임을 볼 수 있어 숨김이 경계가 되지 못한다. 표기도 제각각이다 |
| 소속 이메일 인증까지 이번에 구현 | 다른 단체 회원이 스스로 소속을 얻는다 | 메일 발송 수단이 없고, 도메인과 소속의 연결, 무료 메일 제외, 이메일 보관, 퇴사나 졸업 뒤 재확인을 따로 정해야 한다. 판정은 확인 방법과 관계없이 `member_affiliation`만 보므로 나중에 더해도 숨김 경로는 바뀌지 않는다 |
| 서블릿 필터에서 판정 | 인터셉터보다 더 앞에서, MVC 밖 요청(WebSocket 핸드셰이크 등)까지 막을 수 있다 | DispatcherServlet 전이라 경로 패턴과 변수가 정해지지 않아 `/api/groups/(\d+)/...` 같은 URL 규칙을 컨트롤러 매핑과 따로 적어야 하고, 새 API에서 빠뜨리는 문제가 남는다. 필터에서 던진 예외는 `GlobalExceptionHandler`를 거치지 않아 오류 봉투를 직접 써야 한다. 인증 필터 뒤로 순서를 맞추고 정적 파일, actuator 등을 제외해야 한다. 채팅 STOMP는 이미 구성원 전용이라 MVC 밖을 막을 이유가 없다 |
| Spring Security `AuthorizationManager` | 보안 설정 한 곳에 권한을 모은다 | 거부가 기본 403이라 404로 바꾸는 처리가 필요하고, 경로 변수 문제는 필터와 같다 |
| 서비스와 쿼리마다 조건 추가 | 구현이 쉽다 | 새 조회 경로에서 빠뜨려도 잡을 장치가 없다. 처음 구현은 이 방식이었다 |
| Hibernate `@Filter` | 엔티티 조회에 자동으로 걸린다 | `findById`와 native SQL(그룹 음악 스트림, 실시간 서버의 JDBC)에는 걸리지 않아 단건 판정을 따로 둬야 하고, 요청마다 필터를 켜야 한다 |
| PostgreSQL Row Level Security | DB가 강제한다 | 단순 조회에 트랜잭션을 걸지 않는 컨벤션에서도 `SET LOCAL`로 회원을 넘겨야 하고, 푸시 워커, 정리 배치, 명단 적재, Flyway, 실시간 서버에 우회 역할이 필요하다. 이름 중복 검사가 숨긴 모임을 못 봐 409 대신 unique 위반이 난다 |
| Access Token에 소속 포함 | 소속 조회가 줄어든다 | 명단 인증으로 소속이 생겨도 토큰 만료 전까지 반영되지 않는다 |
| 화면에서만 숨김 | 백엔드 변경이 없다 | API를 직접 부르면 그대로 보이고 신청도 된다 |
| 숨김과 설정을 한 번에 배포하고 롤백 노출을 운영 문서에 적음 | PR과 배포가 한 번이다 | 소속 공개 모임이 생긴 뒤 롤백하면 모두에게 보이고 소속 밖 신청도 된다 |
| 기능 플래그로 설정을 꺼 둔 채 배포 | 코드는 한 번에 들어간다 | 설정 하나, 거절 분기, 화면 노출 경로와 켜는 릴리스가 필요하다. PR을 나누는 것과 효과가 같다 |

## 결과와 감수할 비용

- 인터셉터 규칙에 걸리는 요청마다 숨김 판정 쿼리가 하나 더 나간다. 전체 공개 모임은 `visibility` 비교에서 끝나고,
  나머지 조건은 `member_affiliation(member_id, affiliation_id)`와 `group_member(group_id, member_id)` 유일 인덱스로 찾는다.
- 목록 쿼리의 숨김 조건은 읽은 행에 붙는 Filter다. 크루 여부로 판정하던 때 데이터 2만 건으로 EXPLAIN한 결과 모임
  목록은 `idx_groups_status_created_id`, 활동 피드는 `idx_activity_post_date_id`, 알림 목록은 `idx_notifications_inbox`에서
  row-value cursor 조건을 그대로 인덱스 조건으로 썼다. 소속 조건은 모임마다 소속이 달라 상관 서브쿼리가 되며, 전체
  공개가 아닌 행에서만 `member_affiliation` 유일 인덱스로 찾는다. 소속으로 바꾼 뒤의 EXPLAIN은 다시 하지 않았다.
- 소속을 모르는 이전 버전이 배포 중이나 롤백 뒤에 크루로 바꾼 회원은 다음 GitHub 로그인이나 명단 적재 전까지
  소속이 없어 소속 공개 모임을 보지 못한다.
- 다른 소속의 확인 방법이 생기기 전까지 소속 공개를 켤 수 있는 모임장은 명단에 있는 우아한테크코스 크루뿐이다.
  명단 인증 전부터 있던 자가 신고 크루 중 명단에 없는 사람은 `CREW`로 보이지만 소속 공개 모임을 보지 못한다.
- 숨김은 이후의 조회만 막는다. 소속 공개로 바꾸기 전에 소속 밖 회원에게 이미 표시된 푸시 알림, 메신저가 저장한
  공유 링크 미리보기, CloudFront에 남은 최대 5분의 이전 미리보기, 브라우저의 조회 캐시와 화면에 떠 있는 내용은
  회수하지 않는다.
- 이미지 파일은 지금처럼 키를 아는 사람이 받을 수 있다. 키는 위 경로에서만 내려가므로 새로 드러나지는 않는다.
- 이미 아지트에 접속한 실시간 세션은 공개 범위를 바꿔도 끊지 않는다. 입장 토큰이 60초짜리라 새 입장만 막는다.
- 결정 대기 중인 소속 밖 신청자는 자기 신청을 보거나 철회할 수 없다.

## 후속 작업

- 다른 소속과 확인 방법(학교나 회사 이메일 도메인 등). 메일 발송 수단, 소속과 도메인의 연결, 이메일 보관 정책을 함께
  정하고 결정을 따로 남긴다.
- 소속 공개 모임 목록과 상세에서 소속 회원에게 배지를 보여 줄지 화면 결정.
- 자가 입력 소속 컬럼(부트캠프, 회사)은 회원 모델의 Contract 단계에서 지운다.
