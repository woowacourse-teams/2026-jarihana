## 배경

서비스 대상이 우테코 크루에서 모임을 열거나 참여하고 싶은 누구나로 넓어졌다. 크루는 GitHub 로그인 때 크루
명단으로 인증되어 `MemberType.CREW`가 되지만, 지금까지 그 사실로 얻는 권한은 없었다. 크루끼리만 모이고 싶은
모임장은 모집 문구로만 대상을 알릴 수 있었고, 비크루 회원은 신청할 수 없는 모임도 목록에서 보게 되었다.
신청도 못 하는 모임을 비크루에게 보여 줄 이유가 없으므로 크루 전용 모임은 숨긴다.

모임은 한 API에서만 드러나지 않는다. develop(efaf04aa)에서 모임 ID나 이름이 응답에 실리는 경로는 목록과 검색,
홈, 상세, 공유 미리보기, 구성원, 모집, 신청, 캘린더, 아지트와 실시간 입장 토큰, 그룹 음악과 변경 알림 SSE, 공지,
활동 기록 피드와 댓글, 반응, 초대, 알림함과 푸시 내용이다. 이 경로들은 서로 다른 모듈과 담당자가 소유한다
(백엔드 ADR 0008). 판정을 경로마다 따로 넣으면 새 경로가 생길 때 한 곳만 빠져도 크루 전용 모임이 드러난다.

인증 토큰에는 회원 ID만 들어 있다. 크루 여부는 명단 인증으로 로그인 중에도 바뀔 수 있으므로 DB의
`member.member_type`이 기준이다.

## 결정

1. **`groups.visibility` 컬럼을 Expand 마이그레이션(V52)으로 더한다.** V53에서 제약에 `PRIVATE`를 더한다. 기본값은
   `PUBLIC`이다. 기존 모임과 공개 범위를 보내지 않은 새 모임은 전체 공개다.
2. **보이는지는 한 가지 조건으로 판정한다.** `visibility = PUBLIC`이거나, 조회자가 현재 구성원이거나, `CREW_ONLY` 모임의 조회자가 `CREW`이면 보인다. 코치(`COACH`)도 크루가 아니므로 비크루와 같다. 숨김 조건 JPQL은
   `GroupVisibilityRepository.HIDDEN_FROM_VIEWER` 한 곳에 둔다.
3. **숨김은 가능한 앞단, 컨트롤러에 닿기 전의 인터셉터에서 처리한다.** `GroupVisibilityInterceptor`가 경로
   접두사와 변수(`/groups/{groupId}`, `/recruitments/{recruitmentId}`, `/activity-posts/{postId}`,
   `/activity-post-comments/{commentId}`, `/invitations/{invitationId}`)로 모임을 찾고, 보이지 않으면 없는 자원과
   같은 404(`GROUP_NOT_FOUND`, `RECRUITMENT_NOT_FOUND`, `ACTIVITY_POST_NOT_FOUND`,
   `ACTIVITY_POST_COMMENT_NOT_FOUND`, `INVITATION_NOT_FOUND`)를 낸다. 조회와 명령 모두에 걸리므로 모임장 전용
   조회와 모임원 전용 명령도 보이지 않는 조회자에게는 403 대신 404가 된다. 서비스마다 판정을 두지 않는다.
4. **인터셉터가 막을 수 없는 경로는 각자 막고, 경로 표 테스트로 빠짐을 잡는다.** 페이지를 나누는 목록(모임 목록과
   홈, 활동 기록 피드, 내 신청, 받은 초대, 알림 목록과 안 읽은 수)은 숨김 조건을 SQL WHERE에 넣는다. 조회 뒤에
   거르면 cursor 페이지가 요청 크기보다 짧아진다(백엔드 ADR 0003). 공유 초대 링크 미리보기는 경로에 모임 ID가
   없어 서비스에서 판정한다. `GroupVisibilityRouteCoverageTest`는 모임을 드러낼 수 있는 기능 패키지의 모든 API가
   인터셉터 규칙에 걸리거나 막는 방법이 표에 적혀 있지 않으면 실패한다.
5. **공유 미리보기는 404를 내지 않는다.** CloudFront가 모든 `/groups/{id}` 첫 요청을 미리보기 HTML로 보내고 5분
   동안 공개 캐시에 두기 때문이다. 크루 공개와 비공개 모임은 이름과 소개를 뺀 일반 미리보기로 모임
   페이지에 넘기고, 넘어간 화면의 모임 API가 다시 판정한다.
6. **새로 들어오는 경로는 커밋 시점에 다시 판정한다.** 크루 전용 모임에는 `CREW`만 신청하고 초대를 수락할 수
   있다. 인터셉터 판정 뒤 트랜잭션이 시작되기 전에 공개 범위가 바뀔 수 있으므로, 신청은 모임 행 공유 잠금 안에서,
   초대 수락은 모임 버전을 검증하는 낙관적 잠금 안에서(백엔드 ADR 0020) 다시 판정한다. 공개 범위 전환은 같은 모임
   행에 쓰기 잠금을 잡고 버전을 올리므로 둘 중 먼저 끝난 쪽의 상태로 판정된다. 지정 초대 대상과 초대 후보도
   `CREW`로 제한하고, 크루 전용으로 만든 모임의 새 모임 알림은 `CREW`에게만 저장한다.
7. **이미 들어온 비크루 구성원은 그대로 둔다.** 크루 전용으로 바꿔도 내보내지 않고 구성원인 동안 계속 본다.
   나가면 판정 조건에서 빠지므로 다시 볼 수 없다.
8. **전환 전에 남은 비크루의 대기 신청은 모임장 재량에 맡긴다.** 모임장이 거절하고 싶으면 거절하고, 승인하면
   승인한다. 자동으로 거절하거나 전환을 막지 않는다. 승인되면 구성원이 되어 모임이 보인다. 결정 전까지 신청자에게는
   그 모임과 신청이 보이지 않고, 신청 철회도 404가 된다.
9. **크루 전용으로 켜는 것은 크루인 모임장만 한다.** 모임장 위임은 크루 여부와 관계없이 허용하되, 위임으로
   모임장이 된 비크루는 공개 또는 비공개로 바꿀 수 있다. 수정 API의 `visibility`를 생략하면 지금 값을 유지한다.
10. **숨김과 설정 화면을 두 PR로 나눠 따로 배포한다.** 먼저 숨김만 배포하고(공개 범위를 바꾸는 API와 화면은 없다),
    그 배포가 운영에 나간 뒤 비공개와 크루 공개를 저장하는 API를 배포하고 그 다음 화면을 배포한다. 롤백은 직전 릴리스까지이므로(백엔드
    ADR 0023), 크루 전용 모임이 생길 수 있는 릴리스에서 롤백해도 숨김을 아는 버전으로 돌아간다. 프론트엔드는
    백엔드 다음에 배포한다. 구 백엔드는 모르는 `visibility`를 무시하고 전체 공개로 만들기 때문이다.

11. **비공개 모임에는 초대로 합류한다.** 현재 구성원만 모임을 본다. 지정 초대는 수신자가, 공유 초대는
    유효한 토큰을 가진 사람이 볼 수 있다. 비구성원에게는 모임 소개를 생략한다. 일반 가입 신청과 기존 대기
    신청의 승인은 비공개 상태에서 거절한다. 지정 초대 알림은 수신자에게 표시하고 새 모임 알림은 발송하지 않는다.

## 결정 이유

- 숨기는 대상은 모임의 내용(이름, 소개, 구성원, 기록, 채팅, 일정)이고, 크루 전용 모임이 있다는 사실 자체는 알려져도
  문제가 없다고 판단했다. 그래도 직접 접근에 404를 내는 것은, 모임 ID가 순번이라 403을 내면 번호를 차례로 넣어
  크루 전용 모임의 수를 셀 수 있기 때문이다. 이름 유일 제약 때문에 같은 이름의 모임이 있다는 사실이 드러나는 것은
  감수한다.
- 숨김을 요청 앞단에서 처리하면, 새 API가 생겨도 경로 규칙에 걸리는 한 판정을 따로 넣지 않아도 된다. 서비스마다
  판정을 두면 새 조회 경로에서 빠뜨리기 쉽다. 같은 앞단 중 필터가 아니라 인터셉터를 고른 이유는 아래 대안 표에 있다.
- 크루 전용으로 바꾸기 전에 들어온 대기 신청은 모임장이 상황에 맞게 판단할 일로 보았다. 비크루 신청을 거절할지
  승인할지는 모임장이 정한다.
- 모임장 위임은 막지 않는다. 다만 크루 전용 여부는 크루를 위한 설정이므로, 위임받은 비크루 모임장은 끄는 것만 할 수
  있게 했다.
- 배포를 나누는 것은 크루 전용 모임이 생긴 뒤 롤백하더라도 숨김을 유지하기 위해서다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 서블릿 필터에서 판정 | 인터셉터보다 더 앞에서, MVC 밖 요청(WebSocket 핸드셰이크 등)까지 막을 수 있다 | DispatcherServlet 전이라 경로 패턴과 변수가 정해지지 않아 `/api/groups/(\d+)/...` 같은 URL 규칙을 컨트롤러 매핑과 따로 적어야 하고, 새 API에서 빠뜨리는 문제가 남는다. 필터에서 던진 예외는 `GlobalExceptionHandler`를 거치지 않아 오류 봉투를 직접 써야 한다. 인증 필터 뒤로 순서를 맞추고 정적 파일, actuator 등을 제외해야 한다. 채팅 STOMP는 이미 구성원 전용이라 MVC 밖을 막을 이유가 없다 |
| Spring Security `AuthorizationManager` | 보안 설정 한 곳에 권한을 모은다 | 거부가 기본 403이라 404로 바꾸는 처리가 필요하고, 경로 변수 문제는 필터와 같다 |
| 서비스와 쿼리마다 조건 추가 | 구현이 쉽다 | 새 조회 경로에서 빠뜨려도 잡을 장치가 없다. 처음 구현은 이 방식이었다 |
| Hibernate `@Filter` | 엔티티 조회에 자동으로 걸린다 | `findById`와 native SQL(그룹 음악 스트림, 실시간 서버의 JDBC)에는 걸리지 않아 단건 판정을 따로 둬야 하고, 요청마다 필터를 켜야 한다 |
| PostgreSQL Row Level Security | DB가 강제한다 | 단순 조회에 트랜잭션을 걸지 않는 컨벤션에서도 `SET LOCAL`로 회원을 넘겨야 하고, 푸시 워커, 정리 배치, 명단 적재, Flyway, 실시간 서버에 우회 역할이 필요하다. 이름 중복 검사가 숨긴 모임을 못 봐 409 대신 unique 위반이 난다 |
| Access Token에 `memberType` 포함 | 크루 여부 조회가 줄어든다 | 명단 인증으로 유형이 바뀌어도 토큰 만료 전까지 반영되지 않는다 |
| 화면에서만 숨김 | 백엔드 변경이 없다 | API를 직접 부르면 그대로 보이고 신청도 된다 |
| 숨김과 설정을 한 번에 배포하고 롤백 노출을 운영 문서에 적음 | PR과 배포가 한 번이다 | 크루 전용 모임이 생긴 뒤 롤백하면 모두에게 보이고 비크루 신청도 된다 |
| 기능 플래그로 설정을 꺼 둔 채 배포 | 코드는 한 번에 들어간다 | 설정 하나, 거절 분기, 화면 노출 경로와 켜는 릴리스가 필요하다. PR을 나누는 것과 효과가 같다 |

## 결과와 감수할 비용

- 인터셉터 규칙에 걸리는 요청마다 숨김 판정 쿼리가 하나 더 나간다. 전체 공개 모임은 `visibility` 비교에서 끝나고,
  나머지 조건은 `member` 기본 키와 `group_member(group_id, member_id)` 유일 인덱스로 찾는다.
- 목록 쿼리의 숨김 조건은 읽은 행에 붙는 Filter다. 데이터 2만 건으로 EXPLAIN한 결과 모임 목록은
  `idx_groups_status_created_id`, 활동 피드는 `idx_activity_post_date_id`, 알림 목록은 `idx_notifications_inbox`에서
  row-value cursor 조건을 그대로 인덱스 조건으로 썼다. 크루 여부는 상관없는 서브쿼리라 한 번만 평가된다.
- 숨김은 이후의 조회만 막는다. 크루 전용으로 바꾸기 전에 비크루에게 이미 표시된 푸시 알림, 메신저가 저장한 공유
  링크 미리보기, CloudFront에 남은 최대 5분의 이전 미리보기, 브라우저의 조회 캐시와 화면에 떠 있는 내용은
  회수하지 않는다.
- 이미지 파일은 지금처럼 키를 아는 사람이 받을 수 있다. 키는 위 경로에서만 내려가므로 새로 드러나지는 않는다.
- 이미 아지트에 접속한 실시간 세션은 공개 범위를 바꿔도 끊지 않는다. 입장 토큰이 60초짜리라 새 입장만 막는다.
- 결정 대기 중인 비크루 신청자는 자기 신청을 보거나 철회할 수 없다.

## 후속 작업

- 크루 전용 모임 목록과 상세에서 크루에게 배지를 보여 줄지 화면 결정.
