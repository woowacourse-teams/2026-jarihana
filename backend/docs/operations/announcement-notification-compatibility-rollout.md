# 공지 알림 호환성 전환

## Flyway 순서

회원 소속 확장 PR [#481](https://github.com/woowacourse-teams/2026-jarihana/pull/481)의 V11을 먼저 반영합니다. #484는 이미 #481 브랜치에 병합되어 있으며 별도 migration을 추가하지 않습니다. 이후 이 PR #490이 V12 구독 지원 버전을 추가하고, 후속 [공지 PR #459](https://github.com/woowacourse-teams/2026-jarihana/pull/459)이 V13 공지 스키마를 추가합니다. 순서는 **#481 V11 → #490 V12 → #459 V13**입니다.

## 두 번 나누어 배포하는 이유

기존 앱은 `GROUP_ANNOUNCEMENT_CREATED` enum과 `announcementId` payload를 모른다.
공지 쓰기를 먼저 시작한 뒤 이 앱으로 롤백하면 수신자의 알림 조회가 실패한다.
기존 프론트도 신규 target을 해석하지 못하므로 함께 준비한다.

이 선배포는 신규 알림 읽기와 구독별 푸시 지원 확인을 준비한다. 공지 테이블·등록 API·이벤트 발행자는 추가하지
않는다. V12는 구독 지원 버전 컬럼을 기본 1로 추가한다. 따라서 이 단계에서는 기존 알림만
계속 생성되며, 원래 앱으로 돌아가도 새 저장 데이터 때문에 깨지지 않는다.

## 적용 순서

1. 이 읽기 호환성 PR을 develop에 병합하고 개발 백엔드·프론트 배포의 성공을 확인한다.
2. 같은 변경을 main에도 반영해 운영 백엔드·프론트 배포 성공을 확인한다.
   환경별 배포 SHA·이미지 태그를 기록한다. PR 병합만으로 배포 완료라고 판단하지 않는다.
3. 각 환경에서 직전 성공 이미지가 이 호환 버전인지 확인한 뒤 공지 기능 PR #459를
   배포한다. 이때 공지 V13이 새 테이블과 event type 허용 범위를 추가하고 새 알림 저장을 시작한다.
4. 기능 배포 이후의 앱 롤백 대상은 2번의 호환 이미지 또는 그 이후 버전으로 제한한다.
   공지 알림이 한 건이라도 저장된 뒤에는 호환 선배포 이전 이미지로 되돌리지 않는다.

기존 자동 롤백이 기록하는 직전 성공 태그에 호환 이미지가 들어간 것을 확인해야 한다.
과거 태그를 지정하는 수동 배포도 같은 제한을 따른다. 이 문서는 배포를 자동 실행하거나
공유 환경의 값을 바꾸지 않는다.

## 브라우저와 Service Worker

- 알림 목록·상세·안 읽은 수·푸시 내용 조회와 전체 읽음의 `clientVersion`은 기본 1, 지원 값은 1과 2다.
- 새 프론트와 SW는 2를 요청한다. 서버는 enum·payload를 해석하고 공지 target을 반환한다.
- 예전 탭이나 SW는 파라미터를 보내지 않는다. 서버는 공지를 DB 조회 조건에서 제외하므로
  기존 목록의 페이지 크기·커서와 카운트가 유지된다. 전체 읽음도 숨겨진 공지는 처리하지 않는다. 공지 상세·푸시 내용은 404다.
- 기존 SW는 push-content가 404여도 일반 문구의 OS 알림을 띄운다. SW 수정이나 조회 필터만으로 설치된 구버전을 보호할 수 없다.
- V12의 `push_subscriptions.client_version`은 기존 행과 구버전 INSERT를 1로 보존한다. 새 페이지도 **실제 활성 SW**의 GET_STATE 응답이 2일 때만 구독을 2로 등록한다. 대기 중인 새 SW는 승격 근거가 아니다.
- #459는 버전 2인 구독에만 공지 전송 작업을 만든다. 선배포 워커도 선점과 전송 준비에서 버전을 검사하여 구버전 구독의 기존 공지 작업을 취소한다. 일반 신청·참여 알림은 계속 처리한다.
- 새 SW 활성화 후 로그인 상태에서 사이트를 다시 열거나 푸시 설정을 동기화하면 지원 구독으로 갱신된다. 그 전 공지는 알림함에 남으며 푸시를 소급 생성하지 않는다.
- 기능 배포 이후 구독·SW·서버의 롤백 하한도 이 호환 버전이다. 이미 외부 푸시 서비스가 수락한 요청은 회수할 수 없다.
- 호환 프론트의 공지 알림 클릭은 모임 상세로 이동한다. #459의 프론트에서는 현재 공지
  공개 범위를 확인한 뒤 읽음 처리하고 공지 상세로 이동한다.

`clientVersion`은 인증이나 권한이 아니다. 본인 알림과 활성 구독의 회원·generation
검증을 유지하고, 공지 제목·본문을 알림 payload에 넣지 않는다.

## 검증

`AnnouncementReadCompatibilityAcceptanceTest`는 테스트 전용 위치의 후속 V13 SQL로
실제 PostgreSQL 스키마를 먼저 준비한다. 이후 호환 앱의 원래 migration 위치·기본
검증 설정으로 시작하고, 신규 공지 행을 직접 넣어 다음을 확인한다.

- V13 적용 DB에서도 기본 Flyway validate가 성공하고 추가 적용·이력 변경이 없다.
- 구버전 목록·커서·안 읽은 수는 기존 알림만 정상 반환하고 전체 읽음은 공지를 건드리지 않는다.
- 계약 2는 신규 enum·payload의 목록·상세·읽음·삭제를 처리한다.
- 구버전 SW에는 신규 내용을 반환하지 않고, 계약 2도 본인 구독에만 식별자를 반환한다.
- 지원하지 않는 계약은 400으로 거부한다.
- 기존 SW 구독의 공지 작업은 선점에서 취소하고 일반 작업은 준비한다. 선점 뒤 지원 버전이 내려가면 전송 준비에서도 제외한다.
- PushSubscriptionAcceptanceTest는 등록 버전 저장·누락 시 1·범위 밖 400을 확인한다.
- FlywayBaselineTest는 V10→V12 기존 행·이력 보존과 구버전 INSERT의 기본 1을 확인한다.

테스트용 V13 리소스는 운영 jar에 포함되지 않는다. #459와 함께 실행할 때는 운영 V13을
사용해 같은 번호를 중복 로딩하지 않는다. 실제 배포 이미지·태그를 이용한 환경별 검증과
실제 기기의 OS 푸시 수신 확인은 별도로 수행한다.
