# 채팅 알림 읽기 호환성 전환

## 목적과 범위

채팅 기능 PR [#579](https://github.com/woowacourse-teams/2026-jarihana/pull/579)이 저장한
`CHAT_MESSAGE_RECEIVED`가 DB에 남은 상태에서 이전 백엔드로 돌아가면 enum 매핑과
`clientVersion=3` 검증 때문에 알림 HTTP 조회가 실패할 수 있다.
읽기 호환 PR [#586](https://github.com/woowacourse-teams/2026-jarihana/pull/586)을 먼저 배포해 후속 기능의 롤백 하한을 준비한다.
현재 #579에는 병합된 #586의 읽기 계약과 채팅 생성·활성 보고·보류·묶음 발송 기능이 함께 포함된다.

선행 호환 버전(#586)은 알림 enum·응답·버전별 조회와 읽음 범위, 버전 3 구독을 준비한다.
채팅 메시지의 알림 생성, 활성 보고, `member_activity`, 보류·묶음 발송은 추가하지 않는다.
프론트·Service Worker·WebSocket 프로토콜은 변경하지 않는다.

## 스키마

- V20은 알림 event type과 구독 `client_version` CHECK의 허용 범위만 넓힌다.
  #579의 V20과 파일 내용·체크섬을 동일하게 유지한다. 이미 적용한 migration을 고치지 않는다.
- 기존 행과 기본값은 그대로다. `NOT VALID` CHECK 교체로 기존 행 전체 검사를 하지 않지만
  DDL 잠금은 필요하다. 5초 `lock_timeout`을 유지한다. 운영 동시 트래픽의 잠금 대기는 미검증이다.
- 선행 호환 버전(#586)은 후속 스키마를 테스트 fixture로 검증한다. 기능 PR #579는 운영 jar에 실제 마이그레이션 V30~V32을 포함한다.
- 후속 스키마에서 돌아올 때 V30~V32과 저장 데이터를 유지한다. Flyway repair·baseline 변경·검증 비활성화를 하지 않는다.

## 두 단계 배포

1. 읽기 호환 PR을 먼저 병합하고, 개발·운영 각각에서 백엔드 배포 성공을 확인한다.
2. 환경별 성공 SHA와 이미지 태그를 기록한다. 자동 롤백의 직전 성공 이미지도 이 호환 버전 이상인지 확인한다.
   **PR 생성·병합과 실제 배포 완료는 다르다.**
3. 그 뒤 #579의 채팅 알림 생성과 활성 상태 기능을 배포한다. #579는 선행 PR의 채팅 작업 제외 조건을
   활성·읽음·묶음 발송 정책으로 교체했다. 조회·스키마 호환 테스트는 유지하고,
   워커 제외·알림 미생성 테스트는 실제 채팅 기능 테스트로 전환했다.
4. 새 채팅 알림 또는 버전 3 구독이 저장된 이후 백엔드 롤백은 호환 버전 이상으로 제한한다.
   그 이전 이미지는 새 데이터를 처리하지 못하므로 롤백 대상으로 삼지 않는다.

| 환경 | 호환 버전 배포 SHA·이미지 | 배포 확인 |
| --- | --- | --- |
| 개발 | 미기록 | 미확인 |
| 운영 | 미기록 | 미확인 |

이 문서는 알림 HTTP·DB 읽기 호환을 보장하는 범위다. 새 프론트의 활성 보고 SEND를
이전 WebSocket 서버가 받는 전체 앱 혼합 배포는 별도 범위이며, 선행 호환 버전(#586)은 해당 SEND를 허용하지 않는다.
기능을 롤백할 때 프론트 배포와 이미 열린 탭의 갱신·재연결도 확인해야 한다.

## 남아 있는 데이터의 처리

- 계약 1은 공지·채팅을, 계약 2는 채팅을 DB 조회 단계에서 제외한다. 페이지 크기·커서·미읽음 수와
  전체 읽음에 같은 범위를 적용한다. 미지원 알림 상세·푸시 내용은 404다.
- 계약 3은 기존·공지·채팅을 읽으며 채팅 목적지는 `GROUP_CHAT`, 식별자는 `groupId`다.
  본인 소유권·활성 구독·generation·CSRF 검증은 유지한다. 계약 버전은 권한이 아니다.
- 채팅 목록·내용 조회 자체가 메시지를 읽었다고 처리되지는 않는다. 알림 읽음·삭제 API는 기존대로 동작한다.
- 호환 워커는 채팅 PENDING/RETRY와 만료된 IN_FLIGHT 작업을 선점하지 않는다.
  LIMIT 전에 제외하므로 앞에 채팅이 쌓여 있어도 일반 알림을 처리한다.
  채팅 행·시도 횟수·원래 발송 기한은 유지하며, 선행 호환 버전(#586)에서는 채팅 푸시가 중단된다.
- #579로 복귀하면 남은 작업을 당시 활성 상태·채팅 읽음 순번·원래 발송 기한으로 재판정한다.
  이미 외부 서비스가 수락한 푸시는 회수할 수 없다.

## 검증

`ChatReadCompatibilityAcceptanceTest`는 실제 PostgreSQL에 후속 스키마를 먼저 적용한 뒤
앱의 기본 Flyway 설정으로 시작한다. #586에서는 fixture를, 현재 #579에서는 운영 migration을 사용해
같은 번호를 중복 로딩하지 않는다. 새 채팅 알림을 SQL로 직접 저장해 읽기 호환성을 검증한다.

확인 범위는 후속 스키마와 이력 보존, 계약별 목록·커서·상세·미읽음 수·전체 읽음,
개별 읽음·삭제, 푸시 내용의 본인 소유권과 구독 연결이다. 버전 3 구독의 해제·재연결은
`PushSubscriptionAcceptanceTest`로 검증한다.
선행 #586의 워커 제외·알림 미생성 검증은 해당 PR에 남아 있다. 현재 #579에서는
`ChatActivityPushTest`와 `ChatMessageNotificationTest`로 생성·보류·읽음 취소·묶음 발송을 검증한다.
실행한 결과는 PR에 남긴다. 실제 배포 이미지 전환, 열린 새 프론트와의 WebSocket 혼합 운영,
실기기 OS 푸시 수신은 이 검증으로 증명하지 않는다.
