# 모임 달력 운영 데이터 이관·배포 가이드

> 범위: `feat/group-calendar`를 운영 방식에 적용할 때의 위험과 순서. 운영 DB에는 접속하지 않았으므로 실제 행 수·스키마·백업 상태는 확인되지 않았다. 이 문서는 배포 승인이나 마이그레이션 실행 기록이 아니다.
> 설계 기준: [백엔드 ADR 0017](../adr/0017-group-calendar-event-and-history-model.md), [일정 모델](../context/domain/model/schedule.md), [그룹 달력 API](../context/api/endpoints/group-calendar.md)

## 현재 저장소에서 확인한 사실

- 운영·공유 개발 프로필은 `ddl-auto: validate`다. 운영 DB 스키마는 애플리케이션이 바꾸지 않는다(`application-prod.yaml`, `application-dev.yaml`).
- SQL은 `backend/db/migrations/`에 두고 운영자가 별도로 적용한다. Flyway/Liquibase 자동 적용과 전체 스키마 베이스라인은 없다(백엔드 ADR 0012, 백엔드 README).
- `main`에 백엔드·프런트 코드가 함께 반영되면 서로 다른 GitHub Actions 배포가 독립 실행된다. DB SQL 적용 단계는 백엔드 배포 워크플로에 없다.
- 원격 `develop`의 기존 프런트는 `PUT /groups/{id}` 다음 `PUT/DELETE /groups/{id}/recurring-schedule`를 별도 요청으로 보냈다. 달력 구현은 모임 정보 저장과 일정 저장을 분리하지만, 배포 전에 열려 있던 브라우저 탭은 배포 후에도 구 계약을 호출할 수 있다.
- 기존 운영 `groups`에는 현재 정기·세션 값만 있고 변경 이력과 별도 종료 일자가 없다. 새 코드의 `Group`은 변경마다 새 인스턴스를 만들어 `save`한다.
- 프런트의 Service Worker는 화면이나 API 응답을 캐시하거나 `fetch`를 가로채지 않는다(`frontend/public/sw.js`, 프런트 ADR 0002). 일반적인 새로고침은 새 화면을 받는 회복 경로다. 다만 열려 있는 탭의 기존 JavaScript는 배포만으로 교체되지 않으며, CDN의 실제 HTML 캐시 설정은 저장소에서 확인되지 않았다.
- 현재 프런트 코드는 오류 코드별 고정 문구를 사용한다. 배포 전에 열린 **구형 탭은 새 `CALENDAR_CLIENT_OUTDATED` 코드를 알지 못해 일반 오류 문구를 볼 수 있다.** 새 화면에서는 새로고침 안내가 나오지만, 구형 탭까지 같은 문구를 보장하려면 안내 문구를 먼저 배포하고 열린 탭의 교체 시간을 두어야 한다.
- 테스트 DB는 PostgreSQL Testcontainers지만 기본 `ddl-auto: create-drop`이다. 엔티티 테스트가 성공해도 운영용 SQL과 기존 행 보정이 맞는지는 자동으로 증명되지 않는다.
- 저장소에서 운영 DB의 백업·복원 검증 절차를 찾지 못했다. 백엔드 ADR 0012도 운영 DB 백업 절차를 후속 작업으로 남긴다. 저장소 밖 백업 유무는 확인되지 않았다.

## 위험과 필요한 대응

| 우선순위 | 위험 | 실제 발생 경로 | 대응·검증 |
| --- | --- | --- | --- |
| 필수 | SQL 누락 시 새 백엔드 기동 실패 | 운영은 `validate`이고 배포 워크플로는 SQL을 적용하지 않는다. | 스키마 확장 SQL을 코드 배포 전에 별도 적용하고, 실제 운영 스키마와 컬럼·제약을 사전 점검한다. SQL 적용 상태를 기록한다. |
| 필수 | 기존 데이터의 장소 이력 부재 | 기존 `groups.location`에는 과거 변경 시각이 없어 개설일부터의 실제 장소를 복원할 수 없다. | 장소 백필은 각 그룹을 처리한 트랜잭션 시점의 현재 값부터만 기록한다. 그보다 과거의 장소 상세는 비워 둔다. 기존 장소를 개설일부터 이어진 기록으로 만들지 않는다. 정기 규칙은 현재 값으로 만든 초기 구간임을 운영자가 확인하고 모임장이 수정할 수 있게 한다. |
| 필수 | 배포 중 이력 불일치 | SQL 적용 뒤 구버전 백엔드가 일정을 바꾸거나, 호환 백엔드 배포 뒤 백필과 새 수정이 같은 그룹을 처리할 수 있다. | 새 백엔드에서 모든 변경 경로를 먼저 기록한다. 이력이 없는 그룹에서 장소가 처음 바뀌면 과거 구간을 추측하지 않고 새 장소만 변경 시각부터 기록한다. 누락 장소 행은 그룹 행 잠금 아래 현재 값을 스냅샷한다. 백필과 변경이 같은 그룹을 처리할 때도 같은 잠금으로 직렬화하고, 최종 대조가 끝나기 전 달력 기능을 노출하지 않는다. |
| 필수 | 구버전 클라이언트의 범위 없는 일정 변경 | 기존 `PUT/DELETE /recurring-schedule`에는 `applyScope`가 없다. 구버전 프런트 탭은 배포 뒤에도 이 경로로 요청할 수 있다. | 신규 범위 선택 명령은 별도 `/recurring-schedule/scoped` 경로로 분리한다. 새 달력 공개 후 기존 정기 일정 변경 경로는 저장하지 않고 거절한다. 공개 전 호환 배포 구간의 동작과 활성화 시점을 명시한다. 프런트·백엔드 배포 순서를 고정하거나 기능 플래그로 노출을 늦춘다. |
| 필수 | 종료 모임에 종료 후 정기 일정 생성 | 기존 `ENDED` 행에는 종료 일자가 없고, 개설일부터 무기한 정기 발생을 만들 수 있다. | `ended_on` 컬럼을 추가하고 신규 종료 명령에서 상태와 함께 서울 날짜를 기록한다. 기존 종료 모임은 `updated_at::date`를 후보로 보정하되 운영 데이터와 이력 확인 후 적용한다. 종료 일자 이후 일정은 숨긴다. |
| 높음 | 새 그룹 컬럼이 수정 시 초기화 | `Group.modify`·`replace*Schedule`·`endAt` 등이 새 `Group`을 구성한다. 새 필드 복사를 빠뜨리면 설정·기간이 유실된다. | 모든 생성·복사 경로에 새 필드를 전달하고 각 경로의 값 보존 테스트를 추가한다. |
| 높음 | 변경 경쟁으로 기간·현재 값 불일치 | 일정 변경, 장소 수정, 종료, 그룹 삭제가 잠금 없는 조회 후 별도 변경을 수행한다. | 같은 그룹의 달력 관련 명령에서 그룹 행을 잠그고 기간·장소 이력·현재 값을 한 트랜잭션으로 갱신한다. 동시 수정·삭제 테스트를 작성한다. |
| 높음 | 24시간 내 그룹 삭제 실패 | 새 개별 일정·정기 묶음·기간·장소 이력이 `groups`를 참조하면 기존 하드 삭제가 FK에서 막힐 수 있다. | 새 자식 행의 삭제 순서나 FK cascade를 명시하고 기존 그룹 하드 삭제 인수 테스트에 포함한다. 종료는 기존 정책대로 이력을 보존한다. |
| 높음 | 모임 정보와 일정의 일부만 저장 | 현 프런트는 정보 변경 성공 뒤 일정 API 실패가 가능하다. | 새 화면은 모임 정보 폼과 정기·세션 일정 모달의 저장을 분리한다. 각 서버 요청은 해당 현재 값과 이력 변경을 한 트랜잭션으로 묶는다. 구버전 모임 정보·SESSION 수정은 유지하므로 오래 열린 탭의 부분 저장 가능성을 배포 점검에 포함한다. |
| 높음 | 앱 롤백 뒤 새 이력이 멈춤 | 확장 스키마는 남아도 구버전 백엔드는 이력 테이블을 갱신하지 않는다. | 기능 노출 전 롤백 절차를 마련한다. 활성화 뒤 백엔드를 구버전으로 되돌릴 때는 관련 쓰기를 잠시 중지하고 누락 변경을 재대조해야 한다. |
| 높음 | 복원할 지점이 불명확 | 저장소에는 운영 DB 백업·복원 검증 기록이 없다. | 운영 DB의 복구 가능한 백업을 확인하고 개발/격리 환경에서 실제 복원을 검증한 뒤 운영 SQL을 적용한다. 기존 컬럼·테이블을 제거하는 SQL은 이 기능에서 사용하지 않는다. |
| 보통 | 짧은 DDL 잠금·백필 부하 | `ALTER TABLE groups`는 잠금이 필요하고, 대량 `UPDATE`는 운영 쓰기와 경쟁한다. | 새 컬럼·테이블만 추가하고 짧은 `lock_timeout`을 둔다. 기존 행 보정은 규모 측정 후 배치 처리한다. 큰 기존 테이블 인덱스가 필요하면 별도 절차로 만든다. |
| 보통 | 테스트 통과가 SQL 안전을 보장하지 않음 | 기본 테스트는 Hibernate가 새 스키마를 직접 만든다. | 기존 스키마·실제 같은 기존 행에서 SQL 적용, 재실행, `validate`, 이관 건수·제약·삭제를 검사하는 PostgreSQL 마이그레이션 테스트를 추가한다. |

## 구현에서 반영한 보안·무결성 기준

기능 백엔드 API를 구현했고 공개 목록에서 상세 정보 제외, 그룹원 전용 상세, 모임장 전용 변경, 구형 요청 차단을 인수 테스트로 확인했다. 아래 항목은 **현재 코드에서 확인한 방어 수단과 기능 공개 전 반드시 검증할 경계**다.

| 위험 | 현재 확인한 근거 | 구현·검증 기준 |
| --- | --- | --- |
| 공개 응답에 그룹원 전용 설명·장소가 섞임 | 기존 그룹 상세는 공개이며 현재 장소를 반환한다. 이는 합의된 기존 동작이다. 새 달력은 공개 목록과 비공개 상세를 함께 제공할 예정이다. | 공개 달력 DTO에는 제목·날짜·시각만 넣는다. 설명·장소는 서버에서 제외하고, 비가입자·탈퇴자·다른 그룹원 요청을 인수 테스트로 거절한다. 달력 상세의 장소 비공개와 기존 그룹 상세의 장소 공개는 명확히 구분한다. |
| 다른 모임의 일정 ID를 이용한 접근 | `SecurityConfig`는 기본적으로 인증을 요구하지만 모임 소속·역할 판단은 서비스가 수행해야 한다. | 모든 상세·수정·삭제에서 `groupId`와 일정/기간 ID의 소속을 함께 검증한다. 현재 그룹원 또는 모임장 여부를 매 요청에서 확인한다. 다른 모임 ID 조합은 해당 모임에서 존재하지 않는 것으로 처리한다. |
| 로그인 전환 뒤 비공개 상세가 남음 | 기존 그룹 조회의 React Query 키는 그룹 ID 중심이다. 알림함은 별도로 회원 ID·세션 버전으로 캐시를 격리한다. | 새 일정 상세·과거 장소 조회 키에는 회원 ID·세션 버전을 넣고 로그아웃·계정 변경·권한 상실 때 제거한다. 해당 HTTP 응답은 `Cache-Control: no-store`로 제공하고 실제 응답 헤더를 검증한다. |
| 여러 탭에서 편집한 이력 덮어쓰기 | 그룹 행 잠금은 동시 쓰기를 직렬화하지만, 오래된 모달의 값을 나중에 저장하는 경우까지 막지는 못한다. | `group_event`와 `group_recurring_series`에 버전을 두고 편집 시 기대 버전을 검사한다. 과거 구간 변경도 묶음 버전을 올린다. 충돌은 마지막 저장으로 덮지 않고 재조회 안내를 보여준다. |
| 공개 월간 조회의 과도한 응답·부하 | 조회 기간은 최대 42일로 검증하지만 해당 기간에 걸치는 개별 일정 수에는 별도 상한이 없다. | 겹침 조회 인덱스와 실제 데이터 규모를 확인하고 부하 테스트를 수행한다. 무한 확장이나 임의 잘림 없이 예측 가능한 최대 응답·오류 처리를 운영 데이터 규모에 맞춰 확인한다. |
| 사용자 입력의 화면·분석 도구 노출 | 현재 `MarkdownContent`는 `rehypeSanitize`를 쓰고, PostHog 설정은 텍스트·입력값·요소 속성을 마스킹한다. 새 화면은 아직 없다. | 제목은 텍스트로 렌더링하고 설명은 기존 안전한 컴포넌트 또는 일반 텍스트로 표시한다. HTML/스크립트 입력 테스트를 추가한다. 설명·장소를 URL, 분석 이벤트, 서버 로그에 넣지 않고 새 상세 모달의 화면 기록 마스킹을 확인한다. |
| 변경 API의 인증·CSRF 누락 | 기존 `SecurityConfig`는 기본 인증과 쿠키 CSRF 방어를 사용한다. | 공개 허용은 달력 목록 GET 한 경로에 한정한다. 상세 GET에는 그룹원 검사를, 모든 변경에는 현재 모임장 검사와 CSRF를 적용해 무인증·비가입·일반 그룹원·다른 모임장 요청을 검증한다. |

이 점검은 설계·저장소의 정적 검토다. 운영 DB, 배포된 CDN 응답, 실제 브라우저·네트워크 경로에는 접근하지 않았으므로 운영 취약점 부재나 마이그레이션 안전성을 확정하지 않는다. 특히 개인 정보 응답의 실제 캐시 헤더와 운영 백업·복원은 구현·배포 단계에서 확인해야 한다.

달력 탭은 공개 DTO의 제목·날짜·시각을 렌더링하고, 설명·장소는 그룹원 전용 상세 API로 조회한다. `/__showcase`는 가상 데이터다. **클라이언트의 데이터 검증과 조건부 렌더링은 보안 통제가 아니다.** 실제 권한과 정보 비공개는 서버의 DTO·그룹원 검사·캐시 헤더로 보장한다.

## 권장 배포 순서

1. **운영 사전 확인:** 실제 스키마와 그룹 건수·유형·상태·현재 일정·`created_at`/`updated_at` 범위를 읽기 전용으로 조사한다. 운영 백업의 복원 가능성을 확인한다. 개발 DB 또는 운영 데이터의 비식별 복제본으로 SQL을 예행 연습한다.
2. **확장 SQL 선적용:** [`2026-10-07-group-calendar-expand.sql`](../../db/migrations/2026-10-07-group-calendar-expand.sql)과 [`2026-10-12-group-recurring-occurrence-overrides.sql`](../../db/migrations/2026-10-12-group-recurring-occurrence-overrides.sql)을 검토해 적용한다. 기존 컬럼을 삭제·변경하지 않고 `ended_on` nullable 컬럼, 기본값이 있는 표시 설정, 새 테이블·연결 컬럼과 제약을 추가한다. 구버전 백엔드가 계속 동작해야 한다.
3. **호환 백엔드 배포:** `GROUP_CALENDAR_LEGACY_RECURRING_WRITE_ENABLED=true`로 시작한다. 기존 API의 정기 일정 변경도 그룹 행 잠금 아래 이전 값을 초기 이력으로 채우고 오늘 경계 이후의 변경을 기록한다. 장소 수정은 새 장소를 수정 시각부터 기록하며, 아직 장소 이력이 없는 그룹의 과거 장소를 추정해 채우지 않는다. 신규 종료는 `ended_on`을 동시에 저장한다. 달력 UI는 아직 노출하지 않는다.
4. **멱등 백필:** [`2026-10-07-group-calendar-backfill-batch.sql`](../../db/migrations/2026-10-07-group-calendar-backfill-batch.sql)을 검토해 그룹 단위로 실행한다. 없는 초기 정기 묶음·규칙 기간을 만들고, 장소는 배치가 처리된 시각의 현재 값을 스냅샷한다. 장소의 배포 전 변경 이력은 복원할 수 없으므로 그 이전 일정 상세에는 장소가 없다. 기존 종료 그룹의 종료 일자는 운영 자료에서 근거를 확인한 뒤에만 보정한다. 진행 중 쓰기와 충돌하지 않게 그룹 단위로 직렬화하고, 재실행해도 중복되지 않도록 한다. 보정 후 현재 값과 최신 이력, 그룹 수·묶음 수·기간 수를 대조한다.
5. **기능 노출:** 새 달력 API와 프런트를 활성화하면서 `GROUP_CALENDAR_LEGACY_RECURRING_WRITE_ENABLED=false`로 전환한다. 기존 정기 일정 API의 변경 요청은 `CALENDAR_CLIENT_OUTDATED`(409)로 차단하고 기존 모임 정보·SESSION 수정은 유지한다. 오래 열린 화면에서는 모임 정보만 먼저 저장될 수 있으므로 새로고침 뒤 현재 저장 상태를 다시 확인하도록 배포 안내에 포함한다. 독립 배포 순서와 기존 탭을 고려해 새 프런트가 구버전 API와 만나지 않도록 한다.
6. **운영 확인:** 활성/종료/유동적/SESSION 표본과 비가입자·그룹원 권한을 확인한다. 오류율, DB 잠금 대기, API 응답 시간을 감시한다. 문제가 나면 UI를 먼저 숨기고 데이터 삭제 없이 원인을 복구한다.

## 운영에서 먼저 확인할 읽기 전용 집계

아래 질의는 실제 스키마를 확인한 뒤 운영 담당자가 실행할 점검 예시다. 개인 정보나 설명 본문은 조회하지 않는다.

```sql
SELECT type, status, COUNT(*) AS group_count,
       COUNT(*) FILTER (WHERE recurring_activity_days IS NOT NULL) AS recurring_count,
       COUNT(*) FILTER (WHERE session_date IS NOT NULL) AS session_count
FROM groups
GROUP BY type, status
ORDER BY type, status;

SELECT COUNT(*) AS ended_count,
       COUNT(*) FILTER (WHERE updated_at < created_at) AS invalid_time_count,
       MIN(updated_at) AS earliest_last_update,
       MAX(updated_at) AS latest_last_update
FROM groups
WHERE status = 'ENDED';

SELECT COUNT(*) AS flexible_group_count
FROM groups
WHERE type IN ('CLUB', 'STUDY') AND recurring_activity_days IS NULL;
```

SQL 적용 후에는 **기존 `groups` 행 수·현재 정기/세션 값이 그대로인지**, 각 장소 기록이 백필 시점 또는 실제 변경 시점부터 시작하는지, 정기 규칙이 있는 그룹과 현재 묶음·초기 기간 행이 각각 대응하는지, 최신 기간과 `groups.recurring_*` 값이 일치하는지 검증한다. 그룹별 현재 정기 묶음이 하나를 넘지 않고 같은 묶음의 발생 키가 기간 분할 뒤에도 유지되는지 확인한다. 종료 모임의 마지막 발생일이 종료일을 넘지 않고, 그룹 하드 삭제·과거 일정 조회가 되는지도 검증한다.

## 기능 공개 전에 필요한 운영 증거

- 기존 `ENDED` 그룹의 종료 일자 이관 기준과 운영 데이터 점검 결과. 신규 종료 그룹은 종료 당일까지 표시하고 여러 날 일정은 그 날짜에서 자른다.
- 새 달력 공개 전 호환 배포 구간에서 기존 정기 일정 수정이 발생했을 때 이력에 반영할 기준. 공개 후에는 기존 정기 일정 변경 요청을 차단한다.
- 구버전 화면은 모임 정보 요청 후 일정 요청을 보낸다. 공개 후 정기 일정 요청만 막으면 앞선 정보 수정이 성공한 상태로 전체 저장 오류가 표시될 수 있다. 이 제한을 수용하고 구버전 모임 정보·SESSION 수정은 유지한다. 기존 번들에서 새 오류 문구를 표시할 수 없으므로 새로고침 뒤 저장 상태 확인 안내는 배포 채널에서 제공한다.
- 구버전 프런트의 `ApiError.userMessage`는 서버의 오류 문구 대신 배포 당시 번들에 있는 코드별 문구를 쓴다. 새 오류 코드를 보내도 구버전 탭에는 일반 실패 문구가 표시된다. API 오류만으로 정확한 새로고침 안내를 제공할 수 있다고 가정하지 않는다.
- 새 프런트에는 구버전 요청 거절 오류를 인식해 `새로고침` 행동을 안내할 수 있다. 배포 전에 이미 열려 있던 탭에는 이 코드가 없으므로 동일한 안내를 보장할 수 없다. 별도 사전 프런트 배포로 대상 탭을 줄일 수는 있지만, 당시 이미 열려 있던 탭까지 모두 교체하지는 못한다.
- 운영 DB의 실제 행 수·스키마와 백업 복원 검증 결과. 저장소 분석만으로 데이터 손실 가능성이 0이라고 단정할 수 없다.
