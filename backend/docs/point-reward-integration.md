# 새 기능에 포인트 적립 연결

새 기능은 자신의 도메인에서 적립 대상과 시점을 결정한다. 포인트 모듈은 적립 요청을 받아 중복 검사, 한도 예약, 원장 기록과 잔액 반영을 처리한다.

새 기능은 `PointRewardRule`을 Spring 빈으로 등록한다. 규칙에 사유 코드, 표시 이름, 기준 지급액과 회원당 1회 또는 주간 횟수 같은 한도를 정의한다. 사진 활동기록처럼 활동 자체의 ID와 별도로 중복 범위가 필요한 경우에는 규칙에 범위 중복 사유를 지정하고 지급 요청에 범위 키를 전달한다.

서버에서 지급 조건을 평가한 뒤 원본 활동을 확정하는 트랜잭션 안에서 `PointRewardService.register`를 호출한다. 같은 활동을 재시도할 때 회원, 사유 코드와 원본 키를 유지한다. 미적립 내역을 남기려면 지급 요청에 `INELIGIBLE` 같은 사유를 넘긴다. 점수별로 지급액이 다르면 서버가 계산한 양의 정수 금액을 `PointReward`에 넣는다. 예약된 금액은 이후 규칙 변경과 무관하게 지급된다.

한 활동에서 여러 회원에게 지급할 때는 트랜잭션 내 지급 요청을 모두 모아 `registerAll`을 한 번 호출한다. 서비스가 회원 ID 오름차순으로 지갑을 잠근 뒤 지급을 예약한다.

일반 활동 요청의 기본 DB 격리 수준(`READ COMMITTED`)에서는 같은 회원의 뒤 요청이 지갑 잠금을 기다린 뒤 남은 한도를 확인한다. 예를 들어 이번 주 모임 생성 보상이 한 번 남았을 때 서로 다른 모임을 동시에 만들면 두 모임 모두 생성된다. 먼저 한도를 확보한 요청만 200P 지급을 예약하고, 다른 요청의 보상은 주간 한도 초과(`WEEKLY_LIMIT`)로 기록한다.

호출부가 별도로 `REPEATABLE READ` 격리 수준을 사용한다면 지갑 잠금에서 동시 변경 충돌이 발생할 수 있다. 이 경우 전체 활동 트랜잭션을 롤백하고 `409 CONCURRENT_MODIFICATION`을 반환한다.

원본 활동 API가 요청을 받을 때마다 새로운 활동 ID를 만드는 경우에는 같은 요청의 활동 ID가 유지되도록 원본 API에서 재전송을 처리한다. 요청 ID를 지원하는 API를 재시도할 때는 기존 요청 ID를 재사용한다.

예를 들어 다음은 주간 한도가 있는 규칙을 등록하는 코드다. 금액과 횟수는 예시다.

```java
@Bean
PointRewardRule rhythmClearReward() {
    return PointRewardRule.weekly("RHYTHM_CLEAR", "리듬게임 클리어", 5, 3);
}
```

서버가 적립 가능한 플레이를 저장했다면 `rewards.register(PointReward.of(rhythmClearReward, memberId, "play:" + playId, occurredAt))`로 연결한다. 새 사유는 공통 원장, 잔액, 주간 한도와 적립 내역을 사용한다. 사유 코드는 영문 대문자로 시작하는 최대 30자의 영문 대문자, 숫자, 밑줄로 구성하며 이 형식 안에서 새 사유별 DB 마이그레이션은 필요 없다.

모임 기능도 같은 확장 지점을 쓴다. 예를 들어 향후 일정 완료로 참석자에게 적립한다면 일정 도메인에서 실제 참석자를 확인한 뒤, 회원마다 동일한 완료 일정 ID를 원본 키로 하는 요청을 만들어 `registerAll`로 전달한다. 기존 지급 흐름을 사용하는 예시이며 해당 활동의 지급액과 조건은 정책 확정 후 정의한다.
