# 모임 달력 데이터·API 설계안

> 상태: 구현 중. 개별 일정·정기 규칙 API, 공개 달력 조회, 최초 정기·장소 이력 기록, 확장 SQL과 배치 백필 초안이 작성됐다. 운영 DB 확인·백업 복원 검증·프런트 첫 등록 흐름 확정 전에는 배포하지 않는다.
> 기준: `origin/develop`에서 분기한 `feat/group-calendar`의 현재 코드와 API 문서.
> 운영 배포 검토: [운영 데이터·배포 위험 점검](group-calendar-production-risk-review.md). 범위 선택 명령은 기존 API와 별도 경로로 분리했다. 새 달력 공개 후 구버전 정기 일정 수정은 차단한다.

## 확정된 제품 동작

- CLUB·STUDY·SESSION 모두 모임 상세에 달력을 제공한다. 기본 화면은 월간이다.
- 기존 `SESSION`은 독립된 그룹 유형이며, 해당 그룹의 일회성 일정을 달력에 표시하고 수정한다. 기존 모임에 딸린 새 단기 세션과 RSVP는 이번 구현 범위에서 제외한다.
- 모임장이 등록하는 개별 일정은 제목, 시작·종료 날짜, 종일 여부, 시작·종료 시각, 설명(필수), 장소(선택)를 갖는다. 여러 날에 걸칠 수 있다.
- 일정 등록 모달은 `개별 일정`을 기본 선택하고, 모임장은 `정기 모임` 회차로 바꿀 수 있다. 회차는 하루짜리이며 제목은 `정기 모임`으로 고정한다. 동아리·스터디에서만 등록할 수 있고, 같은 날짜에 반복 규칙이 이미 회차를 만들면 중복 등록을 거절한다. 설명은 필수, 장소는 선택이며 종일 또는 시작·종료 시각을 지정한다. 과거와 미래 날짜 모두 등록·수정할 수 있다.
- 비가입자를 포함한 누구나 달력에서 제목·날짜·시각을 본다. 개별 일정의 설명·장소를 포함한 상세 정보는 현재 그룹원만 조회한다.
- 기존 정기 일정과 세션 일정의 달력 노출은 모임장이 켜고 끈다. 기본값은 켜짐이며 그룹 정보 자체에는 영향을 주지 않는다.
- 정기 일정의 달력 제목은 `정기 모임`, 세션 일정 제목은 현재 모임 이름이다.
- 정기 일정은 기본적으로 모임 개설일(서울 날짜)부터 발생한다. 모임장은 정기 규칙 전체의 시작일·종료일을 편집할 수 있다. 시작일은 모임 개설일보다 이를 수 없다.
- 요일을 정하지 않고 개설한 모임에 첫 정기 규칙을 나중에 등록하면, 정기 발생 건은 **첫 등록일부터** 표시한다. 유동적 운영 기간은 날짜 칸에 막대로 표시하지 않고, 해당 날짜를 선택했을 때 일정 목록에 안내 문구로 보여준다.
- 정기 규칙의 **전체 시작·종료일**과 요일·시각의 **변경 이력 구간**은 별도로 관리한다. 과거 규칙을 누르면 당시 규칙이 보이며 해당 구간의 요일·시각을 직접 고칠 수 있다. 이력 구간의 날짜 경계는 유지한다.
- 현재 규칙 C를 새 규칙 D로 바꿀 때 `모든 일정`은 A·B·C의 요일·시각, `직전 일정`은 C의 요일·시각, `앞으로의 일정`은 서울 날짜의 오늘부터의 요일·시각을 바꾼다. 과거 B를 눌러 B의 정보만 고치는 작업에는 이 범위 선택을 사용하지 않는다. 개별 일정에도 이 범위를 적용하지 않는다.
- 정기 규칙 종료일은 비울 수 있다. 종료일이 없으면 정기 일정이 무기한 이어진다.
- 요일만 있고 시각이 없는 정기 일정도 달력에 제목·날짜를 표시한다. 시각 문구와 `시간 미정` 문구는 표시하지 않는다.
- 개별 일정은 종일 또는 시작·종료 시각을 지정해야 한다.
- 개별 일정은 과거 날짜에도 등록·수정할 수 있다. 제목은 최대 50자, 장소는 최대 255자, 설명은 최대 10,000자다.
- 종료된 모임은 종료 일자 이후의 정기·세션·개별 일정을 달력에서 숨긴다. 종료 일자까지의 일정은 조회할 수 있고, 종료 뒤 변경은 허용하지 않는다. 여러 날에 걸친 개별 일정은 종료 일자에서 달력 표시를 자른다.
- 달력에서 정기·세션 일정의 장소는 비가입자에게 숨긴다. 기존 모임 상세 화면의 현재 장소 공개 방식은 유지한다.
- 그룹원에게 보이는 정기·세션 일정의 장소는 **그 일정 당시의 모임 장소**다. 모임 장소 변경 이력을 별도로 보존한다.
- 개별 일정은 달력에서 등록·수정·삭제한다. 정기·세션 일정은 달력과 모임 관리 카드에서 같은 일정 수정 모달을 연다. 기존 모임에서는 모달 저장 시 바로 반영한다.
- 기존 모임의 **모임 정보 수정**과 **정기·세션 일정 수정**은 서로 독립된 저장 작업이다. 일정 모달의 저장은 일정 변경만 수행하고, 모임 정보 저장은 일정 변경을 이어서 호출하지 않는다. 새 모임 생성은 생성 요청에 최초 일정을 포함하는 기존 흐름을 유지한다.
- 새 달력 공개 후 구버전 화면의 **정기 일정** 수정 요청은 변경 범위가 없으므로 거절한다. 구버전 모임 정보 수정과 SESSION 일정 수정 요청은 유지한다. 오래 열린 구버전 탭에서 모임 정보만 먼저 저장되고 정기 일정이 거절될 수 있는 제한은 배포 안내와 검증에 포함한다.

## 향후 확장에 대해 확정한 방향

- 정기 모임의 **각 발생일**에도 장래 RSVP와 참석 인원 제한을 붙일 수 있어야 한다. 이번 구현은 묶음 ID와 날짜로 발생 건을 안정적으로 식별할 수 있게 한다.
- 외부인도 신청할 수 있는 모임 주최 단기 세션은 **이번 구현에 포함하지 않는다.** 장래에는 기존 개별 일정을 외부 모집으로 전환하거나, 처음부터 모집 일정으로 생성하는 두 경로를 모두 지원하는 방향으로 설계한다. 어느 경로든 모임 소속 일정 한 건을 기준으로 달력과 장래 홈·목록에 표시한다.
- 장래 마이페이지 개인 달력은 여러 모임의 일정과 본인의 참석 정보를 모아 보여준다. 이번 구현은 같은 일정을 참조할 수 있는 ID를 마련하고, 개인 달력의 자동 포함 기준은 해당 기능 설계 때 정한다.

## 현재 코드와 달라지는 점

현재 `groups`의 embedded 정기·세션 일정은 최신 값 하나만 저장한다. 따라서 과거의 규칙을 달력에 남기려면 정기 일정의 적용 구간을 별도로 보관해야 한다. 기존 `PUT/DELETE /api/groups/{groupId}/recurring-schedule`을 달력 기록과 무관하게 실행하면 이력이 깨지므로 모든 정기 일정 변경 경로를 동일한 트랜잭션으로 묶는다.

기존 모임 관리 화면은 한 번의 저장 버튼 뒤 `PUT /groups/{id}`와 일정 변경 API를 순서대로 호출한다. 새 화면에서는 두 저장 버튼·폼 상태를 분리한다. 모임 정보 요청에는 이름·소개·장소 등 모임 필드만 담고, 정기 일정 모달은 요일·시각·범위·표시 기간을 일정 API로 저장한다. SESSION 일정 모달도 모임 정보 저장과 분리한다. 한 요청이 실패해도 다른 저장 작업을 자동 실행하거나 취소하지 않는다. 각 요청 안에서는 관련 현재 값과 이력 갱신을 한 DB 트랜잭션으로 처리한다. 특히 장소 수정과 장소 이력, 정기 규칙 수정과 기간 이력은 각각 함께 성공하거나 함께 롤백한다.

## 데이터 모델

| 저장 대상 | 제안 필드 | 이유 |
| --- | --- | --- |
| `groups` | `show_base_schedule_in_calendar BOOLEAN NOT NULL DEFAULT TRUE`, `ended_on DATE NULL` | 기본 일정의 달력 노출 설정과 새로 종료하는 그룹의 서울 기준 종료 일자. 기존 embedded 일정은 그룹 상세의 현재 요일·시각으로 유지한다. 기존 `ENDED` 행은 최종 수정 일자를 종료 일자 후보로 점검한 뒤 보정한다. |
| `group_event` | `id`, `group_id`, `title`, `start_date`, `end_date`, `all_day`, `start_time`, `end_time`, `description`, `location`, `recurring_series_id`, `recurring_period_id`, `recurrence_source_date`, `deleted_at`, `version`, `created_at`, `updated_at` | 모임장이 직접 등록하는 개별 일정 또는 특정 반복 회차의 예외 일정. 달력 외의 화면에서도 같은 일정 ID를 참조할 수 있는 모임 소속 자원이다. 종료 날짜는 사용자가 입력한 마지막 날을 **포함**하며 시작일부터 1년 이내여야 한다. 삭제는 기존 기본 정책에 따라 soft delete한다. `version`은 여러 탭의 수정 충돌을 검출한다. |
| `group_recurring_series` | `id`, `group_id`, `calendar_start_date`, `calendar_end_date`, `flexible_from_date`, `is_current`, `version`, `created_at`, `updated_at` | 한 번 등록된 정기 일정 묶음의 안정적인 ID와 **전체** 표시 기간. 요일·시각 이력 구간을 나눠도 ID가 유지된다. `flexible_from_date`는 정기 일정 삭제 후 유동적으로 운영하는 시작일을 보존한다. 전체 삭제에서는 모임 개설일을 기록해 선택 날짜의 유동적 운영 안내를 제공한다. 제거 후 다시 등록하는 경우를 구별하도록 과거 묶음은 보존한다. 그룹별 현재 묶음은 최대 한 건이다. `version`은 묶음의 범위·기간 변경과 과거 구간 수정을 함께 보호한다. |
| `group_recurring_schedule_period` | `id`, `series_id`, `days_of_week`, `start_time`, `end_time`, `effective_from`, `effective_until`, `created_at`, `updated_at` | A·B·C처럼 같은 묶음 안에서 서로 다른 요일·시각이 적용된 이력 구간. 구간은 겹치지 않으며 종료일은 포함한다. |
| `group_location_history` | `id`, `group_id`, `location`, `effective_from_at`, `effective_until_at`, `created_at`, `updated_at` | 모임 장소의 시각별 이력. 현재 `groups.location`은 기존 그룹 상세용 최신 값으로 유지한다. 종료 시각은 배타적이다. |

`group_event`는 종일이면 두 시각 모두 `null`, 시간이 있으면 둘 다 필수다. 시작 일시가 종료 일시보다 앞서야 하며 일정 날짜 범위는 시작일부터 1년 이내다. 종일 일정의 시작일은 종료일보다 늦을 수 없다. 요일만 고정한 현행 정기 일정은 시각 두 개가 모두 `null`일 수 있으며 공개 응답도 `null`을 반환한다. 화면에서는 해당 일정의 제목·날짜만 보여준다. 모든 날짜 경계와 변경 기준일은 `Asia/Seoul`의 주입된 `Clock`으로 계산한다.

정기 발생일은 이력 구간 `effective_from..effective_until`과 해당 묶음의 전체 표시 기간 `calendar_start_date..calendar_end_date`의 교집합에서 해당 요일만 계산한다. 발생 건마다 DB 행을 만들지 않고 조회 구간 안에서 생성한다. 같은 묶음의 이력 구간은 겹치지 않게 한다. 정기 발생 건의 공개 식별 키는 `seriesId + 발생 날짜`로 만든다. 기간 수정·분할로 `periodId`가 바뀌어도 같은 날짜의 발생 키는 유지된다. 요일 수정으로 발생일 자체가 사라지거나 다른 날짜에 새 발생 건이 생기는 경우의 RSVP 처리 정책은 기능 도입 시 정한다. 모임 삭제 시 새 자식 테이블의 해당 행도 같은 트랜잭션에서 정리한다.

기존 모임은 마이그레이션 시 현재 정기 규칙으로 개설일부터 시작하는 묶음과 기간을 각 한 건 만든다. 실제로 과거에 규칙이 달랐더라도 이전 이력은 복원할 수 없으며, 이 초기 구간을 사용자가 수정할 수 있다. 정기 일정이 없는 모임에는 묶음·기간을 만들지 않는다. 다만 정기 규칙 이력이 전혀 없고 모임 방식이 `FLEXIBLE`인 모임은 조회 시 개설일부터 현재 또는 종료일까지를 유동적 운영 기간으로 반환한다. 기존 장소 변경 이력은 복원할 수 없다. 배치 백필은 현재 `groups.location`을 처리 시점부터만 스냅샷하고, 그보다 과거의 일정 상세에는 장소를 반환하지 않는다. 백필 전에 장소가 처음 수정된 그룹은 수정 전 장소의 유효 시작일을 추측하지 않고 새 장소만 수정 시각부터 기록한다. 따라서 첫 추적 시점 전의 장소는 표시되지 않을 수 있다. 배포 전 규칙 변경 기록도 복원할 수 없으므로 현재 규칙으로 만든 초기 구간을 검토·수정할 수 있게 한다. 배포 전 첫 정기 등록이 있었는지 확인할 수 없는 모임에는 유동적 운영 안내를 소급 생성하지 않는다. 신규 종료 요청은 종료 상태와 `ended_on`을 같은 트랜잭션에 기록한다. 기존 종료 그룹의 `ended_on`은 최종 수정 일자를 후보로 삼되 운영 데이터와 가능한 이력 소스를 확인한 뒤 확정한다.
새 모임을 만들 때 정기 규칙이 있으면 모임 생성 트랜잭션에서 최초 묶음·기간도 함께 만든다.
요일 없는 유동적 모임에서 첫 정기 규칙을 등록하면 범위 선택 없이 새 묶음을 만든다. 묶음의 `calendar_start_date`와 최초 이력 구간의 `effective_from`은 등록한 서울 날짜로 둔다. 그룹 개설일과 최초 묶음 시작일 사이를 이전의 유동적 기간으로 해석한다.
새 모임을 만들 때는 현재 장소로 최초 장소 이력을 함께 만든다. 모임 정보 수정에서 `location`이 바뀌면 같은 트랜잭션에서 기존 장소 이력을 종료하고 변경 시각부터 새 이력을 연다. 같은 시각에 겹치는 장소 이력이 없도록 한다. 모임 삭제 시 장소 이력도 함께 지운다.

## 조회 계약 초안

| API | 권한 | 역할 |
| --- | --- | --- |
| `GET /api/groups/{groupId}/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD` | PUBLIC | 표시 범위와 겹치는 개별 일정, 정기 발생 건, 세션 일정을 반환. `from`과 `to`는 포함하며 최대 42일을 허용한다. |
| `GET /api/groups/{groupId}/events/{eventId}` | 현재 그룹원 | 개별 일정 설명·장소와 수정 충돌 검출용 `version`을 포함한 상세 조회. 현재는 그룹원만 상세를 볼 수 있으며, 미래의 공개 모집은 별도 공개 정책으로 확장한다. `Cache-Control: no-store`. |
| `GET /api/groups/{groupId}/calendar/schedule-details?kind=RECURRING\|SESSION&date=YYYY-MM-DD` | 현재 그룹원 | 해당 날짜에 적용된 정기·세션 일정과 당시 모임 장소를 달력 상세용으로 조회. `Cache-Control: no-store`. |
| `GET /api/groups/{groupId}/recurring-schedule/manage` | LEADER | 현재 규칙, 정기 일정 전체 표시 시작·종료일, 묶음 `version`을 모달 편집용으로 조회. `Cache-Control: no-store`. |
| `GET /api/groups/{groupId}/recurring-schedule/periods/{periodId}` | LEADER | 달력에서 선택한 과거 규칙 구간의 요일·시각, 고정된 구간 경계, 묶음 `version`을 조회. `Cache-Control: no-store`. |

공개 목록 응답은 달력 설정값 `showBaseSchedule`과 일정 배열을 담는다. 각 일정에는 `kind`(`GROUP_EVENT`, `RECURRING`, `SESSION`), `id` 또는 발생 식별 키, `title`, `startDate`, `endDate`, `allDay`, `startTime`, `endTime`만 포함한다. **설명과 장소 필드는 공개 DTO에 존재하지 않는다.** `showBaseSchedule=false`이면 정기·세션 일정만 배열에서 제외한다. 장기간 걸치는 개별 일정은 `startDate <= to AND endDate >= from`으로 찾는다. 정기 발생 식별 키는 묶음 ID와 발생일을 조합한다. 편집용 `periodId`는 별도 필드로 제공하고 RSVP의 참조 키로 쓰지 않는다. 그룹이 종료되어도 종료 일자까지의 일정은 읽을 수 있으나 변경 API는 막는다. 종료 일자 이후의 발생 건은 제외하고 여러 날에 걸친 개별 일정은 종료 일자까지만 표시한다.

첫 정기 규칙의 시작일이 개설일보다 늦고 조회 범위와 유동적 운영 기간이 겹치면 공개 달력 응답에 `flexibleBeforeFirstRecurring` 정보를 포함한다. 이 값은 `fromDate`(모임 개설일), `untilDate`(첫 등록일 전날), `registeredOn`(첫 등록일)을 갖는다. 개별 일정이나 매일 반복되는 달력 이벤트가 아니다. 날짜 칸에는 표시하지 않으며, 사용자가 해당 날짜를 선택하면 일정 목록에 `이 날짜에는 정해진 정기 모임 없이 유동적으로 운영했어요.`라고 안내한다. `showBaseSchedule=false`이면 이 정보도 화면에서 숨긴다.

정기 묶음의 종료일 다음부터 유동적으로 운영하면 공개 응답의 `flexibleAfterRecurring`에 시작일과 다음 정기 묶음 직전 종료일을 담는다. 전체 삭제는 과거 정기 묶음까지 달력에서 숨기고 모임 개설일부터 유동적 운영 기간으로 취급한다. 정기 규칙 이력이 없는 `FLEXIBLE` 모임은 개설일부터 조회 시점 또는 종료일까지를 유동적 기간으로 반환한다. 해당 기간은 날짜 칸에 표시하지 않고, 선택 날짜 일정 목록에서만 안내한다. 모임장이 기본 일정 표시를 끄면 안내도 함께 숨긴다.

공개 응답의 `data` 예시:

```json
{
  "showBaseSchedule": true,
  "flexibleBeforeFirstRecurring": null,
  "flexibleAfterRecurring": [],
  "events": [
    {
      "kind": "RECURRING",
      "occurrenceKey": "recurring:42:2026-10-14",
      "periodId": 99,
      "title": "정기 모임",
      "startDate": "2026-10-14",
      "endDate": "2026-10-14",
      "allDay": false,
      "startTime": "19:00:00",
      "endTime": "21:00:00"
    },
    {
      "kind": "GROUP_EVENT",
      "id": 61,
      "title": "가을 번개 모임",
      "startDate": "2026-10-17",
      "endDate": "2026-10-18",
      "allDay": false,
      "startTime": "14:00:00",
      "endTime": "18:00:00"
    }
  ]
}
```

정기·세션 일정은 별도 설명 필드를 만들지 않는다. 그룹원용 달력 상세에서 시각이 있는 일정의 장소는 발생 시작 시각에 유효했던 `group_location_history` 값을 사용한다. 시각이 없는 정기 일정은 **그날 마지막으로 설정된 장소**를 사용한다. 해당 시점의 이력이 없으면 장소를 반환하지 않으며 현재 장소로 과거를 채우지 않는다. 현재 그룹 상세 API는 모임 장소를 비가입자에게도 반환하며, 이 동작은 유지한다. 비가입자 장소 숨김은 **달력 화면과 달력 API에 한정**된다.

달력은 특정 날짜 범위의 완전한 결과가 필요하므로 커서 목록과 별도의 범위 조회를 사용한다. `from <= to`이고 양끝을 포함해 최대 42일이다. 결과를 임의 건수에서 잘라 달력 일부만 보이게 하지 않는다. 그 외 일반 목록 API의 커서 규칙은 유지한다.

편집용 API는 전체 이력 목록을 내려주지 않는다. 공개 발생 건의 기간 식별자로 선택한 구간 한 건만 조회한다. 기존 모임 관리 카드에서는 현재 규칙 한 건을 조회한다.

| API | 권한 | 역할 |
| --- | --- | --- |
| `POST /api/groups/{groupId}/events` | LEADER | 개별 일정 생성. `201 Created`와 `Location`. |
| `PUT /api/groups/{groupId}/events/{eventId}` | LEADER | 개별 일정 전체 교체. `200 OK`. |
| `DELETE /api/groups/{groupId}/events/{eventId}` | LEADER | 개별 일정 soft delete. `204 No Content`. |
| `PUT /api/groups/{groupId}/calendar/settings` | LEADER | `{ "showBaseSchedule": true/false }` 갱신. `200 OK`. |
| `POST /api/groups/{groupId}/recurring-schedule/series` | LEADER | 현재 정기 규칙이 없는 모임에 새 묶음을 등록. 등록한 서울 날짜부터 달력에 표시한다. 삭제 후 재등록도 새 묶음 ID를 사용한다. |
| `PUT /api/groups/{groupId}/recurring-schedule/scoped` (신규) | LEADER | 요일·시각과 필수 변경 범위를 받아 이력 구간을 갱신. 현재 구간이 바뀌면 embedded 값도 같은 트랜잭션에서 갱신. |
| `PUT /api/groups/{groupId}/recurring-schedule/periods/{periodId}` | LEADER | 선택한 과거 이력 구간의 요일·시각만 교체. 구간의 시작·종료일은 유지. |
| `PUT /api/groups/{groupId}/recurring-schedule/calendar-range` | LEADER | 정기 규칙 **전체**의 표시 시작·종료일을 갱신. 이력 구간의 경계는 바꾸지 않음. |
| `DELETE /api/groups/{groupId}/recurring-schedule/scoped` (신규) | LEADER | 삭제 범위를 명시하고 해당 이력 구간과 현재 embedded 값을 함께 갱신. 구체적 삭제 범위 동작은 구현 전 인수 기준으로 확인한다. |
| 기존 `PUT/DELETE /api/groups/{groupId}/recurring-schedule` | LEADER | 기본 설정에서는 `CALENDAR_CLIENT_OUTDATED`(409)로 차단한다. 배포 전 호환 설정을 켰을 때에만 구형 변경을 이력에 함께 기록한다. |
| 기존 `PUT /api/groups/{groupId}/session-schedule` | LEADER | 구버전 요청도 유지한다. 새 화면에서는 모임 정보 저장과 분리하며 최신 세션 일정을 달력에 반영한다. |

개별 일정 예시 요청:

```json
{
  "title": "가을 번개 모임",
  "startDate": "2026-10-17",
  "endDate": "2026-10-18",
  "allDay": false,
  "startTime": "14:00:00",
  "endTime": "18:00:00",
  "location": null,
  "description": "모여서 함께 작업해요."
}
```

새 범위 선택 명령에는 `applyScope`가 필수다. 구버전 프런트가 보내는 기존 `PUT/DELETE /recurring-schedule`에는 이 필드가 없으므로 **기존 경로를 곧바로 필수 필드 계약으로 바꾸지 않는다.** `/scoped`를 새 계약으로 분리해 구버전 요청과 구분한다. 새 달력 공개 후 기존 경로로 들어오는 정기 일정 수정은 저장하지 않고 오류로 거절한다. 공개 전 전환기 처리는 운영 위험 점검에서 확정한다. 새 명령의 `ALL`은 모든 이력 구간의 요일·시각을 바꾸되 날짜 경계를 유지하고, `PREVIOUS_RULE`은 현재 C 구간 전체를 바꾸며, `FROM_TODAY`는 오늘 경계에서 현재 구간을 나눈 뒤 오늘 이후만 바꾼다. 과거 B 구간 직접 수정은 `periodId`를 받는 별도 API로 분리한다. 전체 시작·종료일은 별도 API에서 수정하므로 이력 구간과 겹치는 날짜 처리 없이 수정할 수 있다. 신규 모임 생성에서는 개설일을 전체 시작일과 최초 이력 구간 시작일로 사용한다.

| 현재 규칙 변경 범위 | A→B→C에서 D로 바꿀 때 | 기간 경계 |
| --- | --- | --- |
| `ALL` | A·B·C 구간 모두 D의 요일·시각으로 갱신 | 기존 경계 유지 |
| `PREVIOUS_RULE` | 현재 C 구간만 D의 요일·시각으로 갱신 | C의 시작일 유지 |
| `FROM_TODAY` | 오늘 이전의 A·B·C는 유지하고 오늘 이후에 D 적용 | 오늘을 기준으로 C를 분할 |

새 범위 선택 변경 요청에는 기존 `daysOfWeek`, `startTime`, `endTime`과 `applyScope`를 담는다. `PUT /recurring-schedule/periods/{periodId}`는 선택한 과거 구간의 `daysOfWeek`, `startTime`, `endTime`만 받는다. `PUT /recurring-schedule/calendar-range`는 `startDate`(필수)와 `endDate`(무기한이면 `null`)만 받는다. 새 범위 선택 삭제 요청에도 `applyScope`를 필수로 받는다. 삭제 시 `ALL`은 현재·과거 정기 묶음을 모두 달력에서 숨기고 모임 개설일부터 선택 날짜의 유동적 운영 안내를 제공한다. `PREVIOUS_RULE`은 현재 구간을 지우며, `FROM_TODAY`는 오늘 이후만 지운다. 두 범위는 삭제 뒤의 유동적 시작일을 기록한다. 이후 현재 `groups.recurringSchedule`도 결과에 맞춰 갱신한다.

## 향후 참석·외부 모집 확장을 위한 경계

이 절은 **이번 구현의 기능 범위가 아니다.** 확장할 때 현재 일정 데이터를 옮기거나 그룹 가입과 일정 참석을 혼동하지 않도록 현재 설계의 경계만 정한다.

- `group_event`는 달력 화면에 종속되지 않은 **모임 소속 개별 일정**이다. 달력과 장래 홈·목록 화면은 같은 `group_event.id`를 참조하며 별도의 일정 사본을 만들지 않는다. `calendar` API는 정기·세션·개별 일정을 합치는 조회 모델로 둔다.
- `group_event.event_type`은 `INDIVIDUAL` 또는 하루짜리 `REGULAR_MEETING`을 구분한다. 기존 행과 eventType을 생략한 구버전 요청은 `INDIVIDUAL`로 처리해 기존 개별 일정 데이터를 유지한다. 날짜별 정기 모임은 별도 row를 가지므로 RSVP가 추가될 때 안정적인 일정 ID를 제공한다.
- `group_event.event_status`는 `AUTO`, `UPCOMING`, `COMPLETED`를 저장한다. `AUTO`는 조회 날짜 기준으로 상태를 계산하고, 모임장이 지정한 두 값은 수동 변경으로 유지한다.
- 반복 회차 예외는 `group_event`의 `recurring_series_id`, `recurring_period_id`, `recurrence_source_date`를 함께 저장한다. 한 시리즈의 원래 날짜당 한 행만 허용하고, 삭제된 예외 행도 원래 반복 발생을 숨기는 tombstone으로 보존한다. 이동한 예외는 `seriesId + sourceDate` 공개 키와 `group_event.id`를 유지한다.
- 이번 개별 일정의 설명과 장소는 기존 합의대로 현재 그룹원에게만 제공한다. 장래 외부 모집용 공개 상세는 별도 공개 정보와 권한 정책을 명시적으로 추가한다. 지금의 비공개 설명·장소가 공개 목록이나 신청 API에서 자동 노출되도록 만들지 않는다.
- 기존 `GroupRecruitment`·`Registration`은 **그룹 가입**을 처리하며 승인 시 `GroupMember`를 만든다. 장래 일정 RSVP·외부 신청은 일정 참석 도메인으로 분리한다. 일정 신청만으로 그룹원이 되지 않게 한다. 참석 인원 제한, 대기·승인 상태, 중복 신청, 취소 및 정원 경쟁 처리는 그 도메인에서 한 트랜잭션으로 정의한다.
- 미래의 모임 주최 단기 세션은 모임이 소유한 `group_event`에 모집·공개 정책을 연결하는 방향이다. 기존 일정에 모집을 추가하는 경로와, 일정과 모집을 처음부터 함께 생성하는 경로를 모두 지원한다. 두 경로 모두 같은 `group_event.id`로 달력·홈·목록을 연결하며 별도 일정 사본을 만들지 않는다. 함께 생성할 때는 일정과 모집의 생성이 한 트랜잭션에서 성공하거나 함께 롤백되어야 한다. 이를 새로운 `GroupType.SESSION` 모임이나 그룹 가입 모집으로 표현하지 않는다.
- 정기 발생 건은 조회 시 계산하지만 `group_recurring_series.id + 발생 날짜`를 안정적인 식별 키로 사용한다. 이력 구간의 `periodId`는 수정 대상을 찾는 데만 사용한다. 장래 각 발생일에 RSVP를 붙일 때는 묶음과 날짜를 기준으로 필요한 발생 건만 영속화할 수 있다. 요일 변경으로 예약된 발생일이 사라질 때의 취소·이동 정책은 RSVP 기능 도입 전에 확인한다. 이번 단계에서는 발생 건 전체를 무기한 DB에 미리 만들거나 사용하지 않는 RSVP·모집 테이블을 추가하지 않는다.
- 장래 마이페이지 개인 달력도 모임 일정·참석 정보의 **조회 모델**로 만든다. 일정 사본을 사용자별로 만들지 않고, 모임 소속과 추후 RSVP 같은 근거를 통해 같은 개별 일정 ID·정기 발생 키를 모아 조회한다. 어떤 모임 일정이 개인 달력에 자동 포함되는지는 별도 제품 결정으로 남긴다. 구현 시에는 그룹마다 달력 API를 하나씩 호출하는 방식 대신 날짜 범위와 접근 가능한 그룹을 기준으로 묶어 조회할 수 있게 서비스 경계를 둔다.

## 권한·오류·검증

- 공개 달력 경로만 `SecurityConfig`의 공개 GET에 추가한다. 개별 일정 상세와 편집용 정기 규칙 조회는 인증 및 현재 그룹원/모임장 검사를 각각 수행한다.
- 목록에서 숨긴 정보를 프런트에서만 가리지 않고 서버 응답 자체에서 제외한다. 개별 일정 상세·과거 장소 조회는 매 요청에서 현재 그룹원 여부를 확인하며, 다른 모임의 `eventId`나 `periodId`를 조합한 요청은 대상 모임에서 존재하지 않는 것으로 처리한다. 공개 상세와 그룹원 전용 상세는 서로 다른 DTO를 사용한다.
- 모든 변경은 현재 모임장만 허용하며, 종료된 모임은 기존 `GROUP_ENDED`로 거절한다. 대상 일정이 다른 모임 소속이면 해당 모임에서 존재하지 않는 것으로 처리한다.
- 날짜 순서, 종일·시각 조합, 필수 설명, 최대 길이, 조회 범위는 서버에서도 검증한다. 오류·응답 봉투는 기존 공통 API 계약을 따른다.
- 새 상세·편집 화면의 그룹원 전용 조회 캐시는 회원 ID와 인증 세션 버전으로 구분하고 로그아웃·계정 전환·권한 변경 때 제거한다. 공개 달력 목록과 비공개 상세 캐시는 섞지 않는다. 설명·장소는 분석 이벤트·URL·서버 로그에 넣지 않고, 화면 기록의 마스킹을 검증한다.
- 새 개별 일정과 정기 묶음의 편집은 조회한 `version`을 조건으로 보낸다. 버전이 바뀌었으면 덮어쓰지 않고 충돌 오류를 반환해 새 내용을 다시 불러오게 한다. 과거 기간 수정도 부모 묶음 버전을 증가시킨다. 장소 이력·기간 이력·현재 값 변경은 각각 동일 트랜잭션으로 묶는다.

## 구현 전 확인

과거 정기 발생 건을 누르면 **그날 적용됐던 규칙**을 모달에 불러와 그 구간의 요일·시각만 편집한다. 범위 수정 API와 모달, 기존 그룹 보정 검증, 그룹 삭제·과거 규칙 변경의 트랜잭션 테스트는 구현 중이다. 구현 중 새로 드러나는 제품 정책은 임의로 채우지 않고 사용자에게 확인한다.
