# 테스트 컨벤션

> 이 문서는 구속력 있는 팀 컨벤션 모듈이다.
> 인덱스: [team-convention.md](../team-convention.md)

## TDD 개발 원칙

- 프로젝트 개발은 테스트 주도 개발(TDD)을 기본 방식으로 한다.
- 기능 개발과 버그 수정은 Red-Green-Refactor 순환으로 진행한다.
- Red: 변경하려는 동작을 표현하는 가장 작은 적절한 테스트를 먼저 작성하고
  실패를 확인한다.
- Green: 테스트를 통과시키는 데 필요한 최소한의 프로덕션 코드를 작성한다.
- Refactor: 모든 테스트가 통과하는 상태에서 중복과 구조를 개선한다.
- 구현을 먼저 작성하고 테스트를 사후 추가하는 방식은 TDD로 보지 않는다.
- 버그 수정은 문제를 재현하는 실패 테스트를 먼저 추가하고, 수정 후 회귀
  테스트로 유지한다.
- 문서나 단순 설정처럼 실행 동작을 검증할 수 없는 변경에는 TDD를 억지로
  적용하지 않고 변경 성격에 맞는 검증을 수행한다.

## 기본 테스트 구성

- 모든 API 기능은 RestAssured 인수 테스트를 작성한다.
- 서비스와 레포지토리가 협력하는 유스케이스는 통합 테스트를 작성한다.
- 도메인에 로직이 있으면 도메인 단위 테스트를 작성한다. 로직이 없으면 생략할 수 있다.
- 그 밖의 단위 테스트는 개발자가 필요성을 판단해 추가한다.
- 슬라이스 테스트와 Controller 단위 테스트는 기본 필수가 아니다.
- 다만 검증하려는 위험을 효과적으로 격리하거나 빠른 피드백을 제공하고, 비용 대비
  시도할 가치가 있다고 판단하면 도입 근거와 범위를 설명해 적극 추천한다.
- Controller 단위 테스트는 API 개수 같은 기계적 기준으로 강제하지 않는다.
- Repository 테스트는 복잡한 쿼리나 저장 로직이 있을 때 도입한다.

## 테스트 대역

- 결제 등 외부 연동은 Stub 또는 Mock으로 격리한다.
- 내부 분기와 상태 흐름이 많아 협력 과정 검증이 중요하면 Fake 객체를 고려한다.

## 작성 규칙

- 테스트 메서드명은 영문 camelCase로 작성한다.
- 메서드명은 `@DisplayName`의 의미와 일치시킨다.

```java
@DisplayName("과거의 데이터는 예약할 수 없다.")
void pastDateCannotReserve() {
    // Given

    // When

    // Then
}
```

- Given/When/Then은 테스트 코드 안의 주석으로 구분한다.
- Spring Context를 올리는 테스트는 `@DirtiesContext`로 컨텍스트를 폐기하지 않는다.
- 인수 테스트 데이터는 truncate 쿼리를 실행하는 `@Sql`로 초기화해 테스트 간 격리를 보장한다.
- `@DirtiesContext` 대신 `@Sql`을 사용해 Spring Context 캐시를 유지한다.
