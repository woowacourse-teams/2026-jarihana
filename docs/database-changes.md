# 배포 중 DB 변경 규칙

Blue-Green 배포 중 구버전과 신버전은 같은 DB를 사용한다. 앱 롤백은 DB 스키마와 이미 저장한
데이터를 되돌리지 않는다. 개발자와 리뷰어는 변경된 DB에서 직전 배포 버전의 조회·저장과
신버전 데이터 처리가 가능한지 PR에서 확인한다. 이 확인을 전제로 main 머지 후 자동 배포한다.

## Expand–Contract

1. **Expand**: 기존 컬럼·제약을 유지하며 새 구조를 추가한다. 구버전 INSERT가 새 필드를
   채우지 않아도 동작하는지 확인한다. nullable 컬럼 추가라고 해서 모든 변경이 안전한 것은 아니다.
2. **전환**: 필요하면 양쪽 컬럼에 기록하고 기존 데이터를 나눠 채운다. 구버전이 계속 쓰는 데이터와
   신버전이 읽는 데이터가 어긋나지 않게 한다. 필드 형식·enum·저장 의미 변경도 호환성 대상이다.
3. **Contract**: 모든 실행 앱과 백그라운드 작업이 이전 구조를 사용하지 않는지 확인한 후
   별도 PR로 제거한다. 제거 이후 허용하는 앱 롤백 범위를 명시한다. 경과 시간만으로 자동 삭제하지 않는다.

예를 들어 `name`을 `display_name`으로 바꿀 때는 먼저 새 컬럼을 추가하고 전환 코드를 배포한다.
기존 앱이 쓰는 `name`을 바로 rename/drop하지 않는다. 구버전과의 공존·롤백 필요가 없어졌을 때
별도 제거 PR을 만든다. 스키마뿐 아니라 실제 데이터의 양방향 처리 가능성을 확인한다.

## PR·검증

- DB 변경 PR은 공통 PR 템플릿의 호환성 근거·검증 방법·롤백 범위를 작성한다.
- 이미 적용한 Flyway 파일은 수정·삭제하지 않고 후속 버전을 추가한다. 기존 환경의 이력 충돌을
  조정해야 한다면 대상 환경·checksum·조정 이유를 별도 운영 절차로 검토한다.
- 대량 backfill, NOT NULL·FK 추가, 타입 변경은 잠금과 작업 시간을 검토한다. 요청 경로에서
  장시간 migration을 실행하는 것으로 판단되면 배포 PR과 분리해 실행 순서를 설계한다.
- CI는 위험한 SQL·기존 migration 변경을 **검토 대상으로 알린다**. 정규식 기반 보조 검사이므로
  주석에 대한 오탐·동적 SQL 등의 누락이 가능하다. 경고 없음이나 Flyway 성공은 호환성 보증이 아니다.
- 직전 앱 이미지와 새 스키마의 핵심 조회·저장을 실제로 검증하는 CI는 후속 작업이다.
  이번 CI가 이 검증을 수행했다고 표시하지 않는다.

호환되지 않는 변경은 자동 앱 롤백이 가능한 일반 배포로 진행하지 않는다. Expand–Contract로
분리하거나, 별도 작업 계획에서 점검 시간·복구·데이터 보존을 결정한다.
