# 코드 리뷰 정책 — 1주 파일럿

## 목적과 기간

코드 리뷰의 목적은 설계 합의 자체를 반복하는 것이 아니라, 구현에서 놓친 버그와 모듈 경계의 영향을 발견하는 것이다. 담당자를 분명히 하고 응답 시점을 예측 가능하게 만들어 대기 시간을 줄인다.

이 정책은 **2026-10-26(월)부터 2026-10-30(금)까지** 1주간 시험한다. 다음 주 회고에서 리뷰 대기 시간, 슬롯 준수율, 핑퐁 횟수, 리뷰로 발견한 버그, 리뷰 부담을 확인하고 유지·완화 여부를 정한다.

## 어떤 PR에 리뷰가 필요한가

아래 중 하나라도 해당하면 작성자가 아닌 사람의 리뷰 1개를 요청한다.

1. `feat` 변경: 작성자 자신의 담당 모듈이어도 리뷰를 받는다.
2. 다른 담당 모듈의 동작이나 계약을 함께 변경하는 교차 모듈 PR.
3. 변경 유형과 관계없이 고위험 변경.

자기 담당 모듈 안의 저·중위험 `fix`, `chore`, `docs`, `refactor`는 셀프 머지할 수 있다. 단, 고위험 기준에 해당하거나 다른 담당 모듈의 동작을 바꾸면 리뷰 대상이다. `feat`와 고위험 조건이 겹쳐도 기본 리뷰 수는 1명이며, 독립된 모듈 불변식을 각각 확인해야 할 때만 추가 리뷰어를 요청한다.

### 고위험 변경

다음 변경은 고위험으로 분류한다.

- DB 마이그레이션, 데이터 삭제·백필, 데이터 보존·복구 방식 변경
- 인증·인가, 소유권 검사, 토큰·세션·개인정보 보호 변경
- 정원·신청 상태·멤버십·일정 등 핵심 상태 전이, 동시성, 트랜잭션, 멱등성 변경
- 호환성을 깨는 API·이벤트·저장 데이터 계약 변경
- 배포, 인프라, 시크릿, 권한, CI 또는 운영 접근 경로 변경
- 브랜치 보호 규칙, `CODEOWNERS`, 리뷰 승인 요건 또는 병합 정책 변경
- 시간대·반복 일정·재시도·백그라운드 작업의 실행 보장 변경

마이그레이션, 인증·인가, 인프라처럼 경로 자체가 위험을 강하게 시사하는 변경은 자동으로 고위험 후보로 올린다. 그 외에는 전체 diff와 호출 흐름에서 확인한 근거를 PR에 적는다. 위험도를 확정하기 어렵다면 낮음으로 축소하지 말고 리뷰를 요청한다.

## 담당자와 리뷰어 선택

아래 담당자표는 AI가 기능 흐름의 담당자를 찾는 기준이다. 코드 경로만 기계적으로 대입하지 말고 실제로 바뀐 API와 도메인 동작을 함께 본다.

| 영역 | 주 담당자 | 백업 담당자 | 우선 책임 |
| --- | --- | --- | --- |
| A · 인증·회원·공통 기반 | 요크 `@Sauter001` | 이삭 `@5jonyuk` | OAuth, 토큰·세션, 회원 가입·인증 기반 |
| B · 그룹 명령·일정·이미지 | 파도 `@choubung` | 에덴 `@RealTake` | 그룹, 일정, 이미지 및 그룹 활동 기록 |
| C · 모집·신청·멤버십 명령 | 에덴 `@RealTake` | 파도 `@choubung` | 모집, 신청 상태, 소속·초대·멤버십 |
| D · 조회·검색·집계 | 이삭 `@5jonyuk` | 요크 `@Sauter001` | 여러 도메인을 가로지르는 조회·검색·집계 |

AI는 A의 `auth`, `member`, `common`; B의 `group`, `image`, `share`, `activitypost`; C의 `recruitment`, `registration`, `groupmember`, `invitation`을 출발점으로 삼되 실제 변경 흐름으로 확인한다. D는 모든 `query` 디렉터리의 일괄 소유자가 아니다. 여러 도메인을 가로지르는 조회·검색·집계가 바뀔 때 선택한다. 이 표로 책임을 분명히 할 수 없는 영역은 임의 배정하지 말고 PR에 `담당 영역 확인 필요`라고 표시해 팀이 정한다.

- 리뷰 대상 모듈을 작성자가 소유한다면 그 모듈의 백업 담당자를 우선 요청한다.
- 교차 모듈 PR은 변경의 중심 또는 가장 위험한 동작을 담당하는 사람 1명을 우선 요청한다. 별개의 핵심 불변식이 각각 바뀌는 경우에만 추가한다.
- 프론트엔드 또는 인프라만의 변경은 네 명 중 현재 열린 리뷰가 가장 적은 사람을 우선하고, 동률이면 무작위로 한 명 선택한다. 리뷰 부하를 확인할 수 없다면 동률로 취급해 한 명을 선택하고 그 사실을 PR에 적는다.
- AI는 리뷰어를 추천·요청할 수 있지만 승인할 수 없다. PR 작성자를 리뷰어로 지정하지 않는다.

담당자와 경로의 매핑은 [`review-owners.yml`](review-owners.yml)에 기계가 읽을 수 있는 형태로 둔다. 모듈 전체를 `CODEOWNERS`에 등록하면 GitHub가 해당 경로가 바뀐 모든 PR에 담당자 리뷰를 자동 요청하므로 `feat`만 리뷰하는 조건이나 셀프 머지 예외를 표현할 수 없다. 따라서 이 파일럿에서는 `CODEOWNERS`를 조건부 배정 수단으로 사용하지 않는다.

## 리뷰 마감 슬롯

슬롯 시각은 리뷰를 시작하는 시간이 아니라 **리뷰를 마칠 목표 시각**이다. 기준 시간대는 한국 표준시(KST)다.

| PR 생성 시각 | 리뷰 마감 |
| --- | --- |
| 영업일 10:30 이전 | 당일 10:30 |
| 영업일 10:30 이상, 17:30 미만 | 당일 17:30 |
| 영업일 17:30 이상 또는 다음 영업일이 아닌 날 | 다음 영업일 10:30 |

마감 슬롯은 리뷰 대상 PR에 적용한다. 해당 시각에 리뷰가 어렵다면 작성자와 리뷰어가 PR에서 새 마감 시각을 합의하고, 아무 응답 없이 다음 슬롯으로 넘기지 않는다. 리뷰어 알림은 현재 연결된 Slack/GitHub 연동을 이용해 담당자를 직접 언급하는 것을 목표로 한다. 연동 설정이 확인되지 않으면 PR 리뷰 요청 알림을 사용하고, 별도의 Slack 자동 발송이 설정된 것처럼 안내하지 않는다.

## 리뷰 코멘트와 수정 확인

- `blocker`: 수정 전 머지 불가. 이 경우에만 GitHub의 `Request changes`를 사용한다.
- `question`: 의도·근거 확인. 답변만으로 해결되면 수정은 요구하지 않는다.
- `suggestion`: 선택적 제안. 작성자가 반영 여부를 결정한다.
- `nit`: 사소한 의견. 머지를 막지 않는다.

리뷰어는 가능한 한 코멘트를 한 번에 모아 전달한다. 작성자가 수정한 뒤에는 PR 전체를 처음부터 다시 보지 않고, blocker와 그에 영향을 받은 변경만 확인한다. `question`, `suggestion`, `nit`만 남았다는 이유로 머지를 막지 않는다.

## 작성 AI가 PR 본문에 남길 내용

PR 작성 AI는 템플릿의 `리뷰 요약`을 다음 원칙으로 채운다.

1. base 브랜치와 비교한 전체 diff를 읽고, 진입점에서 핵심 처리·저장소·외부 연동까지 변경 흐름을 요약한다.
2. 실제로 영향받는 모듈과 API·데이터·상태 전이를 표시한다. 특히 권한 검사, 동시성, 트랜잭션, 멱등성, 실패·재시도 경로를 확인한다.
3. 변경 유형과 위험도, 리뷰 필요 여부를 이 정책에 따라 분류하고 구체적인 근거를 쓴다. 불명확한 부분은 불확실하다고 밝힌다.
4. 리뷰가 필요하면 주 담당자/백업 규칙과 현재 열린 리뷰 부하를 고려해 사람 리뷰어를 추천한다. GitHub 연동을 사용할 수 있으면 리뷰 요청까지 수행하고, 불가능하면 작성자가 요청할 수 있도록 이름을 남긴다.
5. 실제 실행한 테스트·검증만 기재한다. 실행하지 않은 테스트를 통과했다고 쓰지 않으며, 사람이 확인해야 하는 위험과 미검증 사항을 별도로 남긴다.

AI 요약은 리뷰를 대체하지 않는다. 리뷰어는 요약의 코드 위치와 위험 근거를 표본 확인하고, 코멘트를 통해 실제 버그나 놓친 조건을 찾는다.

## 현재 GitHub 설정과 적용 한계

2026-10-23 확인 기준으로 현재 저장소 ruleset은 모든 PR에 승인 1개를 요구하고 있다. 따라서 위 정책의 셀프 머지 예외는 문서만 반영해서 활성화되지 않는다. 반대로 전역 승인 수를 0으로 내리면 `feat`와 고위험 PR의 승인을 GitHub가 자동으로 강제하지 못한다. `CODEOWNERS`도 PR 유형에 따른 조건부 승인 기능은 제공하지 않는다.

그러므로 파일럿을 시작하기 전 저장소 관리자는 다음 중 운영 방식을 명시적으로 선택해야 한다.

1. 현재 승인 1개 규칙을 유지해 보수적으로 파일럿을 시작한다. 이 경우 모든 PR 승인이 필요하므로 셀프 머지는 아직 불가능하다.
2. 셀프 머지를 허용하도록 규칙을 완화하고, `feat`·고위험 리뷰는 파일럿 기간에 사람의 리뷰 요청과 승인 전 머지 금지 절차로 운영한다. 이 경우 조건부 승인은 자동 강제가 아니라 팀 프로세스다.

조건부 승인 자동화는 신뢰할 수 있는 기준 브랜치 코드에서 PR 유형·변경 경로·승인 상태를 판정하는 별도 검증을 설계·검증한 뒤 도입한다. 이 문서나 PR 템플릿만으로 자동 enforcement가 된다고 간주하지 않는다.
