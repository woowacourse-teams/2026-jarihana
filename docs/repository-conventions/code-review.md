# 코드 리뷰 정책 — 1주 파일럿

## 목적과 기간

코드 리뷰의 목적은 구현에서 놓친 버그와 모듈 경계의 영향을 발견하는 것이다. 작성 AI는 코드와 테스트를 검토하고, 사람은 본문에서 바뀌는 동작과 선택·예외·위험을 판단한다. 이미 합의된 설계를 반복하지 않고 이번 변경에서 확인할 판단에 집중한다. 담당자를 분명히 하고 응답 시점을 예측 가능하게 만들어 대기 시간을 줄인다.

이 정책은 **2026-10-26(월)부터 2026-10-30(금)까지** 1주간 시험한다. 다음 주 회고에서 리뷰 대기 시간, 슬롯 준수율, 핑퐁 횟수, 리뷰로 발견한 버그, 리뷰 부담을 확인하고 유지·완화 여부를 정한다.

## 어떤 PR에 리뷰가 필요한가

아래 변경은 작성자가 아닌 사람의 승인 1개가 필요하다.

1. PR 작성 AI가 위험도를 `high`로 분류한 변경.
2. 위험도 선언이 `low` 또는 `medium`이어도 자동 고위험 경로가 변경된 PR.

위험도 선언이 없거나 형식이 잘못된 경우에는 사람 승인을 요구하지 않고, PR 작성자가 위험도를 바로잡을 때까지 게이트를 통과시키지 않는다.

`feat` 여부와 작성자의 담당 모듈 여부만으로 승인을 요구하지 않는다. 위험도가 `low` 또는 `medium`이고 자동 고위험 경로에 해당하지 않으면 `feat`, `fix`, `chore`, `docs`, `refactor`를 포함해 셀프 머지할 수 있다. 교차 모듈 변경도 그 사실만으로 승인을 요구하지 않는다. 영향받은 모듈 담당자에게 변경을 알리되, 공식 리뷰 요청이나 답변 대기를 만들지 않는다.

### 고위험 변경

다음 변경은 고위험으로 분류한다.

- DB 마이그레이션, 데이터 삭제·백필, 데이터 보존·복구 방식 변경
- 인증·인가, 소유권 검사, 토큰·세션·개인정보 보호 변경
- 정원·신청 상태·멤버십·일정 등 핵심 상태 전이, 동시성, 트랜잭션, 멱등성 변경
- 호환성을 깨는 API·이벤트·저장 데이터 계약 변경
- 배포, 인프라, 시크릿, 권한, CI 또는 운영 접근 경로 변경
- 브랜치 보호 규칙, `CODEOWNERS`, 리뷰 승인 요건 또는 병합 정책 변경
- 시간대·반복 일정·재시도·백그라운드 작업의 실행 보장 변경

다음 경로는 PR에 선언한 위험도와 관계없이 자동으로 고위험 처리한다.

- `backend/db/migrations/**`, `backend/src/main/resources/db/migration/**`
- 백엔드 인증·보안 구현, 토큰·OAuth·보안 설정 파일
- 프론트엔드 인증·보안·OAuth·토큰 경로
- `infra/**`, `.github/workflows/**`, `backend/Dockerfile`, `frontend/netlify.toml`
- 백엔드 운영 `application*.yaml` 설정
- `CODEOWNERS`, `AGENTS.md`, PR 템플릿, 리뷰 정책·담당자 매핑
- `.github/scripts/`의 `review-gate.cjs`, `publish-review-gate.cjs`, `auto-assign-reviewer.cjs`, `slack-review-notifications.cjs`

그 외 의미상 고위험 변경은 PR 작성 AI가 전체 diff와 호출 흐름을 보고 `high`로 선언해야 한다. 위험도를 확정하기 어렵다면 `low`나 `medium`으로 낮추지 않는다. 자동화는 코드의 의미를 독립적으로 이해하지 못하므로, 경로에 드러나지 않는 의미상 위험을 AI가 잘못 낮게 분류하면 자동으로 찾아내지 못한다. 이 한계는 파일럿 회고에서 따로 점검한다.

## 담당자와 리뷰어 선택

아래 담당자표는 AI가 기능 흐름의 담당자를 찾는 기준이다. 코드 경로만 기계적으로 대입하지 말고 실제로 바뀐 API와 도메인 동작을 함께 본다.

| 영역 | 주 담당자 | 백업 담당자 | 우선 책임 |
| --- | --- | --- | --- |
| A · 인증·회원·공통 기반 | 요크 `@Sauter001` | 이삭 `@5jonyuk` | OAuth, 토큰·세션, 회원 가입·인증 기반 |
| B · 그룹 명령·일정·이미지 | 파도 `@choubung` | 요크 `@Sauter001` | 그룹, 일정, 이미지 및 그룹 활동 기록 |
| C · 모집·신청·멤버십 명령 | 에덴 `@RealTake` | 파도 `@choubung` | 모집, 신청 상태, 소속·초대·멤버십 |
| D · 조회·검색·집계 | 이삭 `@5jonyuk` | 에덴 `@RealTake` | 여러 도메인을 가로지르는 조회·검색·집계 |

AI는 A의 `auth`, `member`, `common`; B의 `group`, `image`, `share`, `activitypost`; C의 `recruitment`, `registration`, `groupmember`, `invitation`을 출발점으로 삼되 실제 변경 흐름으로 확인한다. D는 모든 `query` 디렉터리의 일괄 소유자가 아니다. 여러 도메인을 가로지르는 조회·검색·집계가 바뀔 때 선택한다. 이 표로 책임을 분명히 할 수 없는 영역은 임의 배정하지 말고 PR에 `담당 영역 확인 필요`라고 표시해 팀이 정한다.

- 고위험 PR의 중심 모듈을 작성자가 소유한다면 그 모듈의 백업 담당자를 우선 요청한다.
- 고위험 교차 모듈 PR은 변경의 중심 또는 가장 위험한 동작을 담당하는 사람 1명을 우선 요청한다. 별개의 핵심 불변식이 각각 바뀌는 경우에만 추가한다.
- 저·중위험 교차 모듈 PR은 담당자에게 요약을 알리되, 공식 리뷰 요청이나 승인 대기를 만들지 않는다.
- 프론트엔드 또는 인프라만의 변경은 네 명 중 현재 열린 리뷰가 가장 적은 사람을 우선하고, 동률이면 무작위로 한 명 선택한다. 리뷰 부하를 확인할 수 없다면 동률로 취급해 한 명을 선택하고 그 사실을 PR에 적는다.

### 리뷰어 자동 배정

`.github/workflows/auto-assign-reviewer.yml`은 PR이 `develop` 또는 `main`을 대상으로 열리거나 다시 열릴 때, 초안에서 준비 완료로 바뀔 때, 커밋이나 본문이 갱신될 때 실행한다. 초안 PR은 준비 완료 전까지 배정을 미룬다. 이 자동화가 기본 브랜치에 반영된 뒤부터 작동한다.

제목만 수정한 이벤트는 리뷰어 배정을 건너뛴다. 게이트는 제목 수정도 재평가하며 현재 head의 유효 승인은 그대로 인정한다. 모든 게이트 실행은 같은 동시 실행 그룹에서 직렬화하고, 대기 중 새 이벤트가 합쳐져도 열린 PR 전체를 다시 조회한다. 예약·리뷰 이벤트·수동 실행에 의한 게이트 평가는 유지한다.

- 위험도가 `high`로 선언됐거나 조건부 승인 게이트가 고위험으로 판정하는 경로가 있으면 GitHub에서 리뷰어 1명을 공식 요청한다. 저·중위험이며 고위험 경로도 없는 PR은 공식 리뷰 요청 없이 셀프 머지 정책을 유지한다.
- 자동화는 PR 본문의 `자동 배정 리뷰어:` 항목에 작성 AI가 적은 팀 GitHub 아이디를 먼저 사용한다. 비어 있거나 팀원이 아니거나 작성자 본인이면, 변경 경로가 한 모듈에만 명확히 대응할 때 주 담당자를 고르고 작성자가 주 담당자라면 백업 담당자를 고른다.
- 프론트엔드·인프라만 바뀐 PR은 현재 열린 리뷰 요청이 가장 적은 팀원을 고르고, 동률이면 무작위로 한 명 고른다.
- 경로로 리뷰어를 추정할 때는 모든 변경 경로가 동일한 모듈 한 개에 대응해야 한다. `backend/src/test/java/`의 테스트는 대응하는 `backend/src/main/java/` 패키지와 같은 모듈로 본다. 담당 미정 코드·테스트·설정 등 매핑되지 않은 경로가 하나라도 섞이거나, 여러 모듈에 걸치거나, GitHub 조회 한도로 파일 목록이 불완전하면 추정 배정을 멈추고 경고를 남긴다. 작성 AI가 실제 변경 흐름으로 담당자를 확인해 본문에 명시적으로 추천하거나, 작성자가 수동 요청한다.
- 이미 개인 또는 팀 리뷰 요청이 있으면 바꾸거나 중복 요청하지 않는다. 이후 커밋에서 변경 범위가 달라져 담당자를 바꿔야 한다면 수동으로 조정한다.
- 대기 중인 리뷰 요청이 없어도 GitHub에서 현재 head와 리뷰 이력을 다시 조회한다. 현재 head에 작성자 외 쓰기 권한자(`write`·`maintain`·`admin`)의 유효한 승인이 있으면 추천 리뷰어가 바뀌어도 새 요청이나 Slack 알림을 만들지 않는다. 이전 head의 승인, 취소되거나 같은 head의 후속 리뷰로 대체된 승인, 작성자 본인·읽기 권한자의 승인은 제외한다. 승인·권한 조회에 실패하면 새 요청 없이 실행을 실패시켜 확인 후 재시도한다.
- 리뷰어 요청은 승인을 뜻하지 않는다. 병합 차단 여부는 별도의 `Conditional Review Gate`가 판단한다. 자동 배정에 성공하면 같은 워크플로의 알림 job이 실제 배정 결과를 받아 Slack으로 직접 멘션한다. 사람이 수동 요청한 리뷰는 별도 Slack 워크플로가 `review_requested` 이벤트로 알린다.

GitHub의 기본 토큰으로 만든 리뷰 요청은 다른 워크플로를 실행시키지 않으므로 자동 배정 알림은 이벤트 연쇄에 의존하지 않는다. Slack 스크립트를 추가하는 #452와 자동 배정 #457이 모두 기본 브랜치에 있어야 연결이 완성된다. 알림 job만 실패하면 GitHub Actions에서 실패한 job을 재실행해 이미 요청한 리뷰어에게 알림을 재시도한다.

워크플로는 `pull_request_target`에서 기본 브랜치의 자동화 코드만 실행하며 PR 브랜치 코드를 체크아웃하거나 실행하지 않는다.

담당자와 경로의 매핑은 [`review-owners.yml`](review-owners.yml)에 기계가 읽을 수 있는 형태로 둔다. `CODEOWNERS`의 자동 리뷰 요청과 코드 소유자 승인 강제는 별개 기능이다. 승인 강제를 끄면 `CODEOWNERS`가 있어도 그 자체로 승인을 요구하지 않는다. 다만 저·중위험에도 자동 리뷰 요청이 생기므로 이번 파일럿에서는 모듈 전체를 등록하지 않고 고위험 PR에만 별도 자동화로 요청한다. 고위험 판단과 승인은 조건부 게이트가 처리한다. [GitHub 공식 설명](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

## 리뷰 마감 슬롯

슬롯 시각은 리뷰를 시작하는 시간이 아니라 **리뷰를 마칠 목표 시각**이다. 기준 시간대는 한국 표준시(KST)다.

| PR 생성 시각 | 권장 리뷰 시각 | 필수 리뷰 마감 |
| --- | --- | --- |
| 영업일 14:00 이전 | — | 당일 14:00 |
| 영업일 14:00 이상, 21:00 미만 | 당일 21:00 | 다음 영업일 14:00 |
| 영업일 21:00 이상 또는 비영업일 | — | 다음 영업일 14:00 |

21:00은 가능하면 리뷰하는 권장 시각이며 필수가 아니다. 해당 시각까지 승인이 없으면 리뷰어에게 권장 알림을 한 번 보내고, 다음 영업일 14:00까지도 승인이 없으면 필수 마감 알림을 보낸다. 권장 알림을 놓쳤다면 다음 날 뒤늦게 보내지 않는다.

Slack 마감 알림은 스캔 시작과 실제 발송 직전에 현재 KST 날짜가 영업일인지 확인한다. 주말·한국 공휴일에는 지난 마감의 미발송 알림도 건너뛰며, 발송 완료 표시는 남기지 않아 다음 영업일에 다시 확인할 수 있다. 현재 날짜의 공휴일 정보를 확인할 수 없으면 영업일로 추정해 발송하지 않고 실행을 중단한다.

위험도 표기 오류만으로는 승인 마감 알림을 보내지 않는다. 본문을 수정해야 게이트를 통과할 수 있다. 자동 고위험 경로나 파일 조회 한도로 별도 승인이 필요한 경우에는 표기 오류가 있어도 승인 마감 알림 대상이다.

마감 슬롯은 리뷰 대상 PR에 적용한다. 필수 마감까지 리뷰가 어렵다면 작성자와 리뷰어가 PR에서 새 마감 시각을 합의하고, 아무 응답 없이 다음 슬롯으로 넘기지 않는다. 자동 알림은 합의한 마감을 읽지 않으므로 해당 사항은 직접 전달한다.

## 리뷰 코멘트와 수정 확인

- `blocker`: 수정 전 머지 불가. 이 경우에만 GitHub의 `Request changes`를 사용한다.
- `question`: 의도·근거 확인. 답변만으로 해결되면 수정은 요구하지 않는다.
- `suggestion`: 선택적 제안. 작성자가 반영 여부를 결정한다.
- `nit`: 사소한 의견. 머지를 막지 않는다.

리뷰어는 가능한 한 코멘트를 한 번에 모아 전달한다. 작성자가 수정한 뒤에는 PR 전체를 처음부터 다시 보지 않고, blocker와 그에 영향을 받은 변경만 확인한다. `question`, `suggestion`, `nit`만 남았다는 이유로 머지를 막지 않는다.

## 작성 AI가 PR 본문에 남길 내용

PR 작성 AI는 템플릿의 `리뷰 요약`을 다음 원칙으로 채운다.

1. base 브랜치와 비교한 전체 diff를 읽고, 진입점에서 핵심 처리·저장소·외부 연동까지 변경 흐름을 요약한다.
2. 실제로 영향받는 모듈과 API·데이터·상태 전이를 표시한다. 특히 권한 검사, 동시성, 트랜잭션, 멱등성, 실패·재시도 경로를 확인한다.
3. 변경 유형과 위험도, 승인 필요 여부를 이 정책에 따라 분류하고 구체적인 근거를 쓴다. 불명확한 부분은 불확실하다고 밝힌다.
4. 고위험이면 담당자 규칙과 현재 열린 리뷰 부하를 고려해 팀원 한 명을 추천하고, 템플릿의 자동 배정 리뷰어 항목에 GitHub 아이디와 이유를 쓴다. 자동화가 기본 브랜치에 반영되면 워크플로가 이 항목을 읽어 리뷰를 요청한다. 후보가 불명확하면 추정하지 않고 확인 필요라고 쓴다.
5. 실제 실행한 테스트·검증만 기재한다. 실행하지 않은 테스트를 통과했다고 쓰지 않으며, 사람이 확인해야 하는 위험과 미검증 사항을 별도로 남긴다.

### 사람이 본문에서 판단할 내용

승인이 필요한 PR의 `리뷰어가 확인할 내용`은 코드를 열지 않아도 판단할 수 있도록 작성한다.

- **바뀌는 동작과 예외:** 누가 어떤 상황에서 무엇을 할 수 있는지, 실패·재시도 시 어떻게 되는지 구체적으로 적는다.
- **선택과 이유:** 이번 변경에서 선택한 방식, 고려한 대안, 사용자·데이터·운영에 미치는 영향을 적는다. 이미 합의된 내용은 짧게 요약한다.
- **사람에게 묻는 판단 1~3개:** 기대 동작과 감수할 영향이 적절한지 답할 수 있는 질문을 쓴다. 실제로 열린 판단이 없다면 합의된 내용과 근거를 쓰고 억지로 질문을 만들지 않는다.
- **남은 위험과 미검증:** 구현·검증으로 아직 확인하지 못한 조건이나 결정이 필요한 부분을 숨기지 않는다.
- **추가 코드 확인 위치:** 코드가 궁금한 리뷰어를 위해 중점적으로 볼 실제 패키지·클래스 또는 파일과 그 이유를 본문에 명시한다. 코드 위치가 결정 사항과 어떤 관련이 있는지 짧게 연결한다.
- **코드·테스트 확인 경로:** 기존 코드 리뷰 지점도 남긴다. 진입점부터 핵심 분기·상태 변경·저장소·외부 연동까지 필요한 순서대로 핵심 코드 최대 3개를 링크하고 역할을 쓴다. 중요한 버그 시나리오 1~3개에 발생 조건·기대 동작·실패 영향, 실제 파일·함수 링크 및 실행한 테스트 또는 미검증 여부를 연결한다. 이 경로는 본문의 동작 설명을 확인하거나 더 깊게 살펴보고 싶을 때 사용한다.

예를 들어 정원이 1명 남았을 때 `동시에 신청한 두 사람 중 한 명만 성공하고 다른 한 명에게 마감 안내를 보여주는 정책이 맞나요?`라고 묻는다. AI는 이 동작이 구현과 테스트에 반영됐는지 별도로 확인한다. AI의 설명과 실제 구현이 항상 일치한다고 보장할 수 없으므로 불확실성이 있으면 구체적으로 밝히고, 리뷰어가 필요할 때 코드나 근거를 열어볼 수 있게 한다.

저·중위험이며 자동 고위험 경로도 없는 PR은 이 절을 `사람 검토 요청 없음 — 작성자가 확인한 핵심 동작: ...` 한 줄로 대체할 수 있다. 이 양식을 이유로 추가 승인이나 응답 대기를 만들지 않는다. 변경 커밋으로 동작이나 검증 결과가 달라지면 본문도 갱신한다.

### 작성 AI의 코드 검토

PR 작성 AI는 최종 diff와 진입점부터 저장소·외부 연동까지 실제 호출 흐름을 검토한다. 이미 읽은 diff와 맥락을 활용하고, 추가 확인이 필요한 경로만 더 읽어 중복 입력을 줄인다. 변경에 해당하는 권한 검사, 상태 전이, 동시성·트랜잭션, 실패·재시도, API·DB 호환성을 확인한다. 문제가 발견되면 수정하고, 해결하지 못했거나 확인이 어려운 위험은 PR에 남긴다. 별도 컨텍스트·에이전트는 필요한 경우에 선택하며, 실제 사용하지 않았다면 사용했다고 쓰지 않는다. 테스트는 가능한 한 결과 요약을 먼저 확인하고, 실패를 분석할 때 필요한 로그를 추가로 읽는다.

본문에는 확인한 위험과 결과, 실제 실행한 테스트·결과, 미해결 문제와 실행하지 못한 검증, 실제 검토 방식을 적는다. 테스트 통과는 기대한 동작이 올바르다는 증거와 구분한다. AI 없이 작성한 경우에는 작성자가 코드와 테스트를 검토하고 AI 미사용을 명시한다.

리뷰어는 이 설명을 바탕으로 동작과 선택에 피드백을 주고 필요하면 코드·테스트를 열어본다. 사람의 코드 검토 범위를 줄이면 구현 오류를 사람이 발견할 기회도 줄고, 작성 AI가 놓친 오류는 남을 수 있다. 자체 검토 지침만으로 AI 실행이나 검토 품질이 자동 보장되지는 않는다. 현재 게이트는 위험도·경로·승인만 검사한다.

### 고위험 PR의 AI 사용량 측정

앞으로 작성하는 고위험 PR은 토큰 사용량을 실측할 수 있으면 템플릿에 기록한다. `high` 선언뿐 아니라 자동 고위험 경로나 변경 파일 조회 한도 때문에 승인이 필요한 PR도 포함한다. 저·중위험이며 자동 고위험 경로도 없는 PR에는 이 항목을 요구하지 않는다.

기본 측정 범위는 코드 구현을 제외한 **최종 코드 검토·위험도 판단·PR 본문 작성 및 제출**이다. 모델, 입력 토큰·그중 캐시된 입력, 출력 토큰, 측정 방법과 범위를 기록한다. 숫자를 제공하지 않는 환경이나 구간을 분리할 수 없는 환경에서는 토큰을 추측하지 않는다. 측정하지 못한 값은 `미측정`과 이유를 적는다.

측정 상태는 다음처럼 구분한다.

- `측정`: 기본 범위의 실측값을 분리해 확인했다.
- `범위 혼합`: 실측값은 있지만 구현 등 다른 작업이 섞여 분리하지 못했다. 실제 포함 작업과 측정 시작·종료 시점을 적는다.
- `미측정`: 기록할 신뢰할 수 있는 실측값이 없다. 측정을 시도하지 않았는지, 시도했지만 수치가 제공되지 않거나 실패했는지 이유를 적는다. 일부 항목만 누락됐다면 해당 항목도 미측정으로 표시한다.

비교할 때 분리 측정치와 혼합 측정치를 구분한다. 캐시된 입력은 입력에 이미 포함되어 있으므로 총계에 다시 더하지 않는다. 토큰 수, 실제 비용과 구독 계정의 사용 한도는 서로 다른 값이다. 측정은 관찰 목적이며 `미측정`이나 사용량 자체로 승인·머지를 차단하지 않는다. 현재 자동화는 토큰 측정이나 이 항목의 진위를 확인하지 않는다.

#### 사용량 수집 절차

1. **범위 결정:** 고위험 PR인지 확인하고 구현이 끝난 뒤 최종 코드 검토를 시작할 때부터 위험도 판단·PR 본문 작성·제출을 마칠 때까지의 AI 호출을 대상으로 잡는다. 이전 구현의 호출은 제외하지만, 검토 중 이전 대화 내용이 입력으로 다시 전달되면 그 입력 토큰은 검토 단계에 포함된다. 추가 에이전트를 사용했다면 접근할 수 있는 사용량과 포함 여부를 기록한다.
2. **측정 가능 여부 확인:** 해당 AI 도구가 작업·턴별 실측 토큰을 제공하는지 확인한다. 같은 계측기의 누적값이 구간 전후로 제공되면 시작·종료 스냅샷의 차이를 사용할 수 있다. 중간에 계측기가 초기화되거나 다른 작업·세션이 끼면 정확한 구간 사용량으로 단정하지 않는다. 구독 계정의 기간별 남은 한도·사용률, 텍스트 길이로 계산한 추정치와 다른 도구의 계측값을 섞어 실측 토큰으로 바꾸지 않는다.
3. **집계:** 구간에 해당하는 각 모델 호출 또는 턴의 입력·캐시된 입력·출력 토큰을 수집한다. 누적값과 개별 턴값, 루트 에이전트와 하위 에이전트의 수치를 함께 쓸 때는 실제 집계 범위를 확인해 같은 사용량을 두 번 더하지 않는다. 모델이 여러 개라면 모델별 수치를 구분한다. 제공되지 않거나 실패·중단으로 누락된 항목은 `미측정`으로 남긴다.
4. **기록:** 최종 수치를 받은 뒤 PR 본문에 모델, 입력·캐시 입력·출력, 측정 방식과 실제 포함 단계·기간을 적는다. 현재 실행이 끝나야 최종 사용량이 나오는 도구라면 작성자나 별도의 수집기가 종료 후 PR을 갱신한다. 사용량을 기록하는 후속 AI 호출을 측정에 포함하지 못했다면 제외했다고 밝힌다. 수치를 아직 받지 못했다면 `미측정`이라고 쓴다.

Codex CLI에서 **별도로 시작하는 PR 작성·검토 작업**이라면 `codex exec --json`의 JSONL 이벤트 중 `turn.completed`에 포함된 `usage.input_tokens`, `usage.cached_input_tokens`, `usage.output_tokens`를 수집할 수 있다. 예를 들어 CLI로 새 검토 작업을 시작하고 `jq`가 설치되어 있다면 다음처럼 본문 초안과 완료 이벤트의 사용량을 각각 확인할 수 있다. [Codex 비대화형 실행 안내](https://developers.openai.com/codex/noninteractive/)

```bash
pr_draft_path="$(mktemp "${TMPDIR:-/tmp}/review-pr-draft.XXXXXX")"
codex exec --json -o "$pr_draft_path" "현재 PR의 최종 diff를 검토하고 PR 본문 초안을 작성하세요" \
  | jq -c 'select(.type == "turn.completed") | .usage | {input_tokens, cached_input_tokens, output_tokens}'
printf 'PR 본문 초안: %s\n' "$pr_draft_path"
```

이 예시는 초안 작성까지의 사용량이며, PR 제출을 별도로 했다면 제출 단계 포함 여부를 실제 범위에 적는다. 이 명령은 **새 작업을 실행**하며 기존 Codex 앱 대화의 특정 구간을 자동으로 가져오지 않는다. 사용량만 측정하려고 완료한 작업을 반복 실행하지 않는다. 앱이나 다른 AI 도구에서 해당 구간의 실측치를 제공하지 않으면 `미측정`으로 기록한다. 여러 턴이나 에이전트가 있다면 포함된 실행과 사용량 집계 범위를 확인하고, 포함 여부를 모르는 값은 미측정으로 구분한다.

JSONL 원본에는 대화 내용·코드·명령 출력이 포함될 수 있다. PR과 저장소에는 필요한 집계 수치와 측정 범위만 기재하고, 원본 로그나 토큰·키 등 비밀값은 올리지 않는다.

## 조건부 승인 게이트와 적용 순서

`.github/workflows/conditional-review-gate.yml`은 PR 위험도 선언, 변경 경로, 최신 승인 상태를 확인해 `Review Approval Policy`라는 커밋 상태를 게시한다. `high` 또는 자동 고위험 경로 변경은 작성자 외 쓰기 권한자의 현재 head 커밋 승인이 있어야 통과한다. 유효한 `low`/`medium`이며 자동 고위험 경로가 없는 PR은 승인 없이 통과한다. 위험도 선언이 없거나 잘못되면 승인 대신 본문 수정을 요구하며, 올바른 위험도가 입력될 때까지 상태가 실패한다.

게이트는 PR 생성·재개·커밋 갱신·본문 수정·준비 완료·닫힘 이벤트에서 재평가한다. 리뷰 제출·수정·취소는 쓰기 권한과 checkout이 없는 `Review Policy Review Events`가 신호를 보내고, 기본 브랜치의 게이트가 `workflow_run`으로 받아 재평가한다. 10분 간격 예약 실행은 이벤트 누락 시 복구용이며, 기본 브랜치에서 수동 실행할 수도 있다.

Checks API로 새 체크를 만들어도 이전 실행 묶음에 연결되어 필수 체크가 `Expected`로 남을 수 있다. 새 커밋 상태는 실행 묶음에 의존하지 않으며, 변경 이벤트에 해당하는 head를 먼저 실패로 표시한 뒤 최종 판정을 기록한다. 파일·승인 확인에 오류가 나거나 평가 도중 본문·head·리뷰 상태가 바뀌면 실패로 기록한다. 변화 없는 예약 검사는 이전 GitHub Actions 상태와 결과가 같으면 기록을 추가하지 않아 같은 SHA/context의 상태 개수 제한을 소모하지 않는다.

같은 head SHA를 공유하는 열린 PR은 모두 통과해야 그 커밋 상태가 성공한다. 하나의 저위험 PR이 같은 커밋의 다른 고위험 PR에 필요한 승인을 대신하지 못하게 한다. 결과 게시 직전에 열린 PR 구성과 각 PR·리뷰를 다시 확인한다.

기존 `Conditional Review Gate` 체크도 전환 중에는 함께 게시한다. 새 상태를 실제 GitHub에서 검증한 뒤 ruleset의 필수 항목을 전환한다. 두 이름을 같게 만들면 체크와 커밋 상태를 모두 요구할 수 있으므로 새 이름은 구분한다. 전환 후 저장소 변수 `REVIEW_GATE_LEGACY_CHECKS=false`로 기존 체크 게시를 중단할 수 있다. 게이트 실행은 직렬화하며 검증 로직은 항상 기본 브랜치에서 읽고, PR 브랜치의 코드나 artifact를 실행하지 않는다.

GitHub 이벤트 전달과 runner 대기 시간은 남아 있으므로 메타데이터 편집과 상태 갱신이 원자적으로 동시에 일어나는 것은 아니다. 전체 PR 목록 조회조차 실패하거나 상태 게시 자체가 실패한 경우에는 모든 이전 성공을 무효화했다고 보장하지 않는다. 실패한 워크플로를 확인하고 재평가가 끝난 결과를 확인한 뒤 병합한다.

자동화는 AI가 작성한 위험도 선언을 의미상 독립 검증하지 않는다. 따라서 자동 고위험 경로 분류는 안전망이고, 나머지 의미상 위험 분류는 PR 작성 AI와 작성자의 책임이다. PR 본문만으로는 의미상 분류의 정확성을 보장할 수 없다.

현재 `main`과 `develop`의 ruleset은 전역 승인 수를 `0`으로 두고 `Conditional Review Gate`와 기존 CI를 필수 체크로 요구한다. 최신 푸시 승인 요건은 꺼져 있다. 실제 설정이 변경되었을 수 있으므로 운영 중에는 GitHub의 활성 ruleset을 확인한다.

게이트의 예약 실행은 기본 브랜치(main)의 워크플로를 사용한다. 새 상태 게시 코드가 main에 도달하고 실제 동작을 검증하기 전에는 필수 항목을 바꾸지 않는다. 설정을 변경할 때는 저·중위험 PR의 승인 없는 통과와 고위험 PR의 승인 전 차단·승인 후 통과를 확인하고 기존 CI 체크와 PR 필수 규칙을 유지한다. 아래 운영 안내의 전환 순서를 따른다.

설정값, 적용 순서, 실제 동작 확인과 실패 시 복구 절차는 [리뷰 자동화 운영 안내](review-automation-operations.md)를 따른다.
