# Git 작업 컨벤션

## 브랜치 컨벤션

| 브랜치 | 용도 |
| --- | --- |
| `main` | 최종 프로덕션 브랜치 |
| `develop` | 개발 통합 브랜치. 작업 브랜치를 이곳으로 병합한다. |
| `feat/{기능명}` | 새로운 기능 개발 |
| `fix/{목적}` | 버그 수정 |
| `docs/{목적}` | 문서 또는 주석 수정 |
| `style/{목적}` | 동작 변화 없는 코드 형식 수정 |
| `refactor/{기능명}` | 개발된 기능 리팩터링 |
| `test/{목적}` | 테스트 추가 또는 수정 |
| `chore/{목적}` | 빌드, 설정, 의존성 등 유지보수 |

`codex/`를 포함한 도구·에이전트 전용 prefix는 사용하지 않는다. 작업 브랜치는
위 표의 허용된 prefix(`feat/`, `fix/`, `docs/`, `style/`, `refactor/`, `test/`,
`chore/`) 중 변경 목적에 맞는 하나를 선택한다.

모든 작업은 파일을 수정하기 전에 변경 목적에 맞는 작업 브랜치를 새로 생성하고 체크아웃한다. 문서만
수정하는 작업도 예외가 아니며 `docs/{목적}` 브랜치를 사용한다. 기존 working tree가 dirty하면
변경사항을 먼저 확인하고 보존한 뒤 브랜치를 만든다.

기능명 또는 목적은 브랜치만 보고도 작업 범위를 이해할 수 있게 작성한다.
브랜치 타입은 변경의 주된 목적을 기준으로 고르며 아래 커밋 타입과 같은 의미로
사용한다. 여러 유형의 변경이 섞이면 핵심 결과물을 기준으로 선택한다. 실제 동작을
추가하거나 고치면 `feat` 또는 `fix`, 동작을 유지하며 구조를 개선하면 `refactor`,
문서만 바뀌면 `docs`를 사용한다.

### 브랜치 보호와 병합

- `main`, `develop`에는 직접 push하지 않고 PR로만 반영한다.
- PR은 최소 1명의 승인과 필수 CI 통과 후 병합한다.
- 작업 브랜치는 Squash merge하여 하나의 의도 단위 커밋으로 남긴다.

## PR 컨벤션

- PR은 [PR 템플릿](../../.github/pull_request_template.md)을 사용한다.
- 템플릿의 `PR 내용`과 `변경 이력`을 작성하고, 관련 이슈는 PR 본문에 연결한다.
