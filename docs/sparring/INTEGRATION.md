## 화면과 참여 규칙

목록에서 주제 등록/선택 → 두 입장 중 하나에 투표 → 여러 번 한마디/받아치기.
투표는 회원당 주제별 하나, 변경 가능. 글 수는 투표에 영향을 주지 않는다.
통의 대표 캡슐 240개 색 비율은 투표 비율이며 사람 수를 뜻하지 않는다.
과거 대화는 리플레이로 표시한다. 연결 여부와 실제 새 글 도착을 구분한다.
지난 메시지는 3.2초 간격으로 하나씩 미끄럼틀을 내려와 열리고, 편당 2명(총 4명)의 작은 캐릭터가 대화한다. 말풍선은 편당 최신 글 하나씩 유지한다. 같은 글을 다시 재생하면 기존 인물이 발언하며 중복 캐릭터를 만들지 않는다.
새 일반 채팅은 파이프와 4.5초 추적 말풍선으로 표시한다. 자동 재생 중인 지난 받아치기는 한 인물로 보이고, 선택 의견의 `받아치기 다시 보기`로 아래 특별 연출을 재생할 수 있다.
받아치기는 양쪽 파이프에서 원문과 답장 캡슐을 발사해 충돌시킨다. 충돌 중심에서 바깥으로 충격이 약 0.85초 동안 퍼지며 가까운 캡슐부터 차례로 튀고 가라앉는다. 맞붙은 두 캡슐은 비비며 아래로 떨어진 뒤 미끄럼틀을 함께 굴러 내려와 열린다. 이후 두 캐릭터의 대치로 이어진다. 연출을 마치면 보존한 지난 대화 캐릭터 모임으로 돌아온다. 실시간 일반 글을 새 받아치기처럼 두 번 출력하지 않는다.
주장/비율은 파이프 주변, 작성창은 선택한 편의 가장자리 연결 파이프에 배치한다.
투표 통과 파이프를 유지하며, 캐릭터가 들어 있는 캡슐이 실제 미끄럼틀을 내려와 열린다.
지난 대화 인물은 열린 위치에서 몸을 펴고 실제 3D 관절을 움직여 걸어나온 뒤 상대를 바라보며 대화한다. 받아치기는 기존 충돌과 VS 연출을 유지한다.

## 통합 경계

React가 목록/등록/인증/HTTP/SSE와 데이터 파싱을 소유한다.
기존 Three.js + Cannon 렌더러는 같은 출처의 전용 iframe 문서로 보존한다.
iframe에는 인증 토큰을 전달하지 않는다. source + origin + 메시지 스키마를 확인한다.
API 호출은 부모의 공통 apiClient를 통해서만 처리한다.
별도 문서는 데모의 전역 스타일/DOM/물리 루프가 서비스 셸에 영향을 주지 않게 한다.
주제 이동 시 iframe 문서와 SSE를 함께 폐기한다. iframe 내부는 API fallback 성공 데이터를 만들지 않는다.
외부 라이브러리는 기존 데모의 Three/Cannon 버전과 라이선스를 그대로 사용한다.

## 시각 기준

지난 대화는 `crew-coach-atlas.png`의 크루/코치 얼굴과 옷을 기준으로 만든 입체 관절 모델을 사용한다.
미끄럼틀의 닫힌 캡슐 안에서도 같은 모델을 쓰고, 개봉 시 정확한 발 위치와 자세를 이어받아 걷는다.
기존 받아치기 VS는 `character-duel-atlas.png`의 항의(`protest`)와 팔짱(`listen`) 포즈를 유지한다.
통 속 다수 캡슐은 기존 `crew-coach-atlas.png`를 유지하며 파이프/통/캡슐/물리 충돌은 기존 3D다.
원본 인물의 회색 니트+배낭, 검정 옷+민트 명찰, 둥근 얼굴/머리카락 재질을 유지한다.
Primary action: 내 편을 정한 뒤 한마디 보내기.
정보 순서: 주제 → 두 주장/비율과 경기장 → 작성창 → 영구 대화 기록.
Required content: 주제, 설명, 양측 주장/표수/비율, 연결 상태, 전송 상태, 원문/받아치기,
전체/내 대화, 이전 대화, 재생 제어, 오류/빈 상태, 로그인 유도.
불필요한 중복 헤더, 체험판 주제 선택기, 카드형 진영 선택, 허구 접속자 수는 제거한다.
Layout: 스파링 상세 - 넓은 경기장과 대화의 문서 흐름 -> stack + content-limiter (https://every-layout.dev/layouts/stack/); scroll owner: 부모 document; anti-patterns: iframe 내부 이중 스크롤과 중첩 카드.

## 실시간과 저장

POST는 인증+CSRF를 검증하고 DB 트랜잭션 안에서 처리한다.
주제 행 잠금이 투표 변경/의견 작성과 revision 증가 순서를 직렬화한다.
글의 requestId는 주제+작성자 단위로 유일하며 재시도는 같은 저장 결과를 반환한다.
SSE는 활성 주제별 DB revision을 1초마다 한 번 조회해 바뀐 revision을 전달한다.
애플리케이션이 여러 개여도 같은 DB의 커밋을 볼 수 있으며 메모리 이벤트 유실에 의존하지 않는다.
초기/재접속 시 HTTP로 현재 투표와 마지막 수신 ID 이후 글을 다시 조회한다.
15초 heartbeat, 120초 연결 교체, 완료/오류 시 제거, 프로세스당 최대 500 연결.
대용량 SSE/DB 부하 한계와 프록시 환경은 배포 전에 별도 측정해야 한다.

## 현재 참여 흐름

1. `/sparring`에서 전체/대화 있는 판/내가 낀 판을 탐색하거나 제목을 검색한다.
   ‘대화 있는 판’은 글이 존재하는 주제이며 현재 접속자가 있다는 뜻은 아니다.
2. 로그인한 회원이 ‘주제 올리기’로 주제 80자, 양측 주장 각 32자, 설명 240자를 등록한다.
   생성한 주제의 상세로 이동한다. 아무도 투표하지 않았으면 양측 0표/0%다.
3. 주장 자체를 누르면 내 편이 정해지고 입력이 열린다. 같은 편을 다시 눌러도 표가 늘지 않는다.
   다른 주장을 누르면 한 표가 이동한다. 투표 없이 관람/전체 기록 조회는 가능하다.
4. 한마디는 160자까지 반복 작성할 수 있다. 작성 당시 편 색과 크루/코치 유형을 사용한다.
   저장 성공 후 캡슐이 미끄럼틀을 내려와 열리면 캐릭터가 나와 상대를 향해 항의하고
   실제 한마디가 말풍선에 나타난다.
   상대 브라우저는 SSE revision을 받은 뒤 새 글을 조회해 보여준다. 전달 간격은 최대 약 1초의
   폴링 주기에 네트워크/조회 시간이 더해지며, 고정 지연을 보장하지 않는다.
5. 캐릭터 말풍선이나 기록을 누르면 의견을 선택한다. ‘받아치기’는 원문을 입력 위에 고정한다.
   전송 시 원문과 답장의 캡슐이 양쪽 파이프에서 날아와 충돌하고, 미끄럼틀에서 나온 캐릭터가 두 의견을 보여준다.
   같은 편끼리 받아쳐도 원래 편 색과 두 의견을 유지한다.
   같은 글을 일반 재생으로 다시 넣지 않는다. 원문이 첫 30개 밖에 있어도 답장의 원문 정보를 받는다.
6. ‘모인 대화’의 전체/내 대화와 이전 대화 더 보기로 지난 글을 찾는다.
   내가 보고 있는 글과 작성 중인 받아치기 대상은 리플레이가 바꾸지 않는다.
7. 연결이 끊기면 상태 문구가 바뀌며 입력은 유지한다. 재접속 시 빠진 글을 ID 기준으로 보충한다.
   HTTP 저장에 실패해도 초안을 지우지 않는다. 같은 초안의 재시도는 UUID로 중복 저장을 막는다.

## 연출의 의미와 제한

통은 투표 비율에 맞춰 이미 채워진 대표 캡슐을 보여준다. 입장마다 전체 통이 다시
쏟아져 채워지는 연출은 적용하지 않았다. 파이프는 비율에 따라 발사 빈도/압력이 달라지고,
새 글이 없는 동안에도 과거 대화를 재생한다. 이 움직임은 신규 참여자/투표/글을 만들지 않는다.

실제 미끄럼틀 물리가 캡슐을 개봉하면 `dispenser.onOpened`에서 DOM 캐릭터의 등장을 시작한다.
캐릭터는 개봉 위치에서 0.95초 동안 커지며 뛰어나온 뒤 항의와 듣기 포즈로 대치한다.
빈 껍데기는 개봉 후 2.5초에 사라지며 마지막 0.35초 동안 작아진다.
일반 의견은 미끄럼틀에서 나온 캐릭터로 표시한다. 받아치기는 이전 파이프 발사·충돌 후 같은 캐릭터
대치로 이어진다. 앞선 장면이 끝난 뒤 시작하며 원문과 답장의 편 색은 같을 수 있다.

과거 대화는 약 10초 간격으로 재생하며 말풍선에 포커스가 있는 동안 교체를 보류한다.
일시정지를 유지하고 화면 밖에서는 움직임을 멈춘다. 모션 감소 설정에서는 미끄럼틀 이동,
캐릭터의 성장·점프와 껍데기 축소를 생략하고 개봉 결과와 의견을 표시한다.
시간 제한/승패/랭킹은 없다.

영구 저장은 서버에 성공한 글/투표를 뜻한다. 작성 중 초안은 현재 페이지 메모리에만 있다.
새로고침/탭 종료까지 초안을 보존하는 기능은 추가하지 않았다. 삭제/수정/신고/운영 제어는
이번 등록·참여 흐름의 범위에 포함하지 않았다.

## 파일과 실행 경계

- `backend/.../sparring/`: 주제·투표·글 명령, 읽기 모델, SSE 연결
- `frontend/src/features/sparring/`: 공통 HTTP 클라이언트, Zod 계약, iframe/SSE 브리지
- `frontend/src/pages/sparring/`: 목록, 등록, 상세 서비스 화면
- `frontend/public/sparring-arena/`: 투표용 3D 렌더러, 지난 대화용 관절형 3D 캐릭터와 기존 DOM 받아치기 대치
- `backend/src/main/resources/db/migration/V11__sparring.sql`: 스파링 테이블과 인덱스를 추가하는 Flyway 마이그레이션

Webpack은 독립 렌더러의 JS를 ESM으로 표시해 top-level await를 포함한 배포 빌드를 최소화한다.
런타임 외부 CDN 요청이나 새로운 npm/Gradle 의존성을 추가하지 않았다.
렌더러를 React 컴포넌트로 전면 재작성하지 않았고 기존 물리·연출 모듈을 재사용했다.

기존 통합 검증을 진행한 작업 위치는 `/Users/cws/.codex/worktrees/sparring-live-integration/2026-jarihana`다.
기존 root checkout, `sparring-list-ui` worktree, `/Users/cws/workspace/2026-jarihana-sparring`의
데모 원본은 수정하지 않았다. 다른 세션에서 계속할 때 작업 브랜치/경로를 먼저 확인한다.
앱의 worktree 첨부는 `thread-not-found`로 실패했지만 디스크의 worktree와 브랜치는 정상이다.
`frontend/node_modules`는 검증에 사용한 기존 의존성 디렉터리의 로컬 링크이며 Git에 넣지 않았다.

기존 격리 검증 당시 실행: 프론트엔드 `http://localhost:5197/sparring`, 백엔드 8098,
전용 PostgreSQL 컨테이너 `jarihana-sparring-integration-db`의 15439 포트.
보이는 예시 주제는 이 전용 DB의 검증 데이터이며 운영 데이터가 아니다.
실제 GitHub OAuth 왕복은 확인하지 않았고, 브라우저 참여 검증에는 전용 DB 회원의 로컬 테스트
쿠키를 사용했다. 애플리케이션 코드에 개발용 로그인 우회 경로를 추가하지 않았다.

일반 실행 환경/비밀값은 기존 backend/frontend README를 따른다.
프론트엔드는 Node 24에서 `API_PROXY_TARGET=http://localhost:8098 ./node_modules/.bin/webpack serve --mode development --port 5197`로
별도 백엔드에 연결할 수 있다. 기본 프록시는 기존 8080을 유지한다.
최신 develop 기준 서버는 Flyway를 통해 스파링 테이블을 적용한다. 기존 격리 검증은 전용 DB의 새 스키마에서 수행했다.
운영 스키마에 적용하거나 원격 브랜치로 push/배포/병합하지 않았다.

다음 세션은 [검증 기록](QA.md)의 남은 범위부터 확인한다. 외형 취향의 최종 승인,
실기기 Safari/키보드, 실제 OAuth, 운영 프록시의 SSE 동작/부하 한계는 로컬 검증과 구분한다.
지난 대화와 미끄럼틀 출력 캡슐의 인물은 `walking-characters.js`의 실제 3D 부품/관절 모델이다.
5197에서 사용한 `crew-coach-atlas.png`를 외형 기준으로 크루/코치를 구성했다.
원본 모델을 복원하거나 PNG를 3D로 자동 변환한 것은 아니며, 원본의 미세한 천/머리 질감은 다르다.
통 속 다수 인물과 기존 받아치기 VS는 이미지 표현을 유지한다.
`history-walk.js`는 개봉 위치 → 몸 펴기 → 바닥 보행 → 상대를 향한 회전을 계산하고,
`history-conversation.js`는 최대 4명의 등장/교체와 말풍선을 관리한다.
3D 부품은 재질별 인스턴스로 묶고 활성 슬롯까지만 제출한다. 추가 패키지나 외부 3D 서비스 호출은 없다.

구현 참고: [Spring MVC 비동기 응답](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html).
SSE 응답이 시작된 뒤의 연결 종료/타임아웃에 JSON 오류를 다시 쓰지 않도록 처리했다.
