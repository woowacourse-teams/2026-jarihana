# 워크플로 컨벤션

> 이 문서는 구속력 있는 팀 컨벤션 모듈이다.
> 인덱스: [team-convention.md](../team-convention.md)

## 브랜치 컨벤션

| 브랜치 | 용도 |
| --- | --- |
| `main` | 최종 프로덕션 브랜치 |
| `develop` | 개발 통합 브랜치. 작업 브랜치를 이곳으로 병합한다. |
| `feat/{기능명}` | 새로운 기능 개발 |
| `fix/{목적}` | 버그 수정 |
| `docs/{목적}` | 문서 또는 주석 수정 |
| `style/{목적}` | 동작 변화 없는 코드 형식 수정 |
| `refactor/{기능명}` | 개발된 기능 리팩터링 |
| `test/{목적}` | 테스트 추가 또는 수정 |
| `chore/{목적}` | 빌드, 설정, 의존성 등 유지보수 |

`codex/`를 포함한 도구·에이전트 전용 prefix는 사용하지 않는다. 작업 브랜치는
위 표의 허용된 prefix(`feat/`, `fix/`, `docs/`, `style/`, `refactor/`, `test/`,
`chore/`) 중 변경 목적에 맞는 하나를 선택한다.

기능명 또는 목적은 브랜치만 보고도 작업 범위를 이해할 수 있게 작성한다.
브랜치 타입은 변경의 주된 목적을 기준으로 고르며 아래 커밋 타입과 같은 의미로
사용한다. 여러 유형의 변경이 섞이면 핵심 결과물을 기준으로 선택한다. 실제 동작을
추가하거나 고치면 `feat` 또는 `fix`, 동작을 유지하며 구조를 개선하면 `refactor`,
문서만 바뀌면 `docs`를 사용한다.

### 브랜치 보호와 병합

- `main`, `develop`에는 직접 push하지 않고 PR로만 반영한다.
- PR은 최소 1명의 승인과 필수 CI 통과 후 병합한다.
- 작업 브랜치는 Squash merge하여 하나의 의도 단위 커밋으로 남긴다.

## 커밋 컨벤션

### 형식

```text
<type>(<scope>): <subject>

<body>

<footer>
```

`scope`, 본문, 푸터는 선택 사항이다. `scope`를 생략하면
`<type>: <subject>` 형식으로 작성한다. 변경 범위를 짧고 명확하게 표현할 수
있을 때만 `scope`를 괄호 안에 작성한다.

### 타입

| 타입 | 의미 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가 | `feat(club): 모집 목록 조회 기능을 추가` |
| `fix` | 버그 수정 | `fix(member): 중복 가입 검증 오류를 수정` |
| `docs` | 문서 또는 주석 수정 | `docs(readme): 로컬 실행 방법을 추가` |
| `style` | 로직 변화 없는 포맷 수정 | `style(club): 들여쓰기를 정리` |
| `refactor` | 기능 변화 없는 구조 개선 | `refactor(club): 모집 상태 변경 로직을 단순화` |
| `test` | 테스트 추가 또는 수정 | `test(auth): 토큰 검증 단위 테스트를 추가` |
| `chore` | 빌드, 설정, 의존성 등 유지보수 | `chore(deps): 스프링 부트 버전을 갱신` |

### 제목

- 한국어 명령문으로 작성한다.
- 현재 시제를 사용한다.
- 끝에 마침표를 붙이지 않는다.
- 무엇을 했는지보다 변경의 의도가 드러나게 작성한다.

### 본문과 푸터

- 본문에는 변경 이유, 이전 동작과의 차이, 주요 구현 내용을 1~3줄로 작성한다.
- 푸터에는 Breaking Change 또는 연관 이슈를 기록한다.

```text
feat(club): 동아리 모집 목록 조회 기능을 추가

사용자가 현재 모집 중인 동아리를 최신 순으로 탐색할 수 있게 한다.

Refs: #12
```
