1. 현재 브랜치와 working tree 상태를 확인한다.
2. 이 파일의 작업 규칙을 확인한다.
3. 작업 유형에 따라 아래 문서를 읽는다.

| 작업 유형 | 읽을 문서 |
| --- | --- |

## 작업 규칙

- 프론트엔드 구현은 JavaScript/JSX 기준으로 작성한다.
- TypeScript, Vite, Vitest를 새로 도입하지 않는다.
- 서버 권한을 클라이언트 guard로 대체하지 않는다.
- API 호출은 공통 API client와 도메인 API 계층을 사용한다.
- 기존 구현·문서·working tree 변경사항을 임의로 되돌리지 않는다.
- 요청 범위를 벗어난 리팩터링과 의존성 변경을 추가하지 않는다.
- 프론트엔드 작업은 TDD(red-green-refactor)를 기본 방식으로 사용하지 않는다.
- agent QA나 별도 에이전트 기반 검증을 사용하지 않는다.

## UI 상호작용의 고정 식별자

자리하나는 PostHog로 사용자 행동과 전환 흐름을 분석한다. 클릭·변경·제출은
자동 수집하지만, DOM 위치나 표시 문구에 의존하면 UI 개편 후 같은 동작을
계속 추적하기 어렵다. 또한 개인정보 보호를 위해 텍스트와 일반 속성을 마스킹한다.
따라서 AI가 UI를 개발할 때는 아래 고정 식별자 규칙을 적용해 PostHog에서
동일한 사용자 동작을 일관되게 구분하고, 방문·클릭에서 로그인·회원가입·신청 완료로
이어지는 흐름을 분석할 수 있도록 한다. 수집 범위와 이벤트 계약은
[`docs/analytics.md`](docs/analytics.md)를 따른다.

- 클릭·변경·제출이 발생하는 UI를 추가하거나 수정할 때는 해당 버튼, 링크, 탭, 메뉴 항목, 입력·선택 요소, 폼에 `data-ph-capture-attribute-action`을 지정한다. 자동 수집만으로 작업을 완료하지 않는다.
- 값은 사용자 동작의 의미를 나타내는 고정된 영문 `snake_case`로 작성한다. 영문자로 시작하고 80자 이내로 유지한다. 예: `group_create`, `registration_submit`, `group_filter_change`.
- 같은 동작은 기존 식별자를 재사용한다. 위치·부모 태그·요소 순서·CSS·표시 문구·컴포넌트 파일이 바뀌어도 식별자를 유지하고, 의미가 다른 동작에는 별도 식별자를 사용한다.
- 배열 인덱스, 좌표, DOM 경로, 동적으로 생성한 값으로 식별자를 만들지 않는다. 사용자 입력·이름·이메일·모임 제목·개별 데이터 ID를 식별자에 포함하지 않는다. 화면·대상 구분에는 기존에 허용된 `route_name`, `group_id`, `recruitment_id` 등의 속성을 사용한다.
- 공통 컴포넌트를 사용하면 속성이 실제 DOM 요소까지 전달되는지 확인한다. 폼 식별자만으로 내부의 서로 다른 버튼 동작을 대신하지 않는다.
- PostHog의 동작 구분은 이 속성으로 전달되는 `action`을 기준으로 한다. DOM 위치·텍스트 기반 선택자에 의존하지 않으며, 기존 마스킹·전송 허용 목록을 임의로 완화하지 않는다.
- 클릭 식별자와 처리 성공 이벤트를 구분한다. `group_created` 같은 성공 이벤트는 기존 규칙대로 도메인 API 성공 시점에 기록한다.

## 검증

- JavaScript/JSX 변경: `npm run lint`
- 동작 변경: 관련 Jest 테스트
- 빌드 영향 변경: `npm run build`
- UI 변경: 필요한 브라우저 확인과 접근성 확인
- UI 상호작용 변경: 변경 대상의 고정 식별자 지정, 실제 DOM 전달, 기존 동작 식별자 유지 여부 확인
- 검증하지 못한 항목은 성공으로 보고하지 않는다.
