# ADR 0003. 초대 이벤트와 사용자 식별

- 상태: 채택
- 날짜: 2026-10-12
- 목적: 초대 기능의 효과를 측정하는 수집 범위와 사용자 식별 방식의 선택을 기록한다.
- 계약: [분석 이벤트와 개인정보 제한](../analytics.md), [초대 화면·API 연결](../IMPLEMENTATION_MAP.md#초대-기능-설계-계약)
- 후속 작업: [사용자별 초대 분석의 개인정보 처리 기준 정비 #384](https://github.com/woowacourse-teams/2026-jarihana/issues/384)

## 배경

모임장의 모집 부담을 줄이려면 초대 발급·복사·조회가 실제 합류로 이어지는지 확인할 수 있어야 한다.
기존 공유 초대 페이지는 원본 토큰 노출을 막기 위해 분석과 녹화를 모두 차단했다. 따라서 모임 상세의
링크 복사는 측정할 수 있지만 공유 초대의 조회·수락·합류는 분석에 남지 않았다.

사용자별 흐름을 연결하면 한 사람의 반복 조회와 여러 사람의 조회를 구분할 수 있다. 사용자 ID는
내부 회원 DB와 연결 가능한 식별자이므로 이름·이메일을 제외해도 익명 통계로 간주하지 않는다.

## 대안

| 대안 | 얻는 것 | 제한 |
| --- | --- | --- |
| 공유 페이지의 전체 수집 차단 유지 | 기존 차단 경계 유지 | 공유 초대의 조회·합류를 분석할 수 없다. |
| 사용자 식별 없이 이벤트 건수 집계 | 유형별 사용량·합류 건수 확인 | 동일 사용자의 반복 행동과 사용자별 전환을 구분하기 어렵다. SDK의 지속 식별자를 제거하는 별도 수집 설계가 필요하다. |
| 사용자 ID로 명시적 초대 이벤트 연결 | 로그인한 회원별 조회·수락·합류 흐름 분석 | 외부 분석 서비스에 회원별 행동 기록이 저장되므로 개인정보 처리 기준을 관리해야 한다. |

## 결정

세 번째 대안을 채택했다. 공유 초대 페이지에서도 명시적 초대 이벤트를 수집하고 로그인한 회원은
DB 사용자 ID를 PostHog `distinct_id`로 사용한다. 개인정보 처리방침 정비는 후속 이슈로 관리하면서
이벤트 구현을 먼저 진행하기로 했다. 이 결정은 개인정보 처리 근거·동의·위탁·국외 이전 검토의 완료를 뜻하지 않는다.

- `/invitations/link/:token`의 유효한 경로에서 초대 조회·수락 시도·신규 합류·이미 참여 중 결과만 허용한다.
- 자동 클릭·페이지뷰·녹화·히트맵·API 요청·오류·`$identify` 이벤트는 공유 페이지에서 차단한다.
- 공유 페이지의 payload는 양의 정수인 초대/모임 ID·LINK 유형·초대 상태와 분석 식별/전송에 필요한 SDK 필드만 재구성한다.
- 이름·이메일·검색어·지정 대상 회원 ID·원본 URL·초대 토큰·프로필 속성은 보내지 않는다.
- 비회원 조회는 기존 SDK 익명 식별자를 사용한다. 공유 페이지에서 익명 ID와 회원 ID를 병합하는 `$identify` 이벤트를 보내지 않으므로 로그인 전후의 흐름을 자동으로 같은 사람이라고 집계하지 않는다.
- 성공 이벤트는 API 응답 검증 또는 클립보드 쓰기 완료 뒤에 기록한다. 신규 JOINED만 합류 성과로 집계한다.
- 요청 시작 시 식별자를 고정하고 계정 변경 뒤의 늦은 결과를 버린다. SDK 실패나 수집 거부는 초대 기능의 결과를 바꾸지 않는다.

## 결과

화면 녹화 없이 로그인한 회원별 초대 흐름을 분석할 수 있다. 유효하지 않은 공유 경로, OAuth 경로와
토큰을 포함하는 API 경로의 차단은 유지한다. 기존 일반 화면의 분석 설정은 그대로 사용한다.

브라우저 차단·응답 유실·탭 종료로 이벤트가 누락될 수 있으므로 서버 감사 이력이나 정확한 전체 합류 수를
대체하지 않는다. 이벤트명·필드·분석 시나리오와 수집 공백은 분석 문서에서 관리한다.
운영 처리방침·수집 근거·위탁/DPA·저장 리전·국외 이전·보유/삭제·접근 권한 검토는 #384에서 이어간다.
