# 상점 미리보기와 연동 계약 초안

## 현재 범위

`/shop`은 공개 체험 화면이다. 실제 포인트·외형을 읽거나 변경하지 않는다.
예시 상품, 체험 포인트 1,200P, 기본 보유 모자 하나로 시작한다. 메모리에만 저장하며
새로고침·화면 재진입·계정/세션 변경 시 초기화한다. 기존 아바타 선택지는 계속 무료다.
마이페이지 아바타 카드와 데스크톱 계정 메뉴에 `상점 미리보기` 진입점이 있다.

기본 규칙은 영구 보유, 동일 아이템 중복 구매 금지, 구매와 착용 분리,
같은 슬롯 하나만 착용, 해제 후 보유 유지다. 상품·가격·정책은 미확정 예시다.
보유 여부와 체험용 착용 버튼은 상점 상품 목록과 상세에 표시한다.
아바타 미리보기는 기존 3D 모델을 사용하고 프로필 프레임·칭호는 일러스트로 표현한다.
프로필 상품은 체험용 슬롯 상태만 바꾸며 실제 프로필에 렌더링하지 않는다.

## 코드 경계

- `src/entities/shop/index.js`: 상품·아이템·잔액·구매 결과의 Zod 계약, 구매 불가 사유.
- `src/features/shop/demoClient.js`: 메모리 어댑터. 실제 포인트 시스템 구현이 아니다.
- `src/features/shop/hooks.js`: 조회와 mutation, 구매·착용 후 캐시 갱신.
- `src/pages/shop/ShopPage.jsx`: 화면과 구매 확인, `ShopPreview({client})` 주입 지점.
- `src/pages/shop/ProductArt.jsx`: 예시 SVG 일러스트. 신규 3D 에셋 제작은 별도 작업.

실제 연동 시 화면을 유지하고 `client`를 공통 API client를 사용하는 도메인 API 어댑터로
교체한다. HTTP 경로는 정하지 않았다. 아래는 서버 합의 전 프론트엔드 계약 초안이다.

| 메서드 | 입력 | 결과 |
| --- | --- | --- |
| `getShopProducts()` | 없음 | `categories`, `products` |
| `getPointBalance()` | 없음 | `balance`(0 이상 안전한 정수), `unit: P` |
| `getOwnedItems()` | 없음 | 독립적인 `items` 메타데이터, 슬롯별 `equipped` |
| `purchaseProduct(request)` | `productId`, `termsVersion`, `requestId` | `purchaseId`, `productId`, `wallet`, `inventory` |
| `setEquipment(request)` | `itemId`, `equipped`(boolean) | 갱신된 `inventory` |

현재는 상품 하나가 아이템 하나를 지급한다. 카테고리는 `categoryId`로 데이터화하고,
미리보기 유형(`avatar`, `profile`)·그림 종류·장착 슬롯은 지원 목록으로 검증한다.
외형 patch도 기존 파츠 허용 목록을 검증한다. 신규 유형·3D 파츠는 렌더러와 검증을 추가한 뒤 제공한다.

## 구매와 오류

별도 확인창에서 구매를 확정한다. 요청에 UUID를 부여하고 구매 결과 불명 오류에는
같은 키를 유지한다. 자동 구매 재시도는 하지 않는다. 이중 제출은 진행 상태와 동기 잠금으로
막으며 같은 키의 상품·조건 일치 여부를 검사한다. 성공 응답의 잔액·보유 상태를 함께 반영하고
이전 조회를 취소한다. 확정적 거절 후에는 창을 닫아 조건을 다시 확인한다.

| 코드 | 의미 |
| --- | --- |
| `INSUFFICIENT_POINTS` | 잔액 부족 |
| `ALREADY_OWNED` | 같은 아이템 보유 |
| `PRODUCT_UNAVAILABLE` | 판매하지 않는 상품 |
| `TERMS_CHANGED` | 가격·지급 조건 변경 |
| `REQUEST_CONFLICT` | 같은 요청 키에 다른 입력 |
| `ITEM_NOT_OWNED` | 미보유 아이템 착용 시도 |

알 수 없는 오류는 결과 불명으로 안내하며 같은 요청으로 확인한다. 원문 오류는 표시하지 않는다.
새로고침·화면 이탈 후 구매 복구는 체험판에 포함하지 않았다. 실제 공개 전 구매 조회 계약과
미확정 요청 키 보존 방식을 추가해야 한다.

## 포인트 담당자와 합의할 사항

1. 잔액 조회 계약과 포인트 명칭·단위·만료 정책.
2. 상점 백엔드에서 호출할 사용 인터페이스와 오류 코드.
3. 차감·구매·지급을 같은 DB 트랜잭션에서 처리할 수 있는지.
4. 원인 구매 ID 기준 중복 차감 방지와 실패 시 취소·복구 계약.
5. 재시도 결과에 최신 잔액·보유 상태를 제공하는 방식과 구매 결과 조회.

서버가 가격·잔액·판매 여부·소유권을 판단하고 차감과 지급을 원자적으로 처리해야 한다.
브라우저에서 차감·지급 API를 각각 호출하지 않는다. 인증·CSRF·계정별 캐시·로그아웃 정리,
새 파츠와 구버전 서버 공존 검증을 갖춘 뒤 실제 판매를 연다.

## 검증 범위

`demo-client.test.js`: 중복·동시 구매, 잔액·판매·조건 검증, 슬롯 교체·보유 유지, 메모리 격리.
메모리 테스트는 DB 동시성 보증이 아니다.
`shop-page.test.jsx`는 구매 취소·완료, 응답 유실 재시도, 상점에서의 보유 표시와 착용,
필터·빈 상태, 가격 변경·분석 action을 확인한다.
`avatar-frame.test.jsx`: 같은 iframe으로 미리보기 변경을 전달하는 계약.
실제 포인트·구매 서버·운영 배포는 이번 검증 범위에 포함하지 않는다.
