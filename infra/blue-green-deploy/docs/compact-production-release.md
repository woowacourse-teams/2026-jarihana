# 운영 무중단 배포 V2

배포 대상 파일이 main에 푸시되면 [Production Release V2](../../../.github/workflows/backend-prod-deploy-v2.yml)가 한 번 실행된다. 프론트 변경은 프론트만 게시하고 백엔드 변경은 기존 프론트를 재사용한다. 양쪽 코드나 공통 배포 설정이 바뀌면 함께 배포한다. 자동 실행 그래프에는 V2의 잡과 복구 분기가 표시된다.

운영 승격 전 같은 커밋 `173b12a`로 공동 배포를 비교했다. [V1 수동 실행](https://github.com/woowacourse-teams/2026-jarihana/actions/runs/44477273481)은 21분 12초, [V2 수동 실행](https://github.com/woowacourse-teams/2026-jarihana/actions/runs/44480052966)은 18분 15초에 성공했다. 두 실행에서 API와 워커의 5분 관측을 통과했다.

## 앱 작업 결과 전달

기존 읽기 전용 허가 키와 앱 관리 API는 그대로 사용한다. 새 앱 잡과 기존 앱 잡은 자기 슬롯에 할당된 명령만 자신의 호스트에서 실행한다. 허가 대기 응답만으로 작업하지 않는다. 기존 `app.sh`가 저널, 권한, 호스트와 실행 신원을 다시 검사한다. 완료 결과를 전송한 뒤 Nginx가 원래의 `bg_accept`로 인스턴스, 부팅 ID, 배포 ID와 허가 ID를 검증한다. 같은 완료 결과의 중복 전달은 허용하고 내용 변경은 거절한다. 전송 실패 시 변경 작업을 다시 실행하지 않는다.

운영 시험 전에 필요한 설정은 다음과 같다. 이 설정은 로컬 검증에 필요하지 않다.

1. Nginx에 `controller/receive-app-result.sh`를 root 소유의 수정 불가능한 실행 파일 `/usr/local/libexec/jarihana-receive-prod-result`로 설치한다.
2. A/B에 서로 다른 결과 전송 전용 SSH 키를 준비한다. 각 앱의 `/etc/jarihana-deploy/prod/result-key`는 root 소유이며 해당 전용 러너만 읽을 수 있어야 한다. 기존 호스트 키 검증 파일을 사용한다.
3. Nginx의 `jarihana-coordinator` 계정에 대해 관리자가 통제하는 authorized_keys에 각 공개키와 슬롯을 고정한다. A 키 예시는 다음과 같다. B 키에는 B를 지정한다. 기존 허가 조회 계정과 키는 수정하지 않는다.

```text
restrict,command="/usr/bin/timeout 15s /usr/local/libexec/jarihana-receive-prod-result A" ssh-ed25519 <A 전용 공개키>
```

4. 파일 전송, 포트 포워딩과 임의 명령이 허용되지 않는지 확인한다. 결과 수신기는 자기 슬롯과 해당 실행의 허가만 확인하고 실행별 임시 디렉터리에 완료 결과를 한 번 기록한다. 배포 상태를 변경할 권한은 기존 코디네이터 단계에 있다.
5. 정상 종료된 실행은 임시 결과를 정리한다. 실패한 실행은 원래 저널과 실행별 결과를 함께 보존한다. 같은 실행을 다시 시작하지 않는다.

## 수동 실행

GitHub Actions에서 `Production Release → Run workflow`를 연다. 브랜치는 `main`, 배포 방식은 `V2`, 모드는 `deploy`를 고른다. 프론트 전용 또는 백엔드 전용 옵션 중 하나를 선택하거나 둘 다 해제해 공동 배포한다. 수동 실행의 기본값은 `V1`이다. V2를 실행하면 선택한 버전이 실제 운영에 배포된다. 이미 자동 배포된 main에서 실행하면 같은 버전이 한 번 더 배포된다.

복구 시점과 종료 보류 기준은 [기존 복구 문서](recovery.md)를 따른다.
