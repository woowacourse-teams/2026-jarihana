# 파일 전송으로 인한 배포 지연 개선

5분 관찰과 기존 복구 조건을 유지하면서 파일마다 반복하던 요청을 줄인다.
20분 안팎은 운영에서 검증할 목표이며, 아래 로컬 검증이나 단일 조회 측정으로 달성을 보장하지 않는다.

## 확인한 병목

2026-11-06의 [운영 실행 42166254451](https://github.com/woowacourse-teams/2026-jarihana/actions/runs/42166254451)은
48분 21초가 걸렸다. plan은 16분 16초, switch는 14분 1초, seal은 4분 28초였고,
세 단계 합계는 34분 45초다. 프론트 artifact에는 161개 파일, 약 20.9 MB가 들어 있었다.
파일 용량보다 파일마다 새 AWS CLI 프로세스를 띄우고 순서대로 요청하는 비용이 컸다.

SSM으로 확인한 coordinator는 t4g.micro, 메모리는 916 MiB였다. 같은 manifest에 대한
S3 HEAD 12회를 호스트 AWS CLI 2.38.0으로 조회하면 순차 실행 8.74초, 4개 병렬 4.74초였다.
단일 조회의 최대 RSS는 61,472 KiB였다. 이 결과를 근거로 동시 실행 수를 4로 제한했다.
실제 workflow는 별도로 설치한 AWS CLI 2.38.5를 사용하므로 이 측정은 실제 배포 시간의 대체값이 아니다.
측정은 읽기만 수행했고 EC2, Nginx, S3 파일이나 배포 pin을 변경하지 않았다.

## 1차 파일 전송 개선

| 작업 | 이전 | 개선 |
| --- | --- | --- |
| 원본 업로드 | PUT 후 같은 파일을 GET하여 비교 | SHA-256을 포함한 PUT 후 S3 체크섬 응답 비교 |
| 게시 전 원본 다운로드 | 순차 다운로드 후 전체 해시 검사 | 4개씩 다운로드하고 각 파일의 크기와 해시 검사 |
| 공개 파일 업로드 | PUT 후 같은 파일을 GET하여 비교 | SHA-256을 포함한 PUT 후 S3 체크섬 응답 비교 |
| 공개 URL 검사 | 전체 파일 순차 검사 | 전체 파일을 4개씩 검사 |
| 최종 확정 | 원본 전체 다운로드 후 공개 파일 전체 검사 | manifest의 실행 정보 대조 후 공개 파일 전체 검사 |

S3는 요청에 제공한 체크섬과 업로드 바이트가 다르면 오류를 반환한다.
코드는 성공 응답의 `ChecksumSHA256`도 기대값과 비교하고 누락이나 불일치를 실패로 처리한다.
[AWS PutObject 설명](https://docs.aws.amazon.com/cli/latest/reference/s3api/put-object.html)과
[업로드 무결성 검증](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)을 따른다.

새 파일 N개에 대한 S3 호출은 원본 보관, 게시, 최종 확정을 합쳐 `7N`에서 `4N`으로 줄어든다.
161개 기준 1,127회에서 644회로 483회, 약 43% 감소한다. 이 수치에는 기존 릴리스 확인,
manifest와 상태 pointer 갱신, 공개 HTTP 검사, GitHub API 호출은 포함하지 않는다.
GitHub 실행 확인의 10초/30초 캐시와 API 예산, 기한, watchdog은 유지한다.

로컬 Docker의 Bash 5.2에서 이전 릴리스와 새 릴리스를 각각 161개 파일로 구성하고,
S3/공개 HTTP 요청 대역에 매번 50ms 지연을 넣어 같은 순서로 비교했다.

| 파일 처리 구간 | 기존 코드 | 개선 코드 |
| --- | ---: | ---: |
| 준비 `fe_stage` | 62.82초 | 17.35초 |
| 게시 `fe_publish` | 71.25초 | 18.47초 |
| 확정 `fe_finalize` | 33.37초 | 5.05초 |
| 합계 | 167.44초 | 40.88초 |

이 시험에서 S3 GET은 972회에서 489회로 줄고 PUT은 327회로 같았다.
공개 HTTP 전체 검사는 두 코드 모두 483회였다. 약 76% 단축은 이 모의 파일 처리 구간의
결과다. 빌드, 앱 준비와 worker 인계, 300초 관찰, 실제 CLI 시작 비용, EC2 CPU/메모리 제약은
이 벤치마크에 포함하지 않았으므로 전체 운영 배포의 단축률로 해석하지 않는다.

원본의 조건부 생성, pointer CAS, 이전 파일 보관, 파일 전체 SHA-256 검사와 index.html 마지막
게시를 유지한다. HTTP 관찰과 worker 관찰의 최소 300초, worker 인계, 기존 요청 종료 확인,
롤백과 EC2 종료 순서는 바꾸지 않는다. 작업 실패나 취소 후 남은 업로드가 복구와 겹치지 않도록
자식 프로세스 그룹을 종료하고 회수한다. 동시 실행 중인 요청은 최대 4개까지 완료될 수 있다.

## Shell 기반 S3 전송 개선

다운로드, 원본 보관과 공개 파일 게시에서 파일마다 실행하던 AWS CLI를 curl의 AWS SigV4
요청으로 대체한다. 게시 직전의 pointer GET도 같은 전송 경로를 사용하되 매 파일마다 실제로
조회하고 기존 소유권과 ETag 검사를 수행한다. manifest와 배치 밖 pointer 조회, pointer CAS는
기존 AWS CLI를 사용한다. 배포 스크립트에 Python 런타임이나 패키지를 추가하지 않는다.

개선 코드가 main에 반영되면 별도 GitHub 변수 없이 새 전송을 기본으로 사용한다. 스크립트가
전송 방식을 내부에서 초기화하며 외부 환경변수로 활성화할 필요가 없다. 복구 함수 `fe_recover`는
기존 AWS CLI로 이전 릴리스를 복구한다. 새 전송 구현에 문제가 있어도 같은 구현에 복구를
의존하지 않도록 분리했다.

자격증명은 AWS CLI의 `configure export-credentials --format process`로 조회한다. 한 전송의
배치 사이에서 메모리로 재사용하므로 252개 파일을 처리할 때 보통 조회는 1회다. 최대 5분 또는
자격증명 만료 60초 전 중 먼저 도달하는 시점에 다음 배치가 새 자격증명을 조회한다. 새로 조회한
자격증명도 이미 만료됐다면 실패한다. 이 캐시는 GitHub 실행, lease나 pointer 검사를 대신하지 않는다.

동시 작업의 최초 조회는 `flock`으로 보호한다. 디스크 사본은 기존 배치의 비공개 디렉터리와
권한 600인 임시 인계 파일에만 저장한다. 성공 시 부모가 메모리로 읽고 즉시 삭제하며 실패나 취소
시에는 자식 프로세스를 회수한 뒤 삭제한다. 비밀값은 외부 명령의 인자에 넣지 않는다.

업로드는 manifest의 SHA-256을 `x-amz-content-sha256`과 `x-amz-checksum-sha256`으로 보낸다.
S3의 성공 응답에서도 SHA-256 체크섬이 일치해야 성공한다. 원본 보관의 `If-None-Match: *`,
공개 파일의 Content-Type/Cache-Control과 index.html 마지막 게시를 유지한다. 409/412 충돌,
잘못된 체크섬 응답과 응답 유실은 실패로 처리하며 자동 재시도를 추가하지 않는다.
[AWS PutObject 계약](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)을 따른다.

파일 경로 분리와 해시 문자열 추출은 Bash 기본 기능으로 처리하고 이미 존재하는 디렉터리를
다시 만들지 않는다. 파일 크기 검사와 전체 SHA-256 계산은 생략하지 않는다. 최대 4개 병렬 처리,
파일/배치별 guard, 전체 배포 기한, 공개 파일 전체 검사, 300초 관찰과 복구 상태 전이를 유지한다.

파일마다 curl을 실행하므로 파일 간 HTTP 연결은 재사용하지 않는다. curl은 한 호출 안에서만
연결을 재사용하며 여러 파일을 미리 넘기는 방식에는 현재 파일별 guard를 실행할 지점이 없다.
이 조건을 바꾸는 일괄 전송은 적용하지 않았다.
[curl 연결 재사용 설명](https://curl.se/docs/manpage.html)을 참고한다.

curl 8.4 미만이거나 AWS_ENDPOINT_URL/AWS_ENDPOINT_URL_S3가 설정되면 기존 AWS CLI 경로를
사용한다. 새 경로는 서울 리전의 고정 S3 주소와 AWS_CA_BUNDLE 또는 curl의 인증서 설정을 사용한다.
AWS profile 내부의 사용자 지정 endpoint와 CA 설정을 해석하는 범용 AWS 클라이언트는 아니다.

연결 제한은 3초다. curl의 `--speed-limit 1 --speed-time 30`은 30초간 전송 속도가 초당 1바이트
미만이면 실패하는 조건이다. 기존 AWS CLI의 30초 socket read timeout과 구현이 다르며 진행 중인
큰 파일에 30초의 총 실행 제한을 두지 않는다. redirect, 요청 자동 재시도와 검사 생략은 추가하지 않는다.

로컬 검증은 실제 AWS CLI 2.38.5와 curl 8.5.0을 실행하고 S3 응답, SigV4 서명, 업로드 체크섬과
조건부 생성은 로컬 TLS 대역으로 확인한다. 운영 IAM, EC2 자격증명 공급, S3 호환성과 전체 운영
배포 시간은 이 시험만으로 확인할 수 없다. 추가 시험 코드와 원시 측정 결과는 저장소 밖에 보관한다.

2026-11-17에 기준 커밋 `5138fd1`과 현재 코드를 각각 3회 비교했다. 동일한 운영 artifact의
252개 파일, 28,803,559바이트를 사용했다. ARM64 Docker를 CPU 2개, 메모리 916 MiB와 swap 없음으로
제한했고 다른 검증 작업을 종료한 뒤 실행했다. S3 대역에 인위적인 응답 지연은 넣지 않았다.

| 구간 | 기존 중앙값 | 개선 중앙값 | 감소율 |
| --- | ---: | ---: | ---: |
| 다운로드 | 86.934초 | 9.535초 | 89.0% |
| 원본 보관 업로드 | 87.732초 | 10.425초 | 88.1% |
| 공개 파일 게시와 pointer 조회 | 170.414초 | 14.571초 | 91.4% |

각 실행의 세 구간 합계 중앙값은 344.711초에서 34.506초로 90.0% 감소했다.
합계는 구간별 중앙값의 합이 아니라 각 실행 합계의 중앙값이다. 세 구간에서 AWS CLI 실행은
1,008회에서 3회로 줄었고 HTTP 요청은 양쪽 모두 1,008회로 같았다. 모든 파일의 크기와 해시가
일치했다. GitHub 응답은 대역이므로 이 결과에 실제 GitHub 네트워크 지연은 포함하지 않는다.
이는 파일 전송 구간의 로컬 결과이며 전체 운영 배포의 단축률이 아니다.

비교 기준은 파일마다 `aws s3api`를 새로 실행하는 기존 코드다. AWS CLI의 `aws s3 cp --recursive`나
`sync`는 한 실행 안에서 여러 파일을 병렬 전송할 수 있다.
[AWS CLI 전송 설정](https://docs.aws.amazon.com/cli/latest/topic/s3-config.html)을 참고한다.
이번에는 파일마다 실행하는 소유권/기한 검사와 게시 직전 pointer 조회의 위치를 유지하려고 curl을
선택했다. CLI 일괄 전송에 같은 검사를 연결하려면 별도 설계와 검증이 필요하다. 최적화된 CLI 일괄
전송 방식과 비교한 결과가 아니므로 AWS CLI 자체의 성능 한계나 curl의 일반적인 우위를 뜻하지 않는다.

이번 S3 경로는 기존 계약 검사 333건, 서명된 HTTP 전송을 사용하는 프론트엔드 시나리오 59건과
추가 읽기/갱신/쓰기 실패 검사 40건을 통과했다. API 요청 예산 시나리오 12개도 통과했다.
실제 PUT 저장 후 응답만 유실된 상황에서 중단하고 이전 릴리스를 복구하는 경로를 확인했다.
Bash 구문 검사와 ShellCheck의 오류/경고 검사도 통과했다. 추가 테스트 파일은 저장소에 넣지 않았다.

## 운영 서버와 실제 S3에서 확인한 결과

2026-11-17에 운영 coordinator(t4g.micro, 916 MiB)에 SSH로 접속해 같은 IAM 역할과 실제 S3에서
각 방식을 1회 비교했다. curl은 8.21.0이며 AWS CLI는 정식 workflow와 같은 2.38.5를 별도 임시
디렉터리에 설치했다. 파일은 현재 운영 릴리스의 252개, 28,803,559바이트다. 기존 방식 측정 후
개선 방식을 측정했으며 쓰기는 비어 있는 전용 시험 prefix로 제한했다.
측정 대상은 `1c6b3c5`의 curl 전송 경로다. 이후 GitHub 선택 변수를 제거하고 같은 경로를
기본값으로 바꿨으며 S3 요청 구현은 변경하지 않았다. 이 기본값 변경 후 운영 재측정은 하지 않았다.

| 파일 전송 구간 | 기존 방식 | 개선 방식 | 감소율 |
| --- | ---: | ---: | ---: |
| 다운로드 | 147.407초 | 14.058초 | 90.5% |
| 원본 보관 업로드 | 145.392초 | 16.582초 | 88.6% |
| 파일 게시와 pointer 조회 | 289.410초 | 31.557초 | 89.1% |
| 합계 | 582.209초 | 62.197초 | 89.3% |

다운로드, 보관 후 다시 읽은 파일과 게시한 파일 모두 크기와 SHA-256이 일치했다. 실제 S3는
중복 조건부 생성을 412로, 잘못된 본문 체크섬을 400으로 거부했다. 시험 후 공개 URL의 파일
252개도 기존 manifest의 SHA-256과 일치했다. 운영 journal, coordinator 설정과 실제 S3
배포 pointer는 그대로였으며 시험 객체 1,010개 버전과 서버 임시 파일을 정리했다.

시험용 정리 스크립트가 첫 1,000개 삭제의 빈 성공 응답을 실패로 판단해 중단됐다. 실제 남은
10개 버전만 다시 조회해 삭제했으며 최종 조회에서 버전과 삭제 마커가 모두 0개였다.
이는 저장소 밖 시험 도구의 응답 처리 문제로 운영 전송 함수의 실패는 아니었다.

이 측정에서는 시험 namespace와 운영 journal 불변 검사를 사용했다. 정식 배포의 GitHub 실행과
lease 검사, 앱 전환, 실제 서비스 파일 게시와 300초 관찰을 실행한 결과는 아니다. 따라서
89.3%는 해당 파일 전송 구간의 결과이며 전체 운영 배포 시간의 단축률로 해석하지 않는다.
GitHub 옵션 제거 후 기본 curl 경로, 외부 설정 없는 초기화, metadata CLI 경로와 curl 경로 고장 시
CLI 복구 및 복구 후 전송 범위 유지 시험 5개도 로컬에서 통과했다.

## 백엔드 전용 배포의 프론트 준비 최소화

`backend_only=true`이고 기존 릴리스가 있으면 이전 원본 전체 다운로드를 생략한다.
`release.json`의 형식과 릴리스 ID, 현재 프론트/백엔드 조합과 전체 파일의 CDN 경로는 검증한다.
공개 파일의 내용 검사는 `index.html`, `sw.js`, `manifest.webmanifest` 3개로 제한한다.
252개 파일 기준으로 원본 파일 GET은 252회에서 0회, 공개 파일 GET은 252회에서 3회로 줄어든다.
이 수치는 manifest와 pointer 조회, CloudFront 설정 조회를 제외한 파일 요청만 센 것이다.

버전 기록과 pointer CAS, 소유권, 기한, 300초 관찰과 worker/백엔드 복구는 유지한다. 백엔드
전용 배포의 성공/복구에서는 현재 프론트 릴리스를 유지하면서 백엔드 이미지 조합만 갱신한다.
최초 baseline이 없으면 기존처럼 전체 원본을 확보한다. 프론트 변경을 포함한 배포의 전체
파일 검증과 curl 전송은 그대로다. 새 GitHub 변수나 서버 설정은 추가하지 않는다.

백엔드 전용 배포가 나머지 정적 자산의 훼손이나 보관 원본 누락까지 탐지하는 범위는 줄어든다.
핵심 공개 파일의 변조, manifest 누락/오류, 버전 불일치, 진행 중인 배포와 CAS 충돌은 계속
실패로 처리한다. 전체 자산에 대한 정기 검사를 새로 구축한 변경은 아니다.

2026-11-17에 동일한 252개 파일, 28,803,559바이트로 각 방식을 3회 비교했다. ARM64 Docker를
CPU 2개, 메모리 916 MiB와 swap 없음으로 제한했고 AWS CLI 2.38.5와 curl 8.5.0을 실제 실행했다.
파일 다운로드는 로컬 TLS 대역이며 인위적 응답 지연은 넣지 않았다.

| 방식 | 준비 구간 중앙값 | 원본 파일 GET | 공개 파일 GET |
| --- | ---: | ---: | ---: |
| 기존 파일별 AWS CLI (5138fd1) | 55.294초 | 252회 | 252회 |
| curl 전환만 적용 (PR #662) | 9.372초 | 252회 | 252회 |
| 이번 백엔드 전용 준비 최소화 | 0.187초 | 0회 | 3회 |

이 시간은 로컬 대역에서 실행한 `fe_stage`의 중앙값이다. S3의 manifest/pointer 처리,
CloudFront 설정과 GitHub 응답은 계약 대역이므로 해당 API의 실제 CLI 실행/네트워크 지연은
포함하지 않는다. 최초 baseline 구성과 사후 전체 파일 검증도 측정에서 제외했다. 실제 plan
전체나 운영 배포 시간의 예측값으로 해석하지 않는다.

9회 모두 버전 조합과 확정 상태를 확인했고 공개/보관 파일 전체의 해시가 유지됐다. 기존 계약
333건, API 예산 12개 시나리오, 추가 조건/실패/복구 23건과 Bash/ShellCheck 검사가 통과했다.
추가 시험 파일과 원시 측정은 저장소 밖에 둔다. 실제 운영 적용과 전체 배포 시간은 별도 검증이 필요하다.

## 검증한 새 프론트 파일의 단계 간 재사용

프론트 변경 배포에서 Plan이 검증하고 S3에 보관한 새 파일을 coordinator 디스크에도 보관한다.

최대 4개씩 검사해 사용한다. 정상 캐시에서는 새 원본 파일 GET이 N회에서 0회가 된다.
manifest/pointer 읽기, 원본 업로드, 공개 게시와 공개 URL 검사는 그대로 수행한다.
캐시 누락/손상은 기존 S3 다운로드로 돌아간다. 보호 경로와 정리, 검증 범위의 차이는

메모리 916 MiB, swap 없음 제한을 적용했다. 실제 AWS CLI 2.38.5/curl 8.5.0을 사용하되

## 검증과 운영 반영

`test-frontend-transfer.sh`는 실제 Bash 자식 프로세스를 사용해 최대 동시 실행 수, index.html의
게시 순서, 형제 작업 실패와 TERM 시 회수, 잘못된 체크섬 응답, 전송 중 파일 변조,

S3와 공개 HTTP는 대역이며 실제 AWS의 응답, IAM과 운영 장애를 증명하지는 않는다.
기존 300초 관찰, 299초 거부, CAS 충돌, 부분 게시와 복구 시험도 함께 실행한다.

최초 병렬 전송 개선 당시 로컬 전체 계약 시험에서 PASS 결과 273건을 확인했다. 별도 API 예산 시나리오
12개가 통과했으며, 161개 파일의 기존 릴리스 공동 배포 성공 경로는 GitHub 요청 454회로
시험 예산 1,000회 안에서 완료됐다. 최종 변경 Bash 파일은 구문 검사와 ShellCheck의 오류/경고
수준 검사를 통과했다. 외부에서 source하는 파일과 공유 전역 변수에 대한 SC1091/SC2034는 제외했다.
실제 운영 배포와 실제 300초 관찰은 아직 이 개선 코드로 실행하지 않았다.

```bash
bash infra/blue-green-deploy/tests/actions/run-tests.sh
bash infra/blue-green-deploy/tests/actions/run-api-budget.sh
# 최근 artifact와 같은 파일 수로 성공 경로를 추가 검증한다.
bash infra/blue-green-deploy/tests/actions/deployment-api-budget-case.sh 161 success both existing
```

현재 배포 방식에서는 main 실행의 SHA에 포함된 성능 개선 코드가 같은 실행에 사용된다.
서버의 임시 파일이나 설정만 바꾸면 checkout 단계가 이를 개선 코드로 선택하지 않는다.
전체 배포 시험은 개선 코드를 main에 반영하고 정식 workflow로 실행해야 한다. GitHub 변수 설정은
필요하지 않다. 시험에 문제가 있으면 기존 복구 흐름이 CLI로 이전 파일을 복원한다. 개선 자체를
철회하려면 코드 변경을 되돌려 반영한다. main 반영 전의 별도 S3 경로 시험은
실제 서버의 IAM과 전송 호환성을 확인하지만 전체 배포, CloudFront 게시나 앱 전환을 검증하지 않는다.
이 문서의 과거 측정은 이 코드의 운영 적용을 증명하지 않는다.
최초 방식 전환은 [SHA 배포 전환](release-sha.md), 설치형 watchdog/수집기는 서버 구성 절차를 따른다.

첫 공동 배포에서는 전체 시간과 plan/switch/seal의 시간, worker 인계에서 활성화까지의 공백,
HTTP/worker 각각 300초 관찰 완료와 최종 COMPLETE를 확인한다. 추가된
`frontend_transfer operation=... files=... concurrency=4 seconds=...` 로그로 전송 시간을 분리한다.
캐시 검증은 `operation=verify`, 원본 선택은 `frontend_candidate source=local|s3 seconds=...`로 구분한다.
동시에 coordinator의 CPU, 가용 메모리와 swap 증가를 확인한다. 20분을 넘으면 이 측정으로
남은 병목을 다시 판단하며 관찰 시간이나 복구 검사를 줄여 목표를 맞추지 않는다.

fsync 순서는 유지한다. 배포 구현은 Bash이며 새 GitHub 변수나 운영 설정은 추가하지 않았다.

세 구간 합계는 각 실행의 합을 구한 뒤 중앙값을 계산했다. 구간별 중앙값의 합과 다를 수 있다.
정적 검사는 같은 소스와 의존성으로 Node 24 컨테이너에서 CPU 2개, 메모리 2 GiB, swap 없이
별도로 3회씩 측정했다. 성능 측정과 회귀 테스트를 동시에 실행하지 않았지만 호스트의 다른 서비스와
페이지 캐시까지 완전히 통제한 시험은 아니다.

파일 처리 6회 모두 게시 PUT, 공개 GET과 게시 직전 pointer GET은 각각 252회였다.
게시 중 새 원본 파일 GET은 두 코드 모두 0회다. 준비와 확정을 포함한 HTTP 요청은 실행당
1,764회로 같았고 모든 서명과 업로드 체크섬이 유효했다. 보관/게시 파일 전체 해시, 최종 버전 조합과
캐시 정리도 확인했다. 이전 파일의 사전 확인과 새 파일의 단계별 무결성 검사는 생략하지 않았다.

이 결과는 전체 운영 배포 시간의 측정이 아니다. 실제 S3/CloudFront/GitHub 지연, artifact 전달,
앱 기동, Nginx 전환, 300초 관측과 EC2 종료를 포함하지 않으므로 22분 58초에서 직접 빼지 않는다.
이전 운영 로그에서 중복 ESLint 한 번은 약 30초였지만 이번 코드의 운영 단축 시간은 아직 미측정이다.

### 검증과 한계

전체 `run-tests.sh`, API 예산 4개 샤드의 12개 시나리오, Bash 구문 검사와 ShellCheck 오류 수준
검사를 통과했다. 변경한 workflow 3개는 기존 전용 러너 이름을 등록한 로컬 actionlint를 통과했다.
구성 변경과 재로딩, 권한 변경, lease 만료, 실행 취소와 동일 소유권의 ETag 변경 거부를 상시
회귀 테스트에 추가했다. 기존 손상, 부분 게시, 롤백과 자식 프로세스 회수 검사도 통과했다.
일반 사용자 UID 1000에서도 coordinator 테스트와 캐시 소유권/권한/심볼릭 링크 검사를 통과했다.

임시 TLS 서버, 성능 측정 스크립트와 원시 로그는 저장소 밖에 보관한다. 상시 회귀 테스트 수정만
저장소 변경에 포함한다. 이 절의 측정은 로컬 검증 결과이며 GitHub CI 결과는 해당 PR에 기록한다.
운영 반영 후에는 전체 시간과 Plan/switch/seal 시간을 별도로 비교해야 한다.
