# ADR 0005. 별도 Nginx와 고정된 운영 EC2 두 대로 Blue-Green 배포한다

- 상태: 채택
- 날짜: 2026-10-21
- 개정: 2026-10-22 — 15분 관찰, 자동 롤백, worker 인계와 DB 변경 정책 확정
- 개정: 2026-10-25 — 팀이 읽고 수정할 수 있도록 GitHub Actions 단계와 Bash로 배포 자동화를 구성
- 개정: 2026-10-30 — 최소 관찰 시간을 5분으로 단축
- 범위: prod 백엔드의 트래픽 전환, 배포 자동화와 운영 EC2 시작, 중지
- 관련 결정: [인프라 ADR 0002](0002-rds-deployment-database.md), [백엔드 ADR 0015](../../../backend/docs/adr/0015-separate-ec2-and-shared-rds.md), [백엔드 ADR 0016](../../../backend/docs/adr/0016-github-hosted-build-and-ghcr.md)
- 구현 범위, 실행법, 운영 전 남은 연결: [Blue-Green 배포 제어](../../blue-green-deploy/README.md)

## 배경

블루그린 도입 전 운영 배포는 기존 컨테이너를 재생성한 뒤 health와 API를 검사했다. 실패하면 이전 이미지로 복구하지만, 기존 앱 종료부터
새 이미지의 앱이 준비될 때까지 요청을 처리할 서버가 없는 다운타임이 생긴다.
실제로 이 시간에 서비스를 이용한 소수의 사용자가 500 오류를 겪었다.

다운타임이 있는 배포에서 사용자 피해를 줄이려면 서버 점검을 미리 공지하거나, 새벽처럼
이용자가 적은 시간대에 배포하는 방안을 고려해야 한다. 현재 구조에서는 배포할 때마다
이러한 대응과 사용자 영향을 고민해야 한다.

무중단 배포를 도입하는 목적은 배포 중 사용자 오류를 줄이고, 점검 공지나 배포 시간대에
대한 운영 제약을 줄이는 데 있다. 팀이 사용자 피해에 대한 걱정을 덜고 필요한 시점에
배포할 수 있도록 하는 운영 편의도 이번 결정의 배경이다.

현재 dev와 prod는 각각 별도 EC2에서 실행하고, 하나의 RDS 인스턴스 안에서 데이터베이스를
나눠 사용한다. 부하 테스트에는 별도 RDS를 사용한다. 이번 무중단 배포의 운영 대상은 prod다.

prod는 t4g.small이며, 논의 중 공유한 메모리 사용량은 다음과 같다.

| 항목 | 확인한 값 |
| --- | --- |
| 호스트에서 사용 가능한 전체 RAM | 약 1.8 GiB |
| 추가 사용 가능한 메모리(`available`) | 약 531 MiB |
| 기존 백엔드 컨테이너 사용량 | 약 678 MiB |
| swap 사용량 | 1 GiB 중 약 364 MiB |

한 시점의 측정값이므로 기동 최대 메모리를 뜻하지는 않는다. 다만 현재 서버에 JVM 두 개를
겹쳐 실행해도 안정적이라는 근거는 없다. 기존 서버를 유지하면서 다른 서버에서 새 버전을
준비하는 방향으로 대안을 검토했다.

인스턴스 삭제 권한이 없어 배포마다 EC2를 생성, 삭제하는 방식은 사용할 수 없다. 외부 SSH
배포도 제한되어 현재처럼 각 서버의 self-hosted runner로 작업을 실행해야 한다. 제공된
예산으로는 ALB 도입 비용을 감당할 수 없어 제외하고, 별도 Nginx용 t4g.micro의 상시 비용은
감수하기로 했다.

## 결정

**고정된 Nginx EC2 한 대와 prod 앱 EC2 두 대를 운영한다. Nginx가 요청을 보내는 대상을
A/B로 교대하고, 비활성 앱 서버는 검증, 롤백 대기 후 중지해 다음 배포에 재사용한다.**

현재 요청 경로는 [배포 개요의 구조 그림](../../blue-green-deploy/README.md#구조)을 따른다.

평소에는 prod A/B 중 한 대가 요청을 처리하고 다른 한 대는 중지한다. 배포 중에만 두 앱
서버를 함께 실행한다. CloudFront의 API Origin은 최초 도입 때 Nginx로 바꾸고, 이후 배포는
CloudFront 설정을 바꾸지 않고 Nginx upstream 변경과 reload로 전환한다.

운영 API용 Nginx는 기존 모니터링 EC2의 Nginx와 별도다. 앱 EC2에는 JVM 하나씩만 실행하며,
빌드, 이미지 공급은 기존 GitHub-hosted ARM runner와 GHCR 경로를 유지한다.

### 선택 이유

- **운영 앱의 메모리 경쟁을 피한다.** 신버전 기동이 기존 앱과 같은 RAM, swap을 경쟁하지 않는다.
- **전환과 원복을 직접 제어한다.** 배포마다 CloudFront 설정의 전파를 기다리지 않고 Nginx에서
  전달 대상을 바꾼다. 단, reload 완료와 기존 요청 종료는 별도로 확인한다.
- **현재 권한 제약에 맞춘다.** 인스턴스를 삭제하지 않고 A/B를 재사용한다. 외부 SSH 대신
  각 서버의 runner가 로컬 작업을 수행한다.
- **추가 비용의 목적이 명확하다.** Nginx 한 대의 상시 비용으로 고정 진입점과 전환 제어 위치를
  확보한다. 비활성 앱 EC2의 컴퓨팅 요금은 중지 중 발생하지 않지만 EBS 등 보관 비용은 남는다.

## 검토한 대안

| 대안 | 장점 | 이번에 선택하지 않은 이유 |
| --- | --- | --- |
| 기존 컨테이너 재생성(Recreate) 유지 | 가장 단순하고 추가 서버가 없다 | 요청 처리 공백을 없애려는 목표를 충족하지 못한다 |
| 단일 EC2의 Nginx와 컨테이너 두 개, swap 2 GiB | 서버 수와 추가 비용이 적다 | swap은 RAM 증설이 아니다. 현재 메모리 여유에서 두 JVM의 기동, 부하를 감당할지 검증되지 않았고, 디스크 입출력으로 기존 요청까지 느려질 수 있다 |
| 운영 EC2 증설 후 컨테이너 두 개 | 전환 구성이 단순하고 메모리 여유를 늘린다 | 상시 사양 증설보다 앱을 서로 다른 호스트에 분리하는 쪽을 선택했다. 이 안이 반드시 더 비싸다고 판단한 것은 아니다 |
| 고정 A/B와 CloudFront Origin 교대 | 별도 프록시가 없어 상시 자원이 적다 | `UpdateDistribution` 권한을 확인하지 못해 배포 자동화 가능 여부가 불확실했고, Origin 변경이 엣지에 전파되는 동안 전환, 원복에 걸리는 시간도 우려되어 선택하지 않았다 |
| 배포마다 새 EC2 생성 후 이전 EC2 삭제 | 새 서버가 그대로 운영을 이어받고 서버 상태를 재현하기 좋다 | 인스턴스 삭제 권한이 없어 생성, 삭제를 반복할 수 없다 |
| 기존 prod의 Nginx에서 임시 EC2로 우회한 뒤 복귀 | 별도 상시 프록시 없이 기존 서버의 메모리 부담을 줄인다 | 같은 버전을 두 호스트에 차례로 배포하고 트래픽도 두 번 전환해야 한다. 고정 프록시와 A/B 교대보다 절차가 늘어난다 |
| ALB와 A/B | 관리형 health check와 연결 draining을 활용한다 | 제공된 예산으로는 ALB 도입 비용을 감당할 수 없어 제외했다. 예산 내에서 운영할 수 있는 Nginx를 선택했다 |
| Rolling | 여러 복제본을 일부씩 교체할 수 있다 | 평소 앱 한 대로 운영하고 다른 한 대를 배포 때만 켜는 요구에는 활성, 비활성 대상을 명확히 나누는 Blue-Green이 더 직접적이다 |
| Canary | 일부 사용자에게 먼저 공개해 영향 범위를 줄인다 | 트래픽 비율, 사용자 분배, 버전별 지표와 승격 판단이 추가된다. 첫 도입은 전환, 검증, 원복을 명확히 만드는 데 집중한다 |
| DNS 변경 또는 Elastic IP 이동 | 별도 프록시 없이 서버 주소를 교체할 수 있다 | DNS는 캐시 때문에 전환, 원복 시점이 분산되고, EIP 이동은 기존 연결을 새 서버로 옮기지 못한다 |
| ECS/Fargate 등으로 실행 환경 이전 | 플랫폼의 배포, 실행 관리를 활용한다 | 기존 Docker, Actions 배포를 개선하는 범위를 넘어 실행, 권한, 네트워크 구조를 이전해야 한다 |

## 배포와 복구 흐름

GitHub Actions workflow가 작업 순서를 연결하고, job별 `runs-on`으로 실행할 runner를 고른다.
Nginx와 prod A/B에 각각 구분된 runner 라벨을 사용하므로 서버 사이 SSH 배포는 필요하지 않다.
Nginx에서 앱으로 향하는 HTTP 통신은 별도로 허용되어야 한다.

팀이 직접 읽고 수정할 수 있도록 배포 순서를 native `workflow_call`, `needs`, job output으로
표현하고, 실제 서버 명령은 Bash 파일로 분리한다. 별도 Python 배포 제어 프로그램을 운영하지 않는다.
앱의 관리 API는 각 서버 loopback으로 유지하며 앱 runner가 직접 호출한다. 앱에서 Nginx로
향하는 SSH는 최신 배포 허가를 읽는 전용 경로로만 사용하고 원격 명령 실행 권한을 주지 않는다.
runner 대기, 취소, 응답 유실에 대비한 영속 기록과 종료 증거는 언어를 바꿔도 유지한다.

실행 입력과 정상 순서는 [배포 실행](../../blue-green-deploy/controller/deployment.md),
통과 조건은 [상태 확인](../../blue-green-deploy/controller/status.md),
실패와 종료 보류는 [장애 복구](../../blue-green-deploy/controller/recovery.md)를 따른다.
HTTP와 worker 인계는 각각 검증하고, 새 서비스와 이전 작업의 안전이 확인된 뒤에만
배포를 확정하고 이전 EC2를 중지한다. 앱 롤백은 DB 데이터를 되돌리지 않는다.

### 최소 관찰 시간

2026-10-30 합의로 최소 관찰 시간을 기존 15분에서 5분으로 단축한다. 검사 주기와 실패 기준,
강제 종료 금지 원칙은 유지한다. 배포 확정과 이전 EC2 종료를 더 일찍 진행할 수 있지만,
자동 롤백을 제공하는 관찰 구간도 10분 짧아지는 비용을 감수한다. 실행 기준은
[관찰 기준](../../blue-green-deploy/controller/status.md#관찰-기준)에 둔다.

## DB 변경과 기존 컬럼 삭제

A/B가 같은 DB를 사용하므로 구버전과 신버전 모두 동작할 수 있도록 스키마와 데이터 형식의
호환성을 유지한다. 컬럼 이름 변경, 삭제 등은 새 구조 추가, 데이터 이관, 동기화, 앱 전환,
기존 구조 제거로 나누는 Expand-Contract 방식으로 진행한다.

기존 컬럼의 삭제 대상과 시점은 개발자가 판단해 **별도 PR**로 작성, 검토한다. 데이터 이관이
끝났고 현재 앱, 백그라운드 작업이 해당 컬럼을 사용하지 않으며, 지원할 롤백 버전도 삭제 후
동작하는지 확인한다. PR 병합 후 실제 삭제는 배포 파이프라인과 Flyway가 실행한다.

몇 시간 정상 운영했거나 배포 관찰을 마쳤다는 이유만으로 컬럼을 자동 삭제하지 않는다.
앱 롤백은 트래픽과 실행 버전을 되돌리는 작업이며, DB 스키마와 이미 저장된 사용자 데이터를
과거 상태로 자동 복원하는 기능은 이번 범위에서 제외한다.
세부 기준은 [공통 DB 변경 규칙](../../../docs/database-changes.md)을 따른다. PR의 migration 검사는
위험 SQL과 기존 Flyway 파일 변경을 검토 대상으로 알리는 보조 수단이다. 직전 앱과 새 스키마의
조회, 저장 호환성을 실행 검증하는 CI는 후속 작업이며 이번 검사가 이를 보장하지 않는다.

## 감수하는 비용과 한계

- Nginx가 단일 장애 지점이 된다. 앱 두 대가 있어도 프록시 장애 시 서비스를 유지하는
  고가용성 구성은 아니다. 앱 장애에 대한 자동 전환도 이번 설계만으로 생기지 않는다.
- Nginx 설정, 업데이트, 로그와 runner, 배포 잠금, 진행 상태를 직접 관리해야 한다.
  t4g.micro가 실제 트래픽과 runner 제어 작업을 감당하는지도 검증한다.
- EC2를 중지해도 디스크를 초기화하지 않는다. 실행 환경, 이전 정상 이미지, 설정은 보존하고,
  오래된 이미지와 로그를 보관 정책에 따라 정리한다.
- A/B는 같은 운영 DB와 JWT 키를 사용한다. Refresh Token과 JDBC 가입 세션도 같은 운영 DB에서
  공유한다. 기존 인증 구조는 [백엔드 ADR 0001](../../../backend/docs/adr/0001-github-oauth-authentication.md)과
  [백엔드 ADR 0002](../../../backend/docs/adr/0002-access-token-cookie.md)를 따른다.
- 구, 신버전이 동시에 DB를 사용하므로 스키마는 Expand-Contract 등으로 호환성을 유지한다.
  Flyway 실행도 이 호환성을 대신 보장하지 않는다.
- worker를 실행 중에 멈추고 인계하는 제어는 Actions, Bash 배포 경로에 연결했다. 운영 호스트의
  설정, 권한과 실제 인계, 복구 동작은 운영 적용 전에 검증한다. 단일 worker로 인계해도
  외부 발송 성공 직후 DB 기록 전 장애가 나면 재시도로 중복 발송될 수 있다. 앱 롤백으로
  이미 발송한 알림을 회수할 수는 없다.
- 인계 제어가 없는 기존 앱을 처음 교체할 때는 최초 등록과 반복 배포를 구분한다.
  사용자 영향과 기존 작업 종료는 [최초 worker 등록](../../blue-green-deploy/controller/environment.md#최초-worker-등록)에서 확인한다.
