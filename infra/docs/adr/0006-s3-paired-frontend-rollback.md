# ADR 0006. 프론트엔드 원본을 S3에 보관하고 백엔드와 함께 복구한다

- 상태: 채택
- 날짜: 2026-10-29
- 범위: prod 프론트엔드 보관, 게시와 백엔드 Blue-Green 복구의 연결
- 관련 결정: [인프라 ADR 0005](0005-nginx-ec2-blue-green-deployment.md), [백엔드 ADR 0016](../../../backend/docs/adr/0016-github-hosted-build-and-ghcr.md)
- 운영 구조와 적용 절차: [프론트엔드 릴리스 보관과 복구](../../blue-green-deploy/docs/architecture.md#프론트엔드-릴리스)

## 배경

백엔드는 Nginx가 A/B 중 하나를 선택하므로 배포 확정 전에 이전 앱으로 돌아갈 수 있다.
프론트엔드는 S3의 같은 경로를 덮어쓰는 별도 배포다. 백엔드만 복구하면 새 화면과 이전 API가
남을 수 있고, 프론트엔드 업로드가 중간에 실패하면 같은 경로 안에 서로 다른 빌드가 섞일 수 있다.
따라서 배포 전에 이전 화면의 실제 파일을 확보하고, 어떤 백엔드 이미지와 함께 서비스했는지
알아야 한다. 과거 커밋을 다시 빌드하면 의존성, 빌드 환경과 당시 환경 변수 차이로 같은 파일을
재현한다는 보장이 없으므로 복구 원본으로 사용하지 않는다.

## 결정

**현재 공개 경로는 유지하고, 같은 S3 버킷의 별도 prefix에 변경하지 않는 릴리스 원본과
파일 목록을 저장한다. 배포 상태는 프론트엔드 릴리스와 백엔드의 정확한 이미지 digest를 한 쌍으로 기록한다.**

복구 범위는 이번 배포에서 변경한 구성요소로 한정한다. 공동 배포 실패는 둘 다 복구하고,
프론트 전용 실패는 프론트만, 백엔드 전용 실패는 백엔드만 복구한다. 백엔드 전용 배포도
현재 프론트와의 조합을 기록하지만 공개 프론트 파일은 덮어쓰지 않는다.

앱 복구는 DB를 되돌리지 않는다. 새 enum 데이터의 구버전 읽기와 이전 브라우저의 응답 계약을
따로 검증해야 한다. 이에 대한 판단은 공통 DB 변경 규칙과 릴리스 준비에서 수행하며,
배포 제어 코드에 특정 회원 유형의 검사나 가입 제어를 추가하지 않는다.

릴리스 경로, manifest와 current/previous/pending의 데이터 형식 및 조건부 갱신 계약은
[프론트엔드 릴리스](../../blue-green-deploy/docs/architecture.md#프론트엔드-릴리스)에 둔다.
복구 원본은 실제 게시한 바이트이며, 불일치 파일을 새 정상 원본으로 자동 승인하지 않는다.

### S3를 선택한 이유

| 대안 | 판단 |
| --- | --- |
| 같은 버킷의 별도 S3 prefix | 기존 전달 경로와 IAM을 재사용할 수 있고 Actions 실행 삭제나 artifact 보존 기간과 독립적으로 복구 원본을 보관할 수 있어 채택한다. 보관 용량과 요청 비용, 향후 보존 정책 관리가 필요하다. |
| GitHub Actions artifact만 보관 | 빌드 runner에서 배포 runner로 전달하기에는 적합하지만 실행 삭제와 보존 기한에 복구 가능성이 묶인다. 임시 전달에는 사용하되 운영 복구 원본은 S3로 확정한다. |
| S3 versioning만 사용 | 개별 객체의 과거 버전은 보존할 수 있지만 완성된 빌드의 파일 목록과 백엔드 조합을 나타내지 않는다. 배포 중 일부만 교체된 시점의 파일을 잘못 조합할 수 있어 릴리스 manifest를 대신하지 않는다. |
| 이전 커밋 재빌드 | 실제 서비스했던 바이트와 같다는 보장이 없고 복구 때 다시 빌드해야 하므로 제외한다. |
| CloudFront OriginPath를 릴리스별로 변경 | 릴리스 디렉터리를 직접 선택할 수 있지만 배포마다 CloudFront 쓰기 권한과 설정 전파를 관리해야 한다. 기존 공개 경로를 유지하는 이번 범위를 넘는다. |

S3 저장 자체가 불변성을 보장하는 것은 아니다. 릴리스 경로의 덮어쓰기 차단, manifest 검증과
조건부 상태 갱신을 배포 코드의 계약으로 둔다. Object Lock이나 bucket versioning을 새로
설정했다고 가정하지 않는다. 보관 수명 정책은 별도 합의 전까지 추가하지 않으며, 이전 원본을
자동 삭제하지 않는다. 현재와 이전 릴리스, 미완료 복구가 참조하는 원본은 항상 보존한다.

### 배포와 복구 경계

백엔드와 프론트엔드를 같은 릴리스로 연결하되 복구 범위는 이번에 변경한 구성요소로 한정한다.
worker 종료가 불확실하면 이전 worker를 재개하지 않는다. 프론트 복구도 유효한 허가 안에서
검증하며 실패 결과를 숨기지 않는다. 실행 순서는 [배포 실행](../../blue-green-deploy/docs/deployment.md),
복구 순서와 수동 조정은 [장애 복구](../../blue-green-deploy/docs/recovery.md)를 따른다.

### 현재 인프라와 권한 경계

CloudFront의 설정 전파와 추가 쓰기 권한에 의존하지 않고 기존 공개 경로를 유지한다.
이 방식이 성립하는 origin, 캐시와 함수 조건은 [프론트 사전 준비](../../blue-green-deploy/docs/server-setup/README.md#프론트엔드-사전-준비)에 둔다.
이 조건이 바뀌면 게시와 복구 계약을 다시 검토한다. API와 이미지 경로는 보존한다.

새 장기 AWS 키, OIDC 또는 모니터링 EC2 배포 의존성을 추가하지 않는다. 기존 EC2 역할에는
공개 prefix와 릴리스 prefix에 필요한 최소 권한만 부여한다. 현재 control tag를 이동하지 않고
새 코드를 포함하는 immutable tag와 SHA를 보호된 서버 설정 및 GitHub 변수에 함께 고정한다.
옛 control release에 새 기능이 없으면 공개 파일이나 서버를 변경하기 전에 실패해야 한다.

비활성화된 배포가 다른 게시 방식으로 우회되지 않게 한다. 활성화 조건과 최초 권한 등록은
[배포 실행](../../blue-green-deploy/docs/deployment.md#배포-실행)을 따른다.

## 감수하는 한계

S3 객체 복사는 여러 파일에 걸친 트랜잭션이 아니다. `index.html`을 마지막에 게시해도 모든
사용자가 같은 순간에 바뀐다는 보장은 없다. 이미 열린 탭은 기존 JavaScript를 계속 실행할 수
있고 브라우저나 서비스 워커의 상태도 서버가 일괄 되돌릴 수 없다. 이전 해시 자산을 공개 경로에
유지하고, 지원할 구버전 화면과 API 사이의 호환성을 유지해야 한다. 대량 `sync --delete`로
기존 탭이 참조하는 자산을 없애지 않는다.

복구는 화면 파일과 API 경로의 이전 조합을 복원하는 작업이다. DB 데이터나 이미 발송한 알림을
되돌리지 않는다. worker 안전 경계와 DB 호환성은 [인프라 ADR 0005](0005-nginx-ec2-blue-green-deployment.md)의
정책을 그대로 따른다. 취소 중 finalizer나 runner 자체의 실행도 보장할 수 없다.

## 검증과 도입

이 문서는 운영 기능이 이미 적용됐다는 기록이 아니다. 로컬 계약 테스트와 실제 AWS, IAM,
GitHub runner, 전체 300초 관찰 및 실패 복구 검증은 구분한다. 구체적인 설치, 최초 baseline,
관찰 및 수동 조정 절차는 [서버 구성](../../blue-green-deploy/docs/server-setup/README.md#프론트엔드-사전-준비),
[관찰 기준](../../blue-green-deploy/docs/status.md#관찰-기준)과
[복구 절차](../../blue-green-deploy/docs/recovery.md#수동-조사)를 따른다.
