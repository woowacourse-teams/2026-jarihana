# 채팅 모니터링

Grafana의 `Jarihana` 폴더에서 **자리하나 · 채팅**을 연다.
경로는 `/d/jarihana-chat`이며 상단에서 `dev` 또는 `prod`, 백엔드 서버를 선택한다.
환경·서버 필터는 모든 패널에 적용된다. 기본 조회 범위는 최근 1시간, 화면 갱신은 30초다.

## 수집과 반영

기존 앱 Alloy가 `/actuator/prometheus`를 5초마다 수집하고 Prometheus로 전달한다.
채팅 대시보드는 공통 데이터소스 `prometheus`와 `job="jarihana-backend"`,
`environment`, `instance` 라벨을 사용한다. 별도 exporter나 scrape job은 추가하지 않는다.

원본은 [jarihana-chat.json](../../monitoring/grafana/provisioning/dashboards/json/jarihana-chat.json)이다.
기존 dashboard provider가 이 파일을 읽는다. `develop`에 모니터링 변경을 병합하면
기존 `Monitoring Deploy` workflow의 배포 대상에 포함된다.
각 환경의 백엔드에도 채팅 기능이 배포되어 있어야 채팅 지표가 나타난다.

운영 적용 후에는 환경을 각각 선택해 앱 수집 상태와 서버 목록을 먼저 확인한다.
LISTEN 상태를 서버별로 확인하고, 테스트 메시지를 보내 전송 시도와 이벤트 전달 지표가
증가하는지 확인한다. 저장소 설정 검증과 실제 개발·운영 배포 확인은 따로 기록한다.

## 패널 읽기

| 패널 | 읽는 방법 |
| --- | --- |
| 앱 지표 수집 | 서버별 수집 성공은 1, 실패는 0. 90초 이상 새 수집이 없으면 값이 비어 있다 |
| LISTEN 연결 | 서버별 알림 연결 상태. 한 서버만 끊겨도 해당 서버가 0으로 보인다 |
| 채팅 연결 | 현재 WebSocket 연결 수. 여러 탭을 연 사용자는 탭마다 집계된다 |
| 전송 시도 | 커밋·롤백별 트랜잭션 완료 횟수. 커밋에는 멱등 재시도, 롤백에는 검증 실패도 들어간다 |
| 전송 처리 평균 시간 | 검증·잠금 대기·저장부터 트랜잭션 종료까지의 시간. SQL만의 시간이나 상대방 화면에 도착한 시간과 구분한다 |
| 이벤트 전달 | 참여자 후보, 사용자 큐 발행, 전달 제외 횟수. 서버마다 같은 이벤트를 처리할 수 있고 브라우저 수신 여부는 클라이언트에서 확인한다 |
| 대화 복구 | 성공한 afterSequence 조회 페이지와 반환 메시지 수. 주기적 동기화와 중복 조회도 포함한다 |
| LISTEN 연결·오류 | 최초 연결을 포함한 연결 성공, 연결·수신 실패, 이벤트 처리 실패, 종료 실패 |
| WebSocket 전송·오류 | 제어 프레임과 하트비트를 포함한 프레임 전송, 전송·종료 실패 |
| WebSocket 연결·만료 | 새 연결과 인증 만료 처리 횟수 |
| 동일 요청 재확인 | 같은 요청 ID·본문으로 재시도해 기존 메시지를 반환한 횟수 |

전송 시간은 기존 timer의 sum/count로 평균을 계산한다. 채팅 timer의 히스토그램은
수집하지 않으므로 이 화면에는 p95·p99를 넣지 않는다.

카운터는 해당 사건이 처음 발생할 때 등록된다. 실패가 한 번도 없었던 서버의 오류 지표는
비어 있을 수 있다. 시계열 부재를 0으로 채우지 않으며 앱 수집 상태를 함께 확인한다.
전송 시도가 없는 구간의 평균 시간도 비워 둔다.
수집에 실패한 서버의 오래된 값은 현재 상태와 처리율 패널에서 제외한다.
선택 기간의 전송 시도 합계는 현재 서버가 내려갔어도 그 기간의 기록을 포함한다.
수집이 끊긴 이후의 요청은 관측할 수 없으므로 상단 앱 수집 상태와 함께 해석한다. 장기간 시계열이 사라진 서버는 배포 서버
목록과 대조해야 한다. 이 대시보드에는 새로운 Slack 알림 규칙을 추가하지 않았다.

## 성능 비용

이번 대시보드는 이미 저장된 지표를 Prometheus에서 조회한다. 화면을 새로고침할 때
백엔드 API나 DB를 추가로 조회하지 않고, 앱 수집 주기도 그대로 유지한다.
추가 비용은 화면을 여는 동안 실행되는 PromQL과 결과 전송이다.
조회 범위를 넓히거나 여러 사람이 동시에 열면 모니터링 서버의 부하가 증가할 수 있다.

기존 채팅 계측에는 카운터·타이머 갱신, 시간 측정, 요청당 트랜잭션 완료 콜백 비용이 있다.
사용자·모임·메시지 ID를 메트릭 라벨로 넣지 않고 전송 결과는 두 값으로 제한한다.
연결 gauge는 기존 메모리 상태를 읽고 별도 SQL을 실행하지 않는다.
LISTEN의 서버당 DB 연결 하나는 채팅 이벤트 수신에 필요한 연결이다.

계측 on/off를 같은 부하로 비교한 결과는 아직 없다. 고부하에서 비용을 확인할 때는
동일한 메시지 전송률·동시 연결 수로 CPU, 할당량, 전송 지연을 비교한다.
Prometheus도 계측이 매우 빈번한 경로에서는 실제 측정을 권장한다.
[Prometheus 계측 지침](https://prometheus.io/docs/practices/instrumentation/#inner-loops)

## 검증

Node 24와 Docker가 있는 환경에서 저장소 루트 기준으로 실행한다.

```sh
node infra/monitoring/grafana/test-chat-dashboard.mjs
```

개발·운영 쿼리 문법, 환경·서버 분리, 일부 LISTEN 장애, 수집 실패·오래된 값,
요청이 없는 구간의 평균을 Prometheus `promtool`로 확인한다.
