# 배포 점검 지표 적용 상태

점검 요청 제외와 수집 주기는 코드 포함, 서버 설치와 실제 관측을 구분해 확인한다.
Git 병합만으로 설치된 제어 릴리스나 활성 Nginx 설정이 바뀌지는 않는다.

| 항목 | 저장소 원본과 적용 경계 |
| --- | --- |
| PROD 배포 관측 주기 | 기본 timer와 prod 30초 drop-in 원본을 함께 관리한다. 설치 경로와 유효 주기는 [중앙 수집기 운영](CENTRAL-DEPLOYMENT-COLLECTOR.md#실행-주기와-권한)을 따른다. |
| 공개 요청의 점검 표시 제거, 내부/직접 점검의 표시 | [PR #548](https://github.com/woowacourse-teams/2026-jarihana/pull/548)에서 Nginx 템플릿과 직접 점검 스크립트를 관리한다. PR #537에는 해당 변경이 없다. |
| 백엔드 점검 제외와 무트래픽 지표 | 점검 헤더를 해석하는 백엔드 설정과 함께 적용한다. 초기 0값 지표 등록 및 실제 Nginx 경로 검증은 PR #548의 범위다. 수집 부재를 0으로 대신하지 않는다. |
| Grafana의 관측 만료 기준 | [쿼리 카탈로그](../../monitoring/grafana/deployment/queries.mjs)가 원본이다. 생성 JSON의 Git 병합과 실제 모니터링 배포를 구분한다. |

## 앱과 배포 제어기의 적용 순서

앱 이미지와 `BLUE_GREEN_CONTROL_REF`는 별도로 적용된다. 점검 요청에 표시를 붙이는
제어기부터 바꾸면 구버전 앱과의 조합에서 배포가 멈출 수 있으므로, **0건 지표를 등록하는
앱 이미지를 먼저 배포하고 점검 표시를 추가한 제어기는 그 뒤에 적용한다.**

| 제어기와 앱의 조합 | HTTP 계측 동작과 제약 |
| --- | --- |
| 점검 표시를 붙이지 않는 제어기 + 0건 초기화 앱 | 이관 중간 조합이다. 점검도 계속 HTTP 통계에 포함되며 점검 제외는 아직 완료되지 않았다. |
| 점검 표시를 붙이는 제어기 + 점검 제외와 0건 초기화가 있는 앱 | 사용자 요청 전에도 count/sum이 0으로 존재하고 점검은 사용자 통계에서 제외된다. |
| 점검 표시를 붙이는 제어기 + 점검 제외만 있고 0건 초기화가 없는 앱 | 지원하지 않는 조합이다. 사용자 요청이 없으면 count/sum 자체가 없을 수 있어 후보 준비 검사가 끝나지 않는다. |

마지막 조합에서 앱이 정상 응답해도 `bg_metrics`는 지표 부재를 UNKNOWN으로 판단한다.
`bg_grant_handoff`는 지표가 준비될 때까지 최대 600초를 기다린 뒤 타임아웃으로 중단한다.
사용자 요청이 우연히 들어와 통과하는 것을 호환성의 근거로 삼지 않는다.

1. 기존 제어기를 유지한 채 0건 초기화 기능이 포함된 앱 이미지를 정상 배포한다.
   실행 중인 이미지의 digest와 구현 포함 여부, Alloy/Prometheus의 count/sum 수집을 확인한다.
   무트래픽 초기화는 격리 환경에서 확인하며 운영 앱을 검증 목적으로 재시작하지 않는다.
2. 다시 후보로 배포할 수 있는 이미지와 복구 대상의 호환성을 확인한다.
   0건 초기화가 없는 이미지를 새 제어기로 후보 기동하는 조합은 복구 선택지에서 제외한다.
3. 그 뒤 검토한 새 불변 control 릴리스를 적용한다. 기존 태그를 이동하거나
   `BLUE_GREEN_CONTROL_REF`만 바꾸지 않는다. 보호된 Nginx/A/B 설정과 설치본,
   저널의 control SHA 및 topology 정합성은 기존 재구성/수동 조사 절차를 따른다.
   절차는 [배포 가이드](../../blue-green-deploy/README.md)의 환경 구성과 장애 복구에서 확인한다.
4. 적용 후 공개 요청의 표시 제거, 내부/직접 점검의 표시와 실제 수집을 다시 확인한다.

### 이전 이미지 재배포와 자동 롤백

이전 이미지를 새 후보로 기동하는 재배포에는 위 호환성 제약이 그대로 적용된다.
정상 prod deploy의 `image_tag`도 현재 main의 backend tree와 같은 digest만 허용하므로,
임의의 과거 이미지를 선택하는 롤백 명령으로 해석하지 않는다.

배포 확정 전, 실행 중인 이전 앱으로 돌아가는 자동 롤백은 후보 준비의
`bg_grant_handoff`를 다시 실행하지 않는다. 기존 HTTP 복구, worker 권한과 연결 정리의
검증을 유지하며, 모든 자동 롤백이 같은 지표 부재로 실패한다고 단정하지 않는다.
확정 후 이전 이미지를 다시 기동하는 별도 복구는 이 자동 롤백과 구분한다.

위 표는 계측 계약과 적용 제약이다. 기존 무트래픽 통합 검증은 양쪽 앱에 동일한 새 JAR를
사용했으므로, 구버전/신버전 혼합과 실제 운영의 control pin 전환까지 검증한 근거가 아니다.

## 운영 반영 확인

- 보호된 제어 태그는 이동하지 않는다. 검토한 새 불변 릴리스를 배포하고 coordinator/A/B의
  ref/SHA 및 설치 경로를 일치시킨다. 구성 절차는 [배포 환경 구성](../../blue-green-deploy/docs/server-setup/README.md)을 따른다.
- 활성 Nginx에서 공개 `/api/`는 `X-Jarihana-Deployment-Probe`를 제거하고,
  내부 `/__deployment`는 `true`를 주입하는지 확인한다. 직접 후보 검사에도 같은 표시가 필요하다.
  활성 설정만 수동 수정하면 다음 트래픽 전환에서 기존 템플릿으로 덮어쓸 수 있다.
- 백엔드 필터가 설치되지 않았거나 점검 표시가 없으면 해당 요청은 HTTP 지표에 포함될 수 있다.
  코드와 설정을 함께 대조하기 전에는 모든 점검 요청이 제외됐다고 판단하지 않는다.
- timer/service와 textfile, Prometheus의 실제 수신 시각은
  [읽기 전용 확인](CENTRAL-DEPLOYMENT-COLLECTOR.md#읽기-전용-확인)을 따른다.
  수집 주기와 소비자 유효 시간은 별도 설정이다.
